# Вопросы и требования к интеграции Manager → Node Agent

Адресат: разработчик менеджера. Статус: результаты сверки и предложения для
согласования; этот документ не добавляет маршруты и не меняет контракт работающего API.

Проверены:

- ветка менеджера `claude/epic-feynman-54aj67`, коммит
  `e8d98e0cfdf9aa98d347ea877761b6e4735a76ad`:
  [CONTRACTS.md](https://github.com/thua48xsen3iemicy-boop/gns-moodle-plugin/blob/e8d98e0cfdf9aa98d347ea877761b6e4735a76ad/manager/docs/CONTRACTS.md),
  `AGENT_REQUESTS.md`, `DESIGN.md`, клиенты агента/Proxmox и `orchestrator.py`;
- ветка агента `feature/proxmox-node-agent`, коммит
  `6a735dfb355314fcc2f1bab68bed6fe90bc4dd27`, исходники Slot в этой ветке.

Далее ссылки на разделы и код менеджера относятся именно к указанному снимку.
Документы менеджера рассматриваются как черновик контракта, а не как разрешение
изменять другие компоненты. В этой правке изменена только документация `agent/`.

## 1. Блокирует интеграцию: единый контракт путей

`AGENT_REQUESTS.md` §1 уже выполнен для кода: mp0 → `/srv/gns3-ro/slot`.
Но вслед за сверкой с реальным Slot изменена и цель mp1:

| Назначение | Источник на хосте | Путь внутри LXC |
|---|---|---|
| Код, venv | `<LAB_CEPH_ROOT>/slot[/<code_revision>]` | `/srv/gns3-ro/slot`, RO |
| Проекты студента | `<LAB_CEPH_ROOT>/students/<student_key>` | `/opt/gns3/projects`, RO/RW |

Просьба обновить `AGENT_REQUESTS.md` §1, `DESIGN.md` §§3, 5, 6.1,
комментарии `storage.py` и отделить текущие пути от будущего `student-state` в
`CONTRACTS.md` §§4.2, 7, 8. Сейчас `/srv/student` агентом не монтируется.
Код Slot и его `SLOT_PROJECT_LOCK_DIR` используют `/opt/gns3/projects`.

Вопрос: будущий `student-state` сохраняет `/opt/gns3/projects`, или предполагается
отдельное дерево с `projects/`, `state/` и другой точкой монтирования? Требуется
единая спецификация и миграция, а не изменение пути только в менеджере.

`_check_student_mount()` сейчас проверяет суффикс источника и RO/RW, но не
`mp=`. Требование к восстановлению: проверить точный разрешённый источник,
`mp=/opt/gns3/projects`, RW и mp0 с выбранной ревизией, фиксированной целью и RO.
Суффикс `/students/<key>` не доказывает, что источник находится под нужным CephFS.
Нужен настроенный ожидаемый CephFS root либо будущий нормализованный отчёт агента;
такого отчёта сейчас нет. Не принимать состояние «CT running» за подтверждение
корректного mount-контракта. Добавить отрицательные тесты для верного суффикса
под чужим root и для неверной точки назначения.

Образы `/opt/gns3/images/{QEMU,IOU}`, QGA `/opt/gns3/qga`, конфигурация GNS3,
токены и установка guest unit обеспечиваются шаблоном LXC. Агент их не создаёт.
При замене student mount в новом каталоге отсутствует `.slot-locks`: кто создаёт
его до `/v1/readyz`? Текущий `init_slot` этого не делает. Это нужно определить в
подготовке шаблона/отдельном разрешённом guest action, не произвольной командой HTTP.

## 2. Переносимость состояния и параллельный доступ

`CONTRACTS.md` правильно помечает `student-state` как будущую возможность.
Текущий Slot хранит SQLite/манифест/операции в `/var/lib/lab-slot`, локально в LXC.
Общий каталог проектов сам по себе не обеспечивает продолжение на другом слоте.

Указания менеджеру:

- Не включать межслотовый `resume` по одному наличию student mount или версии
  deploy-схемы. Требовать явно подтверждённую возможность переноса состояния.
- До согласования миграции состояния оставлять `fresh` либо явно ограничивать
  resume тем слотом, где сохранено состояние. Не удалять существующие данные для
  восстановления после ошибки.
- Разделять `lab_revision` (ревизия манифеста) и `code_revision` (версия ПО Slot).
  SHA256 с `sha256:` не является допустимым значением `code_revision`: агент
  принимает один компонент `[A-Za-z0-9][A-Za-z0-9_-]{0,63}`.

Вопрос: допускаются ли одновременные активности одного студента? Ключ каталога
`<site_slug>-<user_id>` общий для всех его лабораторий, тогда как workspace
менеджера различается ещё по `instance_id` и `lab_ref`. Нужна явная политика:
изоляция проектов по стабильному `project_id`, общий UID mapping и защита от
одновременного RW-доступа к одному проекту между сессиями/слотами. Блокировка агента
по VMID этого не гарантирует, student provisioning не является lease каталога.

Проверить уникальность `site_slug` между сайтами, длину ключа и стабильность slug
после создания данных. Его смена не должна молча создавать новую рабочую копию.

## 3. Ресурсы и мониторинг: зафиксировать владельца операций

`CONTRACTS.md` §3.1 и `DESIGN.md` §§3, 6.2 сейчас задают такую реализацию:
менеджер читает Proxmox API, выбирает слот по памяти и сам меняет `cores/memory`
остановленного CT через API. Агент не принимает `resources` и не резервирует
ёмкость. Не передавать эти поля в текущие mounts/start: будет 422.

Обсуждаемое расширение — локальные измерения и admission/reservation на агенте,
глобальное размещение на менеджере — пока предложение, не реализованный контракт.
Просьба ответить:

1. Оставляем ресурсы CT за Proxmox API или переносим применение лимитов в агент?
   При переносе должен остаться один владелец записи; исключить гонку API и `pct`.
2. Каковы единицы: `memory_mb` означает MiB (как в расчёте менеджера `* 1024**2`)?
   Как учитываются swap, запас хоста, CPU overcommit и свободное место CephFS?
3. Что считается резервом: обещанный лимит памяти или текущее потребление? Сейчас
   резерв снимается из расчёта при `CT running`, хотя GNS3 ещё мог не выделить память
   устройств. Старт нескольких таких CT способен переоценить оставшуюся ёмкость.
4. Как связать атомарное резервирование с выдачей слота: `session_id`, VMID,
   generation, требования, node identity? Как сверять после миграции CT?
5. Если вводим агентские leases: какой TTL, renew/release, восстановление после
   рестарта и поведение при сетевой изоляции? Истечение TTL не должно автоматически
   останавливать работающий CT или освобождать уже потреблённую память.

Разные слоты в БД ещё не означают атомарную резервацию памяти физической ноды.
Нужно определить транзакционную границу расчёта/выдачи и единый ledger, проверить
две конкурирующие заявки и устаревшие показания Proxmox. Даже один активный
оркестратор требует явного подтверждения, что его выдачи не расходятся по ресурсам.

Для будущих metrics нужны `node`, время измерения, срок допустимой давности и
раздельные признаки agent reachable / CephFS ready / capacity available.
`GET /health` сейчас возвращает только liveness. Недоступность агента не доказывает
выключение хоста; `CT running` не означает, что лаборатория готова — это сообщает Slot.

## 4. Ошибки и восстановление после частичного исполнения

Запрос структурированных `detail.code` в `AGENT_REQUESTS.md` §2 поддерживаю.
Он ещё не реализован: текущий агент отдаёт строковый `detail`, валидация — список.
Согласовать отдельно введение кодов и расширение capabilities; не считать их
наличие свойством текущего релиза. Менеджер должен сохранять совместимость со
строками и трактовать неизвестный код консервативно, без опасного повтора.

Есть два важных уточнения к классификации:

- `SOURCE_MISSING` не всегда означает «CT не тронут». В `start()` после `pct set`
  выполняется вторая `source_paths()`. Каталог может исчезнуть именно тогда;
  mounts уже изменены. `AgentSourceMissing` и комментарий в `_stage_ct_start`
  сейчас обещают больше, чем гарантирует агент. После ошибки сверять состояние и
  конфиг; не возвращать слот в `free` без проверки безопасного состояния.
- `STUDENT_DIR_OWNER` сейчас объединяет постоянное несовпадение владельца и
  короткую гонку `mkdir → chown`. Один код сам по себе их не различит. Нужны
  разные результаты/подтверждение готовности либо ограниченный retry с последующим
  ручным разбором. Повтор не должен делать chown существующего дерева.

Ошибку настройки `LAB_STUDENT_HOST_UID/GID` стоит отличать от временной
недоступности storage. Сейчас обе — 503. Единые host UID/GID на всех нодах должны
соответствовать trusted LXC template; HTTP не выбирает владельца и custom mappings
не поддерживаются автоматически.

При таймауте start CT может работать, а guest action — не завершиться. Статус CT и
mounts не подтверждают выполнение действий. Текущие фиксированные действия в
основном повторяемы, но агент не предоставляет журнал операций или replay по ключу.
Менеджер должен проверять фактическую готовность Slot; для будущих неповторяемых
действий потребуется отдельный operation contract. Не повторять действия вслепую.

Fencing в БД менеджера не отменяет уже доставленный агенту HTTP-запрос. До
повторной выдачи слота необходимо завершение/сверка старой операции. Будущий
generation fence на агенте должен быть отдельным согласованным расширением.

## 5. Тайм-ауты и освобождение слота

`DESIGN.md` §3 задаёт start=330 с, stop=100 с, прочее=30 с. Это меньше суммы
возможных тайм-аутов вложенных команд агента:

| Операция | Сумма заданных subprocess timeout, без файлового I/O |
|---|---|
| start, три разных actions | 385 с: status 15 + источники 30 + set 40 + повторная проверка 30 + start 120 + actions 135 + status 15 |
| PUT mounts | 85 с: status 15 + источники 30 + set 40 |
| graceful stop | 110 с: status 15 + shutdown 80 + status 15 |

Это не гарантированная верхняя граница: зависший CephFS/pmxcfs I/O не ограничен
этими subprocess timeout. Увеличить только HTTP timeout недостаточно для полной
гарантии; согласовать общий deadline и состояние «исход неизвестен». Разорванный
HTTP-запрос не является отменой sync-обработчика агента. Не освобождать slot lease
по одному истечению времени менеджера. Сверять состояние, учитывать `SLOT_BUSY`,
использовать bounded retry/backoff и операторский разбор затяжного зависания.

`_stage_ct_park()` сейчас пишет событие и освобождает слот даже при отказе установки
заглушки. В результате состояние `free` может сохранять mount прежнего студента,
хотя `DESIGN.md` §6.3 обещает заглушку. Просьба согласовать: при неудаче park —
`maintenance/failed`, без автоматической выдачи, пока безопасный конфиг не подтверждён.
`students/placeholder` подготавливается администратором отдельно: вызов student
provisioning назначит ему владельца gns3 и не является подготовкой root-owned
заглушки. Force stop — отдельная явно журналируемая эскалация после проверки
состояния, не универсальная реакция на любой 409.

## 6. Версии и минимальные совместные проверки

В `CONTRACTS.md` §1 обратная совместимость необязательных полей не работает
автоматически для строгого агента: старый получатель отклонит новое поле.
Нужно распространять правило capability negotiation и на Manager → Agent.
У агента сейчас нет `/capabilities`; не добавлять `schema`, `extensions`,
`resources`, `generation` или idempotency fields без выпуска поддержки агента.
Кодовые сообщения об ошибках нельзя использовать как transport negotiation.

Предлагаю закрывать интеграцию следующими совместными сценариями:

1. Холодный старт: provisioning → проверенные resources → mounts → start →
   Slot readiness → deploy. Верные mp0/mp1 и mapping проверены на PVE.
2. Обрыв после `pct start`, ошибка guest action и исчезновение source после `pct set`:
   повтор не исполняет вслепую start, слот не выдаётся другому студенту.
3. Одновременные заявки на разные слоты одной ноды, недостаточная ёмкость,
   миграция CT между выбором и стартом, недоступный агент при статусе узла online в PVE.
4. Два provisioning одного key, неверный владелец, отсутствующая UID/GID-настройка;
   содержимое существующего каталога сохраняется.
5. Неудачный park, неверная цель mp1 и правильный суффикс под чужим root:
   CT не становится безопасным `free` только по факту остановки.
6. Resume на другом слоте запрещён до поддержки переносимого состояния;
   после её реализации сохраняются проект, манифест и контроль конкурентной записи.

Ответы желательно дать по разделам 1–6: выбранная политика, ответственный
компонент и критерий приёмки. Изменения runtime API агента оформляются отдельно.
