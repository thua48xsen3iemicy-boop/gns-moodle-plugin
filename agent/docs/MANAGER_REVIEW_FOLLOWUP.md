# Ответ агента на изменения менеджера

Сверено с `manager/docs/AGENT_REVIEW_ANSWERS.md` и исходниками в ветке
`claude/epic-feynman-54aj67`, коммит
`45ecd1374674615265819336b1545b11f347fb7b` (изменения `f19e201`, `45ecd13`).
Это дополнение к `MANAGER_CONTRACT_REVIEW.md`; замечания ниже не означают изменения
кода менеджера в ветке агента.

## Принятые изменения

Точные mp0/mp1, запас тайм-аутов, повторная проверка перед force stop,
stop/park после исчезновения источника и maintenance при неподтверждённой заглушке
согласуются с контрактом агента. Учёт ещё не потреблённой обещанной памяти работающих
CT исправляет ранее найденный пропуск. Ресурсы CT по-прежнему меняет менеджер через
Proxmox API; агент не получает `resources` и не выполняет scheduling/reservation.

## Реализовано на стороне агента в этой правке

1. Ошибки политики/операций имеют `detail: {code, message}`. Коды из
   `AGENT_REQUESTS.md` поддержаны; стандартные FastAPI validation errors остаются
   списком. Настройка UID/GID — отдельный `STUDENT_IDS_NOT_CONFIGURED` (503),
   проблемы storage — `STORAGE_UNAVAILABLE`. Неверный CephFS root —
   `AGENT_CONFIG_INVALID` (500). Список в README агента.
2. Ненулевой findmnt — 503 `STORAGE_UNAVAILABLE`, не 409 `PCT_FAILED`;
   ошибка запуска утилиты — `PCT_UNAVAILABLE`. Это не повод для force stop.
3. Фиксированный `init_slot` готовит `.slot-locks` перед restart службы.
   Подготовка выполняется с правами gns3, проверяет owner/mode, запрещает symlink,
   не меняет существующие данные и не делает recursive chown. Обновление нужно
   установить в guest template/существующие LXC; host installer туда не пишет.

Ограничение: `STUDENT_DIR_OWNER` пока не различает постоянного другого владельца
и окно mkdir/chown конкурирующего создателя, особенно на другой ноде. Рекомендован
ограниченный retry только provisioning; код не является доказательством, что
каталог сейчас создаётся. Автоматического chown существующего каталога нет.

## Осталось исправить/подтвердить в менеджере

### 1. Failed-сессия не освобождает право записи в каталог студента

Индекс `(site, user_id)` защищает только сессии со статусом вне `stopped/failed`.
`_fail()` может пометить сессию failed, оставив CT работающим (например, ошибка
после запуска/тайм-аут готовности). `finish_session()` сохраняет слот failed,
но новый POST того же студента уже может получить другой свободный слот и тот же
RW source. Поэтому утверждение в ответе «каталог никогда не смонтирован RW в два
слота» пока неверно, даже при одной живой сессии в БД.

Требование: отдельное владение student workspace до подтверждённых stop/park
или явной операторской процедуры. Failed-сессия и блокировка каталога должны
быть разными сущностями. Приёмка: CT1 остаётся running после ошибки; второй
запуск того же студента не получает RW mount на CT2 до безопасного освобождения.
Не снимать этот запрет по TTL без сверки фактического состояния.

### 2. Резервирование ёмкости требует сериализации по физической ноде

`tick()` запускает `drive()` разных сессий отдельными asyncio tasks. `placement()`
читает telemetry/reservations до транзакции `allocate_slot()`, которая блокирует
сессию и выбранный слот, но не общий бюджет ноды. Две заявки могут увидеть один
остаток и получить разные слоты на одной ноде. Единственный лидер этого не исключает.

Требование: сериализовать расчёт + запись резерва по ноде, либо выдачи целиком;
проверять лимит внутри той же критической секции, где создаётся резерв. Приёмка:
две одновременные заявки по 16 GiB при 20 GiB доступной ёмкости дают только одну
выдачу. Запас хоста не заменяет атомарность и не гарантирует свежесть telemetry.
При миграции между размещением и стартом нужна повторная проверка бюджета новой
ноды либо запрет такой миграции во время подготовки; ограничение уже признано.

### 3. Нужна отдельная миграция ограничения сессий

Изменён `migrations/001_init.sql`, но `db.migrate()` пропускает уже применённую
версию 001, не сверяя содержимое. На существующей БД индекс останется по
`(site, user_id, instance_id)` и не обеспечит новую политику.

Добавить следующую номерную миграцию с проверкой конфликтующих живых сессий и
пересозданием индекса. Не завершать/удалять конфликтующие сессии молча. Приёмка:
обновление старой БД обеспечивает то же ограничение, что чистая установка.
Если старая схема нигде не применялась, это допущение нужно явно подтвердить.

### 4. Необязательная заглушка ослабляет гарантию free

В `_stage_ct_park()` проверка находится внутри `if placeholder_student_key`;
при пустом значении слот может стать free без подтверждённой заглушки. Либо
запретить отключение заглушки, либо документировать и отдельно защищать этот режим.
Приёмка: конфигурация без placeholder не нарушает заявленную гарантию безопасного free.

## Проверки

На стороне агента выполнены mock pct/HTTP-тесты кодов, тесты подготовки гостевого
каталога на временных путях и локальный TLS-тест. В тесте guest privilege drop
подменён проверяемыми вызовами: реальные root/LXC/PVE не используются.
Тесты менеджера и реальный Proxmox здесь не запускались. Указанные сценарии
менеджера требуют его собственных regression tests и затем проверки на стенде.
