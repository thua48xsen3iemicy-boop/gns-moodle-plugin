# Автопроверки лаб

Проект, а не контракт. Формат API и документов, которые он вводит, вносится в `manager/docs/CONTRACTS.md` (§2.9) вместе с
кодом (правило `AGENTS.md`). Задача на стыке компонентов: менеджер (движок, хранение, API), плагин (настройки, отчёт,
журнал оценок), слот (новые коллекторы фактов).

Статус: этап 0 согласован (пороги §5.3 — решение владельца, остальные вопросы §10 — по предложению), этап 1 сделан в
менеджере 0.17.0 (§9). Всё ниже — 🆕.

## 1. Зачем и решения владельца

Прежняя система (репозиторий autochck, PNETLab) ставит оценку по проценту выполненных пунктов. Пунктов много, большинство
выполняются почти даром (имена, «адрес есть», «форвардинг выключен» на каждом клиенте), поэтому грубая ошибка — общий VLAN
у двух подразделений — растворяется, и сломанная сеть получает 4 или 5. Новая система строится иначе.

Решено владельцем:

1. **Баллы только за правильный результат.** Нет пунктов «за присутствие»: адрес засчитывается, только если он на том
   интерфейсе, кабель которого ведёт в нужный сегмент, с нужной маской и в нужной подсети. Неверно сделанное — ошибка, а
   не «почти»: адрес на чужом интерфейсе даёт и «нужного адреса нет», и «лишний адрес».
2. **Оценка по числу ошибок каждой тяжести, а не по проценту** (§5). Строгость выбирает **преподаватель** в настройках
   элемента курса; автоматического определения курса студента нет. Строгость меняет только тяжесть ошибки, превратить
   неверное в частично верное она не может.
3. **Cisco: авторитетна сохранённая конфигурация.** Не сделан `write memory` — настройки для проверки нет. Это правильно:
   после перезагрузки ничего не должно сломаться (`CONTRACTS.md` §4.6, `ios.config/1`).
4. **Linux: живой адрес сверяется с конфигурацией.** Адрес, добавленный утилитой `ip` и отсутствующий в конфиге, пропадёт
   после перезагрузки — в режиме «сохранённая настройка» это ошибка. Есть образы без ifupdown, где задание как раз про
   утилиту `ip`: там режим «живая настройка», конфиг не нужен. Режим задаёт преподаватель (§4.4).
5. **Оценивает сервер.** Гость отдаёт данные (факты, вывод команд), решение «верно / неверно» принимает менеджер. У студента
   в госте root, и подменить вывод он может; если смог — он молодец. Защищаемся только от того, чтобы обход не стал
   готовым рецептом: оценка на сервере и сверка с соседями (§6).
6. **Код преподавателя в менеджере не выполняется.** Свои проверки преподавателя — команды и скрипты, которые выполняются
   **в гостях лабы** через `qga/exec` (§7). Сломать он может только экземпляр лабы, не инфраструктуру.

## 2. Что уже есть

- **Топология** — `session.topology` (`.gns3` с живыми `node_id`): ноды, линки, порты, `suspend`, статусы нод.
- **Факты** (`CONTRACTS.md` §4.6, `plugin/docs/live-state.md` §3), журнал в PostgreSQL менеджера с `facts_rev` (DESIGN §6.7):

| ОС / образ | Коллектор | Что даёт |
|---|---|---|
| Linux (QEMU с QGA) | `linux.net/1` | интерфейсы (`kind`, MAC, порт GNS3, `admin`/`oper`, IPv4), сабинтерфейсы VLAN, маршруты |
| Windows | `windows.net/1` | адаптеры, IPv4, маршруты |
| MikroTik RouterOS (CHR) | `routeros.net/1` | интерфейсы, VLAN-сабинтерфейсы, IPv4, активные маршруты `main` |
| Linux-коммутатор | `switch.net/1`, `switch.fdb/1` | порты (`switchport`, `admin`/`oper`), таблица MAC |
| Cisco IOL | `ios.config/1` | сохранённая конфигурация: интерфейсы, `shutdown`, IPv4, сабинтерфейсы, SVI, `switchport`, имена VLAN (VTP off/transparent) |
| Cisco IOL, пары Cisco–Cisco | `iol.l1/1` | живой линк пары портов |

- **Модель слоёв** L1 / L2 / L3 и «проблемы» (дубль адреса, пересечение подсетей, подсеть разорвана на L2, несколько подсетей
  в домене, тег не проходит по транку) — в плагине (`live-state.md` §4, `amd/src/facts.js`).
- **Намерение преподавателя** — сегменты `gns3lab.lab/2` (`CONTRACTS.md` §2.6): участники, подсеть, VLAN, шлюз. Компилятор
  менеджера раздаёт по ним адреса (`lab_manager/segments.py`, `plan`).
- **Выполнение в госте** — `POST /v1/labs/{project_id}/nodes/{node_id}/qga/exec` слота (Linux, Windows, RouterOS; у IOL нет).

Чего в фактах нет: hostname, `ip_forward`, DNS, nftables (Linux); маршруты, OSPF, NAT, `hostname` у Cisco; состояние OSPF
(поля в формате есть, коллектора нет); конфиг сети Linux. Это этап 3 (§9).

## 3. Модель

- **Ожидание** — что должно получиться: сегменты, группы, параметры правил (§4). Берётся из лабы, входит в её версию.
- **Правило** — код (`subnet_split`), который сравнивает ожидание с фактами и топологией и выдаёт **находки**.
- **Находка** — одна ошибка про один объект: `{code, nodes, ifaces, message, caused_by}`. Один интерфейс без нужного
  адреса — одна находка `address_missing`, а не по находке на каждое следствие.
- **Класс** находки — `critical` · `major` · `minor` · `note`. Определяется профилем строгости и фокусом лабы (§5).
- **Первопричина.** Неверный VLAN на порту ломает подсеть, шлюз и связность. Движок проходит слои по порядку
  (L1 → L2 → адреса → шлюзы → связность) и у находки, объяснённой находкой нижнего слоя на том же пути, ставит
  `caused_by`. В оценку идут только находки без `caused_by`; следствия показываются как пояснение. Без этого строгая
  система несправедлива: одна опечатка дала бы двойку.
- **Непроверенное.** Если правило не может проверить объект из-за системы (факты устарели, сбор ноды не удался не по вине
  студента, у ОС нет нужного коллектора), объект получает статус `skipped` с причиной и в оценку не идёт. Если из-за
  студента (нода задания остановлена, линк приостановлен) — это находка. Если по временной причине системы
  (`stale_facts`, `collect_failed`) без проверки остался объект правила из фокуса лабы (нет фокуса — любого правила),
  прогон получает `incomplete` и оценки не ставит: «повторите проверку». Постоянные причины (`no_collector` — у ОС нет
  нужного коллектора) повтор не исправит: такое правило просто `skipped`.
- **Cisco без сохранённой конфигурации.** У IOL, который ничего не сохранял, нет фактов (`ios.config/1`). Проверка
  видит его так, как он загрузится: коммутатор — все порты access в VLAN 1, маршрутизатор — все порты выключены, и
  выдаёт находку `config_not_saved`. Всё, что из этого следует (не тот VLAN, разорванный сегмент), — её следствия.

## 4. Ожидание: что должно получиться

Описание — документ `gns3lab.checks/1`. Лаба из Moodle — поле `checks` определения `gns3lab.lab/2`; эталонная лаба —
поле `checks` в `meta.json` (`CONTRACTS.md` §3.1). Входит в `lab_def` (у эталонной — в ревизию): поменял проверки — новая
версия лабы, начатые проекты проверяются по своей.

```json
{
  "format": "gns3lab.checks/1",
  "focus": ["l2"],
  "persistence": "saved",
  "nodes": {"PC3": {"persistence": "runtime"}},
  "addresses": {"allowed": ["rfc1918"], "match": "plan", "forbid_prefix": [8, 32]},
  "groups": {"by_name": true, "explicit": [{"name": "BUH", "members": ["BUH-1", "BUH-2"], "vlan": 10}]},
  "switches": {"unused_ports_shutdown": true, "trunk_prune": true, "vlan_names": "group", "mgmt_vlan": 333},
  "reachability": "segments",
  "rules": {"vlan_extra": "off"},
  "scripts": []
}
```

Нет поля `checks` — работают только общие правила без ожиданий (§8, колонка «Без ожиданий»).

### 4.1. Сегменты: `configure`

Сегмент `lab/2` сейчас всегда преднастраивается компилятором. Для проверок нужен сегмент-**задание**: его описывает
преподаватель, а настраивает студент. Новое необязательное поле сегмента:

| `configure` | Что делает менеджер |
|---|---|
| `manager` (по умолчанию) | как сейчас: преднастройка участников, шлюза IOL и коммутаторов IOL на пути |
| `student` | ничего не настраивает, предупреждения `gateway_not_configured` и `switch_not_configured` не выдаёт; адреса раздаёт по тем же правилам (`plan`) — это ожидание для проверок |

Проверки сравнивают факты с сегментами **обоих** видов: преднастроенный сегмент студент мог сломать. В лабах на поиск
неисправностей (`faults`, этап 6 конструктора) эталоном служат сегменты без поломок.

### 4.2. Группы по именам

Для лаб без сегментов (`lab/1`, эталонные лабы) ожидание задаётся группами узлов.

- `by_name: true` — группы выводятся из имён узлов, подключённых к коммутаторам: имя в нижнем регистре без хвостовых цифр и
  разделителей `-`/`_` (`BUH-1`, `buh2` → `buh`; `ADM-1` → `adm`). Маршрутизаторы (категория образа `router`; у эталонной
  лабы без каталога — имя `R`, `R1`, `router-2`) групп не образуют. Меньше двух групп — групп нет. Так делает autochck
  (`guess_l2_groups_by_names`).
- `explicit` — группы списком; узел из `explicit` в группы по имени не попадает. `vlan` — необязательный номер.

Группа даёт ожидания слабее сегмента (подсеть и адреса неизвестны): узлы группы — в одном L2-домене, разных групп — в
разных; в домене одна подсеть; в домене группы есть шлюз (интерфейс маршрутизатора, сабинтерфейс или SVI), шлюз хостов
группы — этот адрес; `vlan`, если задан, — VLAN портов группы.

### 4.3. Адреса

| Поле | Смысл |
|---|---|
| `allowed` | допустимые диапазоны: `rfc1918` (по умолчанию: `10/8`, `172.16/12`, `192.168/16`) или сети `A.B.C.D/N`. Подсети сегментов допустимы всегда |
| `match` | `plan` (по умолчанию) — у участника сегмента ровно адрес по плану компилятора (`host` или по порядку); `subnet` — любой свободный адрес подсети сегмента, шлюз — по плану |
| `forbid_prefix` | маски, запрещённые там, где маска не задана сегментом (по умолчанию `[0, 8, 32]`, loopback не в счёт) |

### 4.4. Сохранённая и живая настройка Linux

`persistence` — для Linux-нод (QEMU без `switch.net`; Windows и RouterOS сохраняют настройки сами, у Cisco и так
сохранённая конфигурация):

| Значение | Правило |
|---|---|
| `saved` | адрес, шлюз и маршрут должны быть и в живых фактах, и в конфиге механизма сети. Только живой — `address_not_saved`; только в конфиге — `config_not_applied` |
| `runtime` | только живые факты, конфиг не читается. Ничего не перезапускается и не перезагружается: иначе проверка сотрёт работу студента |

По умолчанию — `saved`, если у образа ноды в каталоге есть `net_config`, иначе `runtime`. `nodes.<имя>.persistence`
переопределяет значение лабы для одной ноды. Данные `saved` даёт коллектор `linux.config/1` (этап 3, §9); пока его
нет, правила `saved` получают `skipped` с причиной `no_collector`.

Почему не перезапуск сети: `systemctl restart networking` трогает только интерфейсы из конфига и не убирает адрес,
добавленный на «чужой» интерфейс, а работу студента при этом ломает. Честная альтернатива — перезагрузка ноды: возможный
режим «финальная проверка с перезагрузкой» на будущее, не в этом проекте.

### 4.5. Прочие поля

| Поле | Смысл |
|---|---|
| `focus` | главное в лабе: группы правил `l1`, `l2`, `addressing`, `gateways`, `routing`, `host` (§8). Тяжесть находок этих групп поднимается на ступень (§5.2) |
| `switches` | правила коммутаторов, по умолчанию выключены: `unused_ports_shutdown`, `trunk_prune`, `vlan_names` (`group` — VLAN назван по группе или сегменту, регистр не важен), `mgmt_vlan` (номер: VLAN с SVI и адресом есть, лишним не считается) |
| `reachability` | связность по таблицам маршрутов: `segments` — каждая пара сегментов со шлюзами, или список пар узлов `[["BUH-1", "ADM-1"]]`; нет поля — не проверяется |
| `rules` | `{"<код>": "off"}` — выключить правило в этой лабе |
| `scripts` | свои проверки в гостях (§7), этап 4; до него поле не принимается (`unknown_field`) |

## 5. Оценка

Оценку считает менеджер по настройкам **элемента курса**, которые плагин передаёт в запросе проверки (`CONTRACTS.md` §2.9).
Настройки сохраняются в результате: оценку можно пересчитать и объяснить.

### 5.1. Профиль строгости

Профиль — таблица «код → класс». Преподаватель выбирает `lenient`, `standard` или `strict` и может переопределить класс
отдельных кодов (`overrides`). Классы по умолчанию — в каталоге правил (§8). Прощённая ошибка (`note`) **показывается**
студенту с пометкой, что при обычной строгости она стоит оценки.

### 5.2. Фокус лабы

Находки правил из `focus` поднимаются на ступень: `note` → `minor` → `major` → `critical`. Первокурснику прощается
небрежность в hostname, но не невыполненная лаба: в лабе про VLAN общий домен двух групп — `critical` при любом профиле.

### 5.3. Пороги

Учитываются находки без `caused_by`, кроме `note`. Оценка — первая строка, условия которой выполнены:

| Оценка | `critical` | `major` | `minor` |
|---|---|---|---|
| 5 | 0 | 0 | ≤ 1 |
| 4 | 0 | ≤ 1 | ≤ 3 |
| 3 | 0 | ≤ 3 | любое |
| 2 | иначе | | |

Пороги — настройка элемента курса, это значения по умолчанию. Что делать с оценкой в журнале Moodle (шкала, перевод в
баллы, лимит попыток, снижение максимума за повторные попытки), решает плагин (§9, этап 2).

### 5.4. Калибровка

До запуска новая оценка прогоняется по истории autochck (SQLite, `check_items`): распределение оценок сравнивается со
старым, чтобы строгость не оказалась неожиданной для преподавателей.

## 6. Честность данных

- Оценка — только на сервере, гость отдаёт данные.
- Важное подтверждается с другой стороны, где это дёшево: адрес узла за портом Linux-коммутатора — по таблице MAC
  (`switch.fdb`), связность — по таблицам маршрутов всех узлов пути, а не по ответу одного узла.
- Противоречие источников (узел говорит одно, соседи видят другое) — находка `facts_conflict` класса `note` с пометкой
  для преподавателя; оценка не снижается автоматически.
- Активные скрипты (§7) меняют маркер в каждом запуске: подменный скрипт, переданный другому студенту, сломается.

## 7. Свои проверки преподавателя (этап 4)

Код преподавателя выполняется только в гостях лабы. Элемент `scripts`:

```json
{"id": "nginx", "title": "Веб-сервер на SRV1", "node": "SRV1", "shell": "sh",
 "run": "systemctl is-active nginx; curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1/",
 "expect": {"exit": 0, "match": "^active\\n200$"}, "group": "host", "class": "major"}
```

- `shell` — `sh`, `powershell`, `routeros` (как у `qga/exec`); IOL — нет.
- `expect` — код выхода и/или регулярное выражение по выводу; не сошлось — находка `script_failed` с `title`.
- Вывод и сравнение — на менеджере. Таймаут, размер вывода и число скриптов ограничены.
- Библиотека готовых фрагментов для копирования — `manager/examples/checks/` (nginx, ключ SSH, ping между группами,
  DHCP-аренда), с инструкцией.
- Проверка «на эталоне»: преподаватель запускает проверку в авторском запуске (`CONTRACTS.md` §2.8) и видит, что скрипт
  работает, до выдачи лабы студентам.

## 8. Каталог правил

Класс по умолчанию — для профилей `lenient` / `standard` / `strict`. «Без ожиданий» — работает ли правило без `checks`
(только по фактам и топологии). ОС: L — Linux, W — Windows, M — RouterOS, S — Linux-коммутатор, C — Cisco IOL.

### L1 (`l1`)

| Код | Что | ОС | Без ожиданий | Классы |
|---|---|---|---|---|
| `node_stopped` | нода задания (участник, шлюз, коммутатор на пути) остановлена | все | да | major / critical / critical |
| `config_not_saved` | у Cisco IOL нет сохранённой конфигурации (§3) | C | да | major / major / critical |
| `link_suspended` | линк на пути сегмента приостановлен (студент линки не приостанавливает: без ожиданий не проверяется) | все | нет | major / critical / critical |
| `port_shutdown` | порт на пути сегмента выключен (`admin: down`) | L W M C | да | major / major / critical |
| `link_down` | линк не поднят: `oper: down`, у пар Cisco–Cisco — `iol.l1` | L W M S C | да | minor / major / major |
| `unused_port_up` | неиспользуемый порт Cisco-коммутатора не выключен (`switches.unused_ports_shutdown`) | C | нет | note / minor / major |

### L2 (`l2`)

| Код | Что | ОС | Без ожиданий | Классы |
|---|---|---|---|---|
| `segments_merged` | два сегмента или группы в одном L2-домене | все | нет | major / critical / critical |
| `segment_split` | участники сегмента или группы в разных L2-доменах | все | нет | major / critical / critical |
| `member_isolated` | участник один в своём домене, хотя в домене есть коммутатор | все | да | major / major / critical |
| `vlan_mismatch` | на концах линка разные native или access VLAN | S C | да | minor / major / major |
| `tag_not_allowed` | тег, который шлёт хост, маршрутизатор или коммутатор, не принимает другой конец. Лишний VLAN на транке к хосту или маршрутизатору — не ошибка линка (это `trunk_not_pruned`) | S C M L | да | minor / major / major |
| `vlan_wrong` | порт участника не в VLAN сегмента или группы (когда VLAN задан) | S C | нет | minor / major / major |
| `vlan_name_wrong` | VLAN назван не по группе (`switches.vlan_names`) | C | нет | note / minor / minor |
| `vlan_extra` | создан VLAN, которого нет в задании (кроме `mgmt_vlan`) | C | нет | note / minor / minor |

  первопричины (`CAUSES`: находка объясняется находкой из списка своего кода, если у них есть общий объект — порт, линк,

## 12. Как сделано на этапе 3 (слот 0.17.0, менеджер 0.18.0)

Слот (`CONTRACTS.md` §4.6): `linux.sys/1` — `hostname`, `ip_forward`, `dns`; `linux.config/1` — `net_saved`
(`mechanism`, `ok`, `message`, `interfaces[]` с `method`, `ipv4`, `gateway`, `routes`; ifupdown читается самим ifupdown,
netplan/networkd/NetworkManager пока `supported: false`); `hostname` в `windows.net/1` и `routeros.sys/1`; `ios.config/1`
даёт `hostname` и `routes` (подключённые сети и `ip route`, у L2 — `ip default-gateway`).

Менеджер:
- `hostname_wrong` — имя узла без учёта регистра или FQDN, начинающийся с имени. У Cisco без строки `hostname` (слот
  0.17.0+) — «имя не задано». Служебные ноды и IOL без сохранённой конфигурации не проверяются.
- `forwarding_off` / `forwarding_on_host` — по `ip_forward` и роли ноды. Выключенная пересылка на Linux-маршрутизаторе
  по пути делает `unreachable` её следствием.
- `persistence` ноды: `checks.nodes.<имя>`, иначе `checks.persistence`, иначе по образу (`net_config` ifupdown,
  networkmanager, netplan, networkd — `saved`, иначе `runtime`); у эталонной лабы образ неизвестен — `runtime`, если
  гость сообщил `mechanism: "none"`, иначе `saved`. В `saved`: живой адрес или шлюз без записи в конфиге —
  `address_not_saved` (адреса интерфейса с `method: dhcp` не сверяются); адрес или шлюз конфига, которого нет вживую,
  и `net_saved.ok: false` — `config_not_applied`. `supported: false` — правило `skipped` (`unsupported_os`).
- Связность через Cisco считается по `routes` из `ios.config`.
