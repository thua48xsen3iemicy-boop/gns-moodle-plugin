# Автопроверки лаб

Проект, а не контракт. Формат API и документов, которые он вводит, вносится в `manager/docs/CONTRACTS.md` (§2.9) вместе с
кодом (правило `AGENTS.md`). Задача на стыке компонентов: менеджер (движок, хранение, API), плагин (настройки, отчёт,
журнал оценок), слот (новые коллекторы фактов).

Статус: этап 0 согласован (пороги §5.3 — решение владельца, остальные вопросы §10 — по предложению), этап 1 сделан в
менеджере 0.17.0 (§9). Всё ниже — 🆕.

## 1. Зачем и решения владельца

Прежняя система (репозиторий autochck, PNETLab) ставит оценку по проценту выполненных пунктов. Пунктов много, большинство
выполняются почти даром (имена, «адрес есть», «форвардинг выключен» на каждом клиенте), поэтому грубая ошибка — общий VLAN
у двух подразделений — растворяется, и сломанная сеть получает 4 или 5. Новая система строится иначе.

Решено владельцем:

1. **Баллы только за правильный результат.** Нет пунктов «за присутствие»: адрес засчитывается, только если он на том
   интерфейсе, кабель которого ведёт в нужный сегмент, с нужной маской и в нужной подсети. Неверно сделанное — ошибка, а
   не «почти»: адрес на чужом интерфейсе даёт и «нужного адреса нет», и «лишний адрес».
2. **Оценка по числу ошибок каждой тяжести, а не по проценту** (§5). Строгость выбирает **преподаватель** в настройках
   элемента курса; автоматического определения курса студента нет. Строгость меняет только тяжесть ошибки, превратить
   неверное в частично верное она не может.
3. **Cisco: авторитетна сохранённая конфигурация.** Не сделан `write memory` — настройки для проверки нет. Это правильно:
   после перезагрузки ничего не должно сломаться (`CONTRACTS.md` §4.6, `ios.config/1`).
4. **Linux: живой адрес сверяется с конфигурацией.** Адрес, добавленный утилитой `ip` и отсутствующий в конфиге, пропадёт
   после перезагрузки — в режиме «сохранённая настройка» это ошибка. Есть образы без ifupdown, где задание как раз про
   утилиту `ip`: там режим «живая настройка», конфиг не нужен. Режим задаёт преподаватель (§4.4).
5. **Оценивает сервер.** Гость отдаёт данные (факты, вывод команд), решение «верно / неверно» принимает менеджер. У студента
   в госте root, и подменить вывод он может; если смог — он молодец. Защищаемся только от того, чтобы обход не стал
   готовым рецептом: оценка на сервере и сверка с соседями (§6).
6. **Код преподавателя в менеджере не выполняется.** Свои проверки преподавателя — команды и скрипты, которые выполняются
   **в гостях лабы** через `qga/exec` (§7). Сломать он может только экземпляр лабы, не инфраструктуру.

| Cisco IOL, пары Cisco–Cisco | `iol.l1/1` | живой линк пары портов |

- **Модель слоёв** L1 / L2 / L3 и «проблемы» (дубль адреса, пересечение подсетей, подсеть разорвана на L2, несколько подсетей
  в домене, тег не проходит по транку) — в плагине (`live-state.md` §4, `amd/src/facts.js`).
- **Намерение преподавателя** — сегменты `gns3lab.lab/2` (`CONTRACTS.md` §2.6): участники, подсеть, VLAN, шлюз. Компилятор
  менеджера раздаёт по ним адреса (`lab_manager/segments.py`, `plan`).

Чего в фактах нет: hostname, `ip_forward`, DNS, nftables (Linux); маршруты, OSPF, NAT, `hostname` у Cisco; состояние OSPF
(поля в формате есть, коллектора нет); конфиг сети Linux. Это этап 3 (§9).

## 3. Модель

- **Ожидание** — что должно получиться: сегменты, группы, параметры правил (§4). Берётся из лабы, входит в её версию.
- **Правило** — код (`subnet_split`), который сравнивает ожидание с фактами и топологией и выдаёт **находки**.
- **Находка** — одна ошибка про один объект: `{code, nodes, ifaces, message, caused_by}`. Один интерфейс без нужного
  адреса — одна находка `address_missing`, а не по находке на каждое следствие.
- **Класс** находки — `critical` · `major` · `minor` · `note`. Определяется профилем строгости и фокусом лабы (§5).
- **Первопричина.** Неверный VLAN на порту ломает подсеть, шлюз и связность. Движок проходит слои по порядку
  (L1 → L2 → адреса → шлюзы → связность) и у находки, объяснённой находкой нижнего слоя на том же пути, ставит
  `caused_by`. В оценку идут только находки без `caused_by`; следствия показываются как пояснение. Без этого строгая
  система несправедлива: одна опечатка дала бы двойку.
- **Непроверенное.** Если правило не может проверить объект из-за системы (факты устарели, сбор ноды не удался не по вине
  студента, у ОС нет нужного коллектора), объект получает статус `skipped` с причиной и в оценку не идёт. Если из-за
  студента (нода задания остановлена, линк приостановлен) — это находка. Если по временной причине системы
  (`stale_facts`, `collect_failed`) без проверки остался объект правила из фокуса лабы (нет фокуса — любого правила),
  прогон получает `incomplete` и оценки не ставит: «повторите проверку». Постоянные причины (`no_collector` — у ОС нет
  нужного коллектора) повтор не исправит: такое правило просто `skipped`.
- **Cisco без сохранённой конфигурации.** У IOL, который ничего не сохранял, нет фактов (`ios.config/1`). Проверка
  видит его так, как он загрузится: коммутатор — все порты access в VLAN 1, маршрутизатор — все порты выключены, и
  выдаёт находку `config_not_saved`. Всё, что из этого следует (не тот VLAN, разорванный сегмент), — её следствия.

## 4. Ожидание: что должно получиться

Описание — документ `gns3lab.checks/1`. Лаба из Moodle — поле `checks` определения `gns3lab.lab/2`; эталонная лаба —
поле `checks` в `meta.json` (`CONTRACTS.md` §3.1). Входит в `lab_def` (у эталонной — в ревизию): поменял проверки — новая
версия лабы, начатые проекты проверяются по своей.

```json
{
  "format": "gns3lab.checks/1",
  "focus": ["l2"],
  "persistence": "saved",
  "nodes": {"PC3": {"persistence": "runtime"}},
  "addresses": {"allowed": ["rfc1918"], "match": "plan", "forbid_prefix": [8, 32]},
  "groups": {"by_name": true, "explicit": [{"name": "BUH", "members": ["BUH-1", "BUH-2"], "vlan": 10}]},
  "switches": {"unused_ports_shutdown": true, "trunk_prune": true, "vlan_names": "group", "mgmt_vlan": 333},
  "reachability": "segments",
  "rules": {"vlan_extra": "off"},
  "scripts": []
}
```

Нет поля `checks` — работают общие правила без ожиданий (§8, колонка «Без ожиданий») и типовая проверка сети (§4.6).

### 4.1. Сегменты: `configure`

Сегмент `lab/2` сейчас всегда преднастраивается компилятором. Для проверок нужен сегмент-**задание**: его описывает
преподаватель, а настраивает студент. Новое необязательное поле сегмента:

| `configure` | Что делает менеджер |
|---|---|
| `manager` (по умолчанию) | как сейчас: преднастройка участников, шлюза IOL и коммутаторов IOL на пути |
| `student` | ничего не настраивает, предупреждения `gateway_not_configured` и `switch_not_configured` не выдаёт; адреса раздаёт по тем же правилам (`plan`) — это ожидание для проверок |

Проверки сравнивают факты с сегментами **обоих** видов: преднастроенный сегмент студент мог сломать. В лабах на поиск
неисправностей (`faults`, этап 6 конструктора) эталоном служат сегменты без поломок.

### 4.2. Группы по именам

Для лаб без сегментов (`lab/1`, эталонные лабы) ожидание задаётся группами узлов.

- `by_name: true` — группы выводятся из имён узлов, подключённых к коммутаторам: имя в нижнем регистре без хвостовых цифр и
  разделителей `-`/`_` (`BUH-1`, `buh2` → `buh`; `ADM-1` → `adm`). Маршрутизаторы (категория образа `router`; у эталонной
  лабы без каталога — имя `R`, `R1`, `router-2`) групп не образуют. Меньше двух групп — групп нет. Так делает autochck
  (`guess_l2_groups_by_names`).
- `explicit` — группы списком; узел из `explicit` в группы по имени не попадает. `vlan` — необязательный номер.

Группа даёт ожидания слабее сегмента (подсеть и адреса неизвестны): узлы группы — в одном L2-домене, разных групп — в
разных; в домене одна подсеть; в домене группы есть шлюз (интерфейс маршрутизатора, сабинтерфейс или SVI), шлюз хостов
группы — этот адрес; `vlan`, если задан, — VLAN портов группы.

### 4.3. Адреса

| Поле | Смысл |
|---|---|
| `allowed` | допустимые диапазоны: `rfc1918` (по умолчанию: `10/8`, `172.16/12`, `192.168/16`) или сети `A.B.C.D/N`. Подсети сегментов допустимы всегда |
| `match` | только для сегментов `configure: student`: `auto` (по умолчанию) — типовая проверка (§4.6), подсеть и план сегмента не требуются; `subnet` — любой свободный адрес подсети сегмента, шлюз — по плану; `plan` — ровно адрес по плану компилятора (`host` или по порядку). `subnet` и `plan` — когда подсеть или план выписаны в задании. Сегмент `configure: manager` всегда проверяется по плану: это выданное окружение |
| `forbid_prefix` | маски, запрещённые там, где маска не задана сегментом (по умолчанию `[0, 8, 32]`, loopback не в счёт) |

### 4.4. Сохранённая и живая настройка Linux

`persistence` — для Linux-нод (QEMU без `switch.net`; Windows и RouterOS сохраняют настройки сами, у Cisco и так
сохранённая конфигурация):

| Значение | Правило |
|---|---|
| `saved` | адрес, шлюз и маршрут должны быть и в живых фактах, и в конфиге механизма сети. Только живой — `address_not_saved`; только в конфиге — `config_not_applied` |
| `runtime` | только живые факты, конфиг не читается. Ничего не перезапускается и не перезагружается: иначе проверка сотрёт работу студента |

По умолчанию — `saved`, если у образа ноды в каталоге есть `net_config`, иначе `runtime`. `nodes.<имя>.persistence`
переопределяет значение лабы для одной ноды. Данные `saved` даёт коллектор `linux.config/1` (этап 3, §9); пока его
нет, правила `saved` получают `skipped` с причиной `no_collector`.

Почему не перезапуск сети: `systemctl restart networking` трогает только интерфейсы из конфига и не убирает адрес,
добавленный на «чужой» интерфейс, а работу студента при этом ломает. Честная альтернатива — перезагрузка ноды: возможный
режим «финальная проверка с перезагрузкой» на будущее, не в этом проекте.

### 4.5. Прочие поля

| Поле | Смысл |
|---|---|
| `focus` | главное в лабе: группы правил `l1`, `l2`, `addressing`, `gateways`, `routing`, `host` (§8). Тяжесть находок этих групп поднимается на ступень (§5.2) |
| `switches` | правила коммутаторов, по умолчанию выключены: `unused_ports_shutdown`, `trunk_prune`, `vlan_names` (`group` — VLAN назван по группе или сегменту, регистр не важен), `mgmt_vlan` (номер: VLAN с SVI и адресом есть, лишним не считается) |
| `network` | `auto` (по умолчанию) или `off` — типовая проверка сети (§4.6) |
| `reachability` | связность по таблицам маршрутов: `segments` — каждая пара сегментов со шлюзами, или список пар узлов `[["BUH-1", "ADM-1"]]`; нет поля — не проверяется |
| `rules` | `{"<код>": "off"}` — выключить правило в этой лабе |
| `scripts` | свои проверки в гостях (§7), этап 4; до него поле не принимается (`unknown_field`) |

### 4.6. Типовая проверка сети

Большинство лаб — про адреса, шлюзы и выход в интернет. Чтобы такую лабу проверять без описания сегментов, ожидание
выводится из топологии. Поле `network`:

| `network` | Что |
|---|---|
| `auto` (по умолчанию, в том числе без поля `checks`) | типовая проверка ниже |
| `off` | сеть не проверяется: правила групп `addressing`, `gateways`, `routing` получают статус `off`, как через `rules`. Для лаб по командной строке и сервисам; L1, L2 и `host` остаются |

Проверка идёт по L2-доменам (`netmodel.py`). Домен берётся, если в нём есть интерфейс хоста или маршрутизатора и ни один
его интерфейс не входит в сегмент `configure: manager` или в группу (у них свои ожидания). Служебные узлы (ISP,
Linux-коммутатор) не проверяются, L2-коммутаторы — только по `address_extra`, как сейчас.

- **Адрес есть.** У каждого интерфейса хоста или маршрутизатора с кабелем в домен есть IPv4-адрес, иначе
  `address_missing` (в тексте — подсеть, которую уже используют соседи по домену, если она одна). Конкретный адрес не
  требуется: годится любой план, лишь бы сеть была рабочей. Порт маршрутизатора в сети ISP тоже должен иметь адрес
  (обычно по DHCP из `198.18.N.0/24`).
- **Одна подсеть в домене** — `subnet_mixed`, как сейчас.
- **Шлюз.** Если в домене есть адрес маршрутизатора в подсети хоста, у хоста есть маршрут по умолчанию через такой
  адрес: нет маршрута — `gateway_missing`, другой адрес — `gateway_wrong`. Хост в нескольких доменах с маршрутизаторами —
  достаточно шлюза через любой из них. В домене без маршрутизатора шлюз не требуется.
- **Выход в интернет** (у любого хоста лабы с адресом, и за сегментом `configure: manager` тоже: его адреса — окружение,
  а выход к ISP — задание). Если в лабе есть ISP и от хоста до порта ISP есть путь по кабелям через коммутаторы и
  маршрутизаторы, маршрут хоста к адресу вне лабы по таблицам маршрутов доходит до порта ISP `198.18.N.1`; иначе
  `unreachable` («Нет выхода в интернет у …», одна находка на причину). Интерфейс IOL с `ip address dhcp` в сети ISP
  получает то, что дал бы DHCP: подключённую сеть ISP и маршрут по умолчанию через порт ISP (расстояние 254).
- **NAT.** Если путь доходит до ISP через IOL, у его интерфейса к ISP есть `ip nat outside`, у интерфейса, откуда пришёл
  трафик хоста, — `ip nat inside`, а правило `ip nat inside source` (`list` с выходом через этот интерфейс или `pool`,
  либо `static`) транслирует адрес хоста: первая подходящая запись ACL — `permit`. Иначе `nat_missing`, одна находка на
  маршрутизатор. ACL, который слот не понял, считается транслирующим. Данные — `nat` в `ios.config/1` (слот 0.24.0).
  У Linux (nftables, iptables, VyOS) и RouterOS — правила исходящего NAT `snat` (`linux.sys/1`, `routeros.sys/1`, слот
  0.25.0): первое подходящее по интерфейсу к ISP и адресу хоста правило должно быть маскарадом или SNAT; правило с
  условиями, которые слот не разобрал, засчитывается. Нет данных — `skipped` (`no_collector`). Обратный путь от ISP не проверяется: у ISP нет фактов.
  Связность между доменами — только по `reachability`.

Сегмент `configure: student` с `match: auto` проверяется так же, но его состав известен: `segment_split` и
`segments_merged` работают как раньше, а подсеть сегмента и план не требуются.

После обновления менеджера лабы без `checks` и студенческие сегменты без `match` проверяются строже прежнего: пустые
адреса и шлюзы становятся находками. Вернуть прежнее — `network: off` или `match: plan` в лабе.

## 5. Оценка

Оценку считает менеджер по настройкам **элемента курса**, которые плагин передаёт в запросе проверки (`CONTRACTS.md` §2.9).
Настройки сохраняются в результате: оценку можно пересчитать и объяснить.

### 5.1. Профиль строгости

Профиль — таблица «код → класс». Преподаватель выбирает `lenient`, `standard` или `strict` и может переопределить класс
отдельных кодов (`overrides`). Классы по умолчанию — в каталоге правил (§8). Прощённая ошибка (`note`) **показывается**
студенту с пометкой, что при обычной строгости она стоит оценки.

### 5.2. Фокус лабы

Находки правил из `focus` поднимаются на ступень: `note` → `minor` → `major` → `critical`. Первокурснику прощается
небрежность в hostname, но не невыполненная лаба: в лабе про VLAN общий домен двух групп — `critical` при любом профиле.

### 5.3. Пороги

Учитываются находки без `caused_by`, кроме `note`. Оценка — первая строка, условия которой выполнены:

| Оценка | `critical` | `major` | `minor` |
|---|---|---|---|
| 5 | 0 | 0 | ≤ 1 |
| 4 | 0 | ≤ 1 | ≤ 3 |
| 3 | 0 | ≤ 3 | любое |
| 2 | иначе | | |

Пороги — настройка элемента курса, это значения по умолчанию. Что делать с оценкой в журнале Moodle (шкала, перевод в
баллы, лимит попыток, снижение максимума за повторные попытки), решает плагин (§9, этап 2).

### 5.4. Калибровка

До запуска новая оценка прогоняется по истории autochck (SQLite, `check_items`): распределение оценок сравнивается со
старым, чтобы строгость не оказалась неожиданной для преподавателей.

## 6. Честность данных

- Оценка — только на сервере, гость отдаёт данные.
- Важное подтверждается с другой стороны, где это дёшево: адрес узла за портом Linux-коммутатора — по таблице MAC
  (`switch.fdb`), связность — по таблицам маршрутов всех узлов пути, а не по ответу одного узла.
- Противоречие источников (узел говорит одно, соседи видят другое) — находка `facts_conflict` класса `note` с пометкой
  для преподавателя; оценка не снижается автоматически.
- Активные скрипты (§7) меняют маркер в каждом запуске: подменный скрипт, переданный другому студенту, сломается.

## 7. Свои проверки преподавателя (этап 4)

> **Формат утверждён владельцем 2026-11-18** вместе с предложениями §7.6: RE2, без `after`, по очереди, студенту — `title` и
> причина. Контракт — `CONTRACTS.md` §2.9 (`scripts`) и §4.2 (оболочка `qga/exec`), просьба к слоту — `SLOT_REQUESTS.md` §9.
> IOL скриптов не получает: у него проверяется сохранённая конфигурация (NVRAM) встроенными правилами.

Код преподавателя выполняется только в гостях лабы, через `qga/exec` слота (`CONTRACTS.md` §4.2). Менеджер его не
исполняет: он подставляет маркер, отправляет скрипт и сравнивает ответ.

### 7.1. Элемент `scripts`

```json
"scripts": [
  {"id": "nginx", "title": "Веб-сервер на SRV1", "node": "SRV1",
   "run": "systemctl is-active nginx; curl -s -m 5 -o /dev/null -w '%{http_code}' http://127.0.0.1/",
   "timeout": 15, "expect": {"exit": 0, "match": "^active\\n200$"}, "group": "host", "class": "major"},
  {"id": "ssh-key", "title": "Вход по ключу с PC1 на SRV1", "node": "PC1",
   "run": "ssh -o BatchMode=yes -o ConnectTimeout=5 admin@10.0.0.10 echo {{nonce}}",
   "expect": {"exit": 0, "contains": ["{{nonce}}"]}}
]
```

| Поле | Обяз. | Правило |
|---|---|---|
| `id` | да | `^[a-z0-9][a-z0-9_-]{0,31}$`, уникален в лабе; по нему плагин сопоставляет прогоны |
| `title` | да | 1…120 символов; это видят студент и преподаватель |
| `node` | да | имя ноды лабы: QEMU с гостевым агентом (без `qga: false`). IOL, VPCS, коммутаторы GNS3 и ISP не подходят |
| `shell` | нет | `sh` · `powershell` · `routeros`. Если не указано, берётся по семейству гостя. Если указано, то нужно для сверки: образ известного семейства с другой оболочкой — ошибка `validate`, в прогоне — `skipped` |
| `run` | да | текст скрипта. UTF-8, не больше 8000 байт после подстановки маркера (у слота предел 8192). `{{nonce}}` заменяется маркером прогона (§7.3) |
| `timeout` | нет | 1…60 с, по умолчанию 20 |
| `expect` | нет | условия ниже, должны выполниться все. Если поля нет, то `{"exit": 0}` |
| `group` | нет | `l1` · `l2` · `addressing` · `gateways` · `routing` · `host` (по умолчанию). Задаёт раздел отчёта и действие `focus` (§5.2) |
| `class` | нет | `critical` · `major` (по умолчанию) · `minor` · `note`. Профиль строгости на скрипт не действует: класс выбрал преподаватель. `focus` поднимает класс на ступень, `grading.overrides["script_failed"]` переопределяет его для всех скриптов |

`expect`:

| Поле | Правило |
|---|---|
| `exit` | int: код выхода должен совпасть |
| `match` | регулярное выражение (синтаксис RE2, не длиннее 500 символов), которое должно найтись в выводе (`search`, без флагов) |
| `contains` | 1…10 строк, каждая должна быть в выводе. `{{nonce}}` подставляется |
| `not_contains` | 1…10 строк, ни одной не должно быть в выводе |

Сравнивается `stdout`. Перед сравнением `\r\n` заменяется на `\n`, а пробелы и переводы строк в конце вывода
отрезаются (у RouterOS слот делает первое сам). `stderr` в сравнении не участвует, его показывают преподавателю.
Сравниваются первые 64 КиБ вывода.

**Почему RE2.** Регулярное выражение пишет преподаватель, а исполняет его менеджер. В обычном `re` выражение вроде
`(a+)+$` на длинном выводе зависает на минуты и занимает воркер менеджера. RE2 работает за линейное время, но это
новая зависимость (`google-re2`, закрепить в `constraints-tested.txt`). Без неё `match` остаётся только с запуском в
отдельном процессе с таймаутом (вопрос 2, §7.6).

### 7.2. Пределы

| Что | Предел |
|---|---|
| скриптов в лабе | 20 |
| `run` | 8000 байт после подстановки |
| `timeout` одного скрипта | 1…60 с |
| сумма `timeout` всех скриптов | 120 с; срок прогона — `CHECK_TIMEOUT` плюс эта сумма |
| сравнение | первые 64 КиБ `stdout` |
| в прогоне хранится | первые 2 КиБ `stdout` и 1 КиБ `stderr` каждого скрипта, `truncated: true`, если обрезано |

Скрипты выполняются **по одному, в порядке массива**, после сбора свежих фактов (§2.9 «Свежесть») и до расчёта правил.
Так результат предсказуем, и следующий скрипт может опираться на предыдущий: например, первый создаёт файл на SRV1, а
второй забирает его с PC1.

### 7.3. Маркер прогона

Для каждого прогона менеджер создаёт маркер — 16 hex-символов, один на все скрипты. Им он заменяет `{{nonce}}` в `run`,
`contains` и `match` (в `match` — как буквальный текст). Скрипт, который проверяет реальный путь (ключ SSH, HTTP-запрос
к соседу, файл через сеть), должен пропустить маркер через этот путь. Тогда заготовка, которая печатает «ok», не пройдёт
ни у этого студента, ни у того, кому её передали (§6). Маркер записывается в прогон (`result.nonce`), чтобы
преподаватель мог разобраться в споре.

### 7.4. Результат в прогоне

Отдельный список `result.scripts[]` — по строке на скрипт, и прошедший, и нет. Так преподаватель в авторском запуске
видит вывод каждого скрипта:

```json
"scripts": [
  {"id": "nginx", "node": "SRV1", "status": "fail", "reason": "mismatch", "exit_code": 0,
   "stdout": "inactive\n000", "stderr": "", "truncated": false, "duration_ms": 412},
  {"id": "ssh-key", "node": "PC1", "status": "pass", "exit_code": 0, "stdout": "3f9a1c0d2b4e5f60",
   "stderr": "", "truncated": false, "duration_ms": 1830}
]
```

| `status` | `reason` | Когда |
|---|---|---|
| `pass` | — | все условия `expect` выполнены |
| `fail` | `exit` · `mismatch` · `timeout` | код выхода не тот; вывод не прошёл `match`/`contains`/`not_contains`; не уложился в `timeout`. Это находка `script_failed` |
| `fail` | `node_stopped` | нода остановлена: находка `script_failed` с `caused_by` на находку `node_stopped` этой ноды, в оценку не идёт |
| `skipped` | `collect_failed` | гостевой агент не ответил: канал в back-off, обмен оборвался, слот вернул `502`. Временная причина: если `group` скрипта в `focus` (или `focus` пуст), прогон получает `incomplete` (§3) |
| `skipped` | `unsupported_os` | семейство гостя не совпало с `shell`. Это ошибка лабы, а не студента: повтор не поможет |

Находка `script_failed` — одна на непрошедший скрипт, с полем `script_id`. `nodes: [node]`, `ifaces: []`,
`message` — `title` и причина по-русски: «Веб-сервер на SRV1: вывод не совпал с ожидаемым». В `result.rules` —
одна строка `script_failed`: `fail`, если не прошёл хоть один скрипт, `pass`, если прошли все, `skipped`, если все
пропущены. Других первопричин (VLAN, адреса) у находки скрипта нет: движок не знает, от чего зависит скрипт (вопрос 3).

Текст `run` в прогон не попадает: он есть в определении лабы. Плагин не показывает студенту ни `run`, ни
`expect` (это подсказка к ответу). Что из `result.scripts` видит студент (только `title` и причину или ещё вывод),
решает плагин; по умолчанию предлагается только `title` и причина.

### 7.5. Что меняется у компонентов

- **Менеджер.** Разбор и проверка `scripts` в `validate` (путь `checks.scripts[2].node`; новые коды
  `script_node_unsupported`, `shell_mismatch`, `bad_regex`; пределы — `out_of_range`), выполнение через `qga/exec`, маркер,
  сравнение, `result.scripts`, `result.nonce`, находка `script_failed`. `CONTRACTS.md` §2.9.
- **Слот** (`SLOT_REQUESTS.md`). Сейчас `POST …/qga/exec` выбирает оболочку так: `routeros` у RouterOS и `sh` у всех
  остальных, то есть и у Windows (`api/nodes.py`). Нужно: у семейства `windows` — `powershell`; необязательное поле
  `shell` в запросе для сверки (не совпало с семейством — `409 SHELL_MISMATCH`, до гостя не доходит). Желательно:
  обрезать `stdout` и `stderr` до 64 КиБ с `truncated: true`, чтобы вывод на мегабайты (qemu-ga отдаёт до 16 МиБ) не
  шёл по сети целиком. Слот и менеджер с этим выпускаются вместе; без новой версии слота скрипты для Windows — `skipped`
  с `unsupported_os`.
- **Плагин.** Поле скриптов в редакторе лабы; в отчёте — `script_failed` и `result.scripts` (преподавателю — с выводом).
- **Библиотека** `manager/examples/checks/`: nginx, ключ SSH (через `{{nonce}}`), ping между группами, DHCP-аренда.
  Каждый фрагмент — JSON элемента `scripts` с комментарием в README: что проверяет, для каких образов.
- **Проверка на эталоне.** Скрипты работают в авторском запуске (`CONTRACTS.md` §2.8) так же, как у студента: тот же
  `POST /sessions/{id}/checks`, а преподаватель видит `result.scripts` целиком.

Скрипт работает в госте студента от root (у Windows — от SYSTEM) и может что-нибудь изменить. В инструкции к библиотеке
сказано: скрипт только читает. Сломать он может только этот экземпляр лабы (§1, п. 6).

### 7.6. Вопросы владельцу (решены: приняты предложения выше)

1. Формат `scripts` и пределы §7.2 — утверждаешь? В частности, 20 скриптов, 60 с на скрипт, 120 с на все.
2. `match`: брать `google-re2` (новая зависимость) или запускать `re` в отдельном процессе с таймаутом? Можно и
   обойтись без регулярных выражений: оставить `exit`, `contains`, `not_contains`.
3. Связывать ли провал скрипта с находками сети? Например, поле `after: ["l2", "addressing"]`: если в этих группах
   есть находки, провал скрипта считается их следствием и в оценку не идёт. Без этого одна ошибка VLAN даст и находку
   L2, и провал скрипта ping.
4. Выполнять скрипты по очереди (предсказуемо, но до 120 с) или параллельно по разным нодам (быстрее, но скрипты
   не смогут опираться друг на друга)?
5. Что из вывода скриптов показывать студенту по умолчанию?

### 7.7. Связи между скриптами

> **Решение владельца 2026-11-23** (по разбору проверок autochck: OKFKS7, OKFKS_5, GIT1, OKFKS6-demo). Контракт —
> `CONTRACTS.md` §2.9, «Связи между скриптами»; менеджер 0.36.0, возможность `check-script-needs`.

В autochck проверка была кодом на Python и брала вывод одной ноды в команду на другой: в OKFKS7 пути к файлам сайтов
берутся из ответов curl на R и проверяются на app1…app4; в GIT1 публичный ключ с ROUTER ищется в `authorized_keys` Git-узлов;
в OKFKS6-demo без nginx на узле все его пункты — 0. Скрипты §7.1 так не умели: каждый оценивался сам по себе, а подставлялся
только маркер. Добавлены два механизма:

- **`needs: ["id", …]`** — скрипт выполняется, только если названные (раньше в массиве) прошли. Иначе — `skipped` с причиной
  `needs_failed` и `blocked_by`: находки нет, ошибка уже засчитана у нужного скрипта. Так одна поломка не даёт несколько штрафов.
- **Значение прошлого скрипта.** Именованная группа RE2 `(?P<имя>…)` в `expect.match` даёт `{{id.имя}}` для следующих
  скриптов. В `run` значение подставляется в кавычках по оболочке ноды: что бы ни напечатал гость студента, это один аргумент,
  а не команда. В `contains` и `match` — как текст. Скрипт, чьё значение берётся, нужен и без `needs`.

Значение, которое берётся дальше, — до 256 байт и без управляющих символов, иначе выдавший его скрипт — `fail` (`mismatch`):
шаблон должен быть узким (`\S+`, а не `.*`). Если `run` берёт значение, менеджеру нужна оболочка ноды: у образа с `net_config`
она известна, у лабы каталога и Windows её нужно указать в `shell`.

Пример по OKFKS7 (часть: один сайт):

```json
"scripts": [
  {"id": "shop", "title": "shop.lab отвечает с R", "node": "R",
   "run": "curl -s -m 5 http://shop.lab/", "expect": {"exit": 0, "match": "^(?P<file>/\\S+)\\n/$"}},
  {"id": "shop-file", "title": "Файл shop.lab на app1", "node": "app1",
   "run": "test -f {{shop.file}} && cat -- {{shop.file}}", "expect": {"exit": 0, "contains": ["{{shop.file}}"]}},
  {"id": "shop-nginx", "title": "nginx на app1 принимает конфигурацию", "node": "app1",
   "run": "nginx -t", "needs": ["shop"]}
]
```

Если `shop` не прошёл (сайт не отвечает), два других не выполняются, и у студента одна находка «shop.lab отвечает с R: …».
`result.scripts[0].captures` — `{"file": "/var/www/shop/index.html"}`: преподаватель видит, какой путь взят.

Чего нет и не планируется: передачи всего вывода, условий «если — то» и циклов. Проверка, которой этого мало, —
повод для коллектора (§2.9 «Свежесть») или правила менеджера, а не языка в JSON.

### 7.8. Промпт для нейросети

> **Решение владельца 2026-11-23.** Скрипты в редакторе собирать руками долго; преподаватель описывает задачу нейросети, а
> форма нужна, чтобы ответ просмотреть и поправить. Плагин 0.46.0, `plugin/docs/autochecks.md` §11.

В редакторе лабы кнопка «Промпт для нейросети»: окно с полем «Что проверить», готовым промптом (формат `scripts`, приёмы
§7.3 и §7.7, устройства, линии и сегменты этой лабы, её скрипты) и полем для ответа, который заменяет скрипты лабы. Ключи и
вызовы нейросети на сервере не нужны; наружу уходит только то, что преподаватель сам скопировал, — схема лабы, без данных
студентов. Позже возможна кнопка «Сгенерировать» через подсистему ИИ Moodle.

**Промпт следует за форматом.** Текст — `plugin/plugin/prompts/checks.<язык>.md`. Первая строка файла — отпечаток формата
(`gns3lab-format`: поля `checks` и `scripts`, `expect`, оболочки, группы, классы, пределы), его строит
`checks.prompt_fingerprint()` менеджера. Тест `manager/tests/test_checks_prompt.py` падает, если формат изменился, а промпт
нет: меняя §2.9 контракта, поправь текст промпта во всех языках и строку отпечатка (тест печатает новую).

## 8. Каталог правил

Класс по умолчанию — для профилей `lenient` / `standard` / `strict`. «Без ожиданий» — работает ли правило без `checks`
(только по фактам и топологии); «типовая» — без `checks` работает в типовой проверке сети (§4.6). ОС: L — Linux, W — Windows, M — RouterOS, S — Linux-коммутатор, C — Cisco IOL.

### L1 (`l1`)

| Код | Что | ОС | Без ожиданий | Классы |
|---|---|---|---|---|
| `node_stopped` | нода задания (участник, шлюз, коммутатор на пути) остановлена | все | да | major / critical / critical |
| `config_not_saved` | у Cisco IOL нет сохранённой конфигурации (§3) | C | да | major / major / critical |
| `link_suspended` | линк на пути сегмента приостановлен (студент линки не приостанавливает: без ожиданий не проверяется) | все | нет | major / critical / critical |
| `port_shutdown` | порт на пути сегмента выключен (`admin: down`) | L W M C | да | major / major / critical |
| `link_down` | линк не поднят: `oper: down`, у пар Cisco–Cisco — `iol.l1` | L W M S C | да | minor / major / major |
| `unused_port_up` | неиспользуемый порт Cisco-коммутатора не выключен (`switches.unused_ports_shutdown`) | C | нет | note / minor / major |

### L2 (`l2`)

| Код | Что | ОС | Без ожиданий | Классы |
|---|---|---|---|---|
| `segments_merged` | два сегмента или группы в одном L2-домене | все | нет | major / critical / critical |
| `segment_split` | участники сегмента или группы в разных L2-доменах | все | нет | major / critical / critical |
| `member_isolated` | участник один в своём домене, хотя в домене есть коммутатор (в сети порта ISP не одинок: там ISP) | все | да | major / major / critical |
| `vlan_mismatch` | на концах линка разные native или access VLAN | S C | да | minor / major / major |
| `tag_not_allowed` | тег, который шлёт хост, маршрутизатор или коммутатор, не принимает другой конец. Лишний VLAN на транке к хосту или маршрутизатору — не ошибка линка (это `trunk_not_pruned`) | S C M L | да | minor / major / major |
| `vlan_wrong` | порт участника не в VLAN сегмента или группы (когда VLAN задан) | S C | нет | minor / major / major |
| `vlan_name_wrong` | VLAN назван не по группе (`switches.vlan_names`) | C | нет | note / minor / minor |
| `vlan_extra` | создан VLAN, которого нет в задании (кроме `mgmt_vlan`) | C | нет | note / minor / minor |
| `vlan_extra_used` | такой VLAN назначен порту узла | S C | нет | minor / major / major |
| `trunk_not_pruned` | на транке между коммутаторами разрешено больше нужного: нужны VLAN сегментов и групп, чей путь идёт через этот транк, и `mgmt_vlan` (`switches.trunk_prune`) | S C | нет | note / minor / major |
| `mgmt_vlan_missing` | нет VLAN `mgmt_vlan`, его SVI или адреса | C | нет | minor / major / major |

### Адреса (`addressing`)

| Код | Что | ОС | Без ожиданий | Классы |
|---|---|---|---|---|
| `address_missing` | у порта участника или шлюза нет нужного адреса; в типовой проверке — нет никакого адреса (§4.6) | L W M C | типовая | major / major / critical |
| `address_wrong` | адрес не по плану (`match: plan`) или не из подсети сегмента | L W M C | нет | major / major / critical |
| `mask_wrong` | маска не совпадает с подсетью сегмента; без сегмента — из `forbid_prefix` | L W M C | да | minor / major / critical |
| `address_misplaced` | нужный адрес стоит на другом интерфейсе | L W M C | нет | major / major / critical |
| `address_extra` | лишний адрес: второй на интерфейсе, на неподключённом интерфейсе, на L2-коммутаторе вне `mgmt_vlan` | L W M C | да | minor / major / major |
| `address_apipa` | адрес 169.254.0.0/16 (DHCP не ответил) | L W M | да | minor / major / major |
| `address_not_private` | адрес вне `allowed` (адрес из сети порта ISP, к которому интерфейс подключён, — не ошибка, см. ниже) | L W M C | да | minor / major / critical |
| `address_duplicate` | один адрес на двух интерфейсах | L W M C | да | major / critical / critical |
| `subnet_overlap` | пересекающиеся подсети | L W M C | да | major / major / critical |

| `config_not_applied` | в конфиге есть, в живых фактах нет (`persistence: saved`) | L | нет | minor / major / major |

### Шлюзы и маршрутизация (`gateways`, `routing`)

| Код | Что | ОС | Без ожиданий | Классы |
|---|---|---|---|---|
| `gateway_missing` | у хоста сегмента или группы со шлюзом нет маршрута по умолчанию; в типовой проверке — у хоста в домене с маршрутизатором (§4.6) | L W M | типовая | major / major / critical |
| `gateway_wrong` | шлюз не адрес шлюза сегмента или группы (без ожиданий — не адрес в лабе или не в подсети хоста; адрес порта ISP в его сети — свой) | L W M | да | major / critical / critical |
| `unreachable` | по таблицам маршрутов путь между сегментами не проходит: нет маршрута, петля, нет обратного маршрута (`reachability`); в типовой проверке — от хоста до ISP (§4.6) | L W M; C — после `ip route` в `ios.config` | типовая | major / critical / critical |
| `nat_missing` | путь хоста в интернет идёт через маршрутизатор, а NAT на нём не настроен: у IOL нет `ip nat outside` к ISP, `ip nat inside` к хостам или правила, транслирующего адрес хоста; у Linux и RouterOS нет маскарада (SNAT) на выходе к ISP для адреса хоста (§4.6) | L M C | типовая | major / critical / critical |

**Сеть ISP** (менеджер 0.21.3). Нода с образом, у которого есть `uplink_port` (`images/lab-uplink`), раздаёт на свой
порт N сеть `198.18.N.0/24`: DHCP `.100–.250`, шлюз и DNS — `198.18.N.1`. Фактов у ISP нет, поэтому проверки видят его сеть
так. Интерфейс, который кабелем (напрямую или через коммутаторы) достаёт до порта N, может иметь адрес из `198.18.N.0/24`
без `address_not_private`. Его шлюз `198.18.N.1` — не `gateway_wrong`, а сам он — не `member_isolated`. Тот же адрес
в любом другом месте или из сети другого порта ISP — по-прежнему `address_not_private`.

Порядок первопричин (§3): `node_stopped`, `config_not_saved`, `link_suspended`, `port_shutdown`, `link_down` → `vlan_*`, `tag_not_allowed` →
`segments_merged`, `segment_split`, `member_isolated` → `address_*`, `mask_wrong`, `subnet_*` → `gateway_*` → `unreachable`,
`nat_missing`. Шлюз «не из лабы» и пути в интернет объясняются ещё и находками маршрутизатора домена хоста (нет адреса,
не сохранена конфигурация).

## 11. Как сделано в менеджере 0.17.0 (этап 1)

- `lab_manager/netmodel.py` — модель сети по топологии сессии и снимку фактов: L1 (приостановка, остановленная нода,
  `shutdown`, нет несущей, `iol.l1`), L2-домены (те же правила, что `facts.js` плагина), адреса.
- `lab_manager/checks.py` — каталог правил (`RULES`, классы по профилям), проверка `gns3lab.checks/1`
  (`check_definition`), ожидания (`build_expected`: сегменты, группы `explicit` и `by_name`), правила (`evaluate`),
  первопричины (`CAUSES`: находка объясняется находкой из списка своего кода, если у них есть общий объект — порт, линк,
  нода, сегмент; `caused_by` указывает на корень цепочки) и оценка (`grade`, `normalize_grading`).
- Роли нод: категория образа у лабы из Moodle; у эталонной — по фактам (`switchport`, `mirror`) и имени (`R1`, `SW1`).
  🆕 (менеджер 0.29.1) Linux-хост (факт `ip_forward` или `net_config` образа Linux), у которого подключено больше одного порта
  и хотя бы один из них ведёт к ISP (напрямую или через коммутаторы), — маршрутизатор: пересылка у него обязательна, хосты
  его сети ходят через него. Узел с одним кабелем к ISP остаётся хостом.
  Ноды с `console_type: none` (ISP, Linux-коммутатор) — служебные: их адреса не проверяются.
- Путь сегмента или группы — порты участников, их соседи и коммутаторы между ними без тупиковых веток
  (как `segments.Fabric.tree`). Если у коммутатора пути нет фактов по причине системы, разрыв и слияние для этого
  набора не проверяются (`skipped`).
- Прогон ведёт лидер (`Orchestrator._check_step`): `queued` → просьба слоту собрать факты → ожидание свежих (до
  `CHECK_FACTS_WAIT`) → расчёт в потоке → `done`. Прогоны остановленных сессий и зависшие дольше `CHECK_TIMEOUT` —
  `failed` (`Store.fail_orphan_check_runs` в каждом такте).

## 12. Как сделано на этапе 3 (слот 0.17.0, менеджер 0.18.0)

Слот (`CONTRACTS.md` §4.6): `linux.sys/1` — `hostname`, `ip_forward`, `dns`; `linux.config/1` — `net_saved`
(`mechanism`, `ok`, `message`, `interfaces[]` с `method`, `ipv4`, `gateway`, `routes`; ifupdown читается самим ifupdown,
netplan/networkd/NetworkManager пока `supported: false`); `hostname` в `windows.net/1` и `routeros.sys/1`; `ios.config/1`
даёт `hostname` и `routes` (подключённые сети и `ip route`, у L2 — `ip default-gateway`).

Менеджер:
- `hostname_wrong` — имя узла без учёта регистра или FQDN, начинающийся с имени. У Cisco без строки `hostname` (слот
  0.17.0+) — «имя не задано». Служебные ноды и IOL без сохранённой конфигурации не проверяются.
- `forwarding_off` / `forwarding_on_host` — по `ip_forward` и роли ноды. Выключенная пересылка на Linux-маршрутизаторе
  по пути делает `unreachable` её следствием.
- `persistence` ноды: `checks.nodes.<имя>`, иначе `checks.persistence`, иначе по образу (`net_config` ifupdown,
  networkmanager, netplan, networkd — `saved`, иначе `runtime`); у эталонной лабы образ неизвестен — `runtime`, если
  гость сообщил `mechanism: "none"`, иначе `saved`. В `saved`: живой адрес или шлюз без записи в конфиге —
  `address_not_saved` (адреса интерфейса с `method: dhcp` не сверяются); адрес или шлюз конфига, которого нет вживую,
  и `net_saved.ok: false` — `config_not_applied`. `supported: false` — правило `skipped` (`unsupported_os`).
- Связность через Cisco считается по `routes` из `ios.config`.
