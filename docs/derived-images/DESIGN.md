# Разностные образы QEMU (черновик дизайна)

Статус: **реализовано в ветке `feature/derived-images`, ожидает стендовой приёмки**.
Результаты и ограничения — `REPORT.md`. Правки форматов помечены 🆕 в `manager/docs/CONTRACTS.md`
(§2.2, §2.3, §2.5, §2.8, §5, §7) и в `manager/docs/AGENT_REQUESTS.md` (§6).

## 1. Зачем

Преподаватель собирает лабу в редакторе, запускает её, донастраивает QEMU-ноды (пакеты, сервисы, конфиги) и нажимает
«Сохранить». Лаба сохраняется уже с изменёнными образами: вместо `debian12` у ноды стоит производный образ — тонкий
слой qcow2 поверх базы (мегабайты, а не гигабайты). Студенты получают преднастроенные ноды. Аналог — «разностные
образы» PNETLab.

Только `kind: "qemu"`. У IOL и VPCS диска нет; преднастройка IOL уже решается `nvram_config` (CONTRACTS §4.2).

Отдельных черновиков образов нет (решение владельца): единица работы — сама лаба. Черновики можно добавить позже.

## 2. На что опираемся

- GNS3 запускает QEMU-ноду как linked clone: в каталоге проекта создаётся `project-files/qemu/<node_id>/hda_disk.qcow2`
  с backing file — образом из `/opt/gns3/images/QEMU/` (`slot/README.md`, Node Wipe). Всё, что сделал преподаватель, —
  уже в этом файле. **Снять слой = забрать этот файл**, ничего пересобирать не нужно.
- Проект лежит в каталоге пользователя на RW CephFS (`gns3-rw/students/<student_key>`), образы — в `IMAGES_DIR`,
  который агент монтирует во все слоты **только на чтение** (`install/README.md`, «Образы GNS3 на CephFS»).
- После остановки сессии CT слота выключен, каталог пользователя ни к одному CT не подключён (менеджер это уже
  отслеживает: `STUDENT_DIR_BUSY`). Файл гарантированно не меняется — его можно снимать без заморозки ФС гостя
  и без новых операций в слоте.
- Определение лабы хранит плагин (`gns3lab.lab/1|2`, CONTRACTS §2.6); менеджер его только проверяет и запускает.
  Поэтому заменить образы в лабе после сохранения должен плагин — менеджер отдаёт ему соответствие «нода → образ».
- Редактор работает с **библиотекой лаб сайта** (`gns3lab_labs`, `gns3lab_lab_versions`: у лабы один изменяемый
  черновик версии и замороженные опубликованные версии; право `mod/gns3lab:managelabs`, контекст системы).
  Образы меняются в **черновике версии**; опубликованные версии и активности на них не трогаются, пока автор не
  опубликует новую версию.

## 3. Как это видит преподаватель

1. Редактор лабы: накидал ноды, соединил, «Запустить» — **авторский запуск** лабы (§6). Консоли те же, что у студента.
2. Донастроил одну или несколько QEMU-нод. Запуск можно остановить и продолжить позже, пока лаба не менялась.
3. «Сохранить с образами»: окно со списком QEMU-нод, которые запускались (галочки, по умолчанию отмечены все,
   кроме образов с `capture: false` — узел «Интернет», Linux-коммутатор). У каждой — название и описание образа;
   по умолчанию «<лаба> — <нода>» и пустое описание, преподаватель может дописать.
4. Менеджер останавливает запуск, агент снимает слои, плагин заменяет образы нод в черновике версии лабы.
   Студенты получат новые образы, когда автор опубликует эту версию.
5. Можно повторить: снова запустить, донастроить, сохранить. Слой каждый раз пересаживается на исходную базу (§5.2),
   цепочка не растёт.

Просто «Сохранить» без образов — как сейчас: меняется только топология.

## 4. Компоненты и поток

```
плагин ──POST /sessions {lab, options.mode: "authoring"}──▶ менеджер ──deploy (обычный)──▶ слот
плагин ──POST /sessions/{id}/capture {nodes}──▶ менеджер:
            1. останавливает сессию (как обычно: lab_stop … ct_stop)
            2. ──POST /images/capture (по каждой ноде)──▶ агент узла (CephFS: каталог автора → IMAGES_DIR/QEMU)
            3. записывает образы в БД; GET /images начинает их отдавать
плагин ──GET /sessions/{id}/capture──▶ {"images": {"R1": "d-…"}} → заменяет image у нод и сохраняет лабу
```

| Компонент | Что меняется |
|---|---|
| плагин | «Запустить» в редакторе (авторский запуск), окно «Сохранить с образами», замена образов в определении, палитра с производными образами |
| менеджер | `options.mode: "authoring"`, маршрут снятия, производные образы в БД (миграция), каталог = `IMAGES_FILE` ∪ БД без перезапуска, вызов агента |
| агент | `POST /images/capture` (AGENT_REQUESTS §6): проверка, копирование, пересадка на базу, `check`, хеши, атомарная публикация |
| слот | **ничего**: производный образ для него — просто ещё один файл в `/opt/gns3/images/QEMU` |
| install | проверка цепочек в каталоге образов, правило «образ на месте не заменяется» в README |

## 5. Решения

### 5.1. Файл слоя и backing file

- Имя: `IMAGES_DIR/QEMU/d-<12 hex>.qcow2`, рядом с базой, без подкаталогов. `id` образа в каталоге совпадает с именем
  без расширения; его выбирает менеджер.
- backing file — **относительное** имя базы (`debian12.qcow2`). Относительный путь qemu считает от каталога слоя, поэтому
  он одинаково работает и в слоте (`/opt/gns3/images/QEMU`), и на узле Proxmox (`/mnt/pve/cfs/<IMAGES_DIR>/QEMU`).
  Абсолютный путь из linked clone (`/opt/gns3/images/QEMU/…`) на узле не разрешается — агент его переписывает.
- Файл и `<имя>.md5sum` (его GNS3 хочет писать рядом, а каталог RO) агент создаёт сам, права `0444`.

### 5.2. Всегда один слой над базой

- **База** — образ из `IMAGES_FILE` (администраторский, не производный). У производного образа всегда ровно один
  backing — база.
- Если нода уже стояла на производном образе (повторное сохранение лабы или чужой образ), агент пересаживает новый
  слой на базу безопасным `qemu-img rebase -b <база>` (без `-u`): qemu переносит в слой отличия промежуточного образа.
  Глубина цепочки всегда 1 (плюс overlay ноды в проекте), ограничения глубины и `flatten` не нужны. Плата — слой
  повторного сохранения содержит все изменения от базы, а не только последние.
- Слой привязан к базе по `sha256`: агент сверяет хеш базы с ожидаемым и записывает его в ответ; менеджер хранит
  `base_sha256`, проверка каталога сверяет его с файлом.
- **Файлы образов неизменяемы.** Замена базы на месте ломает все слои над ней и — уже сегодня — все проекты студентов,
  у которых диски нод лежат поверх этой базы. Новая версия базы — новое имя файла и новый `id`. Правило вносится
  в `install/README.md`.

### 5.3. Версии и удаление

- `id` и файл неизменяемы. Повторное сохранение даёт **новый** образ с `supersedes` — `id` прежнего образа той же ноды
  этой лабы. Палитра показывает только последние; заменённые видны в истории образа.
- Лаба ссылается на конкретный `id`: сохранение меняет определение лабы, значит и `lab_def`. Студенты, начавшие лабу
  раньше, продолжают на старом манифесте и старых образах (как при любой правке лабы); новые запуски — на новых.
- Удаления файла нет. `retired` — образа нет в палитре, но лабы и проекты с ним работают. Физически удалить слой можно,
  только когда на него не ссылается ни одна лаба и ни один проект; это отдельная админ-команда позже.

### 5.4. Видимость

Образы принадлежат **автору**, а не курсу, и не засоряют палитру.

- Палитра редактора: базовые образы каталога и **«Мои образы»** — раскрыты. Ниже свёрнутый раздел
  **«Образы других преподавателей»**: группы по автору, у каждого образа название, база, лаба-источник и описание,
  поиск по названию и описанию. Так снятую ноду можно поставить и в другую лабу.
- Образ другого преподавателя можно поставить в свою лабу как есть; донастроить и сохранить — получится свой образ
  над той же базой (§5.2).
- **Рекомендованные** (`featured`) — образы, которые администратор Moodle (capability `mod/gns3lab:manageimages`,
  контекст системы) поднял в основную палитру для всех. Необязательный шаг, а не условие видимости.
- Студенты палитру не видят; в лабе образ показывается как обычно.
- Менеджер Moodle-права не проверяет: он отдаёт `author_user_id` и `featured`, группирует и фильтрует плагин
  (доверенный клиент по секрету сайта, как сейчас). Имя автора плагин берёт из Moodle по `user_id`.
- Производный образ разрешён сайту (`limits.images`), только если разрешена его база.
- Свойства (`ram_mb`, `cpus`, `adapters`, `console_type`, `net_config`/`preconfig`, `slot`, `symbol`) наследуются от базы.

### 5.5. Подготовка гостя перед сохранением

Клон гостя несёт уникальное: `/etc/machine-id`, SSH host keys, DUID DHCP, историю shell. В первой версии — подсказка
в окне «Сохранить с образами». Позже — шаг `seal`: менеджер перед остановкой просит слот выполнить через QGA
сценарий очистки из каталога (поле образа `seal`); это новый маршрут слота и отдельное согласование.

### 5.6. Лимиты

`IMAGE_MAX_BYTES` — размер одного слоя (по умолчанию 8 ГиБ; агент проверяет до копирования), не больше
`IMAGE_CAPTURE_MAX_NODES` нод за одно сохранение (по умолчанию 10). Общая квота на автора или сайт — позже.

## 6. Авторский запуск

- Обычная сессия менеджера по определению из плагина (`lab`) с `options.mode: "authoring"`; в объекте сессии
  `mode: "authoring"`. Плагин показывает её тем же UI. Не попытка: не оценивается, не видна в отчётах курса.
- Право в Moodle — то же, что у редактора: `mod/gns3lab:managelabs` (контекст системы). Отдельное право на запуск
  не вводим: кто правит лабу библиотеки, тот и запускает её. Проверяет плагин.
- `student_key` авторского запуска выводится из сайта, пользователя, `id` лабы библиотеки (`library_lab_id`) и признака `authoring`: у каждой лабы
  свой проект преподавателя, отдельный от его собственных лаб как студента (правило «одна живая лаба» действует внутри
  ключа). Слот при этом один, как у студента.
- Продолжение: пока `lab_def` не изменился, следующий авторский запуск продолжает тот же проект. Изменилось
  определение (в том числе после «Сохранить с образами») — менеджер начинает **новый проект**, прежний удаляет.
  Это то же пересоздание, что нужно будущему `options.reset` (CONTRACTS §7); для авторского запуска оно включено всегда.
- Длительность — `AUTHORING_MAX_DURATION` менеджера (по умолчанию 240 мин), `options.max_duration` действует в его пределах.

## 7. Что проверить на стенде (делает владелец)

1. GNS3 2.2.61 принимает как образ QEMU файл, у которого **есть backing file** (относительный), и делает над ним
   linked clone; нода стартует, `qemu-img info --backing-chain` в слоте показывает три уровня. Если GNS3 такой образ
   отвергает — запасной вариант: агент делает `qemu-img convert` в самостоятельный файл (выигрыша в размере нет,
   остальное работает).
2. GNS3 не пытается писать рядом с образом ничего, кроме `.md5sum` (каталог RO).
3. Продолжение проекта студента, созданного на производном образе, в другом слоте.
4. Время копирования, `rebase` (в том числе безопасного, с пересадкой) и sha256 слоя 1–5 ГиБ на CephFS укладывается
   в тайм-аут агента.

## 8. Порядок работ

1. Агент: `POST /images/capture` + тесты (подделка `qemu-img`).
2. Менеджер: миграция, `mode: authoring` и пересоздание авторского проекта, маршрут снятия, каталог из БД,
   `image_capture` в `info`.
3. Плагин: «Запустить» в редакторе, окно «Сохранить с образами», замена образов в определении, палитра.
4. install: проверка цепочек, README.
5. Позже: `seal` через QGA (слот), физическое удаление неиспользуемых слоёв, черновики образов.

## 9. Решения владельца

1. Точка входа — редактор лабы. Отдельных черновиков образов нет: преподаватель запускает саму лабу и сохраняет её
   с образами.
2. Видимость — по автору: свои раскрыты, чужие под спойлером с описанием; администратор может сделать образ
   рекомендованным (§5.4).
3. Слой снимается **только из авторского запуска**. Опубликованные лабы и проекты студентов не трогаем.
4. Хранение — каталог образов остаётся RO во всех слотах, пишет агент (§10).

## 10. Где хранить слой: варианты

Слой **уже лежит на RW-хранилище** — в каталоге авторского проекта (`mp1`, `/opt/gns3/projects` слота). Вопрос только
в том, кто переносит его оттуда в общий каталог образов и делает неизменяемым.

| Вариант | Плюсы | Минусы |
|---|---|---|
| **А. Пишет агент узла** (выбран) | каталог образов RO везде; переносит и проверяет доверенный компонент, у которого CephFS уже есть; слот не меняется | новый маршрут агента |
| Б. RW-точка монтирования образов в слоте | нет маршрута агента | любой слот (в т. ч. со студентом) может испортить базу, на которой стоят все проекты; слою нельзя доверять — его же и проверяет слот; пропадает неизменяемость |
| В. Отдельная RW-точка «приёмник» только у авторских запусков, публикует агент | ничего | то же, что А, плюс третья точка монтирования и логика «какой CT авторский»: `mp1` авторского проекта уже и есть такой приёмник |
| Г. Пишет менеджер (свой RW-доступ к CephFS) | без агента | менеджеру даётся запись в общий каталог образов, которой у него сейчас нет; ломает разделение «Proxmox и CephFS — только через агента» |

Внутри варианта А можно положить производные образы не в `IMAGES_DIR/QEMU`, а в отдельное дерево
(`gns3-rw/derived/`), смонтированное в слоты отдельной RO-точкой. Плюс — образы администратора и преподавателей не
смешиваются, проще считать квоту. Минус — GNS3 ищет образы в одном каталоге, понадобится вложенная точка
монтирования и ссылки на базу вида `../base.qcow2`; это лишняя проверка на стенде. В первой версии — общий
`QEMU/` с префиксом `d-`, отдельное дерево — если квоты станут нужны.
