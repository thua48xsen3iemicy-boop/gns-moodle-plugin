# Разностные образы QEMU (черновик дизайна)

Статус: **предложение для согласования**, кода нет. Правки форматов помечены 🆕 в `manager/docs/CONTRACTS.md`
(§2.8, §5, §7) и в `manager/docs/AGENT_REQUESTS.md` (§6).

## 1. Зачем

Преподаватель берёт образ из каталога (например `debian12`), запускает его, донастраивает (пакеты, сервисы, конфиги)
и публикует результат как новый образ каталога. Опубликованный образ — тонкий слой qcow2 поверх базового
(мегабайты, а не гигабайты), его можно ставить в лабы, как любой другой образ. Аналог — «разностные образы» PNETLab.

Только `kind: "qemu"`. У IOL и VPCS диска нет; преднастройка IOL уже решается `nvram_config` (CONTRACTS §4.2).

## 2. На что опираемся

- GNS3 запускает QEMU-ноду как linked clone: в каталоге проекта создаётся `project-files/qemu/<node_id>/hda_disk.qcow2`
  с backing file — образом из `/opt/gns3/images/QEMU/` (`slot/README.md`, Node Wipe). Всё, что сделал пользователь, —
  уже в этом файле. **Снять слой = забрать этот файл**, ничего пересобирать не нужно.
- Проект лежит в каталоге пользователя на RW CephFS (`gns3-rw/students/<student_key>`), образы — в `IMAGES_DIR`,
  который агент монтирует во все слоты **только на чтение** (`install/README.md`, «Образы GNS3 на CephFS»).
  Значит, писать в каталог образов может только агент узла (или администратор), а не слот.
- После остановки сессии CT слота выключен, каталог пользователя ни к одному CT не подключён (менеджер это уже
  отслеживает: `STUDENT_DIR_BUSY`). В этот момент файл гарантированно не меняется — его можно снимать без
  заморозки ФС гостя и без новых операций в слоте.

## 3. Как это видит преподаватель

1. В редакторе лабы (решено: точка входа — только редактор), в палитре образов: «Новый образ на основе…» → выбрать базовый образ, название,
   галочку «нужен интернет» (узел `lab-uplink`, если у сайта есть слоты с `uplink`).
2. Плагин создаёт **черновик образа** в менеджере и запускает **авторскую сессию**: служебная лаба из одной ноды
   `SRC` (базовый образ) и, при необходимости, узла «Интернет». Консоль та же, что у студента (telnet или noVNC).
3. Преподаватель настраивает систему. Сессию можно остановить и продолжить позже: черновик — обычный продолжаемый
   проект, как у студента.
4. «Опубликовать»: преподаватель задаёт id, название и описание образа. Менеджер останавливает сессию, агент снимает слой,
   образ появляется в `GET /api/v1/images` с пометкой «производный от debian12».
5. Новая версия: продолжить тот же черновик, донастроить, опубликовать снова. Получится **новый образ** (`web-srv-v2`),
   а не замена старого (§5.3). Глубина цепочки при этом остаётся 1: черновик всегда лежит прямо на базе.

Авторская сессия — не попытка студента: не оценивается, не видна в отчётах преподавателя курса, не занимает
«одну живую лабу» студента (у автора может параллельно идти своя лаба в курсе — это решается отдельным ключом
`student_key`, §6). Право в Moodle — новая capability `mod/gns3lab:authorimages` (контекст курса), по умолчанию
у `editingteacher` и `manager`.

## 4. Компоненты и поток

```
плагин ──POST /image-drafts──▶ менеджер ──deploy (обычный)──▶ слот   (авторская сессия)
плагин ──POST /image-drafts/{id}/publish──▶ менеджер:
            1. останавливает сессию (как обычно: lab_stop … ct_stop)
            2. ──POST /images/capture──▶ агент узла (CephFS: каталог автора → IMAGES_DIR/QEMU)
            3. записывает образ в БД; GET /images начинает его отдавать
```

| Компонент | Что меняется |
|---|---|
| плагин | палитра «Новый образ…», страница черновиков, capability, отображение производных образов и их версий |
| менеджер | черновики и производные образы в БД (миграция), маршруты §2.8, каталог = `IMAGES_FILE` ∪ БД без перезапуска, вызов агента |
| агент | `POST /images/capture` (AGENT_REQUESTS §6): проверка цепочки, копирование, `rebase -u`, `check`, хеши, атомарная публикация |
| слот | **ничего** в первой версии: производный образ для него — просто ещё один файл в `/opt/gns3/images/QEMU` |
| install | проверка цепочек в каталоге образов (`lab-provision check` или отдельная команда), правило «образ на месте не заменяется» в README |

## 5. Решения

### 5.1. Файл слоя и backing file

- Имя: `IMAGES_DIR/QEMU/d-<image_id>.qcow2`, рядом с базой, без подкаталогов (поддержку подкаталогов в имени образа
  GNS3 2.2.61 надо отдельно подтверждать — не опираемся).
- backing file перезаписывается **относительным** именем базы (`qemu-img rebase -u -F qcow2 -b debian12.qcow2`).
  Относительный путь qemu считает от каталога слоя, поэтому одинаково работает и в слоте (`/opt/gns3/images/QEMU`),
  и на узле Proxmox (`/mnt/pve/cfs/<IMAGES_DIR>/QEMU`), где агент проверяет файл. Абсолютный путь из linked clone
  (`/opt/gns3/images/QEMU/debian12.qcow2`) на узле не разрешается.
- Файл и `<имя>.md5sum` (его GNS3 хочет писать рядом, а каталог RO) агент создаёт сам, права `0444`.

### 5.2. Целостность цепочки

- Слой привязан к базе по `sha256`: агент сверяет хеш базы с ожидаемым (менеджер передаёт его из каталога/БД) и
  записывает в ответ. Менеджер хранит `base_sha256`; проверка каталога сверяет его с файлом.
- **Файлы образов неизменяемы.** Замена базы на месте ломает все слои над ней и — уже сегодня — все проекты студентов,
  у которых диски нод лежат поверх этой базы. Новая версия базы — новое имя файла и новый `id`. Это правило вносится
  в `install/README.md`.
- Глубина цепочки (без учёта overlay ноды) — не больше `IMAGE_MAX_DEPTH` (по умолчанию 2: база → слой → слой).
  Глубже — публикация с `flatten: true`: агент делает `qemu-img convert` всей цепочки в самостоятельный файл
  (тяжёлый, зато без зависимостей).

### 5.3. Версии и удаление

- `id` образа и его файл неизменяемы. Версии — отдельные образы с общим `family` (`web-srv`, `web-srv-v2`):
  лаба ссылается на конкретный `id`, поэтому манифест и `lab_revision` существующих лаб не меняются, продолжение
  проектов студентов не ломается (сравнение `manifest`, §4.2).
- Удаления файла нет. `DELETE /images/{id}` — **вывод из оборота** (`retired`): образа нет в палитре для новых
  нод, но лабы и проекты с ним продолжают работать. Диски нод студентов лежат поверх слоя, поэтому физически
  удалить файл можно только когда на него не ссылается ни один проект; это отдельная админ-команда позже.

### 5.4. Видимость

Решено с владельцем: образы принадлежат **автору**, а не курсу, и не засоряют палитру.

- Палитра редактора: базовые образы каталога и **«Мои образы»** — раскрыты. Ниже свёрнутый раздел
  **«Образы других преподавателей»**: группы по автору, у каждого образа название, база и **описание**
  (что установлено и настроено — обязательное поле при публикации), поиск по названию и описанию.
- Образ другого преподавателя можно поставить в свою лабу как есть; донастроить — только через свой черновик
  на его основе (это слой над его слоем, глубина 2).
- **Рекомендованные** (`featured`) — образы, которые администратор Moodle (capability `mod/gns3lab:manageimages`,
  контекст системы) поднял в основную палитру для всех. Это необязательный шаг, а не условие видимости.
- Студенты палитру не видят; в лабе образ показывается как обычно.
- Менеджер Moodle-права не проверяет: он отдаёт `author_user_id` и `featured`, группирует и фильтрует плагин
  (плагин — доверенный клиент по секрету сайта, как сейчас). Имя автора плагин берёт из Moodle по `user_id`.
- Производный образ разрешён сайту (`limits.images`), только если разрешена его база.
- Свойства (`ram_mb`, `cpus`, `adapters`, `console_type`, `net_config`/`preconfig`, `slot`) наследуются от базы;
  при публикации можно сузить `ram_mb.default` и т. п. в пределах базы, но не расширить `kind`/`console_type`.

### 5.5. Подготовка гостя перед публикацией

Клон гостя несёт уникальное: `/etc/machine-id`, SSH host keys, DUID DHCP, историю shell. В первой версии — подсказка
в интерфейсе (чек-лист перед «Опубликовать»). Во второй — шаг `seal`: менеджер перед остановкой просит слот выполнить
через QGA сценарий очистки из каталога (поле образа `seal`), это новый маршрут слота и отдельное согласование.

### 5.6. Лимиты

`IMAGE_DRAFTS_PER_USER` (по умолчанию 3), `IMAGE_MAX_BYTES` размер слоя (по умолчанию 8 ГиБ; агент проверяет
до копирования), общий размер производных образов на сайт — позже. Авторская сессия получает свой
`max_duration` (`IMAGE_DRAFT_MAX_DURATION`, по умолчанию 240 мин).

## 6. Авторская сессия

- Это обычная сессия менеджера с полем `kind: "authoring"` и `draft_id`. Плагин показывает её тем же UI.
- `student_key` черновика выводится из сайта, пользователя **и** `draft_id`, поэтому проект черновика лежит в
  отдельном каталоге и не конфликтует с лабами автора как студента (правило «одна живая лаба» действует внутри ключа).
  Слот одновременно один, как у студента.
- Служебная лаба строится менеджером: нода `SRC` (`image` = база, ресурсы — `default` базы), опционально `Internet`
  (`lab-uplink`, `uplink_port`) и линк между ними. Сегментов и `preconfig` нет: гость настраивается вручную.
- `options` и `lab`/`lab_ref` плагин не передаёт — лабу задаёт черновик.

## 7. Что проверить на стенде (делает владелец)

1. GNS3 2.2.61 принимает как образ QEMU файл, у которого **есть backing file** (относительный), и делает над ним
   linked clone; нода стартует, `qemu-img info --backing-chain` в слоте показывает три уровня. Если GNS3 такой образ
   отвергает — запасной вариант: всегда `flatten: true` (выигрыша в размере нет, остальное работает).
2. GNS3 не пытается писать рядом с образом ничего, кроме `.md5sum` (каталог RO).
3. Продолжение проекта студента, созданного на производном образе, в другом слоте.
4. Время `rebase -u`/`check`/sha256 слоя 1–5 ГиБ на CephFS укладывается в тайм-аут агента.

## 8. Порядок работ

1. Агент: `POST /images/capture` + тесты (подделка `qemu-img`).
2. Менеджер: миграция, черновики, авторская сессия, публикация, каталог из БД, `image_authoring` в `info`.
3. Плагин: capability, палитра «Новый образ…», черновики, производные образы в палитре.
4. install: проверка цепочек, README.
5. Позже: `seal` через QGA (слот), физическое удаление неиспользуемых слоёв.

## 9. Решения владельца и открытые вопросы

Решено:
1. Точка входа — редактор лабы.
2. Видимость — по автору: свои раскрыты, чужие под спойлером с описанием; администратор может сделать образ
   рекомендованным (§5.4).
3. Слой снимается **только из черновика**. Опубликованные лабы и проекты студентов не трогаем.
4. Хранение — каталог образов остаётся RO во всех слотах, пишет агент (§10).

Открыто:
1. Хранить ли черновик после публикации (для версий) бессрочно или удалять через N дней неактивности?

## 10. Где хранить слой: варианты

Слой **уже лежит на RW-хранилище** — в каталоге черновика (`mp1`, `/opt/gns3/projects` слота). Вопрос только в
том, кто переносит его оттуда в общий каталог образов и делает неизменяемым.

| Вариант | Плюсы | Минусы |
|---|---|---|
| **А. Пишет агент узла** (выбран) | каталог образов RO везде; переносит и проверяет доверенный компонент, у которого CephFS уже есть; слот не меняется | новый маршрут агента |
| Б. RW-точка монтирования образов в слоте | нет маршрута агента | любой слот (в т. ч. со студентом) может испортить базу, на которой стоят все проекты; слою нельзя доверять — его же и проверяет слот; пропадает неизменяемость |
| В. Отдельная RW-точка «приёмник» только у авторских сессий, публикует агент | ничего | то же, что А, плюс третья точка монтирования и логика «какой CT авторский»: `mp1` черновика уже и есть такой приёмник |
| Г. Пишет менеджер (свой RW-доступ к CephFS) | без агента | менеджеру даётся запись в общий каталог образов, которой у него сейчас нет; ломает разделение «Proxmox и CephFS — только через агента» |

Внутри варианта А можно положить производные образы не в `IMAGES_DIR/QEMU`, а в отдельное дерево
(`gns3-rw/derived/`), смонтированное в слоты отдельной RO-точкой. Плюс — образы администратора и преподавателей не
смешиваются, проще считать квоту. Минус — GNS3 ищет образы в одном каталоге, понадобится вложенная точка
монтирования и ссылки на базу вида `../base.qcow2`; это лишняя проверка на стенде. В первой версии — общий
`QEMU/` с префиксом `d-`, отдельное дерево — если квоты станут нужны.
