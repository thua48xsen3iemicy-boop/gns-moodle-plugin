# TASK-3 — выключенный изнутри узел снова роняет лабу студента

Доработка PR #82, ветка `feature/derived-images`, отдельными коммитами по компонентам. Правила — `../../AGENTS.md`;
контекст — `TASK-2.md` и `REPORT.md` этой папки.

## Проблема

В TASK-2 фоновая проверка слота (`Lifecycle.watch`, `slot/api/lifecycle.py`) стала пропускать **любую** остановленную
QEMU-ноду («A guest may power itself off»). Это изменило поведение всех лаб: раньше выключенный изнутри узел переводил
лабу в `FAILED`, теперь лаба живёт дальше. Студенты этим пользуются — выключают узел, чтобы по пропавшему линку понять,
к какому порту он подключён, вместо того чтобы смотреть таблицу коммутации.

## Решение (не пересматривать без владельца)

Слот терпит остановленную QEMU-ноду **только если выключил её сам** маршрутом
`POST /v1/labs/{project_id}/nodes/{node_id}/shutdown` и операция завершилась `SUCCEEDED`. Любая другая остановленная
нода — как было до TASK-2: `RuntimeError("Required node stopped or missing")`, лаба `FAILED`. Признака режима
(студент/автор) в билете нет и не появляется.

Следствие для автора: ручной `poweroff` в авторском запуске тоже роняет лабу. Гостя без QGA автор сохраняет
«как есть» (`force: true`), это уже реализовано.

## Задача А — слот (`slot/`)

1. В записи лабы — множество `node_id`, выключенных операцией `shutdown` с исходом `SUCCEEDED` (например
   `lab["shutdown_nodes"]`). Пишется под той же блокировкой/`generation`, что и остальные изменения лабы; переживает
   перезапуск службы слота (лежит в SQLite вместе с лабой).
2. `watch`: остановленная QEMU-нода допустима, только если её `node_id` в этом множестве; иначе — `FAILED`, как на `main`.
   Пропуск provisioning для таких нод — как сейчас. Пропуск всей лабы, пока по ней идёт `shutdown` в статусе `RUNNING`, —
   оставить: GNS3 может показать `stopped` раньше, чем операция запишет исход.
3. Множество очищается, когда лаба снова разворачивается или продолжается (`DEPLOYING`) и при `STOPPED`; нода из
   множества, которая снова `started`, из него убирается.
4. Неуспешная операция `shutdown` (`GUEST_AGENT_UNAVAILABLE`, `GUEST_SHUTDOWN_TIMEOUT`) ноду в множество не добавляет:
   если гость всё же выключился позже сам, лаба падает — это правильное поведение (менеджер увидит `SLOT_LAB_FAILED`).
5. `slot/README.md`: заменить абзац «A powered-off QEMU guest remains part of a READY lab…» на новое правило.
6. Тесты (`slot/tests/test_shutdown.py`, `test_reliability.py` или рядом):
   - QEMU-нода остановилась без операции → лаба `FAILED` (то же поведение, что на `main`);
   - нода выключена операцией `shutdown` → лаба остаётся `READY`, provisioning её пропускает;
   - операция `shutdown` завершилась ошибкой, нода потом остановилась → `FAILED`;
   - множество переживает перезапуск `Lifecycle` и очищается при новом развёртывании/продолжении;
   - пока операция `RUNNING`, `watch` лабу не трогает (уже есть — не сломать).
7. Версия `slot/release.json`; `compatibility.components` в `install/lab-release-build.json.example`, если меняется
   версия; `install/tests` (`test_allowlist_matches_delivered_trees`).

## Что проверит владелец на стенде

1. Студенческая лаба: `poweroff` в госте QEMU → в пределах `SLOT_MONITOR_INTERVAL` лаба `FAILED`, студент видит
   сбой; «Запустить» снова продолжает проект, узел снова работает.
2. Авторский запуск, гость с QGA: «Сохранить с образами» → гость выключается штатно, лаба не падает до остановки,
   образ снят без пометки «как есть».
3. Авторский запуск, ручной `poweroff` в госте → лаба падает (ожидаемо); гость без QGA сохраняется только «как есть».
