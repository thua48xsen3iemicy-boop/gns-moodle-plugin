# Кастомный преднастрой лабы

Проект, а не контракт. Новые поля, коды и маршруты вносятся в `manager/docs/CONTRACTS.md` вместе с кодом (правило
`AGENTS.md`). Задача на стыке менеджера, плагина и (на этапе 2) слота.

Статус: черновик 2026-11-28, ждёт решения владельца по §11. Всё ниже — 🆕.

Связанные документы: конструктор лаб `docs/lab-constructor/README.md` (сегменты, правила жизненного цикла §7, поломки §9),
проверки в активности `docs/activity-checks/README.md`, скрипты проверок `docs/autochecks/README.md` §7, слот
`slot/README.md` («Жизненный цикл и гарантии», «Преднастройка»), контракт `CONTRACTS.md` §2.6, §4.2.

## 1. Зачем и решения владельца (2026-11-28)

Сегменты конструктора описывают намерение (домен, VLAN, подсеть, шлюз), а настройку строит компилятор. Многое так не
описать: поднять веб-сервер на SRV1, завести пользователей, положить ключи, настроить OSPF на части маршрутизаторов,
сломать что-то для лабы на поиск неисправностей. Нужен преднастрой, который пишет преподаватель — и, скорее всего,
нейросеть по его описанию.

Решено владельцем:

1. **Преднастрой — часть лабы.** Он определяет, что выдано студенту, и потому — что это за лаба и как она называется. Он
   входит в определение и в `lab_def`: правка преднастроя — новая версия лабы, как правка топологии. Отлаживается в
   редакторе лаб, в авторском запуске.
2. **Проверки — в активности** (`docs/activity-checks/README.md`): одна лаба с преднастроем служит разным задачам.
3. **Пишется в основном нейросетью.** Преподаватель описывает задачу словами, отдаёт промпт нейросети и вставляет ответ.
   Основной путь интерфейса — промпт, ответ, проверка, авторский запуск (§6a); ручные поля — для мелкой правки.

## 2. Что уже есть

Слот умеет всё нужное для QEMU, IOL и VPCS; не хватает только того, чтобы это описывал преподаватель.

- **`NodeSpec.provisioning`** — список `{command, timeout_seconds}` (до 8192 символов, 1…120 с). Слот выполняет команды
  **один раз, при создании проекта**: QEMU — через гостевой агент (`/bin/sh -c`, у RouterOS — скрипт RouterOS), IOL — строками
  CLI по консоли (`iol-cli`). Продолжение проекта их не повторяет; прерванная первая подготовка не повторяется и не
  пропускается (`PROVISIONING_UNKNOWN`). Ненулевой код выхода — лаба `FAILED`, в тексте ошибки — нода и последняя строка
  `stderr` (`slot/README.md`).
- **`NodeSpec.nvram_config`** (IOL) — `startup-config`, который слот кладёт в NVRAM до первого старта ноды, один раз.
- **`NodeSpec.startup_script`** (VPCS) — строки, которые VPCS выполняет при старте.
- **Порядок у ноды сейчас**: команды образа из каталога → случайные имена интерфейсов → скрипт сети сегментов.
  Ноды готовятся **по очереди**, после того как запущены все (`slot/api/lifecycle.py`, `run`).
- **Правило конструктора** §7.4: ошибка преднастройки — лаба `FAILED`, студент не начинает работу на недонастроенной лабе.
  Сейчас такая лаба получает `SLOT_OPERATION_FAILED` с `retryable: true`: студент видит «попробуйте ещё раз», хотя повтор даст
  тот же сбой.

## 3. Модель

Преднастрой — список **шагов**. Шаг относится к одной ноде и выполняется после встроенного преднастроя этой ноды
(команды образа, имена интерфейсов, сегменты). Так шаг может опираться на адреса сегментов — или намеренно их сломать.

| Нода | Чем задаётся шаг | Во что превращает менеджер |
|---|---|---|
| QEMU с гостевым агентом (Linux, RouterOS; Windows — этап 2) | `run` — скрипт оболочки гостя | `ProvisionCommand` в `NodeSpec.provisioning` |
| IOL (коммутатор, маршрутизатор) | `config` — строки `startup-config` | дописывается в `NodeSpec.nvram_config` после конфигурации сегментов |
| VPCS | `config` — команды VPCS | дописывается в `NodeSpec.startup_script` после строки адреса сегмента |
| QEMU без агента (`qga: false`), узел «Интернет», коммутаторы GNS3 | — | `setup_node_unsupported` |

Для IOL выбран `startup-config`, а не ввод строк в консоль (`iol-cli`): он детерминирован, не зависит от приглашения
консоли и уже используется для сегментов. Цена — IOS при загрузке молча пропускает неверные строки; что получилось,
преподаватель видит в авторском запуске (консоль, факты `ios.config/1`).

Поломки конструктора (§9, `faults[]`) остаются отдельным будущим этапом: это декларативные типовые поломки с известным
эталоном. Кастомный преднастрой — общий механизм, на котором можно сделать и поломку, но эталон для проверки тогда
задаёт преподаватель в проверках активности.

## 4. Формат: поле `setup` в `gns3lab.lab/2`

Имя `setup`, а не `preconfig`: у образа в каталоге уже есть флаг `preconfig` (можно ли ставить ноду в сегмент).

```json
"setup": [
  {"id": "web", "title": "nginx на SRV1", "node": "SRV1", "timeout": 90,
   "run": "apt-get install -y nginx >/dev/null && systemctl enable --now nginx"},
  {"id": "ospf", "title": "OSPF на R1", "node": "R1",
   "config": "router ospf 1\n network 10.0.0.0 0.0.0.255 area 0"},
  {"id": "pc-dns", "title": "DNS на PC3", "node": "PC3", "config": "ip dns 10.0.0.53"}
]
```

| Поле | Обяз. | Правило |
|---|---|---|
| `id` | да | `^[a-z0-9][a-z0-9_-]{0,31}$`, уникален в лабе (`duplicate_name`) |
| `title` | да | 1…120 символов; видят автор и наблюдатель в отчёте, студент — нет |
| `node` | да | имя ноды лабы (`unknown_node`); нода, которой шаг не подходит, — `setup_node_unsupported` |
| `run` | у QEMU | скрипт, UTF-8, не больше 8000 байт (предел слота 8192 минус обёртка менеджера, §6). У IOL и VPCS — `unknown_field` |
| `shell` | нет | `sh` · `powershell` · `routeros`; без поля — по семейству гостя (`net_config` образа). Указано и не совпадает с семейством — `shell_mismatch`. `powershell` — только при `setup-windows` у менеджера (этап 2) |
| `config` | у IOL и VPCS | IOL: строки `startup-config`, печатный ASCII и `\n`; VPCS: команды VPCS, по строке. У QEMU — `unknown_field` |
| `timeout` | нет | только у `run`: 1…120 с, по умолчанию 60 |
| `required` | нет | этап 2 (§7): `false` — сбой шага не останавливает лабу. До этапа 2 — `unknown_field` |

Пределы (`out_of_range`, путь `setup`): не больше 30 шагов; сумма `timeout` — не больше 600 с (запуск лабы удлиняется на
время шагов: менеджер сверяет сумму со своим сроком ожидания запуска). IOL: итоговый `nvram_config` ноды — до 65536
символов (`too_large`, путь — последний шаг этой ноды). VPCS: итоговый `startup_script` — до 4096 символов (`too_large`).

`setup` есть только в `lab/2` (как `segments` и `checks`): лаба только с преднастроем отправляется как `lab/2` с пустыми
`segments`. Всё поле входит в `lab_def`, порядок шагов — тоже.

## 5. Порядок и жизненный цикл

1. **Один раз, при создании проекта студента** — как вся преднастройка (конструктор §7.1). Продолжение проекта не
   повторяет шаги; сброс лабы (новый проект) — выполняет заново.
2. **У ноды** — после встроенного преднастроя, шаги в порядке массива.
3. **Между нодами** — ноды готовятся по очереди в порядке определения лабы. Шаг может опираться на ноды **выше** по
   списку: их шаги уже выполнены (например, PC1 копирует ключ на SRV1, если SRV1 выше). Слот сейчас идёт по порядку нод
   проекта GNS3; закрепить в контракте, что это порядок билета, — просьба к слоту (§9).
4. **Авторский запуск** выполняет те же шаги: так автор отлаживает преднастрой.
5. **Разностные образы** (`CONTRACTS.md` §2.8): слой, снятый в авторском запуске, уносит и результат преднастроя, а у
   студента шаги выполнятся ещё раз поверх. Поэтому шаги пишутся **повторяемыми** (повторный запуск даёт тот же
   результат) — это правило уходит и в промпт. Снимать слой с образа лучше без шагов на этой ноде.
6. **Правка преднастроя** — новая версия лабы (решение 1); начатые проекты остаются на своей версии.

## 6. Сбой шага (этап 1)

По правилу конструктора §7.4 шаг обязательный: сбой — лаба `FAILED`. Отличие от нынешнего — понятная причина:

- менеджер оборачивает `run` так, чтобы при ненулевом коде выхода последней строкой `stderr` шла метка
  `gns3lab-setup <id> exit <код>` (`sh`: подоболочка и проверка кода; `routeros`: `:do {…} on-error={:error …}`). Слот уже
  переносит последнюю строку `stderr` в текст ошибки — менеджер узнаёт по метке шаг;
- сессия получает код `SETUP_FAILED` с `retryable: false` (повтор даст тот же сбой) и поле `setup_error`:
  `{"step": "web", "node": "SRV1", "exit_code": 100, "message": "<строка stderr перед меткой>"}`;
- шаги IOL и VPCS не «падают»: IOS и VPCS пропускают неверные строки. Их результат виден только в лабе.

Плагин: студенту — «Лаба не подготовилась: ошибка в преднастрое лабы. Сообщите преподавателю» (без текста шага);
автору в авторском запуске и наблюдателю — шаг, нода, код и строка ошибки.

## 6a. Как преподаватель пишет преднастрой

Код шагов пишет нейросеть, преподаватель — задачу и проверку результата. Блок «Преднастрой» в панели лабы редактора
устроен под этот путь:

1. **«Промпт для нейросети»** — главная кнопка блока. Окно: поле «Что настроить» («на SRV1 поднять nginx, на R1 OSPF в
   area 0, на PC3 сломать шлюз»), под ним готовый промпт и «Скопировать». В промпт подставлены лаба (`[[LAB]]`: устройства с
   видом, ОС и оболочкой, могут ли они нести шаг; линии портами; сегменты с адресами плана — чтобы нейросеть знала адреса),
   уже имеющиеся шаги (`[[SETUP]]`) и задача (`[[TASK]]`). Задача и ответ живут до закрытия редактора.
2. **«Вставить ответ»** — вкладка того же окна. Ответ берётся целиком: `{"setup": [...]}`, голый список или то же в блоке
   ` ```json ` среди текста. Справа — карточки шагов: устройство, название, что делает, код. Сразу видно, что редактор находит
   сам: устройства нет в лабе, на нём шаги не выполняются, оболочка не та, повтор `id`, превышены пределы. «Проверить у
   менеджера» — `validate_lab` лабы с этими шагами, ошибки с путём `setup[i]` ложатся на карточку.
3. **«Заменить преднастрой»** — шаги лабы заменяются ответом одной правкой (отменяется «Отменить»). Можно и «Добавить к
   имеющимся»: нейросеть дописала шаги к уже отлаженным.
4. **Авторский запуск** — проверка результата: консоли, факты, схема. Упал шаг (`SETUP_FAILED`, §6) — на странице авторского
   запуска шаг, нода и строка ошибки и кнопка **«Промпт: исправить шаг»**: окно промпта открывается с задачей, куда уже
   подставлены код шага и ошибка («шаг web на SRV1 вышел с кодом 100: … — исправь»). Ответ заменяет только этот шаг.

Ручные поля (устройство, название, `id`, код или строки конфигурации, оболочка, время) и JSON всего списка — свёрнуты под
карточками: для мелкой правки без нейросети.

Качество зависит от промпта (`prompts/setup.<язык>.md`), поэтому правила, которые человек держал бы в голове, — в нём:

- шаги **повторяемые**: второй запуск даёт тот же результат (дописывать файл — только если строки ещё нет);
- ноды готовятся по очереди сверху вниз: шаг опирается только на ноды выше по списку;
- `config` IOL — строки `startup-config` (блоки `interface …`, `router …`), а не команды консоли: без `enable`, `configure
  terminal`, `write memory`; VPCS — команды VPCS по строке;
- адреса сегментов уже настроены (кроме сегментов «Настраивает студент»): шаг их не повторяет, а меняет только намеренно;
- интернет — только через узел «Интернет» лабы и только если он есть; надёжнее то, что уже есть в образе;
- пределы §4 и ответ строго в формате `setup`, без пояснений внутри JSON.

Текст промпта пишется вместе с владельцем, как промпт проверок. Первая строка — отпечаток формата `gns3lab-setup-format`,
его сверяет тест менеджера.

## 7. Этап 2: отчёт, необязательные шаги, Windows (слот)

- **Отчёт по шагам.** Слот возвращает результат каждой команды первой подготовки с меткой (`label`): код, первые 2 КиБ
  `stdout`, 1 КиБ `stderr`, время. Менеджер хранит отчёт с проектом (шаги выполняются один раз) и отдаёт его
  `GET /api/v1/sessions/{id}/setup` — для автора и наблюдателя. Обёртка с меткой (§6) больше не нужна.
- **Необязательный шаг** (`required: false`): сбой записывается в отчёт, лаба запускается; у сессии
  `setup: {"status": "partial", "failed": ["web"]}`, студенту — «лаба подготовлена не полностью». Для шагов, без которых
  задание всё равно выполнимо (например, «положить подсказку в /etc/motd»).
- **Windows**: шаг QEMU с семейством `windows` — PowerShell (как у `qga/exec` с `exec-shell`); сейчас `provisioning`
  запускает `/bin/sh` и у Windows. Возможность менеджера `setup-windows`.
- **Порядок нод** — порядок билета, закреплённый в контракте.

## 8. Этап 3: значения для каждого студента

Конструктор (§1.3, §5) обещает значения, индивидуальные для студента (`{{LAN1.subnet}}`). Шагу нужны те же подстановки
(`{{var.user}}`, `{{LAN1.gateway}}`) — и проверкам активности, чтобы ждать именно эти значения. Это общий механизм значений
конструктора; в этом проекте только оговорено место для подстановок в `run` и `config`. Отдельный проект.

## 9. Что меняется у компонентов

**Менеджер (этап 1).** Возможность `lab-setup` в `info.features` (вместе с `lab_constructor`).
- `labdef.py`: поле `setup` в `lab/2`, проверка по §4 (ноды, семейство и оболочка — как у скриптов проверок,
  `scripts.family_of`), коды `setup_node_unsupported`, `shell_mismatch`, `duplicate_name`, `unknown_node`, `out_of_range`,
  `too_large`. Без `lab-setup` — `unknown_field`.
- Компилятор (`deploy_ticket`, `segments.setup`): `run` — `ProvisionCommand` с обёрткой (§6) после встроенных команд; IOL —
  текст после конфигурации сегментов, перед завершающим `end` (`iosconfig.py`; у ноды без сегментов — с тем же заголовком:
  `hostname`, `no ip domain-lookup`, `line con 0`); VPCS — строки после адреса. Лаба без `setup` — билет не меняется ни на байт.
- Сбой: распознать метку в ошибке операции слота → `SETUP_FAILED` (`retryable: false`), `setup_error` в сессии (§6).
- Срок ожидания запуска лабы — с учётом суммы `timeout` шагов.
- Промпт: отпечаток формата `setup` (`prompt_fingerprint`), тест `tests/test_setup_prompt.py` по образцу `test_checks_prompt.py`.
- `CONTRACTS.md` §2.6 (поле, коды), §2.3 (`setup_error`), §2.5 (`SETUP_FAILED`); `SOURCE_FILES` при новых файлах.

**Плагин (этап 1).**
- Редактор лаб: блок «Преднастрой» по §6a — главные кнопки «Промпт для нейросети» и «Вставить ответ», карточки шагов,
  «Заменить преднастрой» / «Добавить к имеющимся»; ручные поля и JSON свёрнуты. Окно промпта — общее с проверками: код окна
  (вкладки, копирование, разбор ответа, карточки, «Проверить у менеджера») выносится из `checksform.js` в модуль, которым
  пользуются оба блока. `lab_definition::from_json` хранит `setup` (форма, размер до 64 КБ).
- Промпт `prompts/setup.<язык>.md` с `[[LAB]]`, `[[SETUP]]`, `[[TASK]]` и строкой `gns3lab-setup-format`; правила — §6a.
  Читает его класс по образцу `checks_prompt.php`.
- Авторский запуск: `SETUP_FAILED` — шаг, нода, строка ошибки и «Промпт: исправить шаг» (§6a, п. 4). Страница лабы
  наблюдателя — то же без кнопки; студенту — общий текст.
- Проверки активности: в `[[LAB]]` их промпта — шаги преднастроя выбранной версии (названия и устройства, без кода): чтобы
  проверки знали, что выдано (`checks_lab::context`).
- Mock-менеджер, ui-harness (редактор с преднастроем, окно промпта), PHPUnit.

**Слот (этап 2).** Метка и отчёт команд первой подготовки, `required: false`, PowerShell для Windows, порядок нод билета.
Просьба — `manager/docs/SLOT_REQUESTS.md`.

## 11. Вопросы владельцу

1. **Сбой шага.** Правило конструктора §7.4: ошибка преднастройки — лаба `FAILED`. Раньше в обсуждении звучало «сбой —
   предупреждение, а не `FAILED`». Предложение: по умолчанию шаг обязательный (правило §7.4 остаётся, этап 1 без
   изменений слота), а на этапе 2 — флаг `required: false` для шагов, без которых задание выполнимо. Согласны?
2. **IOL через `startup-config`**, а не вводом строк в консоль: детерминированно, но неверные строки IOS молча
   пропускает. Устраивает?
3. **Имя поля `setup`** (в интерфейсе — «Преднастрой»). Устраивает?
4. **Пределы**: 30 шагов, до 120 с каждый, до 600 с в сумме. Не мало ли для лаб, где нужно поставить пакеты? Установка из
   интернета — только через узел «Интернет» лабы; надёжнее заранее собранный образ (разностные образы, §2.8).

## 12. Проверка на стенде (владелец), после этапа 1

1. Лаба: SRV1 (Debian), PC1 (Debian), R1 (IOL), PC2 (VPCS). «Промпт для нейросети»: «на SRV1 nginx, на R1 OSPF area 0 на всех
   интерфейсах, на PC2 DNS 10.0.0.53» → нейросеть → «Вставить ответ»: карточки трёх шагов, «Проверить у менеджера» без
   ошибок, «Заменить преднастрой». Авторский запуск — `curl` с PC1 на SRV1 отвечает, `show run | section ospf` на R1,
   `show ip` на PC2.
2. Шаг с ошибкой (`exit 3`) — авторский запуск `FAILED` с кодом `SETUP_FAILED`, автор видит шаг и строку ошибки; студент —
   общий текст и не получает «попробуйте ещё раз». «Промпт: исправить шаг» — в задаче код шага и ошибка; исправленный
   ответ заменяет только этот шаг.
3. Остановить и продолжить лабу — шаги не повторяются (файл, который шаг дописывает, не удвоился).
4. Сброс лабы — шаги выполнились заново.
5. Правка шага в редакторе — новая версия; активность, переведённая на неё, даёт студенту новый проект.
