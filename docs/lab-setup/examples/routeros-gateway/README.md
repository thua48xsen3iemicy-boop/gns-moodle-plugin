# Пример: шлюз на MikroTik RouterOS — преднастрой и автопроверки к нему

Пара «преднастрой лабы + автопроверки активности», где проверки подтверждают, что преднастрой сработал. Нужна, чтобы
проверить на стенде весь путь: поле `setup` редактора лаб (плагин 0.51.0, менеджер 0.41.0), скрипты проверок в
активности (плагин 0.50.0, менеджер 0.40.0) и гостя RouterOS в обоих. Формат — `manager/docs/CONTRACTS.md` §2.6 (`setup`)
и §2.9 (`scripts`), проект — `docs/lab-setup/README.md`.

| Файл | Что | Куда |
|---|---|---|
| `lab.json` | топология и сегменты (`gns3lab.lab/2` без `setup`) | собрать в редакторе лаб по таблице ниже |
| `setup.json` | 5 шагов преднастроя | редактор лаб → «Преднастрой» → «Промпт для нейросети» → «Вставить ответ» (или «Преднастрой в JSON») |
| `checks.json` | 15 скриптов проверок (`gns3lab.checks/1`) | настройки активности → автопроверки (поле JSON или «Вставить ответ») |
| `show.py` | печатает шаги и проверки ноды текстом для вставки в консоль | проверка на стенде, ниже |

Тест без стенда — `manager/tests/test_setup_example.py`: лаба с шагами проходит проверку менеджера, шаги попадают в билет
слота как задумано, документ проверок верен, а проверки на заготовленных ответах гостей проходят и падают так, как ниже.

## Лаба

```
PC1 (Debian 12) ── eth0 · adapter 0 ── R1 (CHR 7.25.1) ── adapter 1 · eth0 ── SRV1 (Debian 12)
        LAN1 192.168.10.0/24                                   LAN2 192.168.20.0/24
   PC1 .10, шлюз .1 = R1                                  SRV1 .10, шлюз .1 = R1
```

| Нода | Образ | Адаптеры |
|---|---|---|
| R1 | `mikrotik-chr7` | 2 |
| PC1 | `debian12` | 1 |
| SRV1 | `debian12` | 1 |

Линии: R1 adapter 0 — PC1 adapter 0; R1 adapter 1 — SRV1 adapter 0. Сегменты: `LAN1` 192.168.10.0/24, шлюз R1 adapter 0
`host 1`, участник PC1 `host 10`; `LAN2` 192.168.20.0/24, шлюз R1 adapter 1 `host 1`, участник SRV1 `host 10`. Порядок нод
— R1, PC1, SRV1. «Проверить» в редакторе даёт два предупреждения `gateway_not_configured` — так и задумано (ниже).

## Преднастрой (`setup.json`)

| Шаг | Нода | Что делает |
|---|---|---|
| `r1-ports` | R1 | ждёт порты, ставит 192.168.10.1/24 и 192.168.20.1/24 на адаптеры 0 и 1 (по MAC), снимает DHCP-клиент |
| `r1-base` | R1 | имя `R1-SETUP`, мост `lo0` с 10.255.255.1/32, DNS `srv1.lab` → 192.168.20.10, пользователь `auditor` (read) |
| `r1-sec` | R1 | выключает telnet, ftp, www, api; фильтр input: established, ICMP, SSH только из LAN2 |
| `pc1-hosts` | PC1 | `srv1.lab` и `r1.lab` в `/etc/hosts` (и в шаблоне cloud-init, если он есть) |
| `srv1-base` | SRV1 | пользователь `netops` с паролем, файл `/srv/lab/README` |

### Нюансы RouterOS и как они учтены

1. **CHR — не шлюз конструктора.** Конструктор сам настраивает шлюзом только маршрутизатор IOL; на CHR-шлюз он ставит
   предупреждение `gateway_not_configured` и ничего не шлёт R1. Хостам он при этом даёт маршрут по умолчанию на адрес
   шлюза. Адреса шлюза на R1 ставит шаг `r1-ports` — ради таких случаев кастомный преднастрой и нужен.
2. **У R1 нет встроенного преднастроя, поэтому шаг — первая команда ноды.** Слот запускает её, как только ответил
   гостевой агент, а RouterOS в этот момент может ещё поднимать порты. `r1-ports` ждёт порты до 90 с (`timeout` 120),
   как это делает скрипт сегментов менеджера.
3. **Адаптер N — это N-й порт по возрастанию MAC, а не `etherN`.** Порядок имён `ether*` в госте не обязан совпадать с
   номерами адаптеров GNS3. Шаг берёт порты тем же приёмом, что и менеджер (`netconfig.py`, массив с ключами-MAC).
4. **Повторяемость.** Разностный образ, снятый в авторском запуске, уносит результат шагов, а у студента шаги
   выполнятся ещё раз поверх. У RouterOS повторный `add` того же адреса — ошибка, поэтому каждое `add` идёт после
   `remove [find …]` или под `:if ([:len [find …]] = 0)`. Тест проверяет это для каждой строки `add`.
5. **Обёртка `:do { … } on-error={…}`.** Менеджер вставляет `run` внутрь блока: скобки и кавычки должны быть парными,
   строка-«меню» без команды (`/ip address` в одиночку) не годится, `:global` не нужен. Сбой шага даёт `SETUP_FAILED` с
   `exit_code` 1 и пустым `message`: текст ошибки RouterOS не доходит. Поэтому перед своим `:error` шаг пишет
   `:log error …` — причину видно в консоли R1: `/log print where message~"gns3lab"`. Синтаксическую ошибку RouterOS
   находит до запуска — тогда метки нет и сессия получает `SLOT_OPERATION_FAILED`.
6. **Код выхода проверки — только `0` или `-1`.** Каждая проверка R1 ждёт `"exit": 0` и печатает значение через `:put`
   так, чтобы и «нет объекта» было строкой вывода (`srv1.lab missing`, `lan1 count=0`), а не ошибкой скрипта.

## Автопроверки (`checks.json`)

| Скрипт | Нода | Проверяет | `needs` |
|---|---|---|---|
| `r1-identity` | R1 | имя `R1-SETUP` | |
| `r1-gw-lan1`, `r1-gw-lan2` | R1 | адрес шлюза есть ровно один раз, порт поднят | |
| `r1-loopback` | R1 | 10.255.255.1/32 на `lo0` | |
| `r1-dns` | R1 | `srv1.lab` → 192.168.20.10 | |
| `r1-user` | R1 | `auditor` в группе `read` | |
| `r1-services` | R1 | telnet, ftp, www, api выключены (все записи с этим именем) | |
| `r1-fw` | R1 | 4 правила преднастроя, запрет SSH не выключен | |
| `srv1-gw` | SRV1 | ping 192.168.20.1 | `r1-gw-lan2` |
| `pc1-gw` | PC1 | ping 192.168.10.1 | `r1-gw-lan1` |
| `pc1-srv1` | PC1 | ping SRV1 через R1 | `pc1-gw`, `srv1-gw` |
| `pc1-hosts` | PC1 | `getent hosts srv1.lab`, `r1.lab` | |
| `pc1-r1-lo` | PC1 | ping `r1.lab` (loopback R1 по имени) | `pc1-gw`, `pc1-hosts`, `r1-loopback` |
| `srv1-user` | SRV1 | `netops`: оболочка bash, пароль задан (`passwd -S` → `P`) | |
| `srv1-file` | SRV1 | `/srv/lab/README` | |

Пинги с хостов — главная проверка нюанса 3: если адрес LAN1 попал не на тот порт, R1 сам по себе выглядит исправным
(`r1-gw-lan1` проходит), а `pc1-gw` и `srv1-gw` падают.

## Проверка без стенда

```bash
PYTHONPATH=manager /tmp/gns-venv/bin/python -B -m pytest -q -p no:cacheprovider manager/tests/test_setup_example.py
```

Тест разыгрывает прогоны проверок на заготовленных ответах гостей (`GOOD` и `SCENARIOS` в тесте): «всё хорошо» — всё
проходит; «нет адреса LAN1» — одна ошибка, проверки PC1 пропущены (`needs_failed`); «LAN1 и LAN2 перепутаны по портам» —
падают `pc1-gw` и `srv1-gw`; «включён telnet», «правило выключено», «нет пароля netops», «пропал loopback», «имена на PC1
потеряны» — по одной ошибке; ошибка RouterOS в проверке — `exit` (код `-1`). Сами RouterOS и Debian тест не запускает:
что они печатают на самом деле — проверка на стенде.

## Проверка на стенде (владелец)

Менеджер 0.41.0+ с `lab-setup` и `activity-checks`, плагин 0.51.0+, образы `mikrotik-chr7` (CHR 7.25.1) и `debian12`.

1. **Сборка.** Лаба по таблице выше. «Преднастрой» → «Вставить ответ» → содержимое `setup.json`: пять карточек без
   замечаний; «Проверить у менеджера» — без ошибок; «Заменить преднастрой»; «Проверить» лабы — только два
   `gateway_not_configured`. Активность с этой лабой, в автопроверках — `checks.json`, «Проверить» — без ошибок.
2. **Авторский запуск.** Лаба `running`. В консоли R1: `/ip address print` — 192.168.10.1/24 на порту с комментарием
   `LAN1 (PC1)`, 192.168.20.1/24 — `LAN2 (SRV1)`, 10.255.255.1/32 на `lo0`; `/system identity print` — `R1-SETUP`;
   `/ip service print` — telnet, ftp, www, api с флагом `X`; `/ip firewall filter print` — 4 правила.
3. **Что печатают проверки.** `python3 show.py checks R1` — вставить в консоль R1; `checks PC1`, `checks SRV1` — в
   консоли хостов. Сверить с ответами `GOOD` в тесте (`lan1 ether1 running=true`, `auditor read`, `rules=4 drop=1`,
   `exit=0` у пингов…). Расхождение — поправить ожидание в `checks.json` и ответ в тесте вместе.
4. **Прогон студента.** Студент открывает активность, «Проверить» — все 15 скриптов `pass`, оценка полная. В отчёте
   (`result.scripts[].stdout`) — тот же вывод, что в п. 3.
5. **Поломки студента — одна ошибка на поломку.** В консоли R1 по одной, с «Проверить» после каждой и возвратом:
   - `/ip service enable telnet` → падает только `r1-services`;
   - `/ip address remove [find address="192.168.10.1/24"]` → падает `r1-gw-lan1`, `pc1-gw`, `pc1-srv1`, `pc1-r1-lo`
     пропущены («не выполнялась: не прошла …»). Вернуть: `python3 show.py steps R1`, вставить блок `r1-ports`;
   - `/ip firewall filter disable [find comment="gns3lab-setup: ssh from elsewhere"]` → только `r1-fw`;
   - на PC1 `sed -i '/r1\.lab/d' /etc/hosts` → `pc1-hosts`, `pc1-r1-lo` пропущен;
   - на SRV1 `passwd -l netops` → только `srv1-user`.
6. **Повторяемость (нюанс 4).** `python3 show.py steps R1` — вставить в консоль R1 все три блока ещё раз: ни одной
   ошибки, `/ip address print`, `/ip firewall filter print`, `/ip dns static print` — без дублей. На PC1 повторить шаг
   (`show.py steps PC1`) — в `/etc/hosts` по одной строке на имя. Затем остановить и продолжить лабу — шаги не
   повторяются, проверки проходят; перезагрузить PC1 (`reboot`) — `pc1-hosts` проходит (шаблон cloud-init).
7. **Сбой шага RouterOS (нюанс 5).** Копия лабы, в конец `r1-base` дописать строку `:error "boom"` → авторский запуск
   `FAILED`, `SETUP_FAILED`, у автора — «Шаг преднастроя … на R1 вышел с кодом 1» без текста ошибки; студент видит общий
   текст без «попробуйте ещё раз». Вместо этого строка `:put (` (синтаксическая ошибка) → `SLOT_OPERATION_FAILED`.
   Для сравнения в `srv1-base` дописать `echo oops >&2; exit 3` → `SETUP_FAILED`, код 3, строка `oops`.
8. **Порты по MAC (нюанс 3).** В консоли R1 `/interface ethernet print detail` — у порта с `LAN1 (PC1)` MAC меньше,
   чем у `LAN2 (SRV1)`. Если имена `ether*` идут не по MAC, это и есть случай, ради которого шаг ищет порты по MAC:
   пинги `pc1-gw`/`srv1-gw` всё равно проходят.

Что может не совпасть и что тогда править:
- `/ip service` в RouterOS 7.2x может показывать несколько записей с одним именем; шаг выключает все (`set [find …]`), а
  проверка требует, чтобы ни одна не была включена. Если `set` отказывает на динамической записи — шаг упадёт с
  `SETUP_FAILED`, тогда сузить `find` до `dynamic=no`;
- `ping`, `getent`, `passwd` в образе `debian12` — из базовой системы Debian; если `ping` нет, пинги дадут `exit 127`;
- комментарии `#` внутри `:do { … }` RouterOS принимает; если CHR на них споткнётся (`SLOT_OPERATION_FAILED` без метки),
  удалить строки с `#` из шагов R1.
