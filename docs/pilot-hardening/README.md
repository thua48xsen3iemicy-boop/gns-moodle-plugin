# Подготовка пилота: изменения и проверка

Отдельный первый этап подготовки неизменяемого выпуска:
[`install/RELEASES.md`](../../install/RELEASES.md). Его build/verify/list не
применяют выпуск и не заменяют регламент обновления/приёмки рабочего стенда.

Версии: Manager **0.6.0**, Agent **1.1.0**, Slot **0.5.0**, миграция БД **006**.
Основание — [аудит исходного среза](../pilot-readiness/README.md).
Изменения подготовлены для стендовой проверки; приёмка настоящих PVE/CephFS/GNS3
и сохранности дисков через оператора ещё не выполнена.

## Что изменено

| Проблема | Реализация |
|---|---|
| H1: продолжение работы прежнего лидера | Потеря лидерского соединения отменяет и дожидается задач сессий. Эпоха руководителя хранится в PostgreSQL. Изменения состояния проверяют её в транзакции. Agent и Slot сохраняют номера владельца и отказывают старым командам. |
| H2: два запуска используют один бюджет | Выбор узла, чтение резервов и выдача слота сериализованы общей advisory-блокировкой PostgreSQL; локальная блокировка предотвращает исчерпание пула ожидающими задачами. Неопределённые резервы failed/maintenance удерживаются. |
| Изменение размера после постановки в очередь | Билет и ресурсы рабочего пространства закрепляются вместе при создании. Подготовка использует сохранённый размер; sizing выполняется агентом под fencing. |
| Перемещение CT на другой узел | Автоматического переноса бюджета пока нет. Перемещение вне процесса менеджера останавливает использование слота с SLOT_NODE_CHANGED; требуется сверка оператора. |
| H3: free без безопасного mp1 | Заглушка обязательна. Проверяется перед подготовкой и после остановки. student_key снимается после подтверждённой парковки. slot-enable выполняет claim, проверяет stopped, паркует и сверяет конфиг. |
| H4: незашифрованные токены/консоли | HTTPS/WSS с проверкой серверного сертификата. Установщик выпускает отдельные сертификаты слотов и CA. HTTP разрешается только явным ALLOW_PLAINTEXT_SLOTS=1 для проверенной изолированной сети. Публичный шлюз требует WSS. |
| Ложная готовность | /readyz требует живого, активного и недавно работавшего лидера. Резервный менеджер не показывает готовность исполнителя. /healthz остаётся проверкой доступности процесса. |
| Потеря исходной ошибки | Сохраняются текст и код ошибки Slot, идентификатор операции при отказе запуска; вторичная ошибка уборки записывается отдельным событием cleanup_failed. |
| FakeAgent скрывает другой контракт | Ответ владельца каталога имеет настоящий код STUDENT_DIR_OWNER; такая ошибка считается постоянной. |
| Невоспроизводимые Python-зависимости | constraints-tested.txt фиксирует проверенные версии и транзитивные зависимости; установщик использует его при сборке venv. |

## Контракт владения

1. Только лидер под выделенной advisory-блокировкой PostgreSQL вызывает
   `Store.next_epoch()`. Он записывает монотонную эпоху в `command_owner`.
   Операции выдачи слотов и slot-enable не создают новую эпоху лидера.
2. Для поколения слота `g` рабочий токен — `(epoch, 2*g)`, токен уборки —
   `(epoch, 2*g+1)`. Уборка сначала отзывает все старые рабочие команды.
3. `POST /slots/{vmid}/claim` агента получает `{epoch,generation}`.
   Все изменяющие `/slots/{vmid}` запросы затем передают точные заголовки
   `X-Lab-Epoch` и `X-Lab-Generation`. `/size` принимает `{cores,memory_mb}`.
   Пути и произвольные команды по-прежнему не принимаются.
4. Claim, start, stop, mounts и size используют одну блокировку CT на агенте.
   Если host-команда ещё выполняется, claim отвечает SLOT_BUSY; менеджер удерживает
   слот и повторяет. После успешного claim запоздалые команды старого владельца
   получают STALE_OWNER, даже после перезапуска агента.
5. Перед запуском изменяющего `pct` агент сохраняет write-ahead маркер inflight.
   Гибель процесса оставляет его для следующего запуска. При собственном таймауте
   дополнительно сохраняется uncertain. В обоих случаях ответ — COMMAND_UNCERTAIN.
   Новая эпоха не снимает этот запрет: нужен разбор оператора.
   HTTP-таймаут клиента не означает завершение команды на хосте.
6. `POST /v1/fence` Slot с API-токеном получает такую же пару. При передаче Slot
   сохраняет новый номер, закрывает приём команд и дожидается уже принятых операций.
   После этого команды с новым токеном допускаются; старые — отклоняются.
   После перезапуска службы требуется строго более новый токен. Токен на диске
   находится в локальной SQLite, а не в студенческом каталоге.
7. При недоступном Slot менеджер может остановить CT через fenced Agent;
   неопределённые операции не дают права автоматически освободить слот.
   Неизвестный исход парковки/остановки удерживает владение и бюджет.

Эпоха защищает от прежнего лидера, поколение — от прежней сессии. Ни один из этих
номеров не является средством аутентификации: mTLS агента, API-токены, TLS и ACL
обязательны независимо от fencing. Изменения PVE вне менеджера и ручной запуск CT
не входят в протокол владения.

Высшие номера агента хранятся в `/var/lib/lab-node-agent/<vmid>.json` на узле.
У Slot — запись `authority/slot` в `/var/lib/lab-slot/state.sqlite3` на rootfs RBD.
Их нельзя удалять при обычном обновлении или копировать в новый слот как готовое
состояние. Клоны CT должны иметь собственные SQLite, токены и TLS-ключи.

## Обновление существующего стенда

Обновление несовместимо со старым протоколом изменяющих запросов. Moodle API
сохраняется; обновлять плагин Moodle для этих исправлений не требуется.

1. Запретить новые запуски; штатно завершить сессии. Неопределённые и failed CT
   разобрать до продолжения. Отключить HA/autostart и внешние миграции слотов.
2. Остановить все экземпляры менеджера и шлюз. Сохранить согласованный набор:
   PostgreSQL, студенческие каталоги CephFS, метаданные владения на узлах/слотах,
   точные версии кода, конфигурации и образов. Секреты хранить отдельно с ограниченными
   правами. Снимок RBD контейнера не заменяет копию данных на bind mount CephFS.
3. Развернуть новый код и собрать venv с constraints-tested.txt. Не изменять
   общий RO-релиз, пока его используют работающие сессии.
4. На каждой ноде обновить Agent. Его unit создаёт StateDirectory; не удалять
   уже существующие номера владельцев. На каждом выключенном слоте обновить Slot.
5. Выпустить TLS-сертификаты слотов с SAN для их адресов. Настроить
   `SLOT_TLS_CERT_FILE`, `SLOT_TLS_KEY_FILE`; ключ должен читаться пользователем gns3.
   В Manager задать `SLOT_SCHEME=https`, `SLOT_CA_FILE` с доверенным CA.
   Шлюз получает WSS и тот же CA через `lab-manager-admin gateway-env`.
   `lab-provision secrets/venv/slot/agent/manager` содержит соответствующие шаги,
   но выполнение на настоящем кластере остаётся действием оператора.
6. Применить `lab-manager-admin migrate` с окружением службы, проверить конфигурацию,
   заново создать gateway.env, запустить менеджер и шлюз. Менеджер сначала фиксирует
   эпоху, даже если нет доступных слотов. Старые исполнители, не подтверждающие claim,
   не допускаются к изменяющим операциям.
7. Для каждого слота выполнить `lab-manager-admin slot-enable VMID`. Команда
   теперь проверяет и парковку, а не только выключенное состояние CT.
8. Проверить ACL из браузерной сети, учебных VM и соседних слотов: запрещены прямые
   Agent/PVE/Slot/GNS3/Telnet/QGA/БД. TLS не заменяет сетевое разграничение.
9. Задать бюджеты памяти и CPU с резервом для хоста/Ceph/Moodle. Значения N,
   допустимое время запуска/очереди и RPO/RTO определяет оператор по своему стенду.
   Нулевые ограничения CPU/guest-memory означают отсутствие соответствующего лимита
   и не подходят как молчаливое подтверждение бюджета пилота.

### Дополнение: Manager 0.7.0, Agent 1.2.0 (слот живёт одну сессию)

После каждой сессии, в том числе упавшей, агент откатывает слот к снимку чистого слота, и слот
снова `free`: сбой лабы больше не требует `slot-enable`. Порядок обновления:

1. Agent 1.2 на всех нодах (`lab-provision agent` пишет `LAB_CLEAN_SNAPSHOT` в unit агента).
2. Слоты выключены и в `maintenance`. На каждой ноде со слотами `lab-provision snapshot` (шаг `slot`
   делает то же в конце). Снимок содержит шаблон и собственные токены, TLS и IP слота; `mp0` и `mp1`
   в него не попадают.
3. `lab-provision check`: у каждого слота `snapshot lab-clean: present`.
4. Manager 0.7.0: `lab-manager-admin migrate` (миграция **007**, счёт сбоев лабы у слота), потом
   `slot-enable` для каждого слота (команда сама откатывает CT и ставит заглушку). Без снимка слот
   после первой сессии уйдёт в `maintenance` с `reset failed: SNAPSHOT_MISSING`.

Проверить на стенде:

- `pct snapshot` проходит на слоте, у которого есть bind-точка `mp2` (задан `IMAGES_DIR`), со
  связанным клоном; после `pct rollback` на месте `mp2`, `net0` и тег `labslot`, `mp0`/`mp1` нет.
  Время отката.
- Сессия с упавшей лабой освобождает слот сама; следующая сессия на том же слоте стартует с чистого
  гостя (нет файлов предыдущей).
- Слот, ушедший в `failed` (на тестовом слоте сломайте старт CT или службы слота: `SLOT_START_FAILED`
  или `TIMEOUT` на `slot_ready`), не откатывается: в госте остаются `/var/lib/lab-slot` и журналы,
  CT выключен, заглушка стоит; `enable` откатывает его.
- Три сбоя лабы у разных студентов подряд переводят слот в `maintenance`; `enable` возвращает его.

Любая ручная правка конфига CT слота (IP, MAC) после снимка откатывается: её закрепляет новый снимок.
Владелец слота после отката: DESIGN §6.3.

Новая роль PVE использует VM.Audit и Sys.Audit; VM.Config.CPU/Memory менеджеру
больше не нужны. Пересоздание ключей/сертификатов при расширении стенда не требуется;
при смене IP сверить SAN и при необходимости перевыпустить конкретный сертификат.

## Разбор неизвестного исхода

Начинать с session_id, slot VMID, stage, исходной ошибки `sessions.error` и событий
`failure_cleanup`, `cleanup_failed`, `ownership_wait`. Для журнала использовать
`journalctl -u lab-manager`, на узле — `lab-node-agent`, в CT — `lab-slot` и `gns3`.
На стенде включить постоянное хранилище journald на rootfs RBD менеджера и слотов
(`Storage=persistent`, ограниченный SystemMaxUse) и проверить сохранение после
перезапуска. Доставка журналов в центральное хранилище определяется инфраструктурой.

При COMMAND_UNCERTAIN остановить менеджеры, исключить старые клиенты управления,
проверить задачи PVE и процессы pct/lxc, доказать завершение прежней команды,
остановить CT и проверить конфиг. Только после этого администратор узла может
снять маркеры `uncertain`/`inflight`, **сохранив epoch/generation**, и вновь выполнить slot-enable.
Автоматической команды «забыть неизвестный исход» намеренно нет.
Удалять state.sqlite3, .lab-slot или файлы fencing для такого восстановления нельзя.

При `SLOT_OWNER_LOST` Slot отверг токен Manager, который ещё владеет своей
лидерской блокировкой. Такое бывает после перезапуска Slot: прежний токен не
принимается повторно. Manager переводит сессию в остановку с новым поколением
команд, останавливает лабу и CT, проверяет парковку каталога и оставляет слот в
`maintenance`. Если остановка не подтверждена, слот остаётся удержанным и требует
ручной сверки. Оператор проверяет `sessions.error`, `failure_cleanup` и
`cleanup_failed`, состояние операции Slot, CT и монтирования в Proxmox. После
подтверждённой остановки и парковки он выполняет `slot-enable`; сохранённый
workspace студента можно снова запустить. При восстановлении не сбрасывать
локальную запись владельца Slot и не удалять SQLite.

При восстановлении БД из старой копии остановить менеджеры на всех узлах. Определить
максимальную сохранённую эпоху по агентам и локальным SQLite всех слотов. Поднять
`command_epochs` выше этого максимума (например, `setval` последовательности в
PostgreSQL); только затем запускать новый менеджер. Недоступный узел исключить
из управления и сверить до повторного включения. Восстановление старой БД без
такой сверки должно приводить к STALE_OWNER, а не к автоматическому сбросу защиты.

Для возврата данных одного студента: остановить его сессию, подтвердить отсутствие
RW-монтирований каталога во всех слотах, сохранить текущее состояние для разбора,
восстановить каталог вместе с соответствующими workspace/project_id/ticket из
согласованной копии. Проверить нужную версию образов и продолжение проекта на
выделенном слоте. Не переносить старые control-state/номера владельцев поверх новых.

## Автоматические и ручные проверки

Новые проверки — `manager/tests/test_pilot_safety.py`, `test_slot_tls.py`,
`agent/tests/test_fencing.py`, `slot/tests/test_fencing.py`.
Тесты бюджета выполняют по 50 конкурирующих выдач для памяти и CPU с настоящей
PostgreSQL и двумя отдельными объектами allocator. Это не нагрузочный тест PVE.
TLS-проверка устанавливает настоящее HTTPS/WSS-соединение и отвергает неверный CA.

Исторический `tools/audit/check_pilot_hypotheses.py` воспроизводит дефекты исходного
коммита 594b9c8; его успешный результат не является критерием текущего релиза.
На новом коде использовать регрессионные тесты выше.

После локальных тестов оператор проходит [C0–C9](../pilot-readiness/README.md#5-проверяемые-критерии-допуска):

- Каждый используемый образ: сохранить контрольный файл/startup-config; A → stop →
  B на прежнем слоте → A на другом слоте/узле, 20 циклов, проверить UUID и данные.
- На выделенном стенде прервать менеджер во время каждой стадии; отдельно оборвать
  лидерское соединение при живом процессе и запустить второй менеджер. После передачи
  слота старые команды должны получить отказ и не менять новую сессию.
- Имитировать потерю ответа на host-команду и таймаут самой host-команды; убедиться,
  что это разные случаи, неопределённость не освобождает владение/бюджет.
- Запустить одновременно больше заявок, чем допускает бюджет одной ноды; проверить
  фактические CT cores/memory и резервы. Миграция слота требует карантина и сверки.
- Проверить отказ парковки и slot-enable; ни одна ошибка не должна выдавать free.
- Проверить чужие/повторные билеты, readonly и прямой сетевой доступ.
- Проверить недоступность CephFS и нехватку места, сохранение первичной ошибки,
  восстановление из копии и измерить время восстановления.

Проведение разрушительных сценариев — только на выделенных тестовых данных.
Диски VM, NVRAM, межузловые блокировки и резервное восстановление должны подтвердиться
на настоящем стенде до допуска студентов. Текущий PR эти результаты не заявляет.
