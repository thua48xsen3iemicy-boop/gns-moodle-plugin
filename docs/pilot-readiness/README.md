# Аудит готовности к ограниченному учебному пилоту

Дата: 2026-10-20. Репозиторий: `thua48xsen3iemicy-boop/gns-moodle-plugin`.
Исходный коммит: `594b9c8370f5b4ec924d06eb52c416b8df76641f`.
Этот PR фиксирует результат аудита; рабочий код компонентов не изменяется.
Каталог координации задач исправления будет создан отдельно.

**Решение: текущий коммит не допускать к пилоту со студентами.** Он пригоден для
подготовки и испытаний выделенного стенда. Причины: подтверждённые пробелы в
управлении лидерством и конкурентном учёте ресурсов, обходы проверки освобождения,
неподтверждённая сетевая изоляция реального развёртывания и отсутствие приёмочного
протокола сохранности данных для текущей комбинации компонентов.

## 1. Что проверено и чего эта проверка не доказывает

- Прослежены Moodle → Manager → Proxmox/Agent → Slot/GNS3, выдача консольного билета,
  размещение, запуск, штатная остановка, аварийная уборка, повторный запуск и команды оператора.
- Изучены действующий код, SQL, тесты, README, DESIGN, CONTRACTS, переписка
  MANAGER_CONTRACT_REVIEW / MANAGER_REVIEW_FOLLOWUP / AGENT_REVIEW_ANSWERS,
  SLOT_REQUESTS / ALIGNMENT и документы плагина.
- Manager: **132 passed, 82 skipped, 1 deselected**. 82 проверки требуют PostgreSQL;
  исключена проверка шлюза с локальным сервером.
- Slot: 5 проверок фиксированного релиза/монтирования и валидации/Telnet прошли.
- Agent: 4 проверки гостевого init прошли.
- Отдельный [сценарий проверки](../../tools/audit/check_pilot_hypotheses.py) выполняет 8 проверок настоящих
  функций менеджера с явно заменёнными внешними зависимостями.
  [Сохранённые наблюдения](observations.jsonl). Они относятся к исходному коммиту аудита,
  а не подтверждают исправление перечисленных дефектов.
- PostgreSQL не запущен: песочница запрещает bind Unix-сокета; запрос дополнительного
  разрешения отменён. Инициализирован только отдельный пустой кластер в рабочей среде аудита;
  существующие базы не трогались. Файлы локального кластера в PR не включены.
- Попытки запуска наборов Slot и Agent с TestClient зависли на взаимодействии
  TestClient/AnyIO и были остановлены. Диагностические стеки остались в рабочей
  среде аудита. Причина не установлена; это не
  положительный результат и не доказанный дефект продукта.
- Moodle PHPUnit, реальные PVE, CephFS, GNS3 и браузеры в этой проверке не запускались.
  Старые описания успешных испытаний не засчитываются за приёмку текущего коммита.

Воспроизведение проверок (из корня репозитория, Python 3.12):

```sh
python3 -m venv .venv-audit
.venv-audit/bin/python -m pip install -r manager/requirements.txt pytest
.venv-audit/bin/python tools/audit/check_pilot_hypotheses.py
.venv-audit/bin/python -m pytest -q manager/tests -k 'not gateway_against_a_fake_slot'
```

Установка зависимостей требует доступа к источнику пакетов; сам сценарий гипотез
не использует сеть или настоящую БД. Он проверяет наличие обнаруженных дефектов:
успешное завершение означает воспроизведение наблюдений, **не готовность к пилоту**.
После исправлений соответствующие проверки нужно заменить регрессионными ожиданиями.
PostgreSQL-тесты без `DATABASE_URL` пропускаются; никогда не указывайте рабочую БД:
фикстура тестов удаляет и создаёт заново её схему `public`.

Дополнительные выбранные проверки Slot/Agent (после установки зависимостей соответствующих компонентов):

```sh
PYTHONPATH=slot .venv-audit/bin/python -m pytest -q slot/tests/test_fixed_mount.py slot/tests/test_slot.py::test_invalid_manifest_and_telnet_filter
```

## 2. Четыре исходные гипотезы

### H1. Задачи продолжаются после потери менеджером блокировки лидера — подтверждена

**Условие.** Уже есть выполняющаяся задача сессии; выделенное соединение PostgreSQL,
держащее advisory lock, теряется. Процесс, HTTP-клиенты и соединения пула БД остаются
работоспособными либо восстанавливаются. Второй менеджер может получить освободившуюся
блокировку; наличие второго менеджера не нужно для самого продолжения старой задачи.

**Доказательство.**
[run_forever/tick/drive](https://github.com/thua48xsen3iemicy-boop/gns-moodle-plugin/blob/594b9c8370f5b4ec924d06eb52c416b8df76641f/manager/lab_manager/orchestrator.py#L151):
при ошибке соединения меняется только `leader=False`; задачи `_tasks` не отменяются
и не дожидаются завершения. `drive` не проверяет лидерство. Более того, `tick` идёт
перед проверкой соединения `SELECT 1`.
[update_session](https://github.com/thua48xsen3iemicy-boop/gns-moodle-plugin/blob/594b9c8370f5b4ec924d06eb52c416b8df76641f/manager/lab_manager/store.py#L290) проверяет
поколение слота, а не эпоху лидера. У двух менеджеров одной сессии поколение одинаковое.
[Agent](https://github.com/thua48xsen3iemicy-boop/gns-moodle-plugin/blob/594b9c8370f5b4ec924d06eb52c416b8df76641f/agent/agent.py#L70) не получает эпоху владельца:
его локальный flock сериализует команды, но не отвергает устаревшего отправителя.

**Выполненная проверка.** `leader_loss`: реальный `run_forever` получает
`OperationalError` на heartbeat через подменённое соединение; реальная задача
`drive → ct_stop` затем вызывает подменённый `agent.stop` при `leader=False`.
Наблюдение: `{"action":"agent.stop","leader":false}`.
Полный сценарий двух процессов с реальной БД пока не выполнен.

**Последствия.** Дублирующие/устаревшие start/stop/mount/config; несогласованные стадии.
Проверка поколения при последующей записи в БД не отменяет уже выполненный внешний
эффект. При переиспользовании слота возможны остановка новой сессии или вмешательство
в её монтирования; такой полный сценарий на стенде не воспроизводился.

**Что нужно.** Контролируемая остановка задач при потере лидерства и проверка полномочий
перед изменениями; для уже отправленных/задержанных команд — согласованный механизм
отсечения старого владельца и сверки результата на стороне исполнителя.
Одного `task.cancel()` или одной проверки boolean недостаточно. До доказанного
исхода внешней команды слот остаётся занят/изолирован от выдачи.

### H2. Между проверкой ресурсов и резервированием есть гонка — подтверждена

**Условие.** Две заявки разных студентов, два свободных слота на одном узле,
свободного бюджета достаточно для одной заявки. Даже один лидер запускает задачи
сессий конкурентно.

**Доказательство.**
[placement](https://github.com/thua48xsen3iemicy-boop/gns-moodle-plugin/blob/594b9c8370f5b4ec924d06eb52c416b8df76641f/manager/lab_manager/orchestrator.py#L349)
читает свободные слоты, снимок PVE и reservations.
[_try_allocate](https://github.com/thua48xsen3iemicy-boop/gns-moodle-plugin/blob/594b9c8370f5b4ec924d06eb52c416b8df76641f/manager/lab_manager/orchestrator.py#L442)
после этого отдельно вызывает
[allocate_slot](https://github.com/thua48xsen3iemicy-boop/gns-moodle-plugin/blob/594b9c8370f5b4ec924d06eb52c416b8df76641f/manager/lab_manager/store.py#L197).
Транзакция блокирует сессию и отдельную строку слота (`SKIP LOCKED`), но не бюджет
узла и не пересчитывает его. Разные слоты могут быть выданы по одному старому снимку.

**Выполненная проверка.** `placement_race`: две настоящие `_try_allocate/placement`
синхронизированы на чтении reservations. Выдача разных свободных строк смоделирована
в памяти по семантике SQL. Обе получили слот: **32768 MiB при бюджете 16384 MiB,
16 vCPU при бюджете 8**. Это воспроизведение логической гонки с моделью allocator;
конкурентный прогон самого SQL на PostgreSQL остаётся обязательным.
Существующие тесты бюджета запускают заявки последовательно:
[test_node_guest_memory_limit...](https://github.com/thua48xsen3iemicy-boop/gns-moodle-plugin/blob/594b9c8370f5b4ec924d06eb52c416b8df76641f/manager/tests/test_orchestrator.py#L179).

**Последствия.** Нарушение обязательного бюджета, риск OOM и давления на хост/Ceph.
Уникальный индекс живой сессии слота не защищает суммарную ёмкость узла.

**Что нужно.** Проверка и запись резерва под общей блокировкой бюджета узла в БД,
с единым учётом starting/running/stopping и неопределённых операций. До запуска —
проверка актуального узла и фактически применяемого размера. Внешние нагрузки
PVE должны входить в модель бюджета или быть запрещены на выделенных узлах пилота.

### H3. Слот можно освободить без отключения каталога студента — подтверждена условно

Нужно различать **оставшийся источник в конфигурации выключенного CT** и
**активное монтирование в работающем CT**.

**Обычная остановка с непустой заглушкой защищена:** `ct_stop` подтверждает stopped,
`ct_park` заменяет mp1 и проверяет полный источник, цель и ro; при несовпадении —
maintenance. Гипотеза «каждая обычная остановка свободно отдаёт работающий CT
с чужим каталогом» не подтверждена.

**Подтверждённые исключения:**

1. Явно пустой `PLACEHOLDER_STUDENT_KEY` допустим
   [config.py](https://github.com/thua48xsen3iemicy-boop/gns-moodle-plugin/blob/594b9c8370f5b4ec924d06eb52c416b8df76641f/manager/lab_manager/config.py#L286).
   [ct_park](https://github.com/thua48xsen3iemicy-boop/gns-moodle-plugin/blob/594b9c8370f5b4ec924d06eb52c416b8df76641f/manager/lab_manager/orchestrator.py#L765)
   пропускает замену и проверку mp1, завершает сессию со слотом `free`.
   `park_disabled` воспроизвёл этот переход без единого вызова PVE/Agent.
2. [slot-enable](https://github.com/thua48xsen3iemicy-boop/gns-moodle-plugin/blob/594b9c8370f5b4ec924d06eb52c416b8df76641f/manager/lab_manager/admin.py#L106)
   проверяет только `status=stopped`, затем
   [снимает student_key](https://github.com/thua48xsen3iemicy-boop/gns-moodle-plugin/blob/594b9c8370f5b4ec924d06eb52c416b8df76641f/manager/lab_manager/store.py#L65).
   Он не паркует каталог. Это сознательно описано в TROUBLESHOOTING.
3. При отказе подготовки каталога до `ct_start` есть прямой возврат `free`;
   прежний mp1 не проверяется. Это безопасно лишь при уже обеспеченном инварианте
   свободного слота и отсутствии стороннего запуска.

**Последствия.** Нарушается утверждение «free всегда означает заглушку».
При ручном/autostart/устаревшем запуске CT прежний каталог снова станет доступен;
после снятия student_key менеджер может разрешить студенту другой слот.
Сам по себе оставшийся mp1 не доказывает межстуденческую утечку:
следующий штатный `agent.start` меняет монтирования, менеджер проверяет их.

**Что нужно.** Для пилота обязательная непустая заглушка и единая процедура
освобождения/slot-enable: нет незавершённых команд → CT остановлен → mp1 заменён
и проверен → снято владение → free. Ошибка любого шага оставляет слот в карантине.
Проверить autostart/HA и запрет обходных запусков в регламенте стенда.

### H4. Защита внутренних HTTP/WS зависит от сети — подтверждена для двух участков

- [Manager → Slot](https://github.com/thua48xsen3iemicy-boop/gns-moodle-plugin/blob/594b9c8370f5b4ec924d06eb52c416b8df76641f/manager/lab_manager/slot_client.py#L35):
  жёстко `http://`, постоянный Bearer.
- [Gateway → Slot](https://github.com/thua48xsen3iemicy-boop/gns-moodle-plugin/blob/594b9c8370f5b4ec924d06eb52c416b8df76641f/manager/gateway/console_gateway.py#L114):
  `ws://`, постоянный консольный токен в `Sec-WebSocket-Protocol`, ввод/вывод терминала.
- Manager → Gateway использует внутренний ключ, штатно loopback в одном LXC.
- Agent — другой случай: [unit требует клиентский TLS-сертификат](https://github.com/thua48xsen3iemicy-boop/gns-moodle-plugin/blob/594b9c8370f5b4ec924d06eb52c416b8df76641f/agent/lab-node-agent.service#L17);
  клиент менеджера настроен на CA/сертификат/ключ. PVE-клиент использует HTTPS и CA.
- Browser → Gateway в штатной установке WSS; конфиг менеджера, однако, допускает WS,
  поэтому профиль пилота должен отдельно требовать WSS.

**Проверка.** `plaintext` перехватил реальный запрос SlotClient на MockTransport:
`scheme=http`, `Authorization=Bearer dummy-audit-token`. WS подтверждён построением URL
и заголовков в коде. Захват трафика и реальные ACL на стенде не проверялись.

**Условие угрозы.** Возможность читать/подменять трафик управления или добраться до
незащищённых GNS3/Telnet-портов. Одна только достижимость Slot API без токена ещё не
означает доступ: аутентификация там есть.

**Последствия.** Перехват долгоживущего токена, подмена управления, чтение/ввод в
консоли в обход разграничения Moodle. Консольный токен отделён от API-токена,
но не ограничен одним студентом/одной сессией.

**Что нужно.** TLS с проверкой стороны для этих участков либо явно принятый профиль
ограниченного пилота в отдельной доверенной сети с проверенными ACL.
Установщик firewall не применяет:
[install/README.md](https://github.com/thua48xsen3iemicy-boop/gns-moodle-plugin/blob/594b9c8370f5b4ec924d06eb52c416b8df76641f/install/README.md#L168).
Тестировать доступ и из браузерной сети, и из учебных VM, и между слотами.

## 4. Что в реализации уже полезно

- Moodle разрешает чужие данные через серверную проверку observe/групп; чтение чужой
  консоли принудительно readonly. Manager доверяет серверу Moodle в пределах сайта,
  а не проверяет конечного пользователя заново. Следовательно, site-secret должен
  оставаться только на сервере Moodle.
- Билеты шлюза случайные, одноразовые, на 30 секунд, привязаны к project/node,
  проверяется Origin; консольный токен не позволяет REST.
- SQL запрещает две живые сессии одного студента и две живые сессии одного слота.
  `student_key` удерживает каталог после неуспешной остановки CT.
- При штатном запуске сравниваются полные mp0/mp1, цели и режимы RO/RW.
  Агент ограничивает VMID, метку labslot, unprivileged CT, пути, symlink и ACL.
- Стабильный project_id и сохранённый билет рабочего пространства используются
  повторно. Запись лабы хранится с каталогом студента. Неизвестное завершение
  provisioning и пропажа сохранённого проекта приводят к отказу, а не перестройке.
- Операции Slot имеют сохраняемые idempotency keys; история успеха не считается
  успехом при нарушенном текущем постусловии.

Эти механизмы — основание для дальнейшей подготовки, а не доказательство готовности
всей связки на реальной инфраструктуре.

## 5. Проверяемые критерии допуска

Предлагаемый минимальный протокол. N — утверждённое число одновременных сессий,
вычисленное для выбранных лабораторных и бюджетов узлов. Пороговые времена
неопределённости, очереди и восстановления фиксируются до испытаний.

| ID | Проверка на стенде | Условие приёмки |

Проверить и уже открытые консоли после stop/смены владельца. |
| C2 | Проверить сеть из студентского сегмента, учебных VM и соседнего слота. | Доступ только к разрешённым публичным точкам; GNS3 API, Telnet/QGA, Slot API, Agent/PVE/БД не доступны студенту; защищённые каналы проверяют сертификат. | C4 | Потеря ответа на start/deploy/stop/mount; рестарт менеджера на каждой границе стадии; потеря его leader connection при живом процессе; второй менеджер. | Старый владелец не оказывает поздних эффектов после передачи слота; максимум один исполнитель/писатель; неизвестный исход удерживает владение и виден оператору. После восстановления нет дублирующего provisioning. |

| C7 | Убить Slot/GNS3/CT, отключить узел, имитировать недоступность CephFS, EIO/ENOSPC и повреждение метаданных; прервать initial provisioning. | Данные не удаляются и не пересоздаются автоматически; сохранённые контрольные данные восстанавливаются в согласованной модели сбоя. Допуск — только после прохождения всех обязательных критериев на точном релизе.
Один удачный happy path или только unit-тесты не заменяют C1–C9.

## 6. Порядок устранения и будущие контракты работ

Это последовательность будущих задач, а не разрешение исполнителям менять код.
Каталог координации будет создан отдельно по принятой пользователем схеме.

1. **Зафиксировать профиль пилота и актуальные контракты.** Архитектурный реестр:
   границы доверия, смысл free/unknown, модель отказов, критерии сохранённой работы,
   владелец ресурса, версии, запрет изменений релиза во время сессий.
   Снять расхождения старых документов, оставить историю с пометками «заменено».
2. **Лидерство, внешние эффекты и безопасное освобождение.** H1/H3 связаны:
   сначала согласовать эпохи/команды/сверку результата, затем общий путь park/enable.
   Затрагиваются Manager/Agent/Slot и их API; выполнить последовательно либо с
   заранее согласованными непересекающимися областями.
3. **Атомарный бюджет узла.** H2, снимок размера, миграция, неопределённые резервы.
   Затрагивает Store/SQL/Orchestrator, пересекается с п.2 — не давать независимые
   параллельные изменения этих файлов без разделения.
4. **Сетевая защита и профиль развёртывания.** Согласовать TLS или ограниченный
   изолированный профиль, внедрить проверяемые ACL, закрыть прямые порты.
   После фиксации API эту работу можно вести независимо от алгоритма бюджетов.
5. **Наблюдаемость и recovery.** Readiness, неизменяемая первичная ошибка, история
   cleanup, исправленные fake-контракты, persistent logs, инструкция
   quarantined → reconcile → parked → free и согласованное восстановление данных.
6. **Интеграция и испытания C0–C9.** Реальная PostgreSQL для гонок/лидерства,
   затем полный стек, восстановление из backup, пробное занятие под нагрузкой.
   В пилот входит одна ограниченная группа и только проверенные лабораторные;
   неопределённое владение/утечка/нарушение бюджета/потеря сохранённого маркера
   немедленно останавливают новые выдачи до разбора.

Для каждой задачи руководитель пишет TASK.md с исходным коммитом и разрешённой
областью; исполнитель до кода пишет PLAN.md, руководитель фиксирует APPROVED
конкретной версии. Исполнение — в отдельной ветке/worktree. RESULT.md и независимый
REVIEW.md относятся к конкретным коммитам. Принятие — после проверки интеграции.
Архитектурные решения и актуальные API ведёт руководитель отдельно от переписки.

## 8. Что требует решения человека перед допуском

Техническое согласование исправлений выполняет руководитель. Человеку остаются
требования и инфраструктура:

- N, лабораторные/образы и резерв ресурсов под Moodle, хост и Ceph; можно ли
  запретить миграции, HA/autostart и сторонние изменения на время пилота.
- Сетевая топология: отдельная доверенная сеть или обязательный TLS на всех
  межмашинных переходах. Изоляцию необходимо проверить, не предполагать по имени VLAN.
- Модель гарантируемого сбоя, что считается сохранённой работой, RPO/RTO и место
  backup. Предлагаемая база: подтверждённо сохранённые данные переживают штатную
  остановку и испытанные одиночные отказы; неизвестный исход никогда не разрешает
  автоматическое пересоздание/перезапись. Потеря всего хранилища требует отдельно
  согласованной политики резервирования.

Эти вопросы не мешают начать исправление доказанных ошибок H1/H2/readiness
после создания согласованного каталога задач.
