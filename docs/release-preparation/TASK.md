Ты — исполнитель задачи по упрощению развёртывания Moodle + Proxmox + CephFS + GNS3.

Цель первого этапа: реализовать подготовку неизменяемого выпуска компонентов на CephFS и его проверку. Применение выпуска к работающему стенду будет отдельной задачей.

Работай по согласованному порядку TASK.md → PLAN.md → APPROVED → RESULT.md → REVIEW.md. Уточни у руководителя расположение общего каталога координации, если оно ещё не задано. До одобрения плана изучай код и готовь предложение; рабочий код не меняй.

Исходное состояние

Начни с актуального main, зафиксируй SHA. Изучи:
- install/lab-provision, install/README.md, install/lab.conf.example;
- установку и запуск Manager, Agent и Slot;

Сейчас код Manager и Slot вместе с venv размещён на CephFS. Обновление общего checkout и пересборка venv требуют ручной координации. Agent устанавливается локально на узлы Proxmox. Эти особенности необходимо учесть.

Ожидаемое поведение

Оператор может подготовить выпуск из конкретного Git-коммита, проверить его и получить каталог с постоянным идентификатором. Подготовка нового выпуска не изменяет ранее опубликованные выпуски и файлы, используемые работающими сервисами.

Предлагаемый интерфейс:
lab-provision release build <release-id> --ref <commit>
lab-provision release verify <release-id>
lab-provision release list
Это предложение: проверь совместимость с устройством установщика и обоснуй окончательный интерфейс в PLAN.md.

Что требуется спроектировать и реализовать
1. Формат выпуска. Предложи структуру каталога с кодом Manager, Slot, Agent и manifest. Manifest должен фиксировать исходный Git SHA, версии компонентов, требования к среде выполнения, хеши поставляемых файлов и сведения о совместимости со схемой БД. Укажи, какие сведения проверяются автоматически, а какие задаёт сопровождающий выпуска.
2. Подготовку во временном каталоге. До успешного завершения всех проверок выпуск не должен считаться опубликованным. Ошибка, прерывание сборки или повторный запуск не должны оставлять частичный выпуск доступным для применения.
3. Публикацию без перезаписи. Готовый выпуск публикуется под новым идентификатором. Существующий выпуск запрещено изменять или пересобирать на месте. Учти одновременную подготовку одного идентификатора двумя процессами и семантику операций на CephFS.
4. Зависимости Python. Определи способ сборки сред Manager и Slot, совместимый с фиксированными путями внутри LXC. Нельзя считать venv переносимым между произвольными каталогами, версиями Python, ОС и архитектурами. Используй отдельную сборочную среду; действующие учебные слоты не должны предоставлять запись в опубликованный код или venv. Для Agent учитывай среду узла Proxmox отдельно от Ubuntu внутри LXC.
5. Проверку целостности. Согласуй общий manifest с существующей проверкой slot/release.py, чтобы не возникли два противоречащих друг другу источника истины. Хеши должны охватывать поставляемые исполняемые артефакты и зависимости либо обеспечиваться проверяемыми хешами пакетов. Опиши границу защиты: хеши сами по себе не подтверждают подлинность выпуска.
6. Инструкцию оператора. Опиши сборку, проверку, просмотр выпусков и действия после прерывания подготовки. Чётко укажи, что публикация выпуска ещё не переключает стенд на него.
Ограничения этапа
- Не изменять протоколы владения, fencing, резервирование ресурсов и очистку слотов.
- Не выполнять миграции БД, перезапуски сервисов, смену монтирований работающих компонентов или автоматическое включение слотов.
- Не включать в выпуск закрытые ключи, токены, конфигурацию конкретного стенда, БД, SQLite, журналы и данные студентов.
- Не вводить обновление работающих сервисов через общий переключаемый symlink.
- Не добавлять Kubernetes, отдельный registry или новую платформу управления конфигурацией.
- Существующий способ установки должен продолжать работать. Его удаление или перевод на новый формат — отдельное согласованное изменение.
- Изменения архитектурных решений и общих контрактов сначала предложить руководителю для согласования.
Содержание PLAN.md

Запиши:
- обнаруженные противоречия между кодом и документацией;
- формат выпуска и manifest;
- точные команды и перечень изменяемых файлов;
- способ сборки зависимостей и требования к сборочной среде;
- механизм защиты от перезаписи, конкурентной публикации и частичного результата;
- проверки, доступные локально, и проверки, требующие настоящего CephFS/LXC;
- зависимости и вопросы, без решения которых реализация небезопасна.
Критерии приёмки
- Выпуск однозначно связан с исходным коммитом.
- Проверка обнаруживает изменение, отсутствие и недопустимое добавление файлов в контролируемой части выпуска.
- Повторная публикация существующего идентификатора не меняет его содержимое.
- Две конкурентные публикации одного идентификатора не создают смешанный выпуск.
- Прерванная подготовка не появляется в списке готовых выпусков.
- Старый выпуск остаётся неизменным при сборке нового.
- Секреты и рабочие данные не попадают в пакет.
- Код и зависимости проходят проверки из ожидаемых путей в заявленной среде исполнения.
- Команды подготовки не изменяют состояние работающего стенда.
- Проверки реального CephFS/LXC, которые выполнить не удалось, явно перечислены; моделирование не выдаётся за стендовый результат.
В RESULT.md укажи коммиты, фактические изменения, команды проверок и результаты, ограничения и отклонения от утверждённого плана. Подготовь PR для независимого ревью. Самостоятельно не сливай и не развёртывай изменения на стенде.
