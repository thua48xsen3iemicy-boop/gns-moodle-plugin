# Непонятный исход запуска слота: лаба работает, а остановиться не может

Разбор случая на стенде 2026-10-28 и задание исполнителю. Компоненты: агент узла, менеджер, `install/`. Слот и
плагин не меняются. Коммиты — по компоненту отдельно (`AGENTS.md`).

## 1. Что случилось

Сессия `s-2b7ac5d516135c8c`, слот 501 на `node-015`.

1. `ct_start` (00:32:09). Агент запустил CT (`pct start`) и выполнял команды запуска внутри CT (`pct exec`:
   `lab-slot-init`, `systemctl … lab-slot.service`). Одна из них шла дольше **45 с** (жёсткий тайм-аут
   `run_cmd` у `pct exec` в `agent/agent.py`). Агент, как и положено по правилу fencing, записал в
   `/var/lib/lab-node-agent/501.json` отметки `inflight`/`uncertain` (`command: exec`) и ответил `504 PCT_TIMEOUT`.
2. Менеджер отнёс ответ к `AgentUncertain` и сделал `Wait` (`_stage_ct_start`). На следующем такте CT уже `running`,
   менеджер проверил монтирования и **пошёл дальше** (`slot_ready` в 00:33:06, события `ct_started` нет). Слот поднялся
   сам, лаба работала 10 минут. Отметка агента осталась.
3. «Остановить» (00:43:41). Любой изменяющий запрос и `claim` у агента для 501 — `409 COMMAND_UNCERTAIN`. Менеджер
   10 минут писал `ownership_wait` («Нет подтверждения владения слотом…»), студент видел «Остановка устройств…». Потом
   `TIMEOUT` на `lab_stop` с `slot_state: free` в ошибке, `ct_stop` не прошёл (ещё 390 с), сессия `failed`. CT 501
   остался работать с открытым проектом и каталогом студента на запись.
4. Восстановление вручную: слот в `maintenance`, `pct shutdown 501`, отметки `inflight`/`uncertain`/`command` сняты с
   сохранением `epoch`/`generation`, `lab-provision enable 501`.

Правило «непонятный исход изменяющей команды — карантин слота до ручной сверки» верное и остаётся. Плохо три вещи:
тайм-аут 45 с слишком мал для команд запуска; менеджер не заметил карантин и пустил студента работать; узнали об этом
только при остановке, через 10 минут ожидания, а в ошибке слот назван свободным.

## 2. Агент (`agent/agent.py`), версия 1.2.1

1. **Тайм-аут команд запуска внутри CT** — настройка `LAB_GUEST_ACTION_TIMEOUT`, по умолчанию **120 с**, пределы
   30–600 (вместо зашитых 45 с). Остальные тайм-ауты `pct` не меняются.
2. **Бюджет маршрута `start`**: `pct start` (120 с) + число действий × `LAB_GUEST_ACTION_TIMEOUT`. Агент сообщает его в
   `GET /capabilities` (🆕 `start_budget_seconds`), чтобы менеджер мог сверить свой тайм-аут (§3.4).
3. В ответе `504 PCT_TIMEOUT` — 🆕 поле `command` (`start`, `exec`, `stop` …), как в отметке fencing. Текст ответа
   по-прежнему без вывода команды.
4. Правило карантина **не ослабляется**: таймаут любой изменяющей команды, в том числе `pct exec`, ставит
   `uncertain`; `claim` его не снимает.
5. README и `manager/docs/AGENT_REQUESTS.md` (ответ агента), версия в `agent.py` и заголовке README.
6. Тесты: тайм-аут из настройки, пределы, бюджет в `capabilities`, `command` в ответе 504, карантин после тайм-аута
   `exec` по-прежнему ставится.

## 3. Менеджер (`lab_manager/`), версия 0.11.1

1. **Карантин — отдельная ошибка, не «подожди».** В `agent_client.py` 🆕 `AgentQuarantined` (подкласс
   `AgentUncertain`, чтобы прочий код не сломался) для `COMMAND_UNCERTAIN` и `PCT_TIMEOUT`: агент записал отметку,
   сама она не пройдёт. Сетевые сбои, `503 PCT_UNAVAILABLE`, `STORAGE_UNAVAILABLE`, `FENCE_STORAGE_ERROR` остаются
   `AgentUncertain` (`Wait`, как сейчас).
2. **`ct_start`**: `AgentQuarantined` от `agent.start` — сессия сразу завершается с 🆕 кодом `SLOT_QUARANTINED`,
   сообщение студенту «Слот требует проверки администратором. Повторный запуск станет возможен после проверки —
   сообщите преподавателю», `slot_state: maintenance`, `retryable: false`. Дальше `slot_ready` не идёт. Событие
   `slot_quarantined` с `vmid`, `node`, `command`. Слот держит `student_key` (каталог может быть примонтирован на запись
   в работающем CT), поэтому повторный запуск того же студента до сверки даёт `STUDENT_DIR_BUSY` с тем же текстом;
   «откроется в другом слоте» не обещаем.
3. **Любой другой этап**: `AgentQuarantined` в общем обработчике (`orchestrator.py`, ветка `except (AgentError,
   SlotError)` с `ownership_wait`) не ждёт тайм-аута этапа, а завершает сессию тем же `SLOT_QUARANTINED`. Очистку,
   которой нужен агент (`ct_stop`, `ct_reset`, `ct_park`), менеджер не начинает — агент её всё равно отклонит.
   Слот — `maintenance` и удерживается за студентом (`student_key` не снимается: каталог может быть примонтирован), как
   при неподтверждённой остановке (`docs/pilot-hardening/README.md`, «Разбор неизвестного исхода»).
4. **Тайм-аут запуска**: `AGENT_START_TIMEOUT` по умолчанию — не меньше бюджета агента (§2.2) с запасом 60 с. Бюджет
   агента считается для трёх действий (максимум запроса): 120 + 3 × 120 = 480 с, плюс 60 с запаса и правка монтирований
   (85 с) — по умолчанию 720 с, нижний предел 540 с. Если агент сообщает
   `start_budget_seconds` больше настройки — предупреждение в журнале при старте менеджера и в `lab-manager-admin check`.
   Предел этапа `ct_start` (`agent_start_timeout * 2`) остаётся.
5. **Слот никогда не `free`, пока CT не остановлен и не припаркован.** Проверить пути `_fail` и
   `_check_stage_timeout`: у `TIMEOUT` на этапах с монтированием (`MOUNTED_STAGES`) в ошибке не должно быть
   `slot_state: free`, если очистка не дошла до конца. Сейчас в этом случае первая ошибка несёт `free`.
6. **Что видит студент при ожидании.** (Сделано: `status_message` уходит в объекте сессии как есть, CONTRACTS §2.3,
   просьба плагину не нужна.) `status_message` с причиной `ownership_wait` есть в сессии; убедиться, что он
   уходит плагину в объекте сессии (`CONTRACTS.md` §2.3), а не только «Остановка устройств…» по этапу. Если контракт
   этого не даёт — записать просьбу плагину в `docs/PLUGIN_REQUESTS.md`, сам плагин не менять.
7. `CONTRACTS.md` (§2.5 коды: `SLOT_QUARANTINED`; §5: `start_budget_seconds`, `command`), README, версия,
   `compatibility.components`, `SOURCE_FILES` при новых файлах.
8. Тесты (поддельный агент `tests/fakes.py`): `start` → `504 PCT_TIMEOUT` → `SLOT_QUARANTINED`, слот `maintenance`,
   `slot_ready` не наступает; `start` → разрыв соединения → `Wait`, потом успех; карантин на `lab_stop` → сразу
   `SLOT_QUARANTINED`, без 10 минут ожидания; слот не становится `free` ни в одном из этих путей.

## 4. `install/`: сверка вручную, но по шагам

Автоматического «забыть неизвестный исход» по-прежнему нет. Есть 🆕 `lab-provision reconcile <VMID>` — то, что
оператор делал руками в §1.4, с проверками:

1. Запускается на ноде слота от root. Без `--yes` только показывает, что сделает.
2. Отказ, если: CT не `stopped` (сначала `pct shutdown <VMID> --timeout 120`); есть процессы `pct` или `lxc-*` с этим
   VMID, кроме монитора остановленного CT; в отметке нет `uncertain`/`inflight` (сверять нечего); слот в менеджере не
   `maintenance` и не `failed`.
3. Печатает отметку, сохраняет копию рядом (`/root/lab-fence-<VMID>-<время>.json`), снимает `inflight`, `uncertain`,
   `command`, **оставляя `epoch` и `generation`**, пишет атомарно (временный файл, `fsync`, `rename`), права 0600.
4. Подсказывает следующий шаг: `lab-provision enable <VMID>`.
5. `install/TROUBLESHOOTING.md` — раздел `COMMAND_UNCERTAIN` по этому случаю: признаки (`ownership_wait`, нет
   `ct_started` в `lab-db events`), команды из §1.4 и `reconcile`.
6. Тесты: `bash -n`; логика правки отметки — функцией, которую можно проверить на поддельном каталоге (сохранение
   `epoch`/`generation`, отказ без `uncertain`, отказ при работающем CT через заглушку `pct`).

## 5. Проверка на стенде (владелец)

1. Обновить агента на нодах (`$P agent`), менеджер (`$P manager`), `$P check`.
2. Обычный запуск лабы: в `lab-db events` есть `ct_started`, между `ct_start` и `slot_ready` меньше бюджета.
3. Искусственно: на одном слоте временно `LAB_GUEST_ACTION_TIMEOUT=30` и медленная команда запуска (например,
   `sleep 40` в начале `lab-slot-init` в шаблоне тестового слота) — запуск даёт `SLOT_QUARANTINED` сразу, студент
   видит сообщение («повторный запуск станет возможен после проверки — сообщите преподавателю»), слот `maintenance`;
   повторный запуск того же студента даёт `STUDENT_DIR_BUSY` с тем же текстом, другой студент работает на другом слоте;
   `$P check` называет слот (VMID, сессия, студент, команда из отметки агента) и шаги `pct shutdown` → `reconcile` →
   `enable`. Затем `pct shutdown`, `$P reconcile <VMID>`, `--yes`, `$P enable <VMID>` — слот
   снова работает. Вернуть настройку и шаблон.
