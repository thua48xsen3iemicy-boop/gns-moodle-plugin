# Подготовка неизменяемых выпусков

Этот инструмент готовит пакет на CephFS, проверяет его и публикует под новым ID.
Он не выбирает выпуск для Manager/Slot, не устанавливает Agent на узлы, не
мигрирует БД и не перезапускает службы. Старые команды `lab-provision` продолжают
работать; применение нового пакета — отдельный согласованный этап.

## Команды оператора

Используйте доверенный чистый checkout инструмента вне проверяемых выпусков.
Вызов через `lab-provision` использует Python в isolated mode (`-I -B`) и
обрабатывает `release` до чтения production lab.conf. Build требует root на узле
PVE; verify/list не требуют root при наличии чтения, не используют сеть/pct и
не читают production конфигурацию/секреты. Системные Python, findmnt и сам
проверяющий инструмент входят в доверенную среду оператора. Для host-инструмента
нужен системный Python 3.11+. Dispatcher и host-команды используют абсолютные
системные пути, чтобы PATH не выбирал executable из проверяемого пакета.
Сам launcher закрепляет `/bin/bash` в shebang, в том числе при прямом запуске.

```sh
P=/path/to/trusted-clean-checkout/install/lab-provision

# source_repo из build-конфига: отдельный root-owned checkout, не рабочий gns3-ro.
# Нужный commit уже должен быть в его Git object database.
$P release build r20261021_01 --ref FULL_40_HEX_COMMIT --config /etc/lab-release-build.json
$P release verify r20261021_01 --root /mnt/pve/cfs/gns3-releases
$P release list --root /mnt/pve/cfs/gns3-releases
```

ID: буквы/цифры, `_`, `-`, максимум 64 символа, начинается с буквы/цифры.
`--ref` принимает полный commit SHA, не branch/tag/сокращение. Экспорт идёт из
Git blobs; dirty и untracked файлы source checkout не попадают в пакет.
Неизвестный путь в поставляемых деревьях требует обновления явного allowlist
инструмента, а не автоматического включения. Никаких `git pull` в рабочем checkout.
Checkout самого сборщика должен быть чистым; его SHA отличается от SHA продукта
и фиксируется отдельно. Пример конфига намеренно неработоспособен до заполнения.

Успешные команды выводят JSON и код 0. Ошибка — код 1; list показывает повреждённый
каталог как `INVALID`, исправные как `READY`, скрытые staging/locks не перечисляет.
verify ничего не исправляет. Сохраните `manifest_sha256` в независимом журнале
выпусков, если нужен внешний эталон целостности.

## Сборочная среда

Достаточно существующего узла PVE с зарезервированными ресурсами и двумя
выделенными unprivileged LXC. Отдельный физический узел рекомендуется для
изоляции, но не обязателен. Builder VMID исключаются из учебной выдачи, agent
VMID ranges, HA, replication и autostart; шаблоны также не входят в выдачу.
Оператор проверяет это до заполнения конфига: tag не доказывает назначение CT.
Сборщик не меняет размещение/бюджеты Manager и не освобождает учебные ресурсы.

Заранее подготовьте два известных чистых immutable шаблона:

- Ubuntu 24.04, `/usr/bin/python3.12`, python3.12-venv, ca-certificates,
  util-linux/findmnt/runuser, dpkg-query; пользователи `gns3`, `lab-manager`
  с ненулевым UID. GNS3 и PostgreSQL для сборочных импортов не требуются.
- Debian/Python той архитектуры и ABI, что целевые PVE-узлы, с python3-venv,
  ca-certificates и теми же системными инструментами; smoke Agent использует
  непривилегированного `nobody`. Python/системные библиотеки целевого узла —
  отдельный профиль совместимости, Ubuntu venv для него не используется.

Шаблоны root-owned, unprivileged: 1, onboot: 0, template: 1, единственный tag
`labrelease-template`. Нет venv продукта, ключей, конфигов стенда, SQLite,
студенческих данных, passthrough, нестандартного idmap, features, hooks, bind
mounts или дополнительных сетевых интерфейсов. Не делайте шаблон из рабочего CT.
Шаблон не должен содержать изменяемых остатков предыдущих сборок.

В копии `lab-release-build.json.example` укажите разные template/builder VMID,
отпечатки, совместимость, cores/cpulimit, RAM/swap, верхний размер rootfs и
конечные лимиты I/O. Rootfs клона не увеличивается: слишком большой шаблон
отвергается. Шаблон должен уже содержать проверенный `lxc.cgroup2.io.max`;
инструмент сверяет его с конфигом, фактическим cgroup и устройством rootfs CT.
Формат: `MAJOR:MINOR rbps=N wbps=N riops=N wiops=N`, все N положительные.
Хранилище должно обеспечивать этот лимит на устройстве клона. Если номера устройств
меняются при клонировании или backend не поддерживает такое ограничение,
проверка откажет; не подставляйте фиктивное устройство для прохождения проверки.
Проверка поддержки выбранного backend относится к стендовой приёмке.

`build_bridge` — существующая отдельная сеть с DHCP, доступом к HTTPS-индексу
wheels и запретом доступа к API/сетям стенда. Firewall/ACL готовит оператор;
`isolated_network_confirmed: true` — его явное подтверждение, а не автоматический
сетевой аудит. Build подключает только net0 с firewall=1; секреты узла, proxy
credentials и production environment в гостя не передаются. Индекс HTTPS без
встроенных логина/пароля/query; CA доверие уже настроено в шаблоне.

Для отпечатка конфигурации шаблона используется UTF-8 вывод
`pct config TEMPLATE --current 1` без начальных/конечных whitespace:

```sh
pct config 9701 --current 1 | python3 -I -c 'import hashlib,sys; print(hashlib.sha256(sys.stdin.read().strip().encode()).hexdigest())'
```

Runtime fingerprint можно получить доверенным helper в отдельном пробном клоне
чистого шаблона, затем удалить пробный CT. Пример команды **внутри этого клона**:

```sh
/usr/bin/python3.12 -I -B /path/to/trusted/release-builder.py runtime
```

Перенесите в runtime-конфиг все поля кроме `python_full` (оно записывается в
отчёт автоматически). `packages_sha256` — SHA256 отсортированных строк
`dpkg-query -W -f='${binary:Package}=${Version}\n'`, с завершающим newline.
Это fingerprint builder, не список пакетов самого PVE-хоста. Сопровождающий
подтверждает совместимость Agent с Python/ABI/системными библиотеками узла.
`template_image_sha256` — записанный сопровождающим SHA256 исходного чистого
образа/среза, из которого подготовлен immutable template. Автоматически
сверяются config fingerprint и runtime, а происхождение template из этого
образа подтверждает оператор (`image_provenance: maintainer_attested`), не
полное хеширование rootfs. Root/Ceph и подготовленные шаблоны доверенные.

Пути `ceph_root`, `release_root`, `source_repo` должны быть каноническими и
root:root, без symlink, writable group/other или extended POSIX ACL у предков.
Release root — новый каталог, например `/mnt/pve/cfs/gns3-releases`, на самом
CephFS, отдельно от gns3-ro, secrets, images и student data. Сам build-конфиг
без секретов, root-owned, без записи group/other. Не используйте рабочий checkout
как source_repo. Не передавайте данные production lab.conf.

## Жизненный цикл и зависимости

Перед каждой попыткой создаются **новые полные клоны** шаблонов, не обновление
старого rootfs. Занятый builder VMID вызывает отказ; автоматического удаления
чужого/старого CT нет. Записываются UUID попытки, hostname и rootfs volume ID;
изменять можно только CT с совпадающими признаками на текущем узле.
Локальные locks VMID исключают гонку сборщиков на одном узле; место сборки этих
VMID фиксировано оператором, внешние PVE операции во время сборки исключены.

Manager и Slot получают venv сразу по будущим путям
`/srv/gns3-ro/{manager,slot}/venv`. Source bind RO; RW разрешён только новым
venv и dependency output staging. После сборки права возвращаются host root,
mounts становятся RO, smoke идёт под непривилегированными пользователями.
Ни один учебный CT не получает RW mount к staging или опубликованному пакету.
У Agent тестовый venv создаётся по `/opt/lab-node-agent/venv`, проверяется RO,
затем удаляется с временными ресурсами. В пакет Agent входят wheels/lock,
а не переносимый venv; установка из них будет отдельным этапом.

Requirements и constraints читаются из выбранного коммита. В соответствующем
runtime разрешается полный граф зависимостей; скачиваются только wheels, без
sdist/build hooks. Из wheel metadata и SHA256 получается полный pinned lock.
Установка идёт заново с `--no-index --require-hashes --find-links`, затем
`pip check`, проверка installed distributions, путей модулей/venv/shebang и
импортов. Manager включает gateway dependencies. pip/bootstrap в venv поставляется
с Python-venv шаблона и покрывается inventory; для Agent bootstrap — часть
заявленной внешней ОС. Кэши и bytecode в опубликованный пакет не включаются.

Все builder CT останавливаются, mounts снимаются, CT/rootfs удаляются до
публикации. Проверяется отсутствие оставшихся volumes VMID через pvesm.
Ошибка удаления блокирует публикацию. Следующая попытка вновь клонирует чистый
template; её пакеты, venv, rootfs и временные файлы не наследуют прошлую попытку.

## Целостность и публикация

Manifest `gns3lab.release/1` фиксирует SHA/tree продукта, отдельную version/SHA
сборщика и хеши helpers, профили/отпечатки шаблонов и runtime, версии компонентов,
миграции, совместимость, wheels/locks, результаты проверок и точный inventory
дерева: содержимое, типы, режимы файлов и допустимые venv links.
Исполняемые файлы и все поставляемые зависимости охвачены SHA256. Добавленный
неизвестный файл также вызывает отказ. Сам manifest исключён из собственного
inventory; его digest выводится отдельно. Owner root:root, файлы 0444/0555,
директории 0555; устройства, FIFO, hardlinks и произвольные symlink запрещены.

`slot/release.py` и `slot/release.json` сохраняются из исходного коммита. Их
согласованность проверяется при build в изолированном builder. Внешний manifest
охватывает вложенный как файл, его files дополнительно сравнивается с проекцией
полного inventory по политике доверенного инструмента `slot-0.5-file-selection/1`.
Устаревший Slot manifest — ошибка, автоматического seal нет. Следует исправить
исходный commit установленным процессом подготовки Slot, затем выбрать новый SHA.

**verify/list не импортируют и не запускают код пакета**, даже его release.py,
venv, entrypoints, hooks или `.pth`. Они не выбирают правила из исполняемого файла
внутри пакета. Неизвестные schema/policy отвергаются. Отчёты smoke checks —
сохранённые результаты сборки, проверка не выполняет эти импорты повторно и не
утверждает готовность живого стенда. PostgreSQL требуется ровно по текущему
набору SQL (для исходного среза 006); миграции не выполняются. Совместимость
Slot/Agent state и откат заявляет сопровождающий; `not_assessed` не обещает откат.

Хеши не подтверждают подлинность поставщика. Администратор с правом записи может
заменить и код, и manifest. Внешний доверенный digest/канал поставки необходим
для защиты от такой подмены; PKI/signing этим этапом не вводится.

ID резервируется атомарным mkdir `.locks/ID`. До готовности всё находится только
в `.staging/ID.UUID`. Публикация — `renameat2(RENAME_NOREPLACE)` на том же CephFS,
после проверок, удаления builders и fsync файлов/каталогов. Существующий final,
включая пустой каталог, не заменяется. Неподдерживаемый NOREPLACE — ошибка;
fallback на перезаписывающий rename/mv отсутствует. Конкретные kernel/CephFS
обязательно проверить двумя клиентами на стенде.

## После прерывания

Сохраните исходную ошибку и путь `/var/lib/lab-release-build/UUID.json`, показанный
build. Recovery metadata root-only содержит host paths и только ресурсы попытки,
не production секреты. `.locks/ID/owner.json` связывает ID со staging/UUID/узлом.

Отказ helper передаётся JSON формата `gns3lab.builder-error/1`: `component`,
`stage`, стабильный `code`, категория `reason`, числовой `returncode` при наличии
и короткое `detail`. Например, download/install/smoke различаются кодами
`WHEEL_DOWNLOAD_FAILED`, `WHEEL_INSTALL_FAILED`, `SMOKE_CHECK_FAILED`.
Пояснения берутся из фиксированного каталога; текст исключения, stdout/stderr
pip, URL, аргументы и окружение не выводятся и не сохраняются. Host принимает
не более 4096 байт JSON с известными полями/кодами и заново формирует detail
из своего каталога; неподдерживаемый ответ даёт `BUILDER_PROTOCOL_ERROR`.

Первичная диагностика сохраняется с fsync в поле `failure` recovery record
**до очистки CT** и остаётся после их удаления. Дополнительная ошибка очистки
пишется отдельно как `cleanup_failure`, не заменяя failure. Если записать
первичную диагностику не удалось, автоматическое удаление builders блокируется;
нужно сначала сохранить безопасный отчёт и выполнить ручной recovery.

1. Подтвердите на узле и в PVE tasks, что прежний сборщик и все pct/LXC операции
   завершились. Timeout/убитый pct-клиент не доказывает завершение фоновой задачи.
   Запись `cloning`/`uncertain` требует ручного разбора, не автоматического retry.
2. Сверьте UUID, hostname, VMID, rootfs/volumes и конфигурацию CT. Не удаляйте CT
   при несоответствии или неопределённом происхождении. Не трогайте шаблоны и
   рабочие CT. Остановите только подтверждённые builders, снимите staging mounts,
   удалите их одноразовые rootfs/volumes и убедитесь, что они действительно исчезли.
3. Если final `ID/` уже существует, выполните verify. Не удаляйте и не собирайте
   final заново: сбой после rename/fsync может означать успешную публикацию с
   неопределённой долговечностью. При INVALID — остановиться и расследовать.
4. Только после исключения активных процессов/mounts удалите подтверждённые
   `.staging/ID.UUID`, `.staging/.work-UUID` и stale `.locks/ID`. Режимы файлов
   staging могли уже стать RO; восстановление выполняет доверенный host root.
   Recovery record сохраняйте для аудита. Команды массового удаления по glob не
   используйте: сначала сверяйте точные пути с записью попытки.
5. Повторный build создаёт новый staging и новые чистые клоны. Автоматического
   resume старого venv/rootfs и takeover stale lock нет. Для нового выпуска
   используйте свободный ID; прежний опубликованный пакет остаётся неизменным.

## Граница локальной проверки

Тесты install используют локальную Linux FS и модель PVE; проверки владельца
в fixture моделируются UID/GID непривилегированного исполнителя. В CLI нет
отключения CephFS/root проверок. Локальный NOREPLACE и два процесса не доказывают
поведение CephFS, LXC, storage IO limits, UID mapping или совместимость wheel ABI.
Стендовые проверки перечислены в PLAN/RESULT и должны выполняться отдельно на
выделенных builders без изменения работающих учебных компонентов.
