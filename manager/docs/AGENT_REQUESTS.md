## 1. Пути в слоте — сделано

Ниже исходный запрос. Агент сделал больше: `mp1` теперь `/opt/gns3/projects` (каталог проектов
GNS3 слота), а не `/srv/student`. Менеджер принимает именно это.

Lab Slot запускается только из `/srv/gns3-ro/slot`: это требуют `slot/run.py`
(`SLOT_PATH_MISMATCH`), `slot/lab-slot.service` и путь venv `/srv/gns3-ro/slot/venv`.
Агент сейчас монтирует код в `/opt/slot`, и в таком слоте служба не стартует.

Нужно поменять только цель `mp0`, источник остаётся прежним (`<LAB_CEPH_ROOT>/slot[/<revision>]`, RO):

```diff
-        "--mp0", f"{code_path},mp=/opt/slot,ro=1,shared=1",
+        "--mp0", f"{code_path},mp=/srv/gns3-ro/slot,ro=1,shared=1",
```

То же место в `agent/README.md` («Mounts always have host path → guest path mapping») и в
тестах агента.

Venv в `<LAB_CEPH_ROOT>/slot` собирается под тем путём, который видит гость, то есть
`/srv/gns3-ro/slot/venv` (`slot/README.md`, «Подготовка и запуск из фиксированного RO-каталога»).

## 2. Коды ошибок

Сейчас ошибки приходят строкой `{"detail": "..."}`, и менеджеру приходится различать случаи 409
и 422 по тексту. Прошу отдавать `{"detail": {"code": "...", "message": "..."}}` с теми же
HTTP-статусами, что сейчас. Ошибки валидации запроса (FastAPI, 422 со списком) можно не трогать.

| HTTP | `code` | Когда | Что делает менеджер |
|---|---|---|---|
| 403 | `VMID_OUT_OF_RANGE` | vmid вне `LAB_VMID_MIN..MAX` | сессия `failed`, слот `failed` (настройка) |
| 403 | `NOT_LAB_SLOT` | нет тега `labslot` | то же |
| 403 | `PRIVILEGED_CT` | нет `unprivileged: 1` | то же |
| 404 | `CT_NOT_ON_NODE` | CT не на этом узле | ищет узел заново через Proxmox API |
| 409 | `SLOT_BUSY` | занята блокировка CT | ждёт и повторяет |
| 409 | `NOT_STOPPED` | mounts/start на запущенном CT | перечитывает `status` |
| 409 | `PCT_FAILED` | `pct` вернул ошибку (в `message` — вывод pct) | старт: сессия `failed`; shutdown: `force=true` |
| 422 | `SOURCE_MISSING` | нет `students/<key>` (или `slot/<revision>`) | сессия `failed` с понятным текстом, слот свободен |
| 409 | `STUDENT_DIR_OWNER` | у существующего `students/<key>` другой владелец | сессия `failed` сразу, без ожидания |
| 422 | `SOURCE_UNSAFE` | симлинк, предок не под root, ACL, не на CephFS-монтировании | сессия `failed`, слот `failed` |
| 422 | `SNAPSHOT_MISSING` | у слота нет снимка чистого состояния (`POST /slots/{vmid}/reset`, агент 1.2) | уборка не удалась: слот `maintenance`, оператор делает `lab-provision snapshot` |
| 422 | `SNAPSHOT_UNSAFE` | в снимке нет `unprivileged: 1` или тега `labslot` (откат оставил бы слот, которым агент не управляет) | то же |
| 503 | `STORAGE_UNAVAILABLE` | CephFS не смонтирована, не проверить ACL, нет конфига CT | ждёт, перечитывает `status` |
| 503 | `PCT_UNAVAILABLE` | `pct`/`findmnt` не запускается, непонятный вывод | то же |
| 504 | `PCT_TIMEOUT` | команда не уложилась в таймаут | агент уже поставил `uncertain` (карантин): менеджер завершает сессию `SLOT_QUARANTINED`, а не ждёт |

**Агент 1.2.1.** В теле `504 PCT_TIMEOUT` — 🆕 `detail.command`: подкоманда `pct` (`start`, `exec`, `stop`, …), как
`command` в отметке fencing. Тайм-аут одного действия запуска внутри CT (`pct exec`) — `LAB_GUEST_ACTION_TIMEOUT`,
по умолчанию 120 с (30–600) вместо 45 с. 🆕 `GET /capabilities` →
`{"version", "start_budget_seconds", "guest_action_timeout_seconds"}`; `start_budget_seconds` =
120 + 3 × `LAB_GUEST_ACTION_TIMEOUT` (три действия — максимум запроса; правка монтирований не входит).
Карантин не ослаблен: тайм-аут любой изменяющей команды ставит `uncertain`, `claim` его не снимает.

Клиент менеджера (`lab_manager/agent_client.py`, `CODES`) уже понимает эти коды, а без них
разбирает текст. Поэтому коды можно вводить постепенно, без синхронного релиза.

## 3. Создание каталога студента — сделано

В ветке есть `PUT /students/{student_key}` (коммит 7688ee7). Менеджер вызывает его на этапе
`student_dir`, перед стартом CT, у агента узла выбранного слота. Как менеджер разбирает ответы:
- 200 `{"student_key", "ready": true}` — каталог готов, менеджер переходит к старту;
- 409 «different owner» — ждёт и повторяет: README агента допускает временный 409 при
  одновременном создании. Через 120 с сессия завершается с `TIMEOUT`, слот остаётся свободным
  (CT не трогался);
- 422 — сессия `failed` с кодом `STUDENT_DIR_REJECTED`, слот свободен;
- 503 (например, не заданы `LAB_STUDENT_HOST_UID/GID`) — ждёт до того же таймаута.

С кодами ошибок (п. 2) постоянный неверный владелец (`STUDENT_DIR_OWNER`) и временный 409
можно было бы различать, и менеджер не ждал бы 120 с зря. Предлагаю код `STUDENT_DIR_OWNER`
для этого случая.

## 5. Шаблон слота и `lab-slot-init` — новое

Выяснилось при сверке консольной связки (плагин → шлюз → слот) и `readyz` слота. Это не API агента,
а шаблон LXC и гостевой скрипт `agent/guest/lab-slot-init`. Кто из нас делает каждый пункт, решает владелец.

1. **`.slot-locks` в каталоге студента.** Каталог студента смонтирован как `/opt/gns3/projects`,
   а `/v1/readyz` слота проверяет `/opt/gns3/projects/.slot-locks` и сам его не создаёт (создаёт
   только deploy). Менеджер ждёт готовности до deploy, поэтому со свежим каталогом слот никогда не
   станет готов. Предложение — строка в `lab-slot-init` перед стартом службы:

   ```sh
   /usr/bin/install -d -o gns3 -g gns3 -m 0700 /opt/gns3/projects/.slot-locks
   ```

   Действие идемпотентно и не трогает проекты. Одновременного доступа к каталогу нет: у студента
   одна живая лаба (решение владельца), так что блокировки здесь нужны только самому слоту.

2. **Уникальные секреты у каждого CT.** `SLOT_API_TOKEN` и `SLOT_CONSOLE_TOKEN` лежат в
   `/etc/lab-slot/slot.env` внутри CT. При клонировании слотов из шаблона они окажутся одинаковыми,
   и утечка одного токена откроет все слоты. Нужен шаг «первый запуск клона»: сгенерировать оба
   токена (`openssl rand -hex 32`) и передать их менеджеру (`slots.json`) и шлюзу (`GW_SLOTS`).
   Кто это делает — шаблон, `init_slot` с отдельным разрешённым действием или администратор при клонировании?

3. **`SLOT_LISTEN_HOST`.** По умолчанию слот слушает `127.0.0.1`, а менеджеру и шлюзу нужен адрес
   CT (`address` в `slots.json` = ключ в `GW_SLOTS`). Значение своё у каждого клона, тот же вопрос, что в п. 2.

4. **Сеть.** Порт 8080 слота открыт только для менеджера и шлюза (firewall CT или Proxmox), порт
   8443 агента — только для менеджера. Консольный трафик агента не касается.

## 4. На будущее (не срочно)

Результаты автопроверок нельзя держать внутри `students/<key>`: каталог принадлежит гостю, и гость
может переименовать или удалить любой подкаталог. Планируется отдельное дерево
`<LAB_CEPH_ROOT>/results/<key>/`. Если слоту понадобится читать результаты, нужна будет третья
фиксированная точка монтирования (RO), например `mp2` → `/srv/results`. Пока не требуется.

## 6. Снятие слоя образа — 🆕 предложение

Дизайн — `docs/derived-images/DESIGN.md`, контракт — CONTRACTS §2.8, §5. Агент — единственный, кто может писать в
`IMAGES_DIR` (в слоты он монтируется RO).

`GET /capabilities` получает поле `"images_capture": true`. Без него менеджер маршрут не вызывает.

`POST /images/capture`, те же mTLS и правила строгости (`extra="forbid"`):

```json
{"student_key": "a1b2…", "project_id": "0b6c9d3e-…", "node_name": "SRC",
 "base_file": "debian12.qcow2", "base_sha256": "sha256:…",
 "image_file": "d-web-srv.qcow2", "flatten": false, "max_bytes": 8589934592}
```

Что делает агент:
1. Каталог `students/<student_key>` не подключён ни к одному CT узла (`mp1`), иначе `409 STUDENT_DIR_BUSY`.
2. Находит ноду по имени в `<project_id>/*.gns3` (JSON), диск — `project-files/qemu/<node_id>/hda_disk.qcow2`.
   Никаких путей от клиента; симлинки и выход за каталог студента — `422 CAPTURE_PATH_UNSAFE`. Нет файла —
   `404 CAPTURE_NODE_MISSING`.
3. `qemu-img info --backing-chain -U --output=json`: формат `qcow2`, первый backing — `base_file` (по имени), sha256 базы
   совпадает с `base_sha256`; иначе `422 CAPTURE_BASE_MISMATCH`. Размер больше `max_bytes` — `422 CAPTURE_TOO_LARGE`.
4. Копирует во временный файл `IMAGES_DIR/QEMU/.incoming/<uuid>` (тот же том — для атомарного `rename`).
   `flatten: false` — `qemu-img rebase -u -F qcow2 -b <base_file>` (относительное имя); `flatten: true` —
   `qemu-img convert -O qcow2` всей цепочки. Затем `qemu-img check`.
5. Пишет `<image_file>.md5sum` (формат GNS3), `chmod 0444`, `rename` в `QEMU/<image_file>`; файл уже есть —
   `409 IMAGE_EXISTS` (агент ничего не перезаписывает никогда).

Ответ `200`: `{"image_file", "size", "virtual_size", "sha256", "md5", "backing": "debian12.qcow2" | null}`.
Операция долгая (копирование гигабайтов по CephFS): тайм-аут — `LAB_CAPTURE_TIMEOUT` (по умолчанию 900 с), он же в
`GET /capabilities` (`capture_timeout_seconds`), чтобы менеджер сверил со своим ожиданием, как `start_budget_seconds`.
Повтор после обрыва: временные файлы `.incoming` старше тайм-аута агент удаляет сам.
