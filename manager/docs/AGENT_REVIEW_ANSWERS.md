## 1. Единый контракт путей

| | |
|---|---|
| Политика | Пути внутри слота — как в агенте 6a735df: код `<LAB_CEPH_ROOT>/slot[/<rev>]` → `/srv/gns3-ro/slot` RO, каталог студента `<LAB_CEPH_ROOT>/students/<key>` → `/opt/gns3/projects` RW (RO у освобождённого слота). Документы менеджера обновлены (`AGENT_REQUESTS.md` §1, `DESIGN.md` §§3, 5, 6.1, `CONTRACTS.md` §§4.2, 5, 7, 8, `storage.py`) |
| Сделано в менеджере | Проверка монтирований теперь точная: `mp0` и `mp1` сравниваются с полным ожидаемым источником под `LAB_CEPH_ROOT` из конфига менеджера, с целью `mp=` и режимом `ro`. Совпадения суффикса недостаточно. Проверяется после старта, при восстановлении (CT уже `running`) и после парковки |
| Тесты | отрицательные: чужой студент; верный суффикс под чужим root; верный источник, но цель `/srv/student`; RO у студента; код в `/opt/slot`; код RW. Плюс сверка с настоящим `agent.py`: то, что пишет `pct set`, проходит проверку, а заглушка после парковки — нет (как студент) |
| `student-state` | Предлагаю не вводить новую точку монтирования: проекты остаются в `/opt/gns3/projects`, а переносимое состояние лабы слот кладёт внутрь того же монтирования (например, `/opt/gns3/projects/.lab-slot/`). Решение и миграцию определяет слот; менеджер включит межслотовый `resume` только по объявленной слотом возможности `student-state` |
| `.slot-locks` | Создаёт шаблон гостя: `lab-slot-init` перед стартом службы выполняет `install -d -o gns3 -g gns3 -m 0700 /opt/gns3/projects/.slot-locks` (это идемпотентно). Альтернатива — агент при `PUT /students`. Решает владелец; менеджер в обоих случаях ничего не передаёт |
| Приёмка | на PVE: после `start` в госте код в `/srv/gns3-ro/slot`, проекты в `/opt/gns3/projects`, `.slot-locks` есть, `/v1/readyz` = ready; `GET /lxc/{vmid}/config` проходит проверку менеджера в том виде, в каком его нормализует Proxmox |

## 2. Переносимость состояния и параллельный доступ

| | |
|---|---|
| Политика | `LAB_PERSISTENCE=fresh` по умолчанию. Межслотовый `resume` — только при возможности слота `student-state`; ни наличие монтирования, ни версия схемы deploy его не включают. Существующие данные при ошибках не удаляются никем |
| `lab_revision` / `code_revision` | разные сущности; `CONTRACTS.md` §4.2 это явно фиксирует. `code_revision` — один компонент пути по правилам агента (`SLOT_CODE_REVISION` проверяется тем же регулярным выражением), `sha256:` туда не попадает |
| Одновременные сессии одного студента | сейчас менеджер допускает одну живую сессию на (сайт, студент, активность), то есть две активности дают два слота с одним RW-каталогом. Предложение: одна живая сессия на (сайт, студент), пока слот не гарантирует безопасный совместный доступ к каталогу. **Решает владелец** (меняет поведение `POST /sessions` для второй активности: `409 session_conflict`) |
| `site_slug` | уникальность между сайтами проверяется при загрузке конфига; длина ключа проверяется (`student_key` ≤ 64). Политика: slug после появления данных не меняется — это записано в README как правило эксплуатации; смена slug означает новые каталоги и рабочие копии, автоматического переноса нет |
| Приёмка | второй слот при `fresh` никогда не открывает чужой проект; `resume` без `student-state` даёт понятный отказ, данные целы |

## 3. Ресурсы и мониторинг

| Вопрос | Ответ |
|---|---|
| 1. Владелец лимитов | Proxmox API в менеджере (`PUT /lxc/{vmid}/config` `cores`/`memory` на остановленном CT, до вызова агента, в той же задаче сессии). Агент ресурсы не принимает и не меняет; полей `resources` в mounts/start менеджер не отправляет. Перенос в агент — только отдельным согласованным расширением с одним владельцем записи |
| 2. Единицы | `memory_mb` — MiB (× 1024² при расчёте). Swap, диск CephFS и CPU при размещении пока не учитываются; `cores` выставляется, CPU считается переподписанным. Запас хоста — `NODE_MEMORY_RESERVE_MB` |
| 3. Что резервируется | Исправлено: резерв = обещанная память лабы минус текущее потребление CT (`mem` из `/cluster/resources`) для **каждого** выданного слота, независимо от `running`. Тест: запущенный CT, у которого GNS3 ещё не развернул устройства, держит остаток, и вторая лаба туда не попадает |
| 4. Атомарность | Транзакционная граница — одна транзакция выдачи в PostgreSQL (`SELECT … FOR UPDATE SKIP LOCKED`, generation), её делает единственный оркестратор (advisory lock). Ledger — таблица сессий с `resources` и `slot_node`. Показания Proxmox могут отставать; запас `NODE_MEMORY_RESERVE_MB` это покрывает. Сверка после миграции: узел CT берётся заново перед каждым вызовом агента; при миграции между выбором и стартом размещение не пересчитывается (ограничение, §6 сценарий 3) |
| 5. Leases на агенте | не вводим сейчас. Если понадобятся — отдельное расширение, TTL не останавливает CT и не освобождает память сам |
| Мониторинг | `GET /health` агента — только liveness, менеджер не считает его признаком CephFS или ёмкости. Готовность лабы определяет только `/v1/readyz` и операции слота |

## 4. Ошибки и восстановление после частичного исполнения

| | |
|---|---|
| Коды | Клиент менеджера понимает и строки, и коды (`AGENT_REQUESTS.md` §2); неизвестный код — по HTTP-статусу, консервативно (как отказ или «исход неизвестен», без повтора изменяющего действия) |
| `SOURCE_MISSING` при start | Исправлено: больше не считается «CT не тронут». Сессия идёт `ct_stop` → `ct_park`, завершается `failed` с `STUDENT_DIR_MISSING`, слот становится `free` только при подтверждённой заглушке |
| Владелец каталога | Отдельный код `STUDENT_DIR_OWNER` и временную гонку действительно не различить одним кодом. Сейчас: ограниченный повтор на этапе `student_dir` (120 с), затем `failed`, слот свободен (CT не трогался). Предлагаю агенту различать результат «каталог создан, владелец ещё не назначен» (временный) и «чужой владелец у существующего каталога» (постоянный); chown существующего дерева не делается никогда |
| 503 настройки vs storage | Согласен, нужны разные коды (`STUDENT_IDS_NOT_CONFIGURED` и `STORAGE_UNAVAILABLE`). Менеджер обрабатывает оба как «ждать до таймаута этапа» |
| Таймаут start / guest actions | Менеджер не повторяет start на запущенном CT, проверяет монтирования и затем ждёт `/v1/readyz` слота с таймаутом; действия вслепую не повторяет. Для неповторяемых действий в будущем нужен operation contract агента |
| Fencing | Генерация в БД не отменяет доставленный запрос, поэтому слот никогда не освобождается по таймауту HTTP: только после `status=stopped` и подтверждённой заглушки (или вручную оператором из `failed`/`maintenance`) |

## 5. Тайм-ауты и освобождение слота

| | |
|---|---|
| Тайм-ауты | Исправлено: start 420 с (у агента до 385 с), PUT mounts и `PUT /students` 120 с (до 85 с), stop 130 с (до 110 с); нижние пределы проверяются в конфиге. Истечение — «исход неизвестен»: состояние перечитывается, `SLOT_BUSY` (409 in progress) ведёт к ожиданию, затяжное зависание — тайм-аут этапа и `failed` для оператора |
| Неудачная парковка | Исправлено: слот становится `free` только если в конфиге CT подтверждена заглушка (`mp1` = `students/placeholder`, `ro=1`, точный путь). Иначе `maintenance`, событие `park_failed`, автоматической выдачи нет. Тест: после неудачной парковки следующий студент ждёт в `queued` |
| `placeholder` | готовит администратор (`root:root 0755`), менеджер никогда не вызывает для него `PUT /students` |
| Force stop | Исправлено: после ошибки graceful shutdown менеджер перечитывает `status`; `force=true` — только если CT всё ещё `running`, с событием `ct_hard_stop` |

## 6. Версии и совместные проверки

| | |
|---|---|
| Negotiation | Принято: правило §1.3 `CONTRACTS.md` распространено на Manager → Agent (`CONTRACTS.md` §5). Пока у агента нет `GET /capabilities`, менеджер не отправляет ничего сверх текущего API; коды ошибок не используются как признак версии |
| Совместные сценарии | Принимаю все шесть как критерии приёмки интеграции. Статус со стороны менеджера (на фейках и с настоящим `agent.py` без PVE): 1 — покрыт; 2 — покрыт (потерянный ответ на start, ошибка действия, исчезновение источника после `pct set`); 3 — конкурирующие заявки и нехватка ёмкости покрыты, миграция во время ожидания покрыта, миграция между выбором и стартом без пересчёта размещения — известное ограничение; 4 — неверный владелец и отсутствие UID/GID покрыты, два параллельных provisioning — только на стороне агента; 5 — покрыт; 6 — покрыт (`SLOT_COLD_RESUME_UNSUPPORTED`). На PVE не проверено ничего — это следующий этап, тестовый стенд |
