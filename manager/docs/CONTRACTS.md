# Форматы данных между компонентами

Документ описывает, какими структурами обмениваются плагин, менеджер, каталог лаб и Lab Slot,
и по каким правилам эти структуры расширяются. Его можно раздать разработчикам плагина и слота.

Статус: **черновик для согласования**. В каждом разделе отмечено, что уже работает (✅), а что
предлагается (🆕). Менеджер сейчас реализует только ✅; 🆕 появится после согласования, и
плагину и слоту при этом нужны свои изменения (§8).

```
Moodle (плагин) ──§2──▶ Менеджер ──§4──▶ Lab Slot
                          ▲   │
          каталог лаб ──§3┘   ├──▶ агент узла (AGENT_REQUESTS.md)
                              └──▶ шлюз консолей (SPEC §4)
```

## 1. Общие правила

### 1.1. Версии

- У каждого документа есть поле `schema` вида `gns3lab.<имя>/<целое>`: `gns3lab.session/1`,
  `gns3lab.meta/1`, `gns3lab.deploy/2`, `gns3lab.capabilities/1`.
- **Обратно совместимое изменение** — новое *необязательное* поле или новое значение в списке
  возможностей. Версия при этом не меняется.
- **Несовместимое изменение** — поле становится обязательным, меняется смысл или тип,
  поле удаляется. Тогда номер версии растёт. На переходный период получатель понимает обе
  версии, а отправитель выбирает версию по возможностям получателя (§1.3).
- Пути REST (`/api/v1`, `/v1`) меняются только при перестройке API целиком, а не при новой версии документа.

### 1.2. Неизвестные поля

| Кто получает | Как поступает с неизвестным полем | Почему |
|---|---|---|
| Менеджер (от плагина) | 400 `unsupported_field` с именем поля | плагин сразу видит, что его не поняли, а не получает молча другое поведение |
| Слот (от менеджера) | 422 (`extra="forbid"`) | слот запускает лабы, и тихо проигнорированная настройка означает неверно запущенную лабу |
| Плагин (от менеджера) | игнорирует | ответы только растут; старый плагин не должен ломаться от новых полей |
| Менеджер (от слота, агента) | игнорирует | то же |

Исключение — объект `extensions`: получатель может не понимать его содержимое и не обязан
отклонять запрос. Там живут эксперименты, пока они не стали частью версии.

Отсутствующее поле значит «не задано» (действует значение по умолчанию), `null` — «явно пусто».
Пустой список `[]` значит «точно ничего нет».

### 1.3. Возможности (capabilities, features)

Отправитель не угадывает, что умеет получатель, а спрашивает:
- плагин → `GET /api/v1/info` менеджера → `features` (§2.1);
- менеджер → `GET /v1/capabilities` слота → `deploy_schemas`, `features` (§4.1).

Новые возможности включаются по такой схеме:
1. Получатель начинает понимать новое поле и объявляет это в `features`.
2. Отправитель передаёт поле, только если возможность объявлена.
3. Если для лабы возможность обязательна (`requires`), а получатель её не объявил, отправитель
   не пытается и сообщает понятную ошибку.

Имена возможностей — короткие строки `[a-z0-9][a-z0-9.-]*`. Реестр — §7.

### 1.4. Общие соглашения

- Время — ISO 8601 в UTC с `Z`: `2026-10-17T10:00:00Z`.
- Идентификаторы: `user_id`, `instance_id`, `course_id` — числа Moodle; `session_id` — `s-` + 16
  hex-символов; `project_id`, `node_id` — UUID; `lab_ref` — `[a-z0-9][a-z0-9._-]{0,63}`.
- Ошибки менеджера: HTTP-код и `{"error": "<код>", "message": "<текст>"}` (SPEC §3).
  Ошибки слота: `{"detail": {"code", "message", …}}` или строка `detail` (`slot/README.md`).
- Тексты, которые видит студент (`status_message`), пишутся по-русски. Коды — латиницей,
  стабильны, по ним работает логика.

## 2. Плагин → менеджер

Транспорт и авторизация — SPEC §3: `Authorization: Bearer <секрет сайта>`, `X-Moodle-Site: <wwwroot>`.
Всё в этом разделе ✅ реализовано в менеджере 0.3, кроме помеченного 🆕. Ответы на просьбы плагина —
`PLUGIN_REQUESTS.md`.

### 2.1. ✅ `GET /api/v1/info`

Плагин вызывает его при сохранении настроек и кеширует ответ (MUC, например на 5 минут).

```json
{
  "schema": "gns3lab.info/1",
  "version": "0.3.0",
  "session_schemas": ["gns3lab.session/1"],
  "options": ["max_duration"],
  "features": ["consoles", "observer"]
}
```

- `options` — какие ключи `options` из §2.2 менеджер принимает;
- `features` — что плагину можно показывать: `consoles` (билеты консолей), `observer` (режим
  наблюдателя), `resume` (следующий запуск продолжает проект студента; с менеджера 0.5.1 есть
  всегда), позже `facts` (live-state), `checks` (автопроверки), `reset`.
- ✅ `images` и `lab_definitions` — есть каталог образов (§2.6) и запуск лабы по определению из
  Moodle. Только вместе с ними в ответе есть `lab_formats: ["gns3lab.lab/1"]` и `limits` сайта:
  `{"max_nodes": 30, "max_memory_mb": 16384, "max_cpus": 8, "images": "*"}` (`null` — без
  ограничения; `images` — список `id` или `"*"`). Без них плагин работает только по `lab_ref`.

### 2.2. ✅ `POST /api/v1/sessions`

```json
{
  "user_id": 42,
  "instance_id": 7,
  "course_id": 3,
  "lab_ref": "cisco-3x2",
  "options": {
    "max_duration": 90
  },
  "client": {
    "plugin_version": "2026101700",
    "moodle_release": "5.1"
  }
}
```

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `user_id` | int > 0 | да | `user.id` в Moodle; вместе с сайтом даёт `student_key` |
| `instance_id` | int > 0 | да | id записи `gns3lab` |
| `course_id` | int ≥ 0 | нет | для журнала и подсказки при конфликте |
| `lab_ref` | строка | одно из двух | эталонная лаба из `GET /api/v1/labs` |
| `lab` | объект | одно из двух | ✅ определение лабы из Moodle, `gns3lab.lab/1` (§2.6); только при `lab_definitions` в `info` |
| `options` | объект | нет | параметры **этого запуска**; только ключи из `info.options` |
| `options.max_duration` | int, минуты | нет | `maxduration` активности (SPEC §5.1); `0` или отсутствие — `DEFAULT_MAX_DURATION` менеджера; сверху ограничено `MAX_DURATION_LIMIT` |
| `client` | объект | нет | `plugin_version`, `moodle_release` (строки ≤ 64); только для журнала |

Любое неизвестное поле на любом уровне — `400 unsupported_field` с именем поля.

Кандидаты в `options` на будущее (каждый появится вместе с возможностью в `info.options`):
`reset: true` — начать лабу заново; `mode: "exam"` — пока не нужен.

Ровно одно из `lab_ref` и `lab`, иначе `400 invalid_request`. Неверное определение —
`422 lab_invalid` с `problems`, как у `POST /labs/validate` (§2.6); проверка та же.

Поведение: у студента одна живая лаба на сайте.
- живая сессия той же активности и той же лабы (`lab_ref`, или `lab_def` для определения) — `200`
  с ней (идемпотентно), `options` не применяются повторно;
- новая — `201`; после `stopped`/`failed` новый запуск всегда создаёт новую сессию, и
  `GET /sessions?user_id=&instance_id=` дальше отдаёт её;
- пока жива лаба в другой активности или с другим `lab_ref` — `409 session_conflict`:

```json
{"error": "session_conflict", "message": "У студента уже запущена другая лаба; сначала остановите её",
 "conflict": {"instance_id": 5, "course_id": 3, "lab_ref": "ospf-1", "lab_def": null, "status": "running"}}
```

### 2.3. ✅ Объект сессии (ответ)

```json
{
  "schema": "gns3lab.session/1",
  "session_id": "s-3f9a1c0d2b4e5f60",
  "lab_ref": "cisco-3x2",
  "lab_def": null,
  "status": "starting",
  "stage": "lab_wait",
  "progress": 40,
  "status_message": "Проверка устройств… 40%",
  "error": null,
  "started_at": null,
  "expires_at": null,
  "features": []
}
```

При `running` добавляются `topology`, `nodes` и, если нужно, `nodes_stale`:

```json
{
  "status": "running",
  "stage": "ready",
  "features": ["consoles"],
  "topology": {"name": "cisco-3x2-s-3f9a1c0d2b4e5f60", "topology": {"nodes": [], "links": [], "drawings": []}},
  "nodes": {"6b1f3c2e-4a7d-4e5b-9c10-000000000002": {"status": "started", "console_type": "telnet"}},
  "nodes_stale": true
}
```

| Поле | Смысл |
|---|---|
| `lab_ref`, `lab_def` | какая лаба: эталонная (`lab_def: null`) или из Moodle (`lab_ref: null`, `lab_def` — `sha256:…` из `validate`) |
| `status` | `queued` · `starting` · `running` · `stopping` · `stopped` · `failed` (SPEC §3). Новые статусы — только с новой версией `session`. После сбоя на этапах с запущенным CT сессия сначала проходит `stopping` (менеджер выключает слот), уже с `error`, затем `failed` |
| `stage` | внутренний этап (DESIGN §6.4): `wait_slot`, `ct_prepare`, `student_dir`, `ct_start`, `slot_ready`, `lab_submit`, `lab_wait`, `ready`, `lab_stop`, `lab_stop_wait`, `ct_stop`, `ct_reset`, `ct_park`; у завершённых — `stopped`/`failed`. Список может расти: незнакомый этап плагин показывает как общий текст своего `status` |
| `progress` | процент текущей операции слота, если известен; иначе поля нет |
| `status_message` | текст для студента по-русски; логика по нему не строится |
| `error` | при `failed`: `{"code", "retryable"}` (§2.5); иначе `null` |
| `features` | что доступно в **этой** сессии: `consoles` при `running`; ✅ `facts`, когда слот отдаёт факты (§2.7) |
| `topology` | формат `.gns3` с живыми `node_id`. У нод сохраняются `node_id`, `name`, `node_type`, `x`, `y`, `z`, `width`, `height`, `symbol`, `label`, `console_type`, `status`, `ports` (с `name`, `short_name`, `adapter_number`, `port_number` — как их отдаёт GNS3 2.2), `locked`; `properties` пустые, номера консоли нет. У линков — `link_id`, `nodes` (с `adapter_number`, `port_number`, `label`), `suspend`, `filters`, `link_type`, `link_style`. `drawings` — из эталона (у лабы из Moodle — пустые: рисунки у плагина). `symbol` — из эталона или каталога образов по имени ноды (GNS3 рисует ноды слота компьютерами) |
| `nodes` | статусы нод (кеш 3 с); `console_type` — `telnet` · `vnc` · `none`. Нода, чей образ в каталоге (§2.6) объявлен с `console_type: "none"`, получает `none`, даже если у неё есть консоль: слот держит её для своих проверок готовности, пользователям она не выдаётся |
| `nodes_stale` | `true`, когда слот не ответил и отдан снимок с начала сессии: статусы могут быть неверны. Нет поля — статусы живые |

### 2.4. ✅ Остальные маршруты

| Запрос | Ответ |
|---|---|
| `GET /api/v1/sessions?user_id=&instance_id=` | живая сессия студента в активности, иначе последняя завершённая; `404 session_not_found`, если не было ни одной |
| `GET /api/v1/sessions?instance_id=` | список для наблюдателя: по одной записи на студента активности (живая или последняя завершённая) — поля §2.3 без `topology`/`nodes`/`features` плюс `user_id`; `[]` — сессий нет |
| `POST /api/v1/sessions/{id}/stop` | тело необязательно: `{"requested_by_user_id": 17}` — кто остановил (только журнал); если это не сам студент, причина «преподаватель» и текст «Лаба остановлена преподавателем». Ответ — сессия со `status: "stopping"` |
| `POST /api/v1/sessions/{id}/console-tickets` | `{"node_id", "readonly", "issued_for_user_id"}` → `{"ticket", "gateway_url", "expires_in"}`. `gateway_url` есть всегда: `ws://` или `wss://` (в бою `wss://`), хост, порт, путь, **без `/` на конце**; плагин дописывает `/console/<node_id>?ticket=…`. К ноде, которая по живым статусам не `started`, — `409 node_not_running` (при `nodes_stale` билет выдаётся). К ноде, чей образ в каталоге объявлен с `console_type: "none"` (например, Linux-коммутатор), — `403 console_disabled`: для всех, и для наблюдателя (`readonly`) тоже; образ узла берётся из билета развёртывания рабочей области по имени файла, поэтому правило одинаково для лаб из Moodle и эталонных. Если лабу сессии уже не разобрать (образ убран из каталога), — `503 console_unavailable`: менеджер не выдаёт консоль, пока не знает, что она разрешена. 🆕 К ноде с `console_type: "vnc"` (§2.6) билет выдаётся только владельцу сессии: билет с `readonly: true` — `403 console_disabled` (экран студента преподаватель не видит). Ответ тот же; тип консоли плагин знает из `session.nodes[].console_type` |

Состояние лабы — `/sessions/{id}/state` (§2.7, ✅ менеджер 0.8.0). Маршруты `/sessions/{id}/checks` появятся
вместе с возможностью `checks`.

### 2.6. ✅ Лабы из Moodle: образы, определение, проверка

Есть, только когда в `info.features` есть `images` и `lab_definitions` (у менеджера задан `IMAGES_FILE`).

**`GET /api/v1/images`** — образы, которые разрешены сайту (`limits.images`); кешировать как `info`.

`console_type` образа — `telnet` · `vnc` · `none` (по умолчанию `telnet`). `none` действует: узлы с таким образом не получают билет
консоли ни у кого (§2.4, `403 console_disabled`) и в `session.nodes` выглядят как `none`. Так закрывается управление устройством, которым
студент управлять не должен (образ `images/linux-switch/`). Каталог читается при старте менеджера: смена значения — после перезапуска.

🆕 `vnc` — у ноды вместо серийной консоли графический экран (QEMU VNC, в браузере noVNC); серийной консоли рядом нет, это
либо то, либо другое. Только `kind: "qemu"` (для `iou`/`vpcs` каталог с `vnc` отклоняется при чтении). Экран только у владельца
сессии: наблюдателю билет не выдаётся (§2.4). Менеджер передаёт слоту `console: "vnc"` в `NodeSpec` (§4.2).

```json
{"images": [{"id": "debian12", "title": "Debian 12", "kind": "qemu", "category": "host",
             "symbol": ":/symbols/computer.svg", "console_type": "telnet",
             "ram_mb": {"default": 768, "min": 512, "max": 4096},
             "cpus": {"default": 1, "min": 1, "max": 2},
             "adapters": {"default": 1, "min": 1, "max": 4},
             "port_name": "Ethernet{adapter}", "ports_per_adapter": 1, "preconfig": true}]}
```

🆕 `preconfig` — можно ли ставить ноду с этим образом в сегмент (см. `gns3lab.lab/2` ниже): `true` у `vpcs` и у образа,
для которого администратор указал в каталоге `net_config` (механизм сети гостя: `ifupdown`, `networkmanager`, `netplan`,
`networkd`; только `qemu`; `template` пока не принимается). Самого `net_config` в ответе нет. Нет поля — `false`.

`cpus` есть только у `qemu`; у `vpcs` `ram_mb`, `cpus`, `adapters` — `null` (один порт 0/0).
`port_name` — как GNS3 2.2.61 называет порты нод слота: `iou` — `Ethernet{adapter}/{port}`
(4 порта на адаптер), `qemu` — `Ethernet{adapter}`, `vpcs` — `Ethernet0`. Имени файла образа и
параметров слота в ответе нет.

**Определение `gns3lab.lab/1`:**

```json
{"format": "gns3lab.lab/1", "title": "OSPF, три зоны",
 "nodes": [{"name": "R1", "image": "cisco-iou-l3", "x": -200, "y": 0, "ram_mb": 1024, "adapters": 2},
           {"name": "PC1", "image": "debian12", "x": -200, "y": 160}],
 "links": [{"a": {"node": "R1", "adapter": 1, "port": 0}, "b": {"node": "PC1", "adapter": 0, "port": 0}}]}
```

| Поле | Правило |
|---|---|
| `format` | ровно `gns3lab.lab/1` |
| `title` | строка до 200 символов, необязательно; в `lab_def` не входит |
| `nodes[]` | 1…`min(100, limits.max_nodes)`. `name` — `^[A-Za-z0-9][A-Za-z0-9_.-]{0,79}$`, уникально; `image` — `id` из каталога, разрешённый сайту; `x`, `y` — целые ±100000 (по умолчанию 0); `ram_mb`, `cpus`, `adapters` — необязательные целые в пределах образа (нет — `default` образа; у образа без параметра — `unknown_field`) |
| `links[]` | до 1000. Концы — `{node, adapter, port}` (`adapter`/`port` по умолчанию 0); порт существует у ноды (`adapter < adapters`, `port < ports_per_adapter`), занят не больше одним линком; нода не соединяется сама с собой |
| `uplink_port` | 🆕 необязательно, только у ноды `qemu` (иначе `unknown_field`): номер адаптера в пределах `adapters` (`out_of_range`) — внешний порт узла «Интернет» (образ `lab-uplink`, `images/lab-uplink/`). Не больше одного узла в лабе (`too_many_uplinks`); к этому порту нет линков (`uplink_port_in_use`). Менеджер кладёт поле в `NodeSpec` без изменений и **только если оно задано** (§4.2); оно входит в `lab_def`. В эталонной лабе (`ticket.json`) поле стоит прямо в узле, каталог проверяет те же правила |
| прочее | неизвестное поле на любом уровне — `unknown_field`; весь документ — до 256 КБ |

🆕 **Определение `gns3lab.lab/2`** (`info.features` содержит `lab_constructor`, `lab_formats` — `["gns3lab.lab/1", "gns3lab.lab/2"]`) —
`lab/1` плюс `segments`: преподаватель описывает намерение, а настройку гостей строит менеджер (проект —
`docs/lab-constructor/README.md`). Этап 2: фиксированные значения, ноды `qemu` с `net_config` и `vpcs`. 🆕 Этап 3: ещё
коммутаторы и маршрутизаторы IOL (см. «Что менеджер делает с сегментами»). `lab/1` принимается как
раньше, его `lab_def` не меняется. Без `segments` плагин присылает `lab/1`.

```json
{"format": "gns3lab.lab/2", "nodes": [], "links": [],
 "segments": [{"name": "LAN1", "vlan": {"fixed": 10}, "subnet": {"fixed": "192.168.10.0/24"},
               "gateway": {"node": "R1", "adapter": 1, "port": 0},
               "members": [{"node": "PC1", "adapter": 0, "port": 0}, {"node": "PC2", "host": 20}]}]}
```

| Поле | Правило |
|---|---|
| `segments[]` | до 100. Неизвестные в этом этапе поля (`values`, `faults`, `vlan.random`, `subnet.random`) — `unknown_field`; в `lab/1` само `segments` — `unknown_field` |
| `name` | `^[A-Za-z][A-Za-z0-9_]{0,31}$`, уникально |
| `vlan` | `{"fixed": N}`, 2…4094 без 1002–1005; нет поля — сегмент без VLAN |
| `subnet` | обязательно, `{"fixed": "A.B.C.D/N"}`: сеть IPv4 (без хостовых битов) от `/8` до `/30`, не 0/8, не loopback, не link-local, не multicast, не 240/4 |
| `gateway` | необязательно: `{node, adapter, port[, host]}`, нода — образа категории `router`. 🆕 Маршрутизатор IOL (`kind: iou`) менеджер настраивает сам; любой другой — адрес шлюза студент задаёт сам (предупреждение `gateway_not_configured`). 🆕 Один порт маршрутизатора может быть шлюзом нескольких сегментов, если у них разные `vlan` (router-on-a-stick); сегмент без `vlan` на таком порту — не больше одного, иначе `gateway_port_conflict` |
| `members[]` | непустой, до 100: `{node, adapter, port[, host]}` — `adapter`/`port` по умолчанию 0; образ ноды с `preconfig: true`. Коммутаторы между ними не перечисляются: путь выводится из `links` |
| `host` | номер адреса в подсети, 1…число рабочих адресов. Без него: шлюз — последний рабочий адрес (`.254` у `/24`), участники — с первого рабочего (`.1`, `.2`…), занятые пропускаются |

Все поля входят в `lab_def`; порядок `members` — тоже (по нему раздаются адреса). Порт ноды — не больше чем в одном сегменте
(участником или шлюзом; порт-шлюз можно повторить в других сегментах как шлюз, см. выше); у ноды-участника не больше одного
сегмента со шлюзом.

Новые `code` в `problems` (путь вида `segments[i].members[j]`, `segments[i].gateway`, `segments[i].subnet.fixed`):
`segment_not_connected` (участник или шлюз не связан по L2 с первым участником через `links` и ноды категории `switch`; на
хосте и маршрутизаторе путь заканчивается), `segment_overlap` (два сегмента на общем коммутаторе: оба без VLAN или с одной VLAN),
`member_in_two_segments`, `gateway_not_router`, `unsupported_image` (участник с образом без `preconfig`), `subnet_too_small`
(длиннее `/30` или адресов не хватает на участников и шлюз), `bad_subnet`, `vlan_out_of_range`, `host_out_of_range`,
`host_in_use` (два участника или шлюз на одном адресе; путь — второй), `multiple_gateways`, `duplicate_segment`,
🆕 `gateway_port_conflict` (один порт — шлюз двух сегментов без `vlan` или с одной `vlan`, либо за портом не коммутатор, а хост;
путь — `segments[i].gateway` второго), а также общие
`required`, `unknown_field`, `bad_type`, `bad_name`, `unknown_node`, `bad_port`; `too_large` — ещё и когда скрипт гостя не
помещается в 8192 символа и когда конфигурация IOL не помещается в 65536. В `warnings` (лаба запускается) —
`{path, code, message}`: `gateway_not_configured` (`segments[i].gateway`; 🆕 только если шлюз не IOL),
`switch_not_configured` (`segments[i].vlan`: на пути есть коммутатор не IOL, настроит студент; 🆕 `message` —
`set by the student: <имена>`; путь — коммутаторы между концами сегмента, тупиковая ветка без участников не в счёт),
🆕 `hostname_not_set` (`nodes[i].name`: имя настраиваемой ноды IOL не годится для `hostname`, строки `hostname` в
конфигурации нет). Для нод IOL остальные предупреждения не выдаются.

**Что менеджер делает с сегментами** (в `deploy_ticket`, слот не меняется; применяется один раз при создании проекта, как
`provisioning`): участнику-QEMU — одна `ProvisionCommand` (`timeout_seconds: 120`) после команд образа: скрипт `/bin/sh` по
`net_config` образа (`lab_manager/netconfig.py`, проект §4.1): проверяет, что механизм работает в госте (`netplan` — есть `netplan` и активен `systemd-networkd`, в файле явный
`renderer: networkd`; образ с netplan поверх NetworkManager указывается как `networkmanager`; иначе выход с
`net_config mismatch: declared X, found Y` и лаба `FAILED`), находит интерфейс по MAC (адаптер N — N-й по возрастанию MAC), пишет
файлы механизма, убирает мешающие конфигурации, выключает сетевую часть cloud-init (`/etc/cloud/cloud.cfg.d/99-gns3lab-network.cfg`,
если в госте есть `/etc/cloud/cloud.cfg.d`; при любом механизме), применяет; задаётся статический IPv4 и маршрут по умолчанию. Участнику-VPCS —
строка `ip A/N [G]` в конце `startup_script`. 🆕 Коммутаторам и маршрутизаторам IOL — `nvram_config` (`NodeSpec`, §4.2), текст
`startup-config` (`lab_manager/iosconfig.py`, проект §15.2):
- настраивается коммутатор IOL (`kind: iou`, `category: switch`) **на пути** сегмента (коммутаторы между концами сегмента; ветка без
  участников и шлюза не в пути, кольцо — целиком) и маршрутизатор IOL, порт которого — шлюз сегмента. Коммутатор не IOL — как раньше;
- сегмент без `vlan` идёт в VLAN 1. Коммутатор: `hostname`, `no ip domain-lookup`, `vtp mode off` (одна константа
  `iosconfig.VTP_MODE`; `vlan.dat` не генерируется), `spanning-tree mode pvst`, блоки `vlan N`/`name <сегмент>` для VLAN сегментов с
  `vlan`, порты к участникам — `access` в VLAN сегмента, порты к другому коммутатору на пути и к шлюзу с сабинтерфейсами — `trunk`
  (`dot1q`, `allowed vlan` — VLAN, идущие через порт; VLAN 1 — native, входит в список, если через порт идёт сегмент без `vlan`);
  порты вне сегментов не трогаются; `line con 0`: `exec-timeout 0 0`, `logging synchronous`;
- маршрутизатор: шлюз сегмента без `vlan` — адрес на физическом порту, с `vlan` и коммутатором за портом — сабинтерфейс
  `Ethernet<a>/<p>.<N>` с `encapsulation dot1Q <N>`; физический порт шлюза — `no shutdown`.

Остальные ноды не меняются. Тикет детерминирован; `lab/1` и `lab/2` без IOL на пути не меняются ни на байт. Ожидаемые факты
(`gns3lab.facts/1` после преднастройки; для IOL — то, что отдаст `ios.config/1`, §4.6: `interfaces` и `vlans`) менеджер умеет
строить (`segments.expected_facts`), но в API не отдаёт.

**`POST /api/v1/labs/validate`**, тело `{"lab": {…}}`, ничего не сохраняет:

```json
200 {"lab_def": "sha256:9c1f…", "resources": {"cores": 4, "memory_mb": 4608}, "warnings": []}   (warnings — для lab/2, см. выше)
422 {"error": "lab_invalid", "message": "…",
     "problems": [{"path": "nodes[2].adapters", "code": "out_of_range", "message": "1..4"}]}
```

- `problems` — все найденные сразу. `path` — `nodes[i]`, `nodes[i].<поле>`, `links[i]`,
  `links[i].a|b`, `links[i].a.node`, `nodes`, `format`, `""` (весь документ). `code`: `required`,
  `unknown_field`, `bad_type`, `bad_format`, `bad_name`, `duplicate_name`, `unknown_image`,
  `image_not_allowed`, `out_of_range`, `unknown_node`, `bad_port`, `port_in_use`, `self_link`,
  `too_many_nodes`, `limit_exceeded` (память или ядра CT сверх `limits`), `too_large`,
  🆕 `too_many_uplinks` (второй узел с `uplink_port`; путь — `nodes[i].uplink_port`), `uplink_port_in_use` (к порту `uplink_port`
  подключён линк; путь — `links[i].a|b`). `message` —
  для отладки. Новые коды могут появиться: незнакомый показывайте общим текстом.
- `lab_def` — `sha256` канонического JSON нормализованного определения **без `title`**: переименование
  лабы не меняет `lab_def` и не заводит новую рабочую копию. Считает его только менеджер.
- `resources` — размер CT: память нод + 10 % + `LAB_MEMORY_OVERHEAD_MB` (1024), с округлением вверх до
  256 МиБ; ядра — vCPU QEMU + одно на два IOL + одно на восемь VPCS, не меньше 2.

**Запуск** — `POST /sessions` с `lab` вместо `lab_ref` (§2.2). Определение передаётся целиком при
каждом запуске и проверяется заново. Рабочая копия (проект студента, который продолжается от сессии к сессии)
привязана к `lab_def`: новая версия лабы — новая рабочая копия. Имя проекта — `lab-<8 символов хэша>-<суффикс>`.
Если администратор убрал образ после запуска, сессия `failed` с `LAB_UNAVAILABLE`.

### 2.7. ✅ Состояние лабы: `/sessions/{id}/state`

Факты о запущенной лабе в формате `gns3lab.facts/1` (`plugin/docs/live-state.md`). Возможность `facts` (§7):
`session.features` содержит `facts`, когда слот отдаёт факты (§4.6). Менеджер авторизует запрос, как остальные
маршруты §2.4; права студента и преподавателя проверяет Moodle.

| Запрос | Ответ |
|---|---|
| `GET /api/v1/sessions/{id}/state` | `200`: последний снимок — `schema`, `rev`, `generated_at`, `ttl`, `nodes` |
| `GET /api/v1/sessions/{id}/state?since_rev=N` | то же, но `304` без тела, если `rev` равен `N` |
| `POST /api/v1/sessions/{id}/state/refresh` | `202` без тела: «собери сейчас». Запрос чаще раза в 10 с нового сбора не вызывает, ответ всё равно `202`. Сессия не `running` — `409 session_not_running` |

- Менеджер собирает снимок из последних сохранённых результатов коллекторов (DESIGN §6.7). Ноды ключуются
  `node_id` запущенного проекта, как в `session.topology`; `name` рядом.
- `GET` отвечает и для остановленной сессии: это последнее сохранённое состояние, время наблюдения — в
  `collected_at` каждой ноды. Данных не было ни разу — `200`, `rev: 0`, `nodes: {}`, без `generated_at`.
  Неизвестная сессия — `404 session_not_found`.
- `ttl` задаёт менеджер (`FACTS_TTL`): не меньше трёх периодов сбора (по умолчанию 90 с при периоде 30 с), чтобы задержки
  штатной работы (период слота плюс период опроса менеджером) не помечали данные устаревшими. Последние данные
  показываются всегда, `ttl` их не скрывает: он только отмечает, что сбор идёт нештатно.
- Неудачный сбор — это `error` у ноды, а не `oper: down`: прежние факты остаются, плагин их бледнит.
- `rev` растёт только при изменении фактов. `status` ноды в снимке — справочно: при `304` он мог устареть, живые
  статусы плагин берёт из `session.nodes` (§2.3).
- Истории в этом маршруте нет. Журнал изменений менеджер хранит с самого начала (DESIGN §6.7), отдавать его
  начнёт позже.

### 2.5. Коды ошибок

**Ошибки запросов** (`{"error", "message"}`; у `session_conflict` ещё `conflict`):
`unauthorized` 401, `invalid_request` 400, `unsupported_field` 400, `lab_not_found` 404,
`session_not_found` 404, `node_not_found` 404, `session_not_running` 409, `node_not_running` 409,
`session_conflict` 409, `lab_invalid` 409 (эталонная лаба сломана) или 422 с `problems` (определение
из Moodle, §2.6), `gateway_unavailable` 502, `storage_unavailable` 503.
🆕 `unsupported_lab` 409 (слоты не умеют того, что требует лаба, §4.3; сейчас — лаба с `uplink_port`, а ни один слот в `slots.json` не объявляет `uplink`).

**Коды `error.code` у `failed`-сессии** (`lab_manager/errors.py`). `retryable: true` — можно просто
нажать «Запустить» ещё раз: слот не привязан к студенту, следующая сессия возьмёт другой.
`false` — без администратора повторится то же самое.

| `code` | `retryable` | Что случилось |
|---|---|---|
| `SLOT_START_FAILED` | да | агент не смог запустить контейнер слота |
| `SLOT_LAB_FAILED` | да | лаба в слоте перешла в FAILED (сбой ноды, рестарт службы слота) |
| `SLOT_OPERATION_FAILED` | да | deploy в слоте завершился ошибкой |
| `SLOT_OPERATION_UNKNOWN` | да | слот потерял операцию |
| `SLOT_STOP_FAILED` | да | слот не смог остановить лабу |
| `SLOT_PROJECT_UNKNOWN` | да | слот не знает проект при остановке |
| `SLOT_REJECTED` | да | слот отклонил запрос (подробность в `status_message`) |
| `SLOT_OWNER_LOST` | да | слот отверг текущего владельца; текущая сессия останавливается, слот остаётся на проверку оператору, следующая попытка может взять другой слот |
| `SLOT_NOT_CONFIGURED` | да | слот есть в БД, но не в конфигурации менеджера |
| `WRONG_STUDENT_MOUNT` | да | у слота неожиданные точки монтирования; слот выведен из работы |
| `CT_SIZE_NOT_APPLIED` | да | Proxmox не применил ресурсы слота |
| `TIMEOUT` | да | этап не уложился во время |
| `INTERNAL` | да | внутренняя ошибка менеджера |
| `PVE_REJECTED` | нет | Proxmox отклонил запрос (права, параметры) |
| `AGENT_REJECTED` | нет | агент узла отклонил запрос (настройка узла или слота) |
| `FILESYSTEM` | нет | ошибка файловой системы менеджера |
| `STUDENT_DIR_MISSING` | нет | каталог студента на CephFS не найден |
| `STUDENT_DIR_REJECTED` | нет | агент не создал каталог студента |
| `LAB_UNAVAILABLE` | нет | лаба удалена из каталога или стала некорректной |
| `SLOT_COLD_RESUME_UNSUPPORTED` | нет | проект нельзя продолжить: его создал слот 0.3 или оборвалась его первая подготовка (слот: `PROVISIONING_UNKNOWN`) |
| `PROJECT_MISSING` | нет | запись слота о лабе есть, а проекта в каталоге студента нет (слот: `PROJECT_MISSING`) |
| `QUEUE_TIMEOUT` | да | слот не освободился за `QUEUE_TIMEOUT` (П9 плагина) |
| `NO_SLOTS` | нет | нет ни одного слота, который можно выдать: все `failed`/`maintenance` (П8 плагина) |
| `STUDENT_DIR_BUSY` | нет | каталог студента ещё подключён к слоту, CT которого не удалось выключить после сбоя; нужен оператор. Если слот держит карантин (`SLOT_QUARANTINED`), `status_message` тот же, что у него: «Слот требует проверки администратором. Повторный запуск станет возможен после проверки — сообщите преподавателю» |
| 🆕 `SLOT_QUARANTINED` | нет | агент держит на слоте отметку `uncertain` (команда `pct` не уложилась во время): менеджер не ждёт и не чистит слот, сессия сразу `failed`, слот `maintenance`, каталог студента остаётся за слотом до сверки оператором. `status_message`: «Слот требует проверки администратором. Повторный запуск станет возможен после проверки — сообщите преподавателю» |

Неизвестный плагину код — считать `retryable: false` и показывать общий текст с кодом.

## 3. Каталог лаб → менеджер

`LABS_DIR/<lab_ref>/`. Каталог ведут авторы лаб; плагин его не видит, слот тоже.

| Файл | Назначение | Кто читает |
|---|---|---|
| `lab.gns3` | эталон для превью, отдаётся плагину как есть | менеджер → плагин |
| `ticket.json` | топология для запуска: `nodes`, `links` (формат `NodeSpec`/`LinkSpec` слота) | менеджер → `manifest` слота |

### 3.1. `meta.json`

✅ Сейчас: `title`, `description`, `resources`.
🆕 Предлагается:

```json
{
  "schema": "gns3lab.meta/1",
  "title": "Три Cisco в кольце и шесть Debian",
  "description": "Кольцо из трёх коммутаторов IOL и шесть хостов Debian",
  "resources": {"cores": 8, "memory_mb": 16384},
  "requires": ["qga", "iol-cli"],
  "ui": {"layers": ["l1", "l2", "l3"]},
  "checks": [],
  "extensions": {}
}
```

| Поле | Смысл |
|---|---|
| `resources` | размер CT слота; по нему менеджер выбирает узел и ставит `cores`/`memory` |
| `requires` | возможности слота, без которых лабу не запустить (§7); попадают в билет слота |
| `ui` | подсказки плагину для отрисовки; менеджер передаёт их без разбора (кандидат в `session`) |
| `checks` | описание автопроверок; формат — на этапе «Автопроверки» |

### 3.2. Ревизия лабы

🆕 `lab_revision = "sha256:" + sha256(канонический JSON {nodes, links} из ticket.json)`.
Менеджер запоминает ревизию в рабочей копии студента при первом deploy:
- новый запуск продолжает проект **с той ревизией, с которой он создан**, даже если автор
  поправил лабу (иначе слот откажет: «manifest differs»);
- новые студенты (и запуск с `options.reset`) получают текущую ревизию;
- правки `title`, `description` и `ui` ревизию не меняют.

## 4. Менеджер → Lab Slot

### 4.1. 🆕 `GET /v1/capabilities`

```json
{
  "schema": "gns3lab.capabilities/1",
  "slot_version": "0.4.0",
  "deploy_schemas": ["gns3lab.deploy/1", "gns3lab.deploy/2"],
  "features": ["qemu", "iou", "vpcs", "qga", "iol-cli", "student-state", "collectors", "iol-nvram"],
  "collectors": ["linux.net/1"]
}
```

✅ `collectors` — коллекторы фактов, которые слот умеет запускать (§4.6). Менеджер `capabilities` не читает
(`SLOT_REQUESTS.md` §5): есть ли факты, он узнаёт по ответу `GET /v1/labs/{project_id}/facts` (404 — слот без фактов).

Если маршрута нет (404, слот 0.3), менеджер считает, что слот понимает только `deploy/1` с
возможностями `qemu`, `iou`, `vpcs`, `qga`, `iol-cli`.

### 4.2. `POST /v1/labs/deploy`

✅ **`deploy/1`** — то, что слот принимает сейчас (`DeployTicket` из `slot/api/models.py`), а
менеджер сейчас отправляет:

```json
{
  "name": "cisco-3x2-s-3f9a1c0d2b4e5f60",
  "project_id": "0b6c9d3e-6f1a-4c5e-9a7b-2d8e1f0a3c4b",
  "nodes": [
    {"name": "SW1", "kind": "iou", "image": "x86_64_crb_linux_l2-adventerprisek9-ms.bin", "ram_mb": 1024, "x": -280, "y": -100}
  ],
  "links": [
    {"a": {"node": "SW1", "port": 0}, "b": {"node": "SW2", "port": 0}}
  ]
}
```

- неизвестные поля молча отбрасываются (нет `extra="forbid"`);
- весь билет служит «паспортом» проекта и сравнивается при повторном deploy. Любое поле «на одну
  сессию» сделало бы продолжение проекта невозможным.

🆕 **`deploy/2`** разделяет неизменяемое и сессионное:

```json
{
  "schema": "gns3lab.deploy/2",
  "requires": ["qga", "iol-cli"],
  "project": {
    "id": "0b6c9d3e-6f1a-4c5e-9a7b-2d8e1f0a3c4b",
    "name": "cisco-3x2-w17"
  },
  "manifest": {
    "lab_ref": "cisco-3x2",
    "lab_revision": "sha256:5d41402abc4b2a76b9719d911017c592",
    "nodes": [
      {"name": "SW1", "kind": "iou", "image": "x86_64_crb_linux_l2-adventerprisek9-ms.bin", "ram_mb": 1024, "x": -280, "y": -100}
    ],
    "links": [
      {"a": {"node": "SW1", "port": 0}, "b": {"node": "SW2", "port": 0}}
    ]
  },
  "run": {
    "session_id": "s-3f9a1c0d2b4e5f60",
    "expires_at": "2026-10-17T11:30:00Z"
  },
  "extensions": {}
}
```

| Часть | Правило |
|---|---|
| `schema` | обязательно; без него слот трактует тело как `deploy/1` |
| `requires` | слот проверяет **до** создания чего-либо; если чего-то нет — 422 `{"code": "UNSUPPORTED_REQUIREMENT", "missing": [...]}` |
| `project` | `id` — стабильный UUID проекта; `name` — имя проекта GNS3 (уникально в слоте) |
| `manifest` | неизменен на всю жизнь проекта; при повторном deploy существующего проекта слот сравнивает **только** `manifest` (канонический JSON), иначе 409 «manifest differs». `nodes`/`links` — как сейчас (`NodeSpec`/`LinkSpec`) |
| `run` | своё в каждой сессии, с манифестом не сравнивается. Слот хранит его в операции и может использовать, например показывать `expires_at`; лабу по `expires_at` останавливает менеджер, не слот |
| `extensions` | слот может не понимать содержимое |
| весь документ | `extra="forbid"` на всех уровнях, кроме `extensions` |

Идемпотентность не меняется: `Idempotency-Key` и fingerprint считаются по всему телу. Тот же
ключ с другим `run` — `IDEMPOTENCY_KEY_CONFLICT`. Менеджер для каждой сессии создаёт новый ключ.

🆕 **`NodeSpec.console`** — `"telnet"` (по умолчанию) или `"vnc"`, только для `kind: "qemu"`. `vnc`: слот создаёт ноду GNS3 с
`console_type: "vnc"`, без серийной консоли; готовность ноды — TCP-подключение к порту VNC, а не проверка `serial-getty`.
QGA (канал virtio-serial) от консоли не зависит и остаётся. Менеджер кладёт поле в узел **только для `vnc`**: у `telnet`-узлов
оно отсутствует, чтобы не менять канонический JSON и `lab_revision` существующих лаб. Пока `deploy/2` и `requires` нет ни в слоте,
ни в менеджере (§4.3), поле идёт в `nodes[]` обычного `deploy/1`; слот до 0.8.0 молча отбросил бы его, поэтому менеджер и слот
выпускаются вместе (выпуск закрепляет совместимые версии). С появлением `deploy/2` лабе с `vnc`-узлом понадобится `requires: ["vnc"]`.

🆕 **`NodeSpec.nvram_config`** — текст `startup-config` для NVRAM, только `kind: "iou"`, до 65536 символов, печатный ASCII и `\n`
(без `\r`). Слот кладёт его в NVRAM ноды **один раз, при создании проекта, до первого старта ноды**, функцией импорта из
gns3server (`iou_import`); продолжение проекта его не повторяет (как `provisioning`). Свойство GNS3 `startup_config_content`
не задаётся. Менеджер кладёт поле только в ноды с преднастройкой (§2.6, «Что менеджер делает с сегментами»): у остальных его
нет, канонический JSON и `lab_revision` прежних лаб не меняются. Слот, который поля не знает, молча отбросил бы его, поэтому
менеджер и слот выпускаются вместе; слот объявляет `iol-nvram` в `features` (§7). Ошибка записи (нет модуля, импорт или запись
не удались) — лаба `FAILED`.

🆕 **`NodeSpec.uplink_port`** — номер адаптера узла «Интернет» (`0 ≤ uplink_port < adapters`), только `kind: "qemu"`, не более
одного узла в билете; к этому порту в `links` ничего не подключается. Слот присваивает порту MAC из своего `SLOT_UPLINK_MAC`
(свойство `mac_address` узла — базовый MAC, GNS3 нумерует адаптеры вверх от него, поэтому база = `SLOT_UPLINK_MAC − uplink_port`),
создаёт в проекте узел GNS3 `cloud` с зарезервированным именем `_uplink` (в `NodeSpec.name` оно невозможно: первый символ `_`),
`ports_mapping` на `eth1` слота, и линк `uplink_port` ↔ облако. Узла `_uplink` и его линка **нет в манифесте**: они описывают
слот, а не лабу. Слот не показывает их в инвентаре, статусе, топологии, фактах и L1, не считает чужими при сверке; при продолжении
проекта не пересоздаёт, а если их нет — ошибка сверки, как для любого расхождения. Поля нет у обычных узлов, и в каноническом
JSON и `lab_revision` прежних лаб оно не появляется (как `console`, `nvram_config`). Билет с `uplink_port` слот без возможности
`uplink` отклоняет `422` до создания проекта; слот объявляет `uplink`, только когда `SLOT_UPLINK_MAC` задан и корректен
(локально администрируемый unicast) и у слота есть интерфейс `eth1`. Менеджер и слот выпускаются вместе.

Консоль слота — WS `/v1/console/{project_id}/{node_id}` (`slot/README.md`) — один маршрут для обоих типов, тип слот берёт из
GNS3. 🆕 Для `vnc` слот отдаёт сырой поток RFB: оба направления двоичные кадры, без разбора telnet; нода не `started` или
тип консоли не `telnet`/`vnc` — закрытие `1008`, как и сейчас.

Пути хранения в билет не входят. Каталог студента агент монтирует как `/opt/gns3/projects`,
где GNS3 и так держит проекты. Переносимое состояние лабы (сейчас SQLite в `/var/lib/lab-slot`) —
будущая возможность `student-state` (§7), её место внутри этого же монтирования определяет слот.

`lab_revision` (ревизия манифеста лабы, `sha256:…`) и `code_revision` агента (версия кода слота,
один компонент пути `[A-Za-z0-9][A-Za-z0-9_-]{0,63}`, каталог `<ceph>/slot/<code_revision>`) —
разные вещи и никогда не подставляются друг вместо друга.

### 4.3. Как менеджер выбирает формат

1. Прочитать `GET /v1/capabilities` у слота (кешировать до рестарта слота).
2. Если `requires` лабы не входит в `features` слота — сессия `failed` с кодом
   `unsupported_lab`, а слот не трогается. Когда слотов станет несколько версий, такие слоты
   просто не будут кандидатами при размещении.
3. Если слот понимает `deploy/2`, отправлять его; иначе `deploy/1`. В `deploy/1` нет `run`,
   поэтому сессионные данные в нём не передаются.

### 4.4. Ответы слота

Не меняются (`slot/README.md`): `202` с `operation_id`, опрос `GET /v1/operations/{id}`, коды
`STALE_IDEMPOTENCY_KEY`, `OPERATION_IN_PROGRESS`, `INVALID_TRANSITION`,
`IDEMPOTENCY_KEY_CONFLICT`. Добавляется `UNSUPPORTED_REQUIREMENT`.

### 4.5. Владелец слота после отката

Слот хранит отметку владельца (`POST /v1/fence`, `X-Lab-Epoch` / `X-Lab-Generation`) в
`SLOT_STATE_DIR=/var/lib/lab-slot` внутри rootfs, а агент при освобождении откатывает CT к снимку
(§5). После отката отметки нет, и слот принимает первого владельца, каким бы ни был его `epoch` и
`generation`. Менеджер на это опирается так: `fence` нового владельца идёт до первого `deploy`, а
прежних исполнителей до этого останавливает fencing агента и проверка лидерства менеджера. Почему
этого достаточно — DESIGN §6.3, «Владелец слота и откат».

### 4.6. ✅ Факты о нодах: `/v1/labs/{project_id}/facts`

Слот сам собирает факты из гостей и держит последние результаты. Менеджер забирает их и хранит (DESIGN §6.7);
слот менеджера не вызывает.

| Запрос | Ответ |
|---|---|
| `GET /v1/labs/{project_id}/facts` | `200`: последние результаты по нодам (ниже). Только чтение: заголовки владельца не нужны, токен слота — как у остальных запросов. Лаба не запущена или коллекторов нет — `nodes: {}`. Слот без этого маршрута отвечает 404 |
| `POST /v1/labs/{project_id}/facts/refresh` | `202`: собрать сейчас. Как у остальных изменяющих запросов слота, нужны заголовки владельца (§4.5). Частоту ограничивает слот |

```json
{
  "schema": "gns3lab.slot-facts/1",
  "project_id": "5f1c…",
  "nodes": {
    "6b1f3c2e-4a7d-4e5b-9c10-000000000002": {
      "name": "PC1",
      "collectors": {
        "linux.net": {
          "schema": "linux.net/1",
          "attempted_at": "2026-10-17T10:00:30Z",
          "observed_at": "2026-10-17T10:00:30Z",
          "ok": true,
          "error": null,
          "data": {"interfaces": [], "routes": []}
        }
      }
    }
  }
}
```

| Часть | Правило |
|---|---|
| ключ в `collectors` | имя коллектора без версии; `schema` — с версией (`linux.net/1`). Новый вид данных — новый коллектор или новая версия, миграция БД менеджера не нужна |
| `data` | фрагмент объекта ноды из `live-state.md` §3 — поля, которыми владеет этот коллектор (`linux.net`: `interfaces`, `routes`). Менеджер собирает ноду, объединяя фрагменты в порядке имён коллекторов; поля коллекторов не пересекаются, единственное исключение — `interfaces` у `switch.net` (ниже) |
| `port` интерфейса | задаётся только при точном совпадении MAC интерфейса с MAC адаптера GNS3: у QEMU-ноды адаптер N имеет MAC `properties.mac_address` ноды + N, у QEMU `port` всегда `0`. Порядок и имена интерфейсов в госте не учитываются. Подтверждено на стенде (GNS3 2.2.61): ноды с одним адаптером — базовый MAC, нода с четырьмя — `ens3`…`ens6` = база + 0…3 |
| `observed_at` / `attempted_at` | когда сбор удался в последний раз / когда была последняя попытка. Успехов не было — `data` и `observed_at` нет |
| `ok`, `error` | `ok: false` — последняя попытка не удалась. `error` — `{"code", "message"}`, коды из `live-state.md` §3; `data` остаётся прежним, последним известным |
| пропущенная попытка | сбор уступает командам менеджера и студента (приоритет `METRICS`, `slot/README.md`). Если канал занят, попытка пропускается: это не ошибка, результаты и `attempted_at` не меняются. Канал в back-off (подряд сбои обмена) — `error.code = unreachable` |
| стабильность `data` | в `data` только значения состояния. Поля, которые меняются сами по себе, коллектор отбрасывает: `valid_life_time` и `preferred_life_time` адресов DHCP/SLAAC, `expires` маршрутов, счётчики. Иначе каждый опрос выглядел бы изменением и попадал в журнал менеджера |
| сырой вывод | слот его не отдаёт и менеджер не хранит. Пересборка истории после исправления разбора — позже, отдельным решением |
| владелец | слот собирает только для лабы текущего владельца; при смене владельца результаты сбрасываются |

Коллектор — одна гостевая команда и разбор её вывода, он живёт в коде слота, и версия растёт вместе с
выпуском слота. Первый — `linux.net`: QEMU-ноды с `qga` (`ip -j addr`, `ip -j route`). У IOL гостевой команды нет:
коллектор `ios.config/1` (ниже) читает сохранённую конфигурацию из файлов ноды. Proxmox добавится тем же форматом позже. Слот собирает факты лабы только после того, как она
перешла в `READY`: пока ноды грузятся, недоступный агент QGA — не ошибка сбора. Состав коллекторов и период (по умолчанию `linux.net`
каждые 30 с у запущенных QEMU-нод с QGA) выбирает слот; настройка лабой появится вместе с `checks`.

#### Коллектор `switch.net/1` (Linux-коммутатор)

Нода с образом `images/linux-switch/` (его гостевой API — `images/linux-switch/docs/CONTRACTS.md`). Слот пробует
коллектор на каждой QEMU-ноде с `qga`: роль ноды заранее неизвестна (в спецификации ноды нет поля «коммутатор»),
её сообщает сам гость. Один гостевой `exec` за запуск: `switchctl ports` и `switchctl vlans` через брокер, как у
`linux.net` (`METRICS`, `wait=False`, `max_age`).

| Правило | Что значит |
|---|---|
| не коммутатор | в госте нет `/usr/local/sbin/switchctl` (код 127). Слот **не публикует** запись `switch.net`, помнит это для ноды до смены владельца или выхода лабы из `READY` и больше не пробует |
| сбои до первого успеха | пока `switch.net` ни разу не удался, не публикуются любой сбой обмена (`timeout`, `unreachable`, отказ агента — всё, что бросил брокер) и `stopped`. Менеджер не удаляет строки коллекторов, пропавших из снимка, поэтому запись, опубликованная об обычном хосте, осталась бы его ошибкой навсегда; недоступность узла и так сообщает `linux.net`. Публикуется только сказанное самим гостем: `failed` (`switchctl` есть, но демон не отвечает, `ok:false`, непонятный вывод) |
| после первого успеха | нода — коммутатор: сбои публикуются, как у других коллекторов (`ok: false`, прежние `data` остаются) |
| `data` | только `interfaces` — порты моста `br0`. Каждый: `name`, `kind: "physical"`, `admin`, `oper`, `mac`, `port` (по MAC адаптера, как у `linux.net`), `switchport`, `mirror: true` (студент портами этого образа не управляет, схема повторяет порт на другом конце кабеля: `live-state.md` §3.1 и §4, L1; признак ставит только `switch.net`). Нет `ipv4`, `gateway`, `routes`, счётчиков и FDB (таблица MAC — отдельный коллектор `switch.fdb/1`, ниже). `admin`/`oper` — то, что видит гость (несущая QEMU почти всегда есть); состояние порта на схеме считает плагин (`live-state.md` §4, L1) |
| `switchport` | по **фактическому** членству VLAN (`vlans.actual` = `bridge -j vlan show`), желаемая политика не берётся: хранятся факты, не намерения. Ровно одна VLAN с флагами `PVID` и `Egress Untagged` → `{"mode":"access","vlan":N}`. Иначе одна и более VLAN → `{"mode":"trunk","allowed":[…по возрастанию…],"native":N}`, где `native` — VLAN с `PVID` и `Egress Untagged`, а `null`, если такой нет (транк без PVID не принимает и не отдаёт кадры без тега). Членства нет → `{"mode":"none"}` (порт изолирован: загрузка, новая карта при сохранённой политике). Диапазоны `vlan`…`vlanEnd` в выводе iproute2 разворачиваются; записи, которых нет среди портов `ports` (например `br0`), игнорируются |
| ожидание применения | `applied`, `last_error` и желаемая политика в `data` не попадают. Зависшее применение видно как `mode: "none"` или не та VLAN; отдельное поле — вместе с управлением VLAN из лабы, не сейчас |
| с `linux.net` | на ноде работают оба коллектора, и оба отдают `interfaces`. Менеджер объединяет фрагменты в порядке имён, `switch.net` стоит после `linux.net`, поэтому его `interfaces` заменяет список целиком (не сливается по именам); `routes` остаётся от `linux.net`. Правило покрыто тестом менеджера |

#### Коллектор `switch.fdb/1` (таблица MAC Linux-коммутатора)

Таблица коммутации той же ноды, что обслуживает `switch.net/1`: метод `fdb` гостевого API (`images/linux-switch/docs/CONTRACTS.md`).
Только чтение: слот выполняет `switchctl fdb` и ничего не меняет в госте. Поле ноды — `mac_table` (`live-state.md` §3.4).

```json
"switch.fdb": {
  "schema": "switch.fdb/1",
  "attempted_at": "2026-10-26T10:00:30Z",
  "observed_at": "2026-10-26T10:00:30Z",
  "ok": true,
  "error": null,
  "data": {
    "mac_table": {
      "entries": [
        {"mac": "52:54:00:12:34:56", "iface": "eth1", "vlan": 10},
        {"mac": "52:54:00:12:34:57", "iface": "eth2", "vlan": 10}
      ],
      "truncated": false
    }
  }
}
```

| Правило | Что значит |
|---|---|
| отдельный коллектор | не поле в `switch.net`. Таблица MAC меняется при каждом обучении и старении записи, порты и VLAN — почти никогда. Менеджер пишет в журнал полную копию `data` коллектора и увеличивает `rev` при любом изменении (`DESIGN.md` §6.7): общий коллектор копировал бы порты в журнал при каждом новом MAC. Второй довод: сбой чтения таблицы не должен ронять сбор портов и VLAN |
| команда | один гостевой `exec` через брокер (`METRICS`, `wait=False`, `max_age`): проверка `/usr/local/sbin/switchctl` (нет — `exit 127`), затем `switchctl fdb --params '{"limit":1024}'`. Статус завершения `switchctl` не проверяется, как у `switch.net`: ответ с `ok:false` разбирает слот. Одна страница, цикла по `offset` нет: страница — срез одного дампа ядра и потому согласована сама с собой, а между страницами таблица успевает измениться (контракт образа) |
| не коммутатор, молчание, сбои | как у `switch.net/1`, с собственной памятью роли. Код 127 — записи нет, пробу не повторять; до первого успеха не публикуются сбои обмена и `stopped`, публикуется только `failed` от самого гостя (`ok:false`, непонятный вывод); после первого успеха сбои публикуются, прежние `data` остаются. Слот называет `switch.fdb/1` в `collectors` ответа `GET /v1/capabilities` (§4.1) |
| `data` | только `mac_table`: `entries` и `truncated`. Других полей нет |
| `entries` | **изученные** адреса: строки `bridge -j fdb show br br0`, у которых `state` не `permanent` и не `static` и в `flags` нет `self` (контракт образа: нельзя считать все строки изученными; у изученных на стенде `state` — пустая строка, `flags` — `[]`). Поля ровно три: `mac` (нижний регистр через двоеточие), `iface` (`ifname`, имя порта коммутатора — как `interfaces[].name` у `switch.net`), `vlan` (1..4094). Всё остальное из вывода iproute2 (`master`, `flags`, `state`, `updated`, `used`, поля будущих версий) в `data` не попадает: таймеры меняли бы `data` при каждом опросе, а менеджер писал бы это в журнал (правило «стабильность `data`»). Порядок — по `vlan`, `mac`, `iface`: одинаковая таблица даёт одинаковые `data`. у изученной строки `vlan` обязателен (мост всегда с VLAN-фильтрацией), у остальных его может не быть; изученная строка без `vlan` или с непонятным `mac` или `ifname` — `failed` («Unexpected output of switchctl»), как у разбора `switch.net`. Остальные строки — служебные: собственные MAC портов и моста (у каждого две строки, с `vlan` и без), групповые адреса с флагом `self`, заданные администратором — в снимок не попадают совсем и числом не учитываются: студент ими не управляет, на схеме они не нужны, а на транках «порт × VLAN» их тысячи. Понадобятся — новая версия схемы |
| `truncated` | `true`: таблица прочитана не целиком, `entries` собраны из прочитанного. Два случая: гость вернул `next_offset` не `null` (строк больше 1024: в `entries` изученные из первых 1024 строк дампа, какие именно — не определено, состав может меняться от опроса к опросу) и гость ответил `RESULT_TOO_LARGE` (вывод ядра больше 1 МиБ: `entries: []`). Второй случай не сбой коллектора: менеджер переносит `ok:false` любого коллектора в `error` ноды, и плагин бледнит всю ноду; для постоянного свойства таблицы это ложная авария. Любой другой код ошибки гостя (`BUSY`, `TIMEOUT`, `COMMAND_FAILED`) — `failed`, как у `switch.net` |
| свежесть | период тот же, что у остальных коллекторов (30 с; «Обновить сейчас» — через ~5 с). Слот снимает состояние, а не журнал обучения: запись, которая появилась и состарилась (по умолчанию 300 с) между двумя опросами, не видна |
| менеджер | код не меняется: `build_state` кладёт ключи `data` в ноду как есть (кроме `name`, `status`, `collected_at`, `error`), `mac_table` ни с чем не пересекается и не заменяет `interfaces` от `switch.net`. Правило закрепить тестом менеджера, как для `switch.net`. Слот без коллектора не отдаёт запись, и у ноды просто нет поля `mac_table` |
| проверено на стенде | коммутатор с портами `ens3`…`ens7`, подключены два узла. Дамп `bridge -j fdb show br br0` — 27 строк, изучена одна (`ens3`, `vlan:1`, `state:""`, `flags:[]`, `master:"br0"`): в `entries` попадает одна строка, остальные 26 служебных отбрасываются. Таймеров (`updated`, `used`) в выводе нет. Имя порта в строке — `ifname`; `dev` в тестовой заглушке `images/linux-switch/tests/test_api.py` эталоном не служит |

#### Коллектор `windows.net/1` (гость Windows)

Тот же формат `data`, что у `linux.net/1`: `interfaces` и `routes`. Слот отдаёт его вместо `linux.net` и
`switch.net` для нод, которые сами сообщили, что это Windows. Менеджер и плагин ничего не меняют: коллекторы
не пересекаются (на ноде работает ровно одно семейство), фрагмент попадает в ноду по общему правилу.

| Правило | Что значит |
|---|---|
| какая ОС | слот один раз на ноду вызывает `guest-get-osinfo` (QGA, без шелла): `id: mswindows` (или `Windows` в `name`) — Windows, остальное и агент без этой команды — Linux. Ответ помнится до смены владельца или выхода лабы из `READY`. Пока ОС неизвестна (нода остановлена, агент не ответил), слот не публикует **никаких** записей `linux.net`/`switch.net`/`windows.net`: запись не того семейства осталась бы чужой ошибкой навсегда (менеджер строки не удаляет). После первого ответа сбои публикуются, как у `linux.net` |
| команда | один запуск `powershell.exe -NoProfile -NonInteractive -EncodedCommand …` через брокер (`METRICS`, `wait=False`, `max_age`): `Get-NetAdapter`, `Get-NetIPAddress -AddressFamily IPv4`, `Get-NetRoute -AddressFamily IPv4`, один JSON в ASCII (не-ASCII символы имён адаптеров идут как `\uXXXX`, кодовая страница гостя не важна). Нужен Windows 10 / Server 2016 и новее; нет `Get-NetAdapter` — `unsupported` |
| `interfaces` | адаптеры `Get-NetAdapter` (`kind: "physical"`, скрытые и loopback не входят). `name` — имя адаптера (`Ethernet 2`), `mac` — в нижнем регистре через двоеточие, `port` — по MAC, как у `linux.net` (у Windows MAC записан через дефис, разбор это учитывает). Подинтерфейсов и других `kind` нет |
| `admin` / `oper` | по `Status`: `Disabled` и `Not Present` — `admin: down`, остальное `admin: up`; `oper: up` только при `Up`. `Disconnected` (кабеля нет, линк в GNS3 погашен) — `admin: up`, `oper: down`: так же, как `NO-CARRIER` у Linux |
| `ipv4` | все IPv4-адреса адаптера с маской, по возрастанию. Адрес в состоянии `Duplicate` не используется и не входит; остальные (в том числе `Tentative` и 169.254.x.x от APIPA, а также адрес на адаптере без кабеля) — то, что настроено. Сроки аренды DHCP не копируются |
| `routes` | `Get-NetRoute`: `0.0.0.0/0` → `default`, `NextHop 0.0.0.0` → без `via`, `dev` — имя адаптера, `proto` — `Protocol` в нижнем регистре (`local`, `netmgmt`, `dhcp`), `metric` — `RouteMetric + InterfaceMetric` (как в `route print`, у Linux метрика только маршрута). Не входят то, чего нет в `ip route`: хост-маршруты `Local` с /32 (свои адреса, широковещание), мультикаст `224.0.0.0/4`, маршруты loopback. `gateway` интерфейса — по правилу `linux.net`: `default` с наименьшей метрикой |

#### Коллектор `ios.config/1` (сохранённая конфигурация IOL)

Решение владельца: у Cisco авторитетна **сохранённая** конфигурация — то, с чем устройство загрузится после
перезагрузки (NVRAM и `vlan.dat`). Настройка, которую студент не сохранил (`write memory`), для фактов и проверок
не существует; студенту это объясняется в задании. Поэтому коллектор не пользуется консолью вообще: ни одной строки
в терминал студента, никаких гонок с его вводом. Подслушивание `show` в консоли — отдельный этап, другой коллектор
(`slot/docs/ALIGNMENT.md` §3.6).

| Правило | Что значит |
|---|---|
| ноды | IOU-ноды лабы (`NodeSpec.kind: "iou"`), в том числе остановленные: файл на диске есть и без запущенной ноды, а «что будет после загрузки» от состояния ноды не зависит. Сбор, как у остальных, только когда лаба в `READY` и для текущего владельца |
| источник | каталог ноды проекта (`node_directory` в ответе GNS3, у 2.2.61 `…/project-files/iou/<node_id>/`). Порядок: (1) `startup-config.cfg`, если он **не пуст**: GNS3 кладёт его в NVRAM при каждом старте и обновляет после изменения NVRAM (`IOUVM._nvram_changed` → `save_configs`, file watcher), поэтому он и есть то, с чем нода загрузится. Но GNS3 пишет и обновляет его **только если файл уже был непустым** (`startup_config_content` при создании ноды; `save_configs` проверяет `self.startup_config_content or self.private_config_content`). Слот создаёт IOU-ноды без него, и для них файла не будет, что бы студент ни сохранил; пустой файл GNS3 тоже не обновляет. (2) Иначе `nvram_<application_id>` ноды: текст достаёт `nvram_export` из `iou_export.py` установленного `gns3server` 2.2.61, а не собственный разбор двоичного формата. Файл грузится по пути: `SLOT_IOU_EXPORT`, иначе путь по умолчанию — `/opt/gns3-server/lib/python3.12/site-packages/gns3server/compute/iou/utils/iou_export.py` (GNS3 в шаблоне слота стоит в своём venv `/opt/gns3-server`, `install/slot-template-setup`; venv слота его не видит). `private-config` и приватная часть NVRAM не читаются. Консоль, API GNS3 для чтения файлов и QGA не используются |
| когда читать | при каждом сборе (период 30 с, «Обновить сейчас») слот сравнивает размер и время изменения источника (файла или NVRAM) с прошлым чтением и разбирает его, только если они изменились. Чтение — локальный файл, в брокер QGA и в очередь консоли не попадает. IOL может писать NVRAM в момент чтения: если разбор не удался, а размер или время источника после чтения уже другие, сбой не публикуется (запись и `attempted_at` не меняются), источник перечитывается на следующем сборе. `failed` — только когда источник между чтениями не менялся |
| нет сохранённой конфигурации | ни непустого `startup-config.cfg`, ни NVRAM с конфигурацией (файлов ещё нет, NVRAM пуст, устройство ничего не сохраняло): записи `ios.config` нет (у ноды просто нет фактов). Это не ошибка. Запись уже была, а сохранённой конфигурации больше нет (`write erase`, источник пропал или опустел): `ok: true`, `data: {}` — устройство загрузится без конфигурации, и схема показывает «нет сохранённой конфигурации», как до первого `write memory`, а не прежнюю настройку. Это не сбой. Различать: конфигурация есть, но интерфейсов в ней нет — `interfaces: []`; конфигурации нет — `data` без полей |
| сбой | файл не читается или не разбирается (неизвестная структура, неверная маска), NVRAM не выгружается — `ok: false`, `error.code = failed`, прежние `data` остаются. Слот не нашёл код экспорта NVRAM у `gns3server` (путь к `iou_export.py` задаёт `SLOT_IOU_EXPORT`) — `unsupported`. Пустая конфигурация — не сбой: `interfaces: []` |
| `data` | `interfaces` и `vlans` (`plugin/docs/live-state.md` §3). Других полей нет; в частности нет `routes`, `router_id`, `adjacencies`, `mac_table` и `oper` (ниже) |
| стабильность | в `data` только то, что задано конфигурацией. Комментарии (`!`, в том числе `Last configuration change at …`, `NVRAM config last updated at …`) и порядок блоков не влияют: тот же сохранённый конфиг даёт тот же `data`, повторный `write memory` без изменений не создаёт строку журнала менеджера |
| секреты | `startup-config` содержит пароли и хэши (`enable secret`, `username`, ключи). В `data` попадают только поля из этой таблицы; сырой текст слот не отдаёт и не пишет в журнал |

`interfaces` — по блоку `interface <имя>` сохранённой конфигурации. IOS сохраняет конфигурацию в каноническом виде
(полные имена, без сокращений), поэтому разбор не знает про сокращения и `interface range`.

| Поле | Откуда |
|---|---|
| `name` | имя из конфигурации как есть: `Ethernet0/0`, `Ethernet0/1.10`, `Vlan10`, `Loopback0`, `Serial2/0`. Это же имя пойдёт в `iface` и `dev` будущих коллекторов этой ноды |
| `kind` | `Ethernet…`/`Serial…` без точки — `physical`; с `.N` — `subif` (`parent` — имя до точки, `dot1q` — из `encapsulation dot1Q N`); `VlanN` — `svi` (`vlan: N`); `LoopbackN` — `loopback`. Остальные (`Tunnel`, `Port-channel`, `NVI` …) в `interfaces` не входят: в `live-state.md` для них нет вида |
| `port` | у `physical`: точное совпадение `name` с `name` порта ноды в API GNS3 (`ports[]`, у IOU `Ethernet{adapter}/{port}`, `ALIGNMENT.md` В8) → `{"adapter": adapter_number, "port": port_number}`. Нет совпадения — поля нет |
| `admin` | `down`, если в блоке есть строка `shutdown`, иначе `up`. IOS всегда сохраняет `shutdown` явно, и у выключенных по умолчанию интерфейсов маршрутизатора тоже |
| `oper` | **нет**: несущую конфигурация не знает. Плагин не рисует «нет несущей» без `oper: "down"` (L1, `live-state.md` §4) |
| `ipv4` | `ip address A M` и `ip address A M secondary` → `A/префикс`, по возрастанию. `no ip address` — `[]`. `ip address dhcp` (адрес не задан конфигурацией) — поля нет |
| `switchport` | только у нод-коммутаторов (ниже). `switchport mode access` → `{"mode":"access","vlan":N}`, N из `switchport access vlan` (нет строки — 1). `switchport mode trunk` → `{"mode":"trunk","allowed":…,"native":N}`: `allowed` из `switchport trunk allowed vlan` вместе со строками `… allowed vlan add …` (диапазоны развёрнуты, по возрастанию; нет строки — `"all"`; `none` — `[]`), `native` из `switchport trunk native vlan` (нет строки — 1). `switchport trunk encapsulation` не учитывается. `no switchport` — поля нет (порт маршрутизируемый). Режим не задан или `dynamic …` — см. «Открытые вопросы» в `SLOT_REQUESTS.md` §8; до ответа — как `access` |
| `ospf` | **нет** в `ios.config/1`. Плагин считает каждое ожидаемое соседство без записи в `adjacencies` отсутствующим (красное ребро и «нет соседей OSPF»), а соседства из конфигурации не узнать. `ospf`, `router_id` и `adjacencies` появятся вместе, другим коллектором |

`vlans` — блоки `vlan N` / `name …` сохранённой конфигурации (их IOS пишет туда в режиме VTP `transparent` или `off`):
`[{"id": N, "name": "…"}]` по возрастанию `id`; у блока без `name` имени нет. В режиме VTP `server`/`client` база VLAN
только в `vlan.dat`: тогда поля `vlans` нет, пока слот не умеет читать `vlan.dat` (`SLOT_REQUESTS.md` §8). Слои L2
строятся по `switchport` портов, `vlans` — только для подписей (`live-state.md` §3), поэтому без `vlan.dat` схема не
ломается; не видно лишь, что порт назначен в несуществующую VLAN.

Коммутатор — нода, в конфигурации которой есть строка `spanning-tree mode …` (у образов IOL L2 она есть в
конфигурации по умолчанию, у L3 — нет; исполнитель проверяет на стенде на образах каталога). У маршрутизатора
`switchport` не выводится никогда. Слот называет `ios.config/1` в `collectors` ответа `GET /v1/capabilities` (§4.1).

Менеджер переносит ключи `data` этого коллектора в ноду как есть. Плагин знает тип
ноды из `.gns3` (`node_type: "iou"`) и может подписать конфигурационные факты
«по сохранённой конфигурации» (`live-state.md` §3). Независимый живой L1 описан ниже.

#### Коллектор `iol.l1/1` (живой L1 физических пар Cisco–Cisco)

Слот 0.12.0 публикует уже имеющиеся результаты L1-обработчика, без дополнительных
команд, QGA, консоли и Ethernet-проб. Только пары IOL с `l1_keepalives=true` на обоих
концах; Cisco–QEMU остаётся в прежнем режиме. Объявляется в `capabilities.collectors`.

В обычном конверте коллектора (§4.6):

```json
{"schema":"iol.l1/1","ok":true,"error":null,
 "attempted_at":"2026-10-28T12:00:00Z","observed_at":"2026-10-28T12:00:00Z",
 "data":{"l1_ports":{"ttl":15,"ports":[
   {"port":{"adapter":0,"port":0},"state":"up","reason":"both_responding"}
 ]}}}
```

- `port` — физический порт GNS3; каждый кабель, включая участников EtherChannel,
  независим. Порядок стабилен по adapter/port. Здесь нет IP, VLAN, административного
  состояния и имени интерфейса; они остаются в `ios.config`.
- `state`: `up` — оба конца подтвердились; `down` — порог пропусков достигнут,
  сосед остановлен или линк suspended; `unknown` — подтверждения ещё нет.
  `reason`: `both_responding`, `no_rx`, `peer_unavailable`, `node_stopped`, `suspended`, `probing`.
  Отсутствие RX не доказывает `shutdown`. Молчащий, намеренно не опрашиваемый сосед
  получает состояние соединения, а не выдуманное административное состояние.
- `ttl` — `max(15, ceil(3 * SLOT_L1_INTERVAL + 2 * SLOT_L1_REPLY_TIMEOUT))` секунд.
  Время наблюдения находится в конверте, не в `data`: неизменившийся heartbeat
  обновляет время, но не `rev` и не журнал. `ports: []` очищает ранее опубликованные
  порты при удалении/смене соединений. Без сохранённого конфига L1 также публикуется.
- Ошибка цикла: `ok:false`, `error.code:failed`, прежние `data` и `observed_at`;
  свежесть не продлевается. Смена владельца/выход из READY очищают память слота.
- Менеджер оставляет `interfaces` от `ios.config` и переносит `l1_ports` отдельно,
  добавляя внутрь `observed_at` из конверта и `ok`. Ошибка этого коллектора не
  становится общей `error` ноды: состояние конфигурации и L1 независимо.
  Для сессии с этим коллектором интервал чтения слота — не больше 3 с.
- Плагин использует `l1_ports` только для Cisco–Cisco и только на совпадающем порту.
  Эти показания имеют приоритет над сохранёнными/консольными `admin`/`oper` для L1,
  не заменяя конфигурационные поля. Ошибка, истечение собственного TTL или
  `unknown` дают серую линию, а не зелёную или административный shutdown.
  Остановка узла и suspend остаются безусловными причинами недоступности.
  Старые слоты без записи продолжают работать по прежним правилам.
- Для сессий с L1 браузер и кэш Moodle используют период 3 с. Кэш запрашивает
  полный снимок, а external `get_facts` возвращает документ даже при прежнем rev:
  обновление времени важно для отличия исправного сборщика от остановившегося.
  Остальные сессии сохраняют периоды 30/15 с. В `seen`/`fog` L1 доступен только
  для уже открытых интерфейсов и группы `l1`; новые факты не раскрывают порты.

Приёмка: up/up, оба shutdown, выключение/восстановление каждого конца, изменение
молчащего соседа, параллельные линки, stop/suspend, истечение L1 при свежем конфиге,
потеря связи с менеджером, смена владельца и отсутствие сохранённого конфига.
Сравнить `/facts`, `/sessions/{id}/state`, схему и IOS; восстановительные пробы могут
кратковременно менять carrier внутри IOS — это ограничение самого L1-механизма.

## 5. Менеджер → агент узла

Формат и доработки — `AGENT_REQUESTS.md`. Агент строгий (`extra="forbid"`, `strict=True`),
поэтому старый агент отклонит любое новое поле. Значит, правило §1.3 действует и здесь: пока у
агента нет `GET /capabilities` с нужным ему полем, менеджер не отправляет ему ничего сверх текущего API (никаких
`schema`, `extensions`, `resources`, `generation`, ключей идемпотентности). Коды ошибок — не
способ узнать версию агента.

**Бюджет запуска и карантин (агент 1.2.1, менеджер 0.11.1).** 🆕 `GET /capabilities` →
`{"version", "start_budget_seconds", "guest_action_timeout_seconds"}`. `start_budget_seconds` — худший случай
`POST /slots/{vmid}/start` без правки монтирований: `pct start` (120 с) + 3 × `LAB_GUEST_ACTION_TIMEOUT`
агента (по умолчанию 120 с, пределы 30–600). Менеджер сверяет его со своим `AGENT_START_TIMEOUT` (нужен запас 60 с) и
предупреждает в журнале при старте и в `lab-manager-admin check`; ничего другого из `capabilities` он не берёт.
Агент без маршрута (404, старше 1.2.1) — бюджета нет, предупреждения тоже. 🆕 В теле `504 PCT_TIMEOUT` — поле
`detail.command`: подкоманда `pct` (`start`, `exec`, `stop`, …), как `command` в отметке fencing; вывода команды в
ответе нет. Менеджер читает ответы так: `409 COMMAND_UNCERTAIN` и `504 PCT_TIMEOUT` на **изменяющий** запрос
(`command` не `status`; агент без поля — тоже) — отметка `uncertain` записана, сама она не пройдёт: это карантин
(`AgentQuarantined`), сессия завершается `SLOT_QUARANTINED` (§2.5). Сетевые сбои, `503 PCT_UNAVAILABLE`,
`STORAGE_UNAVAILABLE`, `FENCE_STORAGE_ERROR` и тайм-аут чтения (`pct status`) остаются «исход неизвестен»: менеджер
ждёт и перечитывает состояние. `GET /slots/{vmid}/status` отдаёт `ownership` с `uncertain`, `inflight` и `command` — по
нему оператор и `lab-manager-admin check` узнают команду.

**Откат слота (агент 1.2).** `POST /slots/{vmid}/reset`, тело `{}`, те же заголовки владельца, что у
`stop`: на остановленном CT выполняет `pct rollback` к снимку чистого слота (имя задаёт
администратор агента, `LAB_CLEAN_SNAPSHOT`, по умолчанию `lab-clean`; клиент его не передаёт).
Ответ: `{"vmid", "state": "stopped", "reset": true, "snapshot"}`. Откат возвращает и диск, и весь
конфиг CT (точки монтирования, `cores`, `memory`, `net0`), поэтому менеджер после него заново
ставит заглушку и размер. Ошибки: `NOT_STOPPED` (409), `SNAPSHOT_MISSING` и `SNAPSHOT_UNSAFE` (422,
`AGENT_REQUESTS.md` §2). Агент старше 1.2 отвечает на этот маршрут 404 без кода `CT_NOT_ON_NODE`:
менеджер считает это «агент слишком старый», а не поводом слать что-то ещё.

## 6. Менеджер → шлюз консолей

`POST /internal/tickets {"slot", "project_id", "nodes", "readonly", "who", "console"}`.
`who` = `<session_id>:owner|observer`: в журнал шлюза не попадает `user_id`.
🆕 `console` — `"telnet"` (по умолчанию, поле необязательное) или `"vnc"`: менеджер знает тип из живых статусов нод. Он
определяет, что шлюз пускает от браузера: `telnet` — только текстовые кадры (как раньше); `vnc` — двоичные кадры RFB в обе
стороны без изменений. `console: "vnc"` вместе с `readonly: true` шлюз отклоняет (`400`): режима «только просмотр» у экрана нет.
Адрес для браузера, билет, Origin и коды закрытия `4000`/`4001` одинаковы для обоих типов.

| Имя | Где объявляется | Значение |
|---|---|---|
| `consoles` | менеджер (`info`, `session`) | билеты консолей через шлюз |
| `observer` | менеджер | консоли только для чтения для преподавателя |
| `facts` | менеджер | ✅ `/sessions/{id}/state` (§2.7, live-state.md); в `session.features`, когда слот отдаёт факты |
| `checks` | менеджер | 🆕 `/sessions/{id}/checks` |
| `reset` | менеджер | 🆕 `options.reset` |
| `resume` | менеджер | следующий запуск продолжает проект студента (всегда, с менеджера 0.5.1) |
| `images` | менеджер | `GET /api/v1/images` (§2.6) |
| `lab_definitions` | менеджер | `POST /labs/validate` и `POST /sessions` с `lab` (§2.6) |
| `lab_constructor` | менеджер | 🆕 `gns3lab.lab/2`: сегменты, `preconfig` образов, `warnings` в `validate` (§2.6); объявляется вместе с `lab_definitions` |
| `qemu`, `iou`, `vpcs` | слот | типы нод `NodeSpec.kind` |
| `qga` | слот | QEMU Guest Agent и provisioning через QGA |

| `collectors` | слот | ✅ (0.6.0) слот собирает факты о нодах: `GET /v1/labs/{project_id}/facts` и список `collectors` в `capabilities` (§4.6) |
| `iol-cli` | слот | provisioning IOL через CLI (`cli_prompt`) |
| `iol-nvram` | слот | 🆕 `NodeSpec.nvram_config`: `startup-config` IOL кладётся в NVRAM при создании проекта, до первого старта (§4.2) |
| `uplink` | слот; менеджер | 🆕 `NodeSpec.uplink_port`: узел «Интернет», его внешний порт получает `SLOT_UPLINK_MAC` и подключается к `eth1` слота через облако GNS3 (§4.2). Только при заданном `SLOT_UPLINK_MAC` и наличии `eth1`; лаба с `uplink_port` выбирает только такие слоты. Менеджер не опрашивает слот (свободный слот — выключенный LXC): возможность записывает администратор в `slots.json` (`"features": ["uplink"]`, `lab-provision secrets` делает это при заданном `INET_BRIDGE`); сам слот в любом случае отклонит такую лабу `422` |
| `student-state` | слот | 🆕 состояние лабы переносится вместе с каталогом студента (`/opt/gns3/projects`): проект продолжается в любом слоте. Без этой возможности межслотовый `resume` не включается |

Новое имя добавляется в эту таблицу тем же изменением, что и код, который его объявляет.

## 9. Открытые вопросы

1. Состав `options` на первую версию: только `max_duration`, или сразу `mode` и `reset`?
2. Что ещё должно ехать в `run`: только `session_id` и `expires_at`, или, например, режим
   экзамена (если слот должен вести себя иначе)?
3. Ревизия лабы: продолжать старую ревизию всегда (как предложено) или давать преподавателю
   «обновить проекты студентов» (это пересоздание, то есть потеря работы)?
4. `ui` из `meta.json`: передавать в сессии плагину как есть или плагин читает подсказки только
   из `.gns3` и настроек активности?
5. Имена возможностей в §7 — устраивают?
6. ✅ Факты (§2.7, §4.6): результаты автопроверок лежат отдельно от журнала наблюдений (`check_runs`, DESIGN §10).
   Результат проверки ссылается на снимок, по которому посчитан (`facts_rev`), чтобы оценку можно было воспроизвести.
7. ✅ Факты: состав коллекторов и период пока задаёт слот (по умолчанию `linux.net`, 30 с). Настройка лабой
   появится вместе с `checks`: проверка объявит, какие коллекторы ей нужны.
