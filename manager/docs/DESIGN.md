# Менеджер лаб — дизайн (прототип 0.3)

Документ описывает, как устроен прототип в `manager/`, какие решения приняты и почему,
и что осталось согласовать. Вопросы к владельцу собраны в §11.

Главное:
- **слот не привязан к студенту**. Это взаимозаменяемый исполнитель: запускает текущую лабу
  с её ресурсами и освобождается. Следующая сессия того же студента может пойти в любой
  другой слот на любом узле;
- **всё привилегированное делает агент на узле Proxmox** (Lab Node Agent, `agent/` в ветке
  `feature/proxmox-node-agent`, mTLS): точки монтирования, `pct start`, действия в госте,
  `pct shutdown`/`stop`. Proxmox API менеджер использует только для чтения и для подгонки
  ресурсов CT — как и задумано в README агента;
- менеджер не трогает файловую систему CephFS: каталоги студентов готовит сторона Proxmox (§5).

## 1. Схема

```
Moodle (mod_gns3lab) ──HTTPS, Bearer + X-Moodle-Site──▶ Менеджер (FastAPI, один процесс)
                                                         │  ├─ PostgreSQL (локально в LXC менеджера)
                                                         │  └─ каталог лаб  /srv/gns3-ro/labs (RO CephFS)
                                                         ├──▶ Proxmox VE API: где CT, загрузка узлов, cores/memory
                                                         ├──▶ Lab Node Agent на узле CT (mTLS): mounts/start/stop
                                                         ├──▶ Lab Slot :8080 в LXC (deploy/stop, операции)
                                                         └──▶ шлюз консолей POST /internal/tickets
Браузер ──wss──▶ шлюз ──ws──▶ Lab Slot /v1/console/{project_id}/{node_id}
```

| Модуль | Что делает |
|---|---|
| `config.py` | `manager.env` и файлы секретов; fail closed; секреты не попадают в `repr` |
| `proxmox.py` | клиент PVE: перебор точек входа, `/cluster/resources`, config, ожидание UPID |
| `agent_client.py` | клиент Lab Node Agent: mTLS, классификация ошибок |
| `storage.py` | `student_key` по правилам агента |
| `db.py`, `migrations/` | пул psycopg, пронумерованные SQL-миграции |
| `store.py` | реестр слотов, сессии, рабочие копии, вызовы слота; fencing |
| `slot_client.py` | клиенты Lab Slot и шлюза |
| `labs.py` | каталог лаб, проверка `lab.gns3` ↔ `ticket.json`, ресурсы |
| `orchestrator.py` | размещение, конечный автомат сессии, восстановление, maxduration |
| `app.py` | API для плагина (SPEC §3), `/healthz`, `/readyz` |
| `admin.py`, `preflight.py` | команды оператора, проверка перед запуском |

## 2. PostgreSQL

**Драйвер — psycopg 3**, а не asyncpg. Один пакет даёт и async API (сервис), и sync API
(миграции, preflight, admin). Он понимает стандартные строки libpq, включая сокет с
peer-аутентификацией (`postgresql:///lab_manager`, без пароля). `psycopg[binary,pool]` ставится
из pip без системных пакетов. asyncpg быстрее, но нагрузка у нас — десятки запросов в
секунду, так что скорость не решает.

**Миграции** — файлы `migrations/NNN_имя.sql` и таблица `schema_migrations`. Каждая миграция
применяется одной транзакцией, только командой оператора `admin migrate` под advisory lock.
Сервис при старте лишь сверяет версию схемы. Данные Postgres лежат в `/var/lib/postgresql`
на rootfs LXC (RBD), не на CephFS.

| Таблица | Назначение |
|---|---|
| `slots` | реестр слотов: vmid, адрес, `state`, `generation`, `session_id`, `in_config` |
| `workspaces` | рабочая копия студента (site, user_id, instance_id, lab_ref): `project_id`, первый `ticket`, `deployed` |
| `sessions` | сессия для плагина: status/stage/сообщение, `student_key`, `project_id`, ресурсы, слот и его generation, узел, топология, сроки |
| `slot_calls` | каждый изменяющий вызов слота: action, **Idempotency-Key**, тело, operation_id, итог |
| `events` | журнал для оператора (без секретов) |

Уникальные индексы гарантируют одну живую сессию на студента и активность и одну живую
сессию на слот. Привязки «студент → слот» в схеме нет.

**Секреты слотов** (`SLOT_API_TOKEN`, `SLOT_CONSOLE_TOKEN`) в БД не хранятся. Они лежат в
`/etc/lab-manager/slots.json` (0600, вне Git и CephFS). Шифровать их в БД нет смысла: ключ всё
равно лежал бы рядом, в `manager.env`, а токены при этом попадали бы в дампы и бэкапы.
Секреты сайтов Moodle (по одному на сайт) лежат в `sites.json`. Секрет привязан к своему сайту,
поэтому один сайт не может выдать себя за другой.

## 3. Lab Node Agent (агент на узле Proxmox)

Сверено с `agent/agent.py` и `agent/README.md` из ветки `feature/proxmox-node-agent`. Клиент
менеджера (`agent_client.py`) прогнан против настоящего `agent.py` (pct и findmnt подменены):
агент принимает его строгий JSON и выполняет ровно ожидаемые команды `pct`.

Агент сам гарантирует: только mTLS (клиентский сертификат от `manager-client-ca`), только CT на
своём узле, с vmid из `LAB_VMID_MIN..MAX`, `unprivileged: 1` и тегом `labslot`; строгий JSON
(лишние поля и неверные типы — 422); пути только `<LAB_CEPH_ROOT>/slot[/<rev>]` и
`<LAB_CEPH_ROOT>/students/<key>`, без симлинков, на CephFS-монтировании. **Все предки** этих
путей должны принадлежать root хоста, быть без права записи для группы и остальных и без ACL.
Агент держит блокировку на каждый CT.

| Метод | Что делает | Как вызывает менеджер |
|---|---|---|
| `GET /slots/{vmid}/status` | `{"state": "running"\|"stopped"}` | перед каждым действием; после сбоя |
| `PUT /slots/{vmid}/mounts` | `mp0=<ceph>/slot[/<rev>]→/opt/slot,ro=1`, `mp1=<ceph>/students/<key>→/srv/student,ro=0\|1`; только на остановленном CT | при освобождении: `student_key=PLACEHOLDER_STUDENT_KEY`, `data_mode=ro` |
| `POST /slots/{vmid}/start` | те же mounts → повторная проверка путей → `pct start` → действия в госте | старт сессии: `student_key` студента, `data_mode=rw`, `code_revision=SLOT_CODE_REVISION`, `actions=AGENT_START_ACTIONS` (по умолчанию `["init_slot"]`) |
| `POST /slots/{vmid}/stop` | `pct shutdown --timeout 60` или `pct stop` при `force` | освобождение; `force=true` — только если shutdown не удался |

`init_slot` — это `/usr/local/sbin/lab-slot-init` внутри гостя (`agent/guest/lab-slot-init`):
`systemctl daemon-reload`, `/run/lab-slot`, `systemctl restart lab-slot.service`.

Как менеджер с ним работает:
- **Адрес агента.** Агент не проксирует запросы к другим узлам, поэтому менеджер обращается
  к агенту того узла, где сейчас стоит CT. Узел берётся из `GET /cluster/resources` (кеш 10 с),
  URL — по шаблону `AGENT_URL_TEMPLATE`, например `https://{node}.lab.local:8443`. Имя хоста
  должно совпадать с SAN сертификата узла (`make-demo-pki.sh`). На 404 «LXC not found on this
  node» (CT мигрировал) кеш сбрасывается.
- **mTLS.** Клиентский сертификат `manager.crt`/`manager.key` выпускает `manager-client-ca`,
  сертификат узла проверяется по `node-server-ca.crt` с проверкой имени. `verify=False` в
  менеджере нет.
- **Таймауты.** start — 330 с (`pct start` 120 с плюс до трёх действий по 45 с), stop — 100 с
  (shutdown 60 с плюс запас), прочее — 30 с.
- **Ошибки** (кодов у агента нет, только текст `detail`):

  | Ответ | Что делает менеджер |
  |---|---|
  | 422 «Required CephFS directory does not exist» при старте | сессия `failed` с кодом `STUDENT_DIR_MISSING`; слот возвращается в `free` (агент проверяет пути до `pct set`, CT не тронут) |
  | прочие 403 и 422 (диапазон, тег, предки не под root, ACL, валидация) | сессия `failed` с кодом `AGENT_REJECTED`, слот `failed`: нужна настройка |
  | 409 «in progress» | ждать |
  | 409 «must be stopped» | перечитать состояние |
  | 409 «Proxmox command failed» | при старте — сессия `failed`; при остановке — `force` |
  | 503, 504, таймаут, обрыв | исход неизвестен: на следующем шаге перечитать `status`, не повторять вслепую |
- **Старт не идемпотентен.** По README агента: при таймауте или упавшем действии гость может уже
  работать, монтирование не откатывается. Если CT уже `running` на этапе `ct_start`, менеджер
  не стартует его повторно, а проверяет `mp1` через `GET /lxc/{vmid}/config`: путь должен
  оканчиваться на `/students/<student_key>`, режим должен быть RW. Если там чужой каталог,
  сессия уходит в `failed` с кодом `WRONG_STUDENT_MOUNT`.
- **Координация.** Блокировка агента не защищает от параллельных `pct` или вызовов Proxmox API.
  Поэтому менеджер меняет `cores`/`memory` через API только на остановленном CT и строго до вызова
  агента, в той же задаче сессии. Слот при этом принадлежит одной сессии (fencing, §6.3).
- **Ресурсы лабы.** `meta.json` → `resources: {cores, memory_mb}` выставляются через
  `PUT /lxc/{vmid}/config`. Это работа Proxmox API, не агента. Bind mount через API менеджер не
  делает: в `pve-container` (`check_ct_modify_config_perm`) монтирование, отличное от `volume`,
  разрешено только при `$authuser eq 'root@pam'`, а у токена `authuser` — это `root@pam!имя`.

## 4. Proxmox API (чтение и ресурсы)

- `PVE_NODES` образуют кольцо, первым идёт последний ответивший узел. Ошибка соединения,
  таймаут или **502/503/504** выводят точку входа из оборота на `PVE_RETRY_AFTER` секунд,
  запрос уходит к следующей. Когда срок истекает, узел снова участвует. Если выведены все,
  их всё равно пробуют, начиная с давно упавшего.
- **4xx** — ответ про сам запрос. Переключения нет, сессия уходит в `failed` без повторов.
- **500/595/596 не переключают** (на согласование, §11, В3). 500 в Proxmox — обычная ошибка
  приложения, и если переключаться по ней, одна такая ошибка по кругу выведет из оборота весь
  кластер. 595/596 означают, что недоступен узел CT, а не точка входа.
- Изменяющий запрос (`PUT config`) повторяется на другом узле, только если он точно не ушёл.
  Иначе исход неизвестен (`PveUncertain`), и следующий шаг перечитывает конфиг.
- UPID: `GET /nodes/{node}/tasks/{upid}/status` до `stopped`, успех — только `exitstatus=OK`.
  Если узел задачи недоступен или ожидание истекло, состояние считается неизвестным и
  перепроверяется. Сейчас UPID нужен только на случай, если `PUT config` вернёт задачу; старт
  и остановка синхронны в агенте.
- TLS проверяется по `PVE_CA_FILE`. Заголовок: `Authorization: PVEAPIToken=USER@REALM!TOKENID=SECRET`.

## 5. Каталог студента

`student_key = "<site_slug>-<user_id>"`, например `main-42`. Это один компонент пути по правилам
агента (`[A-Za-z0-9][A-Za-z0-9_-]{0,63}`), уникальный для пары «сайт + пользователь».
Агент монтирует `<LAB_CEPH_ROOT>/students/<key>` в слот как `/srv/student` (RW), а у
освобождённого слота — `students/placeholder` (RO).

**Кто создаёт каталоги.** Агент требует, чтобы все предки (`/mnt/pve/data`, `students/`)
принадлежали root хоста и не были доступны на запись группе и остальным, а сам каталоги не
создаёт. Менеджер — непривилегированный LXC: его root на хосте имеет uid 100000. Значит, в
`students/` менеджер писать не может, и в 0.3 он этого больше не делает. Каталоги студентов
готовит сторона Proxmox:
- `students/` — `root:root 0755`, `students/placeholder` — `root:root 0755`, пустой;
- `students/<key>` — владелец `gns3` слота в пересчёте на хост (например, uid 1000 в слоте →
  101000), режим `0700`. Сам каталог может принадлежать гостю, агент проверяет только предков;
- пока создание не автоматизировано, сессия студента без каталога завершается понятной ошибкой
  `STUDENT_DIR_MISSING` («Каталог студента на CephFS не создан»), а слот остаётся свободным.

**Предложение разработчику агента (§11, В2).** Добавить идемпотентный
`PUT /students/{student_key}`, который создаёт `students/<key>` с фиксированными владельцем и
режимом из конфигурации агента и больше ничего не делает. Менеджер вызывал бы его на этапе
`ct_prepare` у агента узла слота. Контракт я не реализую, пока его нет в агенте.

**Результаты проверок.** Их нельзя класть внутрь `students/<key>`: этот каталог принадлежит
гостю, и гость может переименовать или удалить любой подкаталог, даже принадлежащий root
(sticky bit не мешает владельцу каталога). Поэтому результаты пойдут в отдельное дерево,
например `<LAB_CEPH_ROOT>/results/<key>/`, которое в слот не монтируется (или монтируется RO —
это потребует ещё одной точки монтирования в агенте). Писать туда будет менеджер через свою
RW-точку монтирования этого дерева. Это задача этапа «Автопроверки».

## 6. Слоты, размещение, сессии

### 6.1. Слот — исполнитель, прогресс — в каталоге студента

Слот берётся из свободных без учёта истории студента. Прогресс студента (проект GNS3 и
состояние лабы слота, которое сейчас лежит в SQLite в `/var/lib/lab-slot`) должен жить в его
личном каталоге `/srv/student`. Агент монтирует его в любой слот, где запускается сессия.
Перенос туда состояния слота — **задача Lab Slot, не менеджера**; пока это отложено.

Со стороны менеджера всё готово, режим выбирается настройкой `LAB_PERSISTENCE`:

| Режим | Что делает |
|---|---|
| `fresh` (по умолчанию, пока слот хранит состояние локально) | каждая сессия — новый `project_id` и новый deploy |
| `resume` | рабочая копия хранит `project_id` и точный `ticket` первого deploy, и каждая сессия делает deploy с ними (по `slot/README.md`, повторный deploy с прежним UUID открывает проект и ничего не пересоздаёт). Нынешний слот 0.3 в чужом слоте ответит `FAILED` «Provisioning completion is unknown»; менеджер покажет это как `SLOT_COLD_RESUME_UNSUPPORTED` |

Когда слот начнёт хранить состояние в `/srv/student`, достаточно переключить `LAB_PERSISTENCE=resume`.

### 6.2. Размещение («компактная укладка»)

Перед выдачей менеджер одним запросом `GET /cluster/resources` получает узлы и CT:
- кандидаты — свободные слоты (`free`, есть в конфиге), чей CT известен кластеру и чей узел `online`;
- потребность лабы — `resources.memory_mb`, а если ресурсов в лабе нет, то текущий `maxmem` CT;
- запас узла = `maxmem − mem − резерв − NODE_MEMORY_RESERVE_MB`. Резерв — память уже выданных
  слотов этого узла, чей CT ещё не запущен (иначе две лабы займут одно место);
- **best fit**: из подходящих берётся слот на узле, где после размещения останется меньше всего
  свободной памяти. Так узлы заполняются плотно, а большие свободные куски остаются для больших лаб;
- если места нет нигде, сессия ждёт в `queued` («Недостаточно ресурсов на узлах, ожидание…»).
  Если Proxmox недоступен — тоже ждёт, с сообщением «Proxmox недоступен».

Затем идёт транзакция: `SELECT … FOR UPDATE` сессии и первый свободный слот из упорядоченного
списка `FOR UPDATE SKIP LOCKED`. Параллельные выдачи берут разные слоты и не ждут друг друга.
CPU при размещении не учитывается (обычно его переподписывают), но `cores` у CT выставляется.
Перенос (миграцию) слотов между узлами ради уплотнения менеджер не делает (§11, В4).

### 6.3. Состояния слота

| state | значение |
|---|---|
| `maintenance` | новый слот из файла или выведен оператором; не выдаётся |
| `free` | свободен; CT выключен; смонтирована заглушка |
| `preparing` | выдан сессии: остановка, ресурсы, старт через агента |
| `ready` | Lab Slot готов (`readyz`), идёт deploy |
| `busy` | лаба READY, сессия `running` |
| `releasing` | остановка лабы, shutdown, заглушка |
| `failed` | ошибка; слот оставлен как есть, решает оператор |

Каждая выдача и освобождение увеличивают `slots.generation` (fencing). Любое изменение сессии
со слотом проверяет generation под `SELECT … FOR UPDATE`. Устаревший обработчик получает
`Fenced` и ничего не трогает. Оркестратор в кластере менеджеров один, его держит
`pg_try_advisory_lock`.

### 6.4. Сессия: статусы плагина, этапы, слот, агент

| status (SPEC §3) | stage | Агент / Proxmox | Lab Slot |
|---|---|---|---|
| `queued` | `wait_slot` | `/cluster/resources`, размещение | — |
| `starting` | `ct_prepare` | агент `status` (и `stop`, если CT запущен); `PUT cores/memory`; каталог студента | — |
| `starting` | `ct_start` | агент `start` (mounts + `pct start` + действия); проверка `mp1` | — |
| `starting` | `slot_ready` | — | `/healthz`, `/v1/readyz` |
| `starting` | `lab_submit` | — | `POST deploy` (Idempotency-Key) |
| `starting` | `lab_wait` | — | `DEPLOYING` → `STARTING` → `PROVISIONING` (процент в `status_message`) |
| `running` | `ready` | — | `READY`; раз в 30 с `GET status` |
| `stopping` | `lab_stop`, `lab_stop_wait` | — | `POST stop` → `STOPPING` → `STOPPED` |
| `stopping` | `ct_stop` | агент `stop`; при неудаче `force=true` (пишется в `events`) | — |
| `stopping` | `ct_park` | агент `PUT mounts` с заглушкой, RO | — |
| `stopped` | — | слот `free`, generation+1 | — |
| `failed` | — | слот `failed`, не тронут | лаба остаётся как есть |

Если остановку запросили во время старта, она выполняется в ближайшей безопасной точке.
Если deploy мог дойти до слота, лаба сначала штатно останавливается, иначе менеджер сразу
переходит к `ct_stop`.

**maxduration.** На этапе `ready` после `expires_at` менеджер сам останавливает лабу и
освобождает слот. Длительность пока берётся из `DEFAULT_MAX_DURATION` (§11, В5).

### 6.5. Вызовы слота и идемпотентность

- Перед HTTP-запросом в `slot_calls` записываются ключ `lm-<session>-<action>-<random>` и точное
  тело. Повтор после сбоя отправляет тот же ключ, и слот отвечает той же операцией.
- Опрос — `GET /v1/operations/{id}`. Успех — только `SUCCEEDED`.
- `STALE_IDEMPOTENCY_KEY`: если лаба `FAILED`, сессия `failed`; иначе старый ключ помечается
  `abandoned` и создаётся новый (новое намеренное действие).
- `OPERATION_IN_PROGRESS`: ждать. `INVALID_TRANSITION`: прочитать `GET /v1/labs/{pid}/status`;
  цель уже достигнута — готово, `FAILED` — сессия `failed`, переходное состояние — ждать.
- Прочие 409 и `FAILED` у операции переводят сессию в `failed`, а слот — в `failed`. Ничего не пересоздаётся.

### 6.6. Восстановление после рестарта менеджера

Живые сессии лежат в БД вместе с этапом и `slot_calls`. После рестарта цикл продолжает
работу, и каждый этап сначала читает реальность: статус CT у агента, `mp1` из конфига
Proxmox, тот же Idempotency-Key у слота, статус лабы перед остановкой. Ничего не удаляется
«на всякий случай». Тесты покрывают потерю ответа на старт (второго старта нет), рестарт
менеджера посреди deploy, повтор deploy после сбоя и миграцию CT во время ожидания.

## 7. Каталог лаб

`LABS_DIR/<lab_ref>/`:
- `lab.gns3` — эталон для `GET /api/v1/labs/{lab_ref}/topology`, отдаётся как есть;
- `ticket.json` — DeployTicket (`slot/api/models.py`). Менеджер сверяет состав имён нод с
  `lab.gns3` и подставляет `name` и `project_id` сессии;
- `meta.json` — `title`, `description`, `resources: {cores, memory_mb}` (необязательно, §11, В7);
- `checks/` — заготовка под автопроверки.

Сломанные лабы не попадают в `GET /api/v1/labs`, причину показывает `admin labs`.
Топология запущенной сессии строится из живого проекта (новые `node_id`). Из нод убираются
`properties` и номер консоли. `drawings` берутся из эталона: слот их не отдаёт, а на
`node_id` они не ссылаются.

## 8. API для плагина

Маршруты — ровно как в SPEC §3. Детали, которых в SPEC нет:
- авторизация: `Bearer` через `compare_digest` с секретом сайта из `X-Moodle-Site`
  (`wwwroot`, завершающий `/` отбрасывается);
- ошибки `{"error","message"}`: `unauthorized` 401, `invalid_request` 400, `lab_not_found` 404,
  `session_not_found` 404, `node_not_found` 404, `session_not_running` 409, `session_conflict` 409,
  `lab_invalid` 409, `gateway_unavailable` 502, `storage_unavailable` 503;
- `GET /sessions?user_id=&instance_id=`: живая сессия, а если её нет — последняя завершённая;
  404 — только если сессий не было вовсе;
- `POST /sessions` при живой сессии — `200` с ней; если `lab_ref` другой — `409 session_conflict`;
- `POST /stop` отвечает `status: "stopping"`;
- `console-tickets`: сессия `running`, нода из её топологии. В шлюз уходит
  `{"slot": адрес слота, "project_id", "nodes": [node_id], "readonly", "who": "<session_id>:owner|observer"}`.
  `issued_for_user_id` пишется только в `events`.

## 9. Эксплуатация

- `/healthz` — процесс жив. `/readyz` — БД со схемой нужной версии, оркестратор жив, каталог лаб доступен.
- `preflight` (ExecStartPre): конфиг и права 0600 на файлы секретов, CA Proxmox, сертификаты
  mTLS агента, каталог лаб, версия схемы.
- Логи: id сессий и vmid. Ни токенов, ни секретов, ни user_id (`student_key` тоже не логируется).

## 10. Позже (схема и API это не блокируют)

- **Автопроверки**: миграция `002_checks.sql` (`check_runs`: session_id, check_id, status, result
  jsonb, времена), маршруты `POST/GET /api/v1/sessions/{id}/checks`. Главная запись — в PostgreSQL,
  копия JSON — в отдельном дереве `results/<key>/` (пишет менеджер, §5). Moodle получает
  результат через API менеджера и БД менеджера не читает.
- **Факты о нодах** (`plugin/docs/live-state.md` §6): `GET …/state?since_rev=`, `POST …/state/refresh`.
  Ключи — `node_id` запущенного проекта, они уже есть в `sessions.topology`.

## 11. Вопросы к владельцу

- **В1. Пути агента и слота расходятся.** Агент монтирует код слота в `/opt/slot`, а Lab Slot
  требует `/srv/gns3-ro/slot` (`run.py`, `lab-slot.service`). Что правим: агента или слот?
  (`/srv/student` для каталога студента — по агенту, менеджеру это всё равно.)
- **В2. Создание `students/<key>`.** Агент требует root-предков, поэтому менеджер создавать каталоги
  не может (§5). Добавляем в агент `PUT /students/{student_key}`, или каталоги создаёт другой
  механизм на стороне Proxmox? Какой uid у `gns3` в слотах (владелец каталога)?
- **В3. 5xx у Proxmox** — переключаю точку входа только по 502/503/504 и ошибкам соединения (§4).
- **В4. Уплотнение.** Сейчас это только best fit при выдаче. Нужна ли миграция выключенных слотов
  между узлами?
- **В5. maxduration** в теле `POST /api/v1/sessions` отсутствует (SPEC §5.1 его имеет). Предлагаю
  необязательное поле `max_duration` в минутах.
- **В6. Коды ошибок агента.** Сейчас 403/409/422 различаются по тексту `detail`. Хорошо бы
  `detail: {"code", "message"}` (`SLOT_BUSY`, `NOT_STOPPED`, `PCT_FAILED`, `SOURCE_MISSING`, …).
- **В7. `resources` в `meta.json`** (cores, memory_mb) — моё дополнение. Оставить так?
- **В8. Шлюз.** Ключ слота в `GW_SLOTS` должен совпадать с `address` из `slots.json`; токены консоли
  шлюз пока получает отдельно.
