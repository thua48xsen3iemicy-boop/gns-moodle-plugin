# Менеджер лаб — дизайн (прототип 0.1)

Документ описывает, как устроен прототип в `manager/`, какие решения приняты и почему,
и что осталось согласовать. Вопросы к владельцу собраны в §10.

## 1. Схема

```
Moodle (mod_gns3lab) ──HTTPS, Bearer + X-Moodle-Site──▶ Менеджер (FastAPI, один процесс)
                                                         │  ├─ PostgreSQL (локально в LXC менеджера)
                                                         │  ├─ каталог лаб  /srv/gns3-ro/labs (RO CephFS)
                                                         │  └─ каталоги студентов /srv/lab-rw (RW CephFS)
                                                         ├──▶ Proxmox VE API (перебор точек входа, UPID)
                                                         ├──▶ Lab Slot :8080 в каждом LXC (deploy/resume/stop)
                                                         └──▶ шлюз консолей POST /internal/tickets
Браузер ──wss──▶ шлюз ──ws──▶ Lab Slot /v1/console/{project_id}/{node_id}
```

Код (`lab_manager/`):

| Модуль | Что делает |
|---|---|
| `config.py` | `manager.env` и файлы секретов; fail closed; секреты не попадают в `repr` |
| `proxmox.py` | клиент PVE: перебор нод, адресация CT по `/cluster/resources`, ожидание UPID |
| `storage.py` | каталоги студентов, защита путей, подключение каталога к слоту |
| `db.py`, `migrations/` | пул psycopg, пронумерованные SQL-миграции |
| `store.py` | реестр слотов, рабочие копии, сессии, вызовы слота; fencing |
| `slot_client.py` | клиенты Lab Slot и шлюза |
| `labs.py` | каталог лаб, проверка `lab.gns3` ↔ `ticket.json` |
| `orchestrator.py` | конечный автомат сессии, восстановление, maxduration |
| `app.py` | API для плагина (SPEC §3), `/healthz`, `/readyz` |
| `admin.py`, `preflight.py` | команды оператора, проверка перед запуском |

## 2. PostgreSQL

**Драйвер: psycopg 3**, а не asyncpg:
- один пакет даёт и async (сервис), и sync API (миграции, preflight, admin) — не нужен второй драйвер;
- стандартные строки libpq, включая сокет и peer-аутентификацию: `postgresql:///lab_manager` без пароля;
- `psycopg[binary,pool]` ставится из pip без системных пакетов; пул — официальный `psycopg-pool`.
asyncpg быстрее, но у нас десятки запросов в секунду, а не тысячи; скорость здесь не решает.

**Миграции**: `migrations/NNN_имя.sql` и таблица `schema_migrations`. Каждая миграция идёт
одной транзакцией. Миграции применяет только оператор (`admin migrate`, под advisory lock).
Сервис при старте лишь сверяет версию схемы и без совпадения не запускается.

**Где данные**: каталог данных Postgres — стандартный `/var/lib/postgresql` на rootfs LXC (RBD).
На CephFS он не лежит.

### Таблицы (`001_init.sql`)

| Таблица | Назначение |
|---|---|
| `slots` | реестр слотов: vmid, адрес, порт, профиль, `state`, `generation`, `session_id`, `in_config` |
| `workspaces` | рабочая копия студента: (site, user_id, instance_id, lab_ref) → закреплённый слот, `project_id`, `deployed` |
| `sessions` | сессия для плагина: status/stage/status_message, слот и его generation, UPID, топология, сроки |
| `slot_calls` | каждый изменяющий вызов слота: action, **Idempotency-Key**, тело, operation_id, итог |
| `events` | журнал для оператора (без секретов) |

Инварианты закреплены уникальными индексами: одна живая сессия на (site, user_id, instance_id)
и одна живая сессия на слот.

**Секреты слотов** (`SLOT_API_TOKEN`, `SLOT_CONSOLE_TOKEN`) в БД не хранятся. Они лежат в
`/etc/lab-manager/slots.json` (0600, вне Git и CephFS), туда же идут адрес, порт и профиль;
при старте эти поля зеркалируются в `slots`. Почему не «зашифрованно в БД»: ключ шифрования
всё равно лежал бы рядом, в `manager.env`, так что безопаснее не стало бы. Зато токены
попадали бы в дампы и бэкапы БД. Секреты сайтов Moodle (по одному на сайт) лежат в
`/etc/lab-manager/sites.json`. Секрет привязан к сайту, поэтому один сайт не может выдать
себя за другой.

## 3. Proxmox API

- `PVE_NODES` образуют кольцо. Первым идёт последний ответивший узел.
- Ошибка соединения, таймаут или **502/503/504** выводят точку входа из оборота на `PVE_RETRY_AFTER`
  секунд, запрос уходит к следующей. Когда срок истекает, узел снова участвует.
  Если выведены все узлы, их всё равно пробуют, начиная с давно упавшего.
- **4xx** — это ответ про сам запрос (права, параметры), поэтому переключения нет, ошибка
  возвращается вызывающему. Отказ по правам сразу переводит сессию в `failed` без повторов.
- **Отступление от постановки, на согласование (§10, В1).** Остальные 5xx, прежде всего 500,
  в Proxmox — обычная ошибка приложения: «CT already running», «config does not exist».
  Узел при этом исправен. Если переключаться по любому 5xx, одна такая ошибка по кругу
  выведет из оборота весь кластер. Поэтому 500 возвращается как ошибка. Коды 595 и 596
  («точка входа не достучалась до узла CT») тоже возвращаются: смена точки входа тут не поможет.
- Изменяющий запрос (start, shutdown, PUT config) повторяется на другом узле, только если он
  точно не ушёл (ошибка соединения). Если запрос был отправлен, а ответа нет (таймаут,
  502–504), исход неизвестен: клиент поднимает `PveUncertain`. На следующем шаге оркестратор
  читает реальное состояние CT и только потом действует.
- Узел CT каждый раз берётся из `GET /cluster/resources?type=vm` (кеш 10 с). После ошибок
  «config does not exist» и 595/596 кеш сбрасывается, поэтому миграция CT отслеживается.
- UPID: `GET /nodes/{node}/tasks/{upid}/status` до `status=stopped`, успех — только при
  `exitstatus=OK`. Узел берётся из самого UPID. Если узел задачи недоступен или ожидание
  истекло, состояние задачи считается неизвестным: менеджер перечитывает статус CT.
  UPID сохраняется в `sessions.pve_upid` до ожидания, так что после рестарта ожидание продолжается.
- TLS проверяется по `PVE_CA_FILE` (`pve-root-ca.pem`). Без CA клиент не создаётся.
  Заголовок: `Authorization: PVEAPIToken=USER@REALM!TOKENID=SECRET`.
- `shutdown` вызывается с `timeout=CT_SHUTDOWN_TIMEOUT`. `stop` применяется только как крайняя
  мера, если задача shutdown упала, и пишется в `events`.

## 4. Каталог студента и точки монтирования

### 4.1. Права (проверено по исходникам Proxmox)

- `pve-container`, `PVE::LXC::check_ct_modify_config_perm`: для `mpN`, у которого тип не `volume`
  (bind mount или устройство), выбрасывается `mount point type … is only allowed for root@pam`.
  Без проверки обходится только `$authuser eq 'root@pam'`.
- `pve-manager`, `PVE::HTTPServer`: при авторизации по API-токену пользователь — это
  **token-ID `root@pam!имя`**, а не `root@pam`. Значит, токен root@pam получит отказ
  **даже с `privsep=0`**. Вывод сделан по текущим исходникам ветки 9.x (pve-container 6.1.x).
  Логика давняя, но на вашей версии PVE её стоит проверить одной командой (README, «Проверка на стенде»).
- Остаются три пути:
  1. Билет `root@pam` по паролю (`/access/ticket` + CSRF). Тогда менеджер хранит пароль root
     всего кластера — **не рекомендую**.
  2. Агент на каждом узле PVE (mTLS, одна узкая операция, внутри `pct set`). Работает, но это
     код с правами root на десяти узлах и учёт миграции CT.
  3. **Постоянная точка монтирования и перенос каталога — выбран по умолчанию (`handover`).**

### 4.2. Режим `handover` (по умолчанию)

Администратор один раз прописывает каждому слоту постоянную точку монтирования:
`mp0: /mnt/pve/cephfs/lab/slots/<vmid>/mnt,mp=/opt/gns3/student`.
Менеджер видит то же дерево у себя (`/srv/lab-rw`, одна точка монтирования) и переносит каталоги
через `rename(2)`:

```
/srv/lab-rw/students/<site>/<user_id>/work/      каталог студента (виден слоту как /opt/gns3/student)
/srv/lab-rw/students/<site>/<user_id>/results/   результаты проверок; в слот не монтируется
/srv/lab-rw/students/<site>/<user_id>/.mounted   маркер «work сейчас в слоте <vmid>»
/srv/lab-rw/slots/<vmid>/mnt                     источник bind mount слота; у свободного — пустая заглушка
/srv/lab-rw/slots/<vmid>/empty                   заглушка, отставленная на время сессии
```

Подключение (CT остановлен): маркер → `mnt`→`empty` → `work`→`mnt`.
Отключение: `mnt`→`work` → `empty`→`mnt` → маркер удаляется.
Каждое переименование атомарно внутри одной CephFS. Состояние после сбоя однозначно
восстанавливается по файловой системе и маркеру (с номером vmid), повторный вызов
идемпотентен. Каталог чужого студента не выносится: без маркера с нужным vmid операция
отказывает.

Этому режиму не нужны права root в Proxmox: токену хватает `VM.Audit` и `VM.PowerMgmt`.

Режим `pve_config` реализован для полноты: `PUT /lxc/{vmid}/config` с `mp0=…` и
`delete=mp0` при освобождении, с теми же проверками путей. Он заработает только с
учётными данными, которые Proxmox признаёт за `root@pam` (см. 4.1). Режим `none`
не подключает каталог вообще и нужен для первых проб на стенде.

### 4.3. Только на остановленном CT

И перенос, и `PUT config` выполняются после того, как статус CT подтверждён как `stopped`.
Перед этим оркестратор при необходимости делает shutdown. Hotplug не используется.
Свободный слот поэтому держится выключенным, и запуск сессии включает старт LXC.

### 4.4. UID и владелец каталога

В непривилегированном LXC UID контейнера сдвинут: uid N внутри CT — это 100000+N на хосте
и в CephFS. Чтобы `gns3` в слоте мог писать в `work/`, а менеджер мог переносить этот каталог
(переносу каталога в другой родительский каталог нужно право записи на сам каталог),
**служебный пользователь менеджера и `gns3` в слотах должны иметь один и тот же числовой uid**
при одинаковой стандартной idmap (например, оба 1001, на хосте это 101001).
- Каталоги `students/<site>/<uid>/{work,results}` создаёт менеджер при первом запуске сессии:
  `work` — 0770, `results` — 0750.
- `students/`, `slots/` и `slots/<vmid>/mnt` один раз создаёт администратор на хосте PVE
  (команды в README, владелец 101001).
- `chown` менеджер не делает: он работает без root.

### 4.5. Результаты проверок недоступны слоту

`results/` лежит рядом с `work/`, но в слот не монтируется. Слот (а через него и студент)
не может ни писать туда, ни читать оттуда. Писать в `results/` будет менеджер, когда
появятся проверки (§9).

### 4.6. Защита путей

- Компоненты пути только из проверенных значений: slug сайта `[a-z0-9][a-z0-9_-]{0,31}`,
  `user_id` — положительное целое, vmid — целое. Без `..`, `/`, пробелов и не-ASCII.
- Обход дерева через `openat` с `O_NOFOLLOW|O_DIRECTORY` на каждом компоненте, переименования через
  `renameat` относительно этих дескрипторов. Подложенный симлинк нигде не уводит наружу.
- Для `mpN` путь и цель проверяются регуляркой `(/[A-Za-z0-9_.-]+)+`. Запятая или `=`
  добавили бы опции в строку свойства Proxmox (`…,shared=1`), поэтому они запрещены.
- Корни берутся из конфига и проверяются при загрузке: абсолютные, без `..`.

## 5. Слоты, сессии, состояния

### 5.1. Закрепление за слотом (открытый вопрос §5 постановки)

**Выбран вариант (а): рабочая копия студента закрепляется за слотом.**

- При первой выдаче `workspaces.slot_vmid` запоминает слот. Дальше эта рабочая копия
  запускается только на нём.
- Если слот занят другим студентом, сессия ждёт в `queued` («Ожидание освобождения вашего слота…»).
  Если слот в `failed`/`maintenance`, сессия ждёт оператора.
- Новые рабочие копии получают свободный слот нужного профиля, в котором меньше всего закреплённых копий.

| | (а) закрепление | (б) проект в каталоге студента + доработка слота |
|---|---|---|
| Код | только менеджер, слот без изменений | нужен «импорт» лабы в слот: перенос записи lab (manifest, `provisioned`) из SQLite слота |
| Надёжность | GNS3 открывает свой же проект, как в проверенном цикле Stop/Resume | новый путь, его надо проверить на QCOW2/NVRAM |
| Загрузка | студент ждёт свой слот, пока там другой; слоты загружены неравномерно | любой свободный слот |
| Отказ слота | рабочие копии этого слота недоступны до ремонта | можно перейти на другой слот |
| Масштаб | число активных студентов на слот ограничено диском и списком проектов GNS3 | без ограничения |

Наблюдение для (б). По `slot/README.md`, проекты уже лежат на общей RW CephFS
(`/opt/gns3/projects`), а блокировки проектов общие для всех слотов. Файлы, значит, уже
доступны из любого слота. Не хватает импорта: состояние лабы хранится в SQLite слота, а
README прямо говорит, что «импорт ранее неизвестного Slot проекта не подтверждает
выполненную преднастройку». Для (б) нужна доработка слота (явный import с переносом флага
`provisioned`). Это решение за вами.

### 5.2. Состояния слота

| state | значение |
|---|---|
| `maintenance` | новый слот из файла или выведен оператором; не выдаётся |
| `free` | свободен; CT выключен; заглушка `mnt` на месте |
| `preparing` | выдан сессии: shutdown/mount/start/readyz |
| `ready` | слот готов (readyz OK), идёт deploy/resume |
| `busy` | лаба READY, сессия `running` |
| `releasing` | остановка лабы, shutdown, отключение каталога |
| `failed` | ошибка в сессии; слот оставлен как есть; решает оператор |

Каждая выдача и освобождение увеличивают `slots.generation` (fencing). Любое изменение сессии
со слотом проверяет generation под `SELECT … FOR UPDATE`. Обработчик с устаревшим generation
получает `Fenced` и останавливается, не трогая новую сессию.

Выдача слота — одна транзакция: `SELECT … FOR UPDATE` сессии → `SELECT … FOR UPDATE SKIP LOCKED`
свободного слота → `generation+1`, `state=preparing` → сессия `starting`. Параллельные
выдачи берут разные слоты и не ждут друг друга.

Оркестратор в кластере менеджеров один: его держит `pg_try_advisory_lock` на отдельном
соединении. Второй экземпляр отвечает на API, но сессии не ведёт. В `/readyz` это видно по `leader`.

### 5.3. Сессия: статусы для плагина, этапы, слот и Proxmox

| status (SPEC §3) | stage | Proxmox / файловая система | Lab Slot |
|---|---|---|---|
| `queued` | `wait_slot` | — | — |
| `starting` | `ct_prepare` | shutdown, если CT запущен | — |
| `starting` | `mount` | CT `stopped` → перенос `work` (или `PUT mpN`) | — |
| `starting` | `ct_start` | start, UPID | — |
| `starting` | `slot_ready` | — | `/healthz`, `/v1/readyz` |
| `starting` | `lab_submit` | — | `POST deploy` (впервые) или `resume` |
| `starting` | `lab_wait` | — | `DEPLOYING` → `STARTING` → `PROVISIONING` (в `status_message` с процентом) |
| `running` | `ready` | — | `READY`; раз в 30 с `GET status` |
| `stopping` | `lab_stop`, `lab_stop_wait` | — | `POST stop` → `STOPPING` → `STOPPED` |
| `stopping` | `ct_shutdown` | shutdown (stop — крайняя мера) | — |
| `stopping` | `unmount` | CT `stopped` → `work` домой (или `delete=mp0`) | — |
| `stopped` | — | слот `free`, generation+1 | — |
| `failed` | — | слот `failed` и не тронут | лаба остаётся как есть |

Остановка, запрошенная во время старта, выполняется в ближайшей безопасной точке. Если
deploy/resume мог дойти до слота, лаба сначала штатно останавливается (`lab_stop`),
иначе менеджер сразу переходит к shutdown и отключению каталога.

**maxduration**: `expires_at = started_at + max_duration`. На этапе `ready` после этого
срока менеджер сам останавливает лабу и освобождает слот («Время лабы истекло»).
Сейчас длительность берётся из `DEFAULT_MAX_DURATION`, потому что контракт её не передаёт (§10, В2).

### 5.4. Вызовы слота и идемпотентность

- Перед HTTP-запросом в `slot_calls` записываются ключ `lm-<session>-<action>-<random>` и точное тело.
  Повтор после сбоя отправляет тот же ключ и то же тело, слот возвращает ту же операцию (`replayed`).
- Дальше опрос идёт через `GET /v1/operations/{id}`. Успех — только `SUCCEEDED`.
- `409 STALE_IDEMPOTENCY_KEY`: прошлый успех больше не действует. Если `laboratory.state=FAILED`,
  сессия уходит в `failed` (решает оператор). Иначе ключ помечается `abandoned` и создаётся новый.
  Это новое намеренное действие; например, deploy уже был — значит, теперь resume.
- `409 OPERATION_IN_PROGRESS`: ждать и повторить тем же ключом.
- `409 INVALID_TRANSITION`: менеджер читает `GET /v1/labs/{pid}/status`. Цель уже достигнута
  (READY или STOPPED) — вызов считается выполненным. `FAILED` — сессия `failed`. Переходное
  состояние — ждать.
- Прочие 409 (слот занят чужой лабой, манифест отличается) и 404 на resume/stop переводят
  сессию в `failed` со слотом `failed`.
- `FAILED` у операции или лабы ничего не пересоздаёт: сессия становится `failed` с понятным
  `status_message`, а слот `failed`.

### 5.5. Восстановление после рестарта менеджера

Состояние каждой живой сессии лежит в БД: stage, UPID и `slot_calls`. После рестарта цикл
просто продолжает работу, а каждый этап сначала читает реальность:
- есть UPID — ждать задачу; если её узел недоступен, сверить статус CT;
- перед переносом каталога — статус CT и расположение каталогов (маркер);
- перед deploy/resume/stop — тот же ключ из `slot_calls`, а при `lab_stop` ещё и статус лабы в слоте.

Ничего «на всякий случай» не удаляется и не пересоздаётся. Тесты покрывают рестарт с задачей
Proxmox в полёте, падение узла задачи и повтор deploy после сбоя.

Рестарт самого слота переводит его READY-лабы в FAILED (`slot/README.md`). Менеджер замечает
это при проверке `ready` и переводит сессию в `failed`. Автоматического resume нет:
решение за оператором.

## 6. Каталог лаб

`LABS_DIR/<lab_ref>/`:
- `lab.gns3` — эталон для `GET /api/v1/labs/{lab_ref}/topology`, отдаётся как есть;
- `ticket.json` — DeployTicket (`slot/api/models.py`). Полную проверку делает слот.
  Менеджер сверяет состав имён нод с `lab.gns3` и подставляет `name=<lab_ref>-w<workspace>`
  и `project_id` рабочей копии;
- `meta.json` — `title`, `description`, необязательный `profile` (профиль ресурсов слота, §10, В8);
- `checks/` — заготовка под автопроверки.

Сломанные лабы в `GET /api/v1/labs` не попадают, причину показывает `admin labs`.
Топология запущенной сессии строится из живого проекта (`GET /v1/labs/{pid}/topology`), то есть
с новыми `node_id`. Из нод выбрасываются `properties` (опции QEMU, пути, сокеты QGA) и номер
консоли. `drawings` берутся из эталона: слот их не отдаёт, а на `node_id` они не ссылаются.
Пример лабы: `examples/labs/cisco-3x2` (построен из `slot/examples/cisco-3x2.json`).

## 7. API для плагина

Ровно маршруты SPEC §3. Детали, которых в SPEC нет (на согласование, §10):
- авторизация — `Authorization: Bearer` сравнивается через `compare_digest` с секретом того
  сайта, что указан в `X-Moodle-Site` (`wwwroot`, завершающий `/` отбрасывается); иначе 401;
- ошибки: `{"error","message"}` — `unauthorized` 401, `invalid_request` 400, `lab_not_found` 404,
  `session_not_found` 404, `node_not_found` 404, `session_not_running` 409, `session_conflict` 409,
  `lab_invalid` 409, `gateway_unavailable` 502, `storage_unavailable` 503;
- `GET /sessions?user_id=&instance_id=` возвращает живую сессию, а если её нет — последнюю
  завершённую (`stopped`/`failed`, чтобы плагин показал итог). 404 — только если сессий не было вовсе;
- `POST /sessions` при живой сессии отвечает `200` с ней. Если `lab_ref` у живой сессии другой —
  `409 session_conflict`;
- `POST /stop` всегда отвечает `status: "stopping"` (для `queued` сессия через мгновение станет `stopped`);
- `console-tickets`: сессия должна быть `running`, нода — из топологии сессии. В шлюз уходит
  `{"slot": адрес слота, "project_id", "nodes": [node_id], "readonly", "who": "<session_id>:owner|observer"}`;
  `issued_for_user_id` пишется только в `events` (БД), но не в логи и не в шлюз;
- `topology` и `nodes` отдаются только при `running`. Статусы нод живые (кеш 3 с), при
  недоступности слота — последний снимок.

## 8. Эксплуатация

- `/healthz` — процесс жив. `/readyz` — БД со схемой нужной версии, оркестратор жив, каталоги
  лаб и студентов доступны.
- `preflight` (ExecStartPre): конфиг и права на файлы секретов (0600), CA, каталоги, одна
  файловая система у `students` и `slots` (иначе `rename` даст EXDEV), версия схемы БД.
- Логи: id сессий и vmid. Ни токенов, ни секретов, ни user_id.

## 9. Позже (схема и API это не блокируют)

- **Автопроверки**: миграция `002_checks.sql` с таблицей `check_runs` (session_id, check_id, status,
  result jsonb, started/finished). Маршруты `POST/GET /api/v1/sessions/{id}/checks`. Главная запись —
  в PostgreSQL, копия JSON — в `students/<site>/<uid>/results/` (пишет менеджер). Moodle получает
  результат через API менеджера (или web service Moodle) и не читает БД менеджера.
- **Факты о нодах** (`plugin/docs/live-state.md` §6): `GET /api/v1/sessions/{id}/state?since_rev=`,
  `POST …/state/refresh`. Ключи — `node_id` запущенного проекта, их уже содержит `sessions.topology`.
