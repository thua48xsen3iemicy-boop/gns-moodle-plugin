## 4. Просьбы менеджера к плагину

### М1. Сниппеты — только для Cisco-нод

`IOS_PREFIX` (`Ctrl-U`, `Enter`, `Ctrl-Z`, `enable`) уходит в любую ноду. В Linux-консоли (ноды
Debian, `node_type: qemu`) `Ctrl-Z` приостановит запущенную программу (например `ping`), а `enable`
выполнит встроенную команду bash. Показывайте полоску сниппетов только для нод IOL (`node_type: iou`)
или по признаку из лабы, когда он появится.

### М2. Вставка больших текстов — кусками

Шлюз принимает от браузера сообщения до 64 КБ (`MAX_MSG`); больше — соединение рвётся. Вставку
конфига разбивайте на кадры, например по 4–16 КБ.

### М3. Новые поля в консоли и на странице

- `409 node_not_running` при получении билета — сразу «Нода остановлена», без попыток переподключения;
- `nodes_stale: true` — при закрытии 4000 не считать `started` достоверным: «Состояние нод неизвестно»
  и переподключение с обычной паузой (или кнопка);
- `stage`/`progress` — свои тексты на языке сайта, `status_message` — подробностью;
- `error.retryable` — «Запустить снова» или «Сообщите преподавателю» с кодом;
- `conflict` в `409 session_conflict` — ссылка на ту активность;
- `unsupported_field` — это ошибка плагина (послал то, чего нет в `info`), стоит писать в журнал Moodle.

### М4. `info` и `options`

Читайте `GET /api/v1/info` (кеш на несколько минут) и передавайте `options.max_duration` из
`maxduration` активности, когда `max_duration` есть в `info.options`. `client` — по желанию.

### М5. Остановка преподавателем

Если владелец разрешит — передавайте `requested_by_user_id` (id преподавателя) в `POST /stop`.

### М6. Mock-менеджер

Просьба обновить `devtools/mock-manager` под §3: `info`, новые поля сессии, `node_not_running`,
`nodes_stale`, `conflict`, список сессий активности, `unsupported_field`.

### М7. Размер окна консоли

Кадры `{cols, rows}` продолжайте слать: сейчас их отбрасывает шлюз, а слот не согласует размер
окна (telnet NAWS), поэтому длинные строки на IOS переносятся по 80 колонкам. Это доработка шлюза и
слота; плагину менять ничего не нужно.

## 7. Менеджер 0.5.1: работа студента всегда сохраняется

Решение владельца: режим один. Следующий запуск студента **всегда продолжает его проект** в любом
слоте. Режима «новый проект на каждый запуск» (`fresh`) больше нет. Проект GNS3 лежит в каталоге
студента на CephFS, его поднимает любой слот. Слот 0.4.0 хранит там же и свою запись о лабе.

Что это значит для плагина:

- **`resume` в `info.features` есть всегда.** Предупреждение «Работа не сохранится» больше не
  показывается. Вместо него можно предупредить о том, что сохраняется **диск, а не память**: ноды
  поднимаются как после перезагрузки. У Debian остаётся всё записанное на диск, у Cisco — только то,
  что студент сохранил командой `write memory`.
- **Один проект на «студент × активность × лаба».** У лабы из Moodle — на `lab_def`: новая
  опубликованная версия означает новый проект, старая работа в ней не смешивается с новой. Имя
  проекта в `topology.name` теперь постоянное (`<lab>-w<номер>`), а не своё у каждой сессии.
- **`node_id` между сессиями одного проекта не меняются**: это тот же проект GNS3. Привязку
  подписей по `name` (М8.1) это не отменяет: у новой версии лабы проект новый.
- **«Начать заново»** (`options.reset`) — будущая возможность. Появится в `info.options`, когда
  будет сделана.
- **Mock-менеджер:** `resume` всегда в `features`, повторный запуск отдаёт ту же топологию.

Новых полей и кодов нет. `SLOT_COLD_RESUME_UNSUPPORTED` остаётся только для проектов, созданных
старым слотом 0.3. На стенде это проекты прежнего режима `fresh`; продолжать их не нужно.

### М9. Сохранение конфигураций при остановке не по кнопке — предложение

Лабу останавливает не только студент. Менеджер сам останавливает её по `expires_at`
(`maxduration`), и её может остановить преподаватель. Тогда `write memory` никто не отправит, и
несохранённая конфигурация Cisco пропадёт. Предложение:

- за 5–10 минут до `expires_at` показывать студенту предупреждение с кнопкой «Сохранить конфигурации»
  (тот же механизм, что у «Остановить»). `expires_at` есть в каждой сессии;
- в остановке преподавателем — та же галочка, но консоли открывает уже преподаватель (билеты
  наблюдателя здесь не подходят: они только для чтения). Это решение за владельцем; если сложно, хватит
  первого пункта.

Менеджеру для этого ничего менять не нужно.


## 9. Консоль: сверка всей цепочки (плагин 0.4.4, слот 0.4.1)

Сверено по коду: `amd/src/console.js`, `amd/src/keyboard.js`, `classes/external/get_console_ticket.php`,
`gateway/console_gateway.py` (ветка `claude/beautiful-turing-ju7n54`, коммит dcfa36f), `slot/api/console.py`
(ветка `claude/optimistic-franklin-fod7zc`, коммит 4a76116) и `console-tickets` менеджера.

**Что сходится.** Цепочка браузер → Moodle (билет) → менеджер → шлюз (одноразовый билет на 30 с) → слот
(`/v1/console/{pid}/{nid}`, консольный токен) → telnet ноды собрана правильно:

- адрес слота в билете совпадает с ключом `GW_SLOTS`, а токен слота в браузер не попадает;
- чужая лаба всегда только для чтения, и ввод наблюдателя отбрасывается дважды: в плагине и в шлюзе;
- `409 node_not_running` переводит консоль в ожидание запуска ноды;
- telnet-согласование вырезает слот, `0xFF` в данных сохраняется, а xterm.js сам собирает UTF-8 из кусков;
- кадры `{cols, rows}` шлюз правильно отбрасывает. Слот сейчас считает любой кадр вводом и напечатал бы
  этот JSON в консоль устройства. Размер окна — это `lab-slot.2` шлюза и слота (ALIGNMENT слота §3.5);
  плагину менять ничего не нужно.

### М10. Переподключение раз в секунду без конца — *исправить до стенда*

Когда слот не пускает к консоли, шлюз **сначала принимает** соединение браузера (`browser.prepare`), а
потом сразу закрывает его кодом 4000. Слот не пускает, например, когда в `GW_SLOTS` неверный токен,
слот недоступен из шлюза или telnet ноды ещё не поднялся. Браузер успевает получить `onopen`, и
`opened()` обнуляет `attempt`. Затем `closed()` с кодом 4000 спрашивает статус ноды, менеджер отвечает
`started`, и `retry()` ждёт `BACKOFF[0]` = 1 с. Так по кругу, пауза не растёт. В терминале — пары строк
«Подключено / Переподключение через 1 с», и каждую секунду идут запрос билета (Moodle → менеджер →
шлюз) и опрос сессии.

Предложение (лучше оба пункта):

1. `console.js`: сбрасывать `attempt` не в `opened()`, а после первого сообщения от ноды или после
   ~10 с живого соединения. Тогда при любом «открылось и сразу закрылось» паузы растут до 30 с.
2. Шлюз: если подключиться к слоту не удалось, закрывать **другим кодом**, например `4001` «консоль
   недоступна», а `4000` оставить для «консоль закрылась на стороне слота». Плагин покажет понятный
   текст («Консоль устройства недоступна, повтор через N с») вместо «Подключено». Можно вместо этого
   отказывать браузеру ещё до рукопожатия (HTTP 502): `onopen` тогда не наступит, но причину браузер
   не узнает.

### М11. Вставка большого конфига в Cisco — *проверить на стенде*

`send()` режет вставку на кадры по 4096 символов, и они уходят подряд, без пауз. Слот пишет их в telnet
так же быстро. IOS на IOU при быстрой вставке длинного конфига известен тем, что теряет символы и строки.
Проверьте на стенде вставку конфига на 200–300 строк. Если строки теряются — для нод `iou` слать
построчно с паузой (например, 20–50 мс на строку) или ждать эха строки перед следующей. Последовательности
командной панели (`enable`, `configure terminal`, …) короткие, их это не касается.

### М12. `GW_ALLOWED_ORIGINS` — обязательная настройка шлюза

При пустом `GW_ALLOWED_ORIGINS` шлюз пускает WebSocket с любого сайта. От чужих подключений защищает и
одноразовый билет, но лучше закрыться наглухо: без этой настройки шлюз не стартует (как без
`GW_INTERNAL_KEY` он не выдаёт билеты). В чек-листе стенда origin Moodle уже есть (§2, В1).

Менеджеру по этой сверке ничего менять не нужно.


## 10. Ответ на плагин 0.4.5 и где работает шлюз консолей

**М10–М12** — видел, спасибо: всё сделано так, как предлагалось. Менеджеру по ним ничего не нужно.

**Решение владельца: шлюз консолей работает в LXC менеджера.** Это отдельный процесс, один на все слоты.
Отвечает на открытый вопрос SPEC «общий адрес шлюза или по одному на узел Proxmox»: общий. Схема и
переменные описаны в README менеджера, §1.1:

```
браузер ──wss──> nginx :443  /console/  ──ws──> шлюз 127.0.0.1:8080 ──ws──> слот :8080 /v1/console/…
менеджер 127.0.0.1:8090 ──http──> шлюз 127.0.0.1:8080/internal/tickets
```

Что нужно от плагина (шлюз — ваш код):

1. **systemd unit шлюза** для этого LXC: свой пользователь без прав, `GW_HOST=127.0.0.1`, `GW_PORT=8080`,
   секреты (`GW_INTERNAL_KEY`, `GW_SLOTS`) из файла в `/etc/…` с правами 0600, а не в самом unit.
   Менеджер слушает 8090, так что порты не пересекаются.
2. **Пример конфига nginx**: наружу публикуется только `location /console/` (WebSocket: `Upgrade`,
   `Connection`, `proxy_read_timeout` больше 25 с). `/internal/tickets` наружу не публикуется.
3. Обновить в SPEC вопрос про адрес шлюза: «общий, в LXC менеджера».

Если удобнее по-другому (например, свой порт по умолчанию или отдельный пользователь на оба
сервиса) — пишите, поправлю README менеджера. Менеджеру со своей стороны менять нечего:
`GATEWAY_INTERNAL_URL=http://127.0.0.1:8080` в `manager.env.example` уже такой.
