# CLAUDE.md — mod_gns3lab

Moodle-плагин (модуль активности) для лабораторных работ в GNS3: студент открывает элемент курса,
видит схему топологии и работает в консолях устройств прямо на странице Moodle.
Лабы запускаются в LXC-слотах Proxmox внешним сервисом (менеджером), консоли идут через отдельный шлюз.

Полное задание, контракты и этапы — в `docs/SPEC.md`. Прочитай его целиком перед работой.

## Параметры проекта

- **Moodle: 5.1** (раскладка с `public/`: плагин ставится в `public/mod/gns3lab`). Если версия другая — спроси, не угадывай.
- PHP: тот, что требует эта версия Moodle.
- Язык общения с владельцем проекта: **русский**. Комментарии в коде и коммиты — на английском (стандарт Moodle).
  Языковые строки: `lang/en` обязательно, `lang/ru` — полный перевод.

## Раскладка репозитория

```
plugin/        корень плагина mod_gns3lab (монтируется в public/mod/gns3lab dev-Moodle)
gateway/       шлюз консолей (готов, Python/aiohttp) + тест против поддельного GNS3
devtools/      mock-менеджер, docker-compose для dev-окружения, скрипты (создать на этапе 0)
prototypes/    рабочие прототипы UI — эталон поведения, НЕ код для копирования как есть
fixtures/      пример .gns3 (11 нод, все типы линков) и демо «живых» данных
docs/          SPEC.md и прочая документация
```

## Жёсткие правила

1. **Права проверяются только на сервере.** Флаги в JS (`observer` и т.п.) — лишь для отрисовки UI.
   Каждая external function: `validate_parameters` → `validate_context` → `require_capability` → проверка групп/владения.
2. **Moodle не проксирует WebSocket.** Браузер ходит в шлюз напрямую по одноразовому билету.
   Билет Moodle получает у менеджера сервер-сервер. Токены GNS3 и секрет менеджера никогда не попадают в браузер.
3. **Только AMD-модули.** Никаких `<script>` через `$PAGE->requires->js()` для библиотек: на странице RequireJS,
   UMD-сборка xterm.js вызовет анонимный `define()` и сломает страницу. xterm.js и addon-fit кладутся в `amd/src/`
   как сторонние библиотеки и регистрируются в `thirdpartylibs.xml`. CSS — в `styles.css` плагина.
4. **`amd/build` коммитится** и пересобирается после каждого изменения `amd/src` (`grunt amd` в dev-Moodle).
5. Любое изменение в `db/` (install.xml, access.php, services.php) — подними `version.php` и, если нужно, `db/upgrade.php`.
6. SVG из `.gns3` (`topology.drawings[].svg`) — недоверенные данные. Только через санитайзер по белому списку
   (см. `sanitize()` в `prototypes/topology-viewer.html`), никогда `innerHTML` как есть. Весь текст в HTML — через экранирование.
7. Внешние HTTP-вызовы из PHP — только классом `\core\http_client` (или `curl` Moodle), с таймаутами.
   Адрес менеджера, секрет и адрес шлюза — настройки плагина (`settings.php`), секрет хранить как `admin_setting_configpasswordunmask`.
8. Privacy API обязателен: провайдер с `external_location_link` (ID пользователя уходит менеджеру).
9. Не добавляй зависимостей без необходимости. Фронтенд — ванильный JS (как в прототипах), без React/Vue/бандлеров.

## Прототипы: что из них брать

- `prototypes/topology-viewer.html` — рендер `.gns3` в SVG: координаты нод (x/y — левый верхний угол, центр = x+w/2),
  параллельные линки, подписи портов вдоль линка, фильтры и suspend на линках, санитайзер drawings,
  жесты (pan, pinch, колесо, двойной тап, инерция), шторка на телефоне со свайпом, панель сведений, Proxmox-гости.
  Переносить в `amd/src/topology.js` + Mustache-шаблон, сохранив поведение. Оформление — через переменные Moodle
  (тема Boost/Bootstrap), а не жёстко заданные цвета прототипа; тёмную тему не ломать.
- `prototypes/console.html` — xterm.js с полоской мобильных клавиш, сниппетами, кликабельными именами портов,
  режимом наблюдателя, подгонкой под экранную клавиатуру (`visualViewport`). Имитатор IOS внутри — только для демо,
  в плагин его не переносить: в плагине терминал подключается к шлюзу (см. SPEC, «Контракт шлюза»).
- `gateway/console_gateway.py` — готовый шлюз. Менять его можно, но контракт (билеты, кадры, коды закрытия) —
  только синхронно с SPEC и тестом `gateway/tests/test_gateway.py`.

## Dev-окружение

- Moodle — через `moodle-docker` той же версии; `plugin/` монтируется в `public/mod/gns3lab`.
- Менеджера пока нет: используй mock из `devtools/mock-manager` (создать по SPEC). Шлюз в dev может смотреть
  на поддельный GNS3 (как в тесте шлюза) или на реальный слот, если владелец даст адрес.
- Проверки перед коммитом: `moodle-plugin-ci phpcs` (стандарт moodle), `phplint`, `phpdoc`, PHPUnit и Behat плагина,
  `python3 gateway/tests/test_gateway.py`.
- Режим разработчика Moodle включён, после правок — сброс кэшей (`admin/cli/purge_caches.php`).

## Как работать

- Иди по этапам из SPEC. В конце этапа — краткий отчёт: что сделано, как проверить руками, что осталось.
- Если в SPEC противоречие или не хватает решения — спроси, а не выдумывай контракт.
- Мелкие коммиты с понятными сообщениями. Не коммить секреты, `.env`, дампы БД.
