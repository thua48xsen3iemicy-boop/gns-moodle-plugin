## 0. Что плагин уже делает с API менеджера

Ветка `claude/beautiful-turing-ju7n54`, версия плагина 0.2.0. Всё ровно по SPEC §3, сверх неё плагин **ничего не
отправляет** (CONTRACTS §1.3): ни `options`, ни `client`, пока нет `GET /api/v1/info`.

| Когда | Запрос | Что плагин берёт из ответа |
|---|---|---|
| рендер страницы активности | `GET /api/v1/labs/{lab_ref}/topology` | `.gns3` целиком (превью). Ошибка — демо-лаба и предупреждение |
| кнопка «Запустить лабу» | `POST /api/v1/sessions` `{user_id, instance_id, lab_ref, course_id}` | объект сессии |
| опрос страницы | `GET /api/v1/sessions?user_id=&instance_id=` | раз в 3 с при `queued/starting/stopping`, раз в 15 с при `running`, не опрашивает при `stopped/failed` и без сессии |
| кнопка «Остановить лабу» | сначала `GET /sessions?…`, потом `POST /sessions/{id}/stop` | объект сессии |
| открыть консоль | сначала `GET /sessions?…`, потом `POST /sessions/{id}/console-tickets` `{node_id, readonly, issued_for_user_id}` | `ticket`, `gateway_url`, `expires_in` |
| консоль закрылась с кодом 4000 | `GET /sessions?…` | `nodes[node_id].status`: не `started` — «Нода остановлена», иначе переподключение через 1 → 2 → 4 … 30 с |

Ещё о том, как плагин работает с API:
- **`session_id` плагин не хранит.** Сессию он каждый раз находит по `user_id` + `instance_id` (SPEC §5.1: состояние
  не дублируем). Поэтому перед каждым билетом и перед остановкой идёт `GET /sessions?…`. Браузер `session_id` видит,
  но ничего по нему не запрашивает.
- **Поля сессии, на которые плагин опирается:** `session_id`, `status`, `status_message`, `started_at`, `expires_at`,
  `topology.topology.{nodes,links,drawings}`, у нод — `node_id`, `name`, `x`, `y`, `width`, `height`, `symbol`, `label`,
  `node_type`, `ports`, `console_type`; `nodes{}` — `status`, `console_type`. Неизвестные поля плагин игнорирует.
- **Билет.** Плагин сам проверяет, что нода есть в `topology` сессии, и не просит билет к ноде с `console_type`
  `vnc`/`none`. У чужой лабы `readonly` всегда `true`, это решает сервер Moodle. `gateway_url` берётся из ответа
  менеджера, а если его нет — из настройки плагина `gatewayurl`. К адресу плагин дописывает `/console/<node_id>?ticket=…`.
- **Ошибки.** Плагин показывает свой локализованный текст по коду `error` (`session_conflict`, `lab_not_found`,
  `lab_invalid`, `session_not_running`, `node_not_found`, `gateway_unavailable`, `unauthorized`, остальные — общий
  текст). `message` менеджера уходит только в отладочную информацию Moodle.
- **Сеть.** HTTP-таймаут — настройка плагина, по умолчанию 10 с. Блок-лист curl Moodle (частные сети, нестандартные
  порты) к адресу менеджера не применяется: адрес задаёт только администратор сайта.

## 1. Просьбы

### П1. Список сессий активности для наблюдателя — *блокирует этап 3 плагина*

На странице преподавателя нужен список студентов со статусами их лаб. Сейчас это один `GET /sessions?…` на каждого
студента, то есть десятки запросов при каждом открытии страницы.

Предложение:

```
GET /api/v1/sessions?instance_id=7
→ [{"user_id": 42, "session_id": "s-…", "status": "running", "started_at": "…", "expires_at": "…"}, …]
```

По одной записи на студента: живая сессия или последняя завершённая, как в `GET /sessions?user_id=&instance_id=`.
`topology` и `nodes` не нужны. Пустой список — сессий нет. Фильтр `user_id` при этом не обязателен.

### П2. `stage` и `progress` в сессии — *не блокирует*

`status_message` написан по-русски, а сайт Moodle может быть и на английском. Плагин хотел бы строить текст сам, а
`status_message` показывать как подробность. Для этого не хватает этапа:

```json
{"status": "starting", "stage": "lab_wait", "progress": 40, "status_message": "Проверка устройств… 40%"}
```

`stage` — значения из DESIGN §6.4 (`wait_slot`, `ct_prepare`, `student_dir`, `ct_start`, `slot_ready`, `lab_submit`,
`lab_wait`, `ready`, `lab_stop`, `lab_stop_wait`, `ct_stop`, `ct_park`). `progress` — процент, если известен, иначе
поля нет. Оба поля необязательные: по CONTRACTS §1.2 старый плагин их проигнорирует.

### П3. Подробности конфликта в `409 session_conflict` — *не блокирует*

Сейчас студент видит «У вас уже запущена другая лаба», но не знает, где именно. Предложение — добавить в тело ошибки:

```json
{"error": "session_conflict", "message": "…",
 "conflict": {"instance_id": 5, "course_id": 3, "lab_ref": "ospf-1", "status": "running"}}
```

Плагин покажет ссылку на ту активность (если у студента есть к ней доступ). Это данные того же студента и того же
сайта, так что чужого ничего не утекает.

### П4. `error` у `failed`-сессии — *не блокирует, поддерживаю CONTRACTS §2.3*

Плагин сделает так: при `retryable: true` — кнопка «Запустить снова», при `false` — «Сообщите преподавателю» и код
для обращения. Просьба: перечислите в CONTRACTS все коды, которые могут прийти (`SLOT_START_FAILED`,
`STUDENT_DIR_MISSING`, `AGENT_REJECTED`, `WRONG_STUDENT_MOUNT`, `SLOT_COLD_RESUME_UNSUPPORTED`, `unsupported_lab`, …),
и для каждого — `retryable`. Под коды, которые увидит студент, плагин заведёт тексты.

### П5. Билет к остановленной ноде — *не блокирует*

Сейчас менеджер выдаёт билет к любой ноде из топологии. Если нода остановлена, шлюз закрывает сокет с 4000, и плагин
делает ещё один `GET /sessions`, чтобы понять причину. Предложение: `console-tickets` отвечает
`409 {"error": "node_not_running"}`, если `nodes[node_id].status != "started"` (с учётом вашего кеша в 3 с). Тогда
плагин сразу покажет «Нода остановлена». Код нужно добавить в CONTRACTS §2.4.

### П6. Признак, что статусы нод устарели — *не блокирует*

`live_nodes()` при ошибке слота молча отдаёт снимок из `sessions.topology`. Для плагина это значит: после 4000 он
увидит `started` у упавшей ноды и будет переподключаться с паузой до 30 с, а не скажет «нода остановлена».
Предложение: необязательное поле `nodes_stale: true`, когда отдан снимок. Плагин тогда напишет «Состояние нод
неизвестно» вместо бесконечных попыток.

### П7. Зафиксировать в контракте имена портов в живой топологии — *не блокирует*

`properties` у нод живой топологии пустые, поэтому имена портов из `ports_mapping` плагину недоступны. Плагин теперь
берёт их из `nodes[].ports[].short_name | name`: `ports` у вас в `NODE_KEYS` уже есть. По этим именам консоль
подсвечивает порт на схеме, когда студент нажимает `Gi0/1` в выводе. Просьба:
- записать в CONTRACTS §2.3, что `ports` (с `name`, `short_name`, `adapter_number`, `port_number`) и
  `links[].nodes[].label` в живой топологии сохраняются;
- проверить, что Lab Slot в `GET /v1/labs/{pid}/topology` вообще отдаёт `ports`. Если нет, то откуда их взять (В6).

## 2. Вопросы

### В1. Адрес шлюза — *нужно подтверждение*

Плагин берёт `gateway_url` из ответа на билет, так что менеджер может выдавать разные шлюзы для разных узлов
(SPEC §8, вопрос 4). Подтвердите формат: `ws://` или `wss://`, хост, порт, путь — **без `/` на конце**, к нему плагин
дописывает `/console/<node_id>?ticket=…`. И ещё: менеджер всегда отдаёт `gateway_url`? Если да, настройку
`gatewayurl` в плагине оставлю только как запасную.

### В2. Остановка лабы преподавателем — *решает владелец, нужно мнение менеджера*

SPEC §8, вопрос 2. Технически `POST /stop` по `session_id` уже работает для любой сессии сайта. Если владелец
разрешит, хотите знать, кто остановил? Предложение: необязательное тело `POST /stop {"requested_by_user_id": 17}` —
только для журнала `events`, как `issued_for_user_id` у билета.

### В3. Сохраняется ли работа студента — *нужно для текстов плагина*

При `LAB_PERSISTENCE=fresh` каждая сессия начинается с нуля. Тогда студента надо честно предупредить на кнопке
«Остановить»: «Работа не сохранится». Как плагину узнать режим? Предложение: возможность `resume` в
`GET /api/v1/info → features`, когда менеджер продолжает проект. Нет `resume` — плагин предупреждает.

### В4. Повторный запуск после `failed` и `stopped` — *нужно подтверждение*

По коду `POST /sessions` после `failed` или `stopped` создаёт новую сессию и отвечает `201`. Верно? А в `GET /sessions`
после этого приходит уже новая сессия (последняя по времени)?

### В5. Частота опроса — *нужно подтверждение*

Одна открытая вкладка студента — это `GET /sessions` раз в 3 с при переходных статусах и раз в 15 с при `running`.
Плюс по одному запросу на каждое открытие консоли и каждое переподключение. На 30 студентов в аудитории это до
~10 запросов в секунду в пике. Устраивает? Если нужен другой интервал, скажите — поменяю.

### В6. Откуда имена портов, если слот не отдаёт `ports` — *если ответ на П7 «не отдаёт»*

Варианты: менеджер берёт `ports_mapping` и имена из эталонного `lab.gns3` по имени ноды (как сейчас `drawings`);
или имена задаются в `ticket.json`. Как вам удобнее?

## 3. Ответы на открытые вопросы CONTRACTS §9 (со стороны плагина)

1. **Состав `options`:** в первой версии хватит `max_duration`. Следом — `reset` (кнопка «Начать заново» с
   подтверждением, только при возможности `reset`). `mode: exam` пока не нужен.
2. **`run`:** плагину всё равно, это между менеджером и слотом.
3. **Ревизия лабы:** продолжать старую ревизию — правильно. «Обновить проекты студентов» плагин будет показывать
   преподавателю, только если менеджер явно объявит такую возможность, с предупреждением о потере работы.
4. **`ui` из `meta.json`:** пока не передавайте. Слои L1/L2/L3/OSPF плагин строит по фактам (`live-state.md`), а
   подсказки отрисовки, если понадобятся, придут вместе с возможностью `facts`.
5. **Имена возможностей §7:** устраивают. Плагин будет смотреть на `consoles`, `observer`, `facts`, `checks`, `reset` и,
   если согласитесь с В3, на `resume`.

## 6. Раунд 3: очередь без слотов

Найдено на стенде: менеджер запущен, агентов и слотов ещё нет. Студент нажимает «Запустить», сессия
уходит в `queued` / `wait_slot` и остаётся там навсегда: у этапа `wait_slot` нет тайм-аута
(`orchestrator.py`, `"wait_slot": None`). Студент видит «Ожидание свободного слота…» без конца.

Решать это лучше менеджеру: только он знает, есть ли рабочие слоты. Плагин уже показывает `failed`
по `error.code` и `error.retryable` («попробуйте ещё раз» или «сообщите преподавателю код: …»), так что
новых полей не нужно — только новые коды. Отменить ожидание студент может уже сейчас: `POST /stop` в `queued`
работает.

### П8. Сразу `failed`, если запускать не на чем — *не блокирует, но нужно до живых студентов*

Если в реестре нет ни одного слота в состоянии, из которого его можно выдать (`free`, есть в конфиге), или все
их узлы недоступны, — сессия сразу `failed` с кодом, например, `NO_SLOTS`, `retryable: false`. Студент увидит
«Лаба не запустилась. Сообщите преподавателю код: NO_SLOTS», а не бесконечное ожидание. Слоты, которые сейчас
заняты (`busy`, `preparing`, `releasing`), — это не «не на чем», а обычная очередь.

### П9. Тайм-аут очереди — *не блокирует*

Настройка `QUEUE_TIMEOUT` (например, 600 с): если за это время слот не нашёлся, сессия `failed` с кодом,
например, `QUEUE_TIMEOUT`, `retryable: true` («Лаба не запустилась. Попробуйте запустить ещё раз»).
`0` — ждать без ограничения, как сейчас.

Оба кода прошу внести в CONTRACTS §2.5. Если удобнее одним кодом с разным `retryable` — тоже подходит:
плагин смотрит на `retryable`, код показывает как есть.

### Что сделано в плагине в этом раунде (0.3.1)

- В превью лабы от менеджера (до запуска) больше нет выдуманных статусов нод: их рисовал вьюер прототипа
  («каждая пятая нода остановлена»). Статусы нод теперь только у запущенной сессии, из `nodes` менеджера.
  Демо-кнопки «Живые данные», «Демо-факты», «Открыть .gns3» и метка «Только просмотр» видны только в демо.
- Имена узлов на схеме: без выделения — поверх подписей портов, при выделении объекта — под ними.
  Менеджеру ничего не нужно.


## 7. Раунд 4: лабы хранятся в Moodle

Сверено с веткой менеджера на коммите 020a8f5 (`labs.py`, `orchestrator.py`, `001_init.sql`). Раунд 3 (П8, П9)
пока без ответа и остаётся в силе.

**Решение владельца проекта.** Лабы теперь хранятся в Moodle, а не в `LABS_DIR` менеджера. Преподаватель собирает
лабу в редакторе на странице Moodle. Кто может создавать и править лабы, решают роли Moodle. Лабы попадают в
резервную копию курса. Сейчас лабу добавляет администратор менеджера руками: `lab.gns3`, `ticket.json` и `meta.json`
на CephFS, имена файлов образов, размер CT. Это не масштабируется на преподавателей.

Менеджер остаётся тем, кто знает, **что можно запустить**, и **проверяет всё, что пришло из Moodle**. Определение
лабы — недоверенные данные: его может прислать любой преподаватель с нужным правом в любом курсе.
**Слот и агенты не меняются.** Менеджер, как и сейчас, отдаёт слоту `DeployTicket` и сам выбирает размер CT.

| Moodle (плагин) | Менеджер |
|---|---|
| определения лаб: ноды, линки, координаты, подписи, рисунки | каталог образов: что стоит на слотах, под каким `id`, с какими пределами |
| версии, черновик и опубликованная версия, редактор, предпросмотр | проверка определения, пределы сайта |
| права (новая capability плагина), резервное копирование, выбор лабы в активности | сборка `DeployTicket` из определения и каталога, размер CT, сессии, workspaces |

**Совместимость.** `lab_ref` и `LABS_DIR` остаются как есть: эталонные лабы администратора и уже настроенные
активности работают дальше. Активность ссылается либо на `lab_ref` (как сейчас), либо на лабу из библиотеки Moodle.

### П10. Каталог образов: `GET /api/v1/images` — *блокирует редактор лаб*

Администратор менеджера описывает образы в своём конфиге (например, `/etc/lab-manager/images.json`): `id`, файл
на слотах, `kind` и параметры, которые нельзя доверить преподавателю (`disk_interface`, `cli_prompt`, `qga`,
`l1_keepalives`…). Плагину отдаётся то, что нужно редактору. Имён файлов в ответе нет: это забота менеджера.

```json
{
  "images": [
    {
      "id": "cisco-iou-l3",
      "title": "Cisco IOU L3 (маршрутизатор)",
      "kind": "iou",
      "category": "router",
      "symbol": ":/symbols/classic/router.svg",
      "console_type": "telnet",
      "ram_mb":   {"default": 1024, "min": 512, "max": 2048},
      "cpus":     null,
      "adapters": {"default": 2, "min": 1, "max": 4},
      "port_name": "Ethernet{adapter}/{port}",
      "ports_per_adapter": 4
    },
    {
      "id": "debian12",
      "title": "Debian 12",
      "kind": "qemu",
      "category": "host",
      "symbol": ":/symbols/classic/computer.svg",
      "console_type": "telnet",
      "ram_mb":   {"default": 768, "min": 512, "max": 4096},
      "cpus":     {"default": 1, "min": 1, "max": 2},
      "adapters": {"default": 1, "min": 1, "max": 4},
      "port_name": "eth{adapter}",
      "ports_per_adapter": 1
    }
  ]
}
```

- `category` — свободная строка для группировки в палитре редактора (`router`, `switch`, `host`, `firewall`…).
- `adapters` — для `iou` это `ethernet_adapters` слота (по 4 порта), для `qemu` — `adapters` (по 1 порту),
  у `vpcs` — `null` (один порт 0/0). `ports_per_adapter` дублирует это правило, чтобы редактор не знал о `kind`.
- `port_name` — шаблон имени порта для редактора и для подписей на схеме до запуска. Если вы знаете точнее, как
  GNS3 называет порты каждого образа, — отдавайте точнее.
- `symbol` — символ GNS3, как в `.gns3`: вьюер плагина уже умеет его рисовать.
- `GET /api/v1/info`: `features` += `"images"`. Каталог меняется редко, плагин кэширует его (как `info`).

### П11. Формат определения лабы `gns3lab.lab/1` — *блокирует редактор лаб*

Плагин присылает определение в своём формате, не `.gns3` и не `DeployTicket`: в `.gns3` много того, чему
нельзя доверять или что не нужно для запуска, а в тикет пришлось бы класть имена файлов образов.

```json
{
  "format": "gns3lab.lab/1",
  "title": "OSPF, три зоны",
  "nodes": [
    {"name": "R1", "image": "cisco-iou-l3", "x": -200, "y": 0, "ram_mb": 1024, "adapters": 2},
    {"name": "PC1", "image": "debian12", "x": -200, "y": 160}
  ],
  "links": [
    {"a": {"node": "R1", "adapter": 1, "port": 0}, "b": {"node": "PC1", "adapter": 0, "port": 0}}
  ]
}
```

- Поля нод и концов линков — те же, что у `NodeSpec` и `Endpoint` слота, только `image` — это `id` из каталога
  (П10). Не задано `ram_mb`, `cpus` или `adapters` — берётся `default` образа.
- Рисунки, подписи, цвета, тексты заданий в определение **не входят**: они остаются в Moodle, и плагин сам
  накладывает их на живую топологию. Тогда `_reference_drawings()` для таких лаб не нужен, и SVG из Moodle
  к менеджеру не попадает.
- Проверки (всё, что слот проверил бы позже, но с понятной ошибкой для редактора): имена по шаблону слота и
  уникальны, до 100 нод, образы есть в каталоге и разрешены сайту (П13), `ram_mb`/`cpus`/`adapters` в пределах
  образа, концы линков ссылаются на существующие ноды и порты, один порт — не больше одного линка, линк не
  соединяет ноду саму с собой, неизвестные поля — ошибка, ограничения на длину строк и размер документа
  (например, 256 КБ).
- Размер CT (`resources`) менеджер считает сам, по нодам и образам (сумма `ram_mb` плюс ваш запас, ядра), вместо
  `meta.json`. Формулу оставляю вам; плагину нужно только её значение (П12), чтобы показать его в редакторе.

### П12. Проверка определения и запуск по нему — *блокирует редактор и запуск лаб из Moodle*

**Проверка** — `POST /api/v1/labs/validate`, тело `{"lab": {…определение…}}`. Ничего не сохраняет, для редактора
(проверка на лету и при публикации):

```json
200 {"lab_def": "sha256:9c1f…", "resources": {"cores": 4, "memory_mb": 9216}, "warnings": []}

422 {"error": "lab_invalid", "message": "…",
     "problems": [{"path": "nodes[2].adapters", "code": "out_of_range", "message": "1..4"},
                  {"path": "links[0].b", "code": "port_in_use", "message": "R1 1/0 already linked"}]}
```

`lab_def` — хэш нормализованного определения, его считает **только менеджер**. Плагин сохраняет его у
опубликованной версии лабы и сам ничего не хэширует: так не нужно договариваться о каноническом JSON между PHP
и Python. `code` у проблем — из короткого списка (`required`, `unknown_field`, `bad_name`, `duplicate_name`,
`unknown_image`, `image_not_allowed`, `out_of_range`, `unknown_node`, `bad_port`, `port_in_use`, `self_link`,
`too_many_nodes`, `limit_exceeded`, `too_large`). По `path` редактор подсвечивает ноду или линк, по `code`
показывает свой текст. `message` — только для отладки.

**Запуск** — в `POST /api/v1/sessions` вместо `lab_ref` поле `lab` с тем же определением (ровно одно из двух):

```json
{"user_id": 42, "instance_id": 7, "course_id": 3, "lab": {"format": "gns3lab.lab/1", …}}
```

- Определение передаётся целиком при каждом запуске, без регистрации заранее. Менеджеру не нужно хранилище
  определений и ошибка «неизвестный хэш», а плагину — повторная отправка. Определение — десятки килобайт, запуск
  редкий. Если вам удобнее хранить определения (`POST /labdefs` и запуск по хэшу) — скажите, плагин подстроится.
  Главное: источник правды — Moodle, у менеджера только копия.
- Проверка та же, что у `validate`: ошибка — `422 lab_invalid` с `problems` (например, администратор убрал образ,
  а лаба на него ссылается). Плагин покажет студенту «Лаба настроена с ошибкой, сообщите преподавателю».
- В объекте сессии: `lab_def` (`"sha256:…"`; у сессий по `lab_ref` — `null`) и `lab_ref: null`. По `lab_def` плагин
  находит свою версию лабы, а с ней рисунки и подписи для схемы.
- **Идемпотентность и конфликт** — как сейчас, только вместо совпадения `lab_ref` сравнивается `lab_def`.
- **Workspaces (`LAB_PERSISTENCE=resume`).** Workspace привязан к `lab_def`, как сейчас к `lab_ref`. Новая версия
  лабы — новый workspace, работа студента в старой версии не смешивается с новой. Активность в Moodle ссылается
  на конкретную опубликованную версию, и преподаватель переводит её на новую версию явно, так что `lab_def`
  меняется редко и осознанно. Что делать со старыми workspaces (держать, удалять по сроку), решайте сами.
- `project_name` для таких лаб — что-то вроде `lab-<первые 8 символов хэша>-<suffix>`.

### П13. Пределы сайта — *нужно до того, как редактор откроют преподавателям*

В `sites.json` у сайта:

```json
{"limits": {"max_nodes": 30, "max_memory_mb": 16384, "max_cpus": 8, "images": ["cisco-iou-l2", "cisco-iou-l3", "debian12"]}}
```

`images` — список разрешённых `id` или `"*"`. Превышение — проблема `limit_exceeded` или `image_not_allowed` в `422`.
В `GET /api/v1/info` — `limits` сайта (без секретов) и `features` += `"lab_definitions"`. Тогда редактор заранее
покажет «не больше 30 нод» и спрячет из палитры недоступные образы (или `GET /images` отдаёт только разрешённые
сайту — так даже лучше).

### В7. Начальная конфигурация нод — *нужен ответ, чтобы спланировать редактор*

Преподавателю часто нужна лаба с уже настроенными устройствами: hostname, адреса, «сломанный» OSPF для поиска
ошибки. Что из этого умеет слот и как это безопасно принять из Moodle?

- IOU: `startup-config` (текст конфигурации)?
- QEMU/Linux: `provisioning` слота (`ProvisionCommand`: до 8192 символов, тайм-аут до 120 с) через `qga`?
- VPCS: `startup_script`?

Предлагаю поле ноды `config` (текст, до 64 КБ). Менеджер превращает его в то, что умеет слот для этого `kind`, или
отвечает `unknown_field`, если образ этого не поддерживает. Можно ли это принять из Moodle, решать вам: команды
выполняются внутри изолированной лабы студента, но вы лучше знаете, что слот делает с `provisioning`. Если пока
нельзя — первая версия редактора обойдётся без начальной конфигурации.

- **Библиотека лаб сайта.** Лаба, её метки (теги Moodle) и версии: один черновик и замороженные опубликованные версии.

- **Что приходит менеджеру.** `title` берётся из названия лабы в Moodle. У каждой ноды есть `adapters`: редактор

- **Когда менеджер ещё не умеет.** Пока у менеджера нет `lab_definitions` в `info`, черновики рисовать и сохранять
  можно, а «Проверить» и «Опубликовать» выключены. Лабы по `lab_ref` работают как раньше.

### П14. Остановка по бездействию — *на будущее, не блокирует, сейчас делать не нужно*

Владелец хочет обсудить это позже. Лаба может заканчиваться не только по `max_duration`: студент закрыл браузер или
выключил телефон и ушёл, а слот занят до `expires_at`. Нужна остановка по бездействию.

Пока лаба открыта, плагин опрашивает сессию: `GET /sessions?user_id=&instance_id=` раз в 15 с при `running`.
Запросы идут с сервера Moodle, но только пока у студента открыта страница лабы. Закрыл вкладку — опрос
прекратился. Так что менеджер может считать последний опрос признаком «страница открыта»: нет опросов N минут,
например 10–15, — сессия `stopped` с причиной «нет активности». Новых полей в API для этого не нужно. Можно учитывать
и консоли: шлюз знает, есть ли открытые консоли и шёл ли через них ввод.

Если удобнее явный сигнал (`POST /sessions/{id}/heartbeat` или поле в `options`) — тоже подходит. Когда дойдём
до этого, напишите, какой вариант вам ближе; плагин добавит предупреждение «Лаба остановится через N минут без
активности».

## 12. Шлюз консолей переходит к менеджеру

### Что плагин ожидает от шлюза (контракт, менять только по договорённости)

предупредите в `PLUGIN_REQUESTS.md`, плагин подстроится.

| Что | Как сейчас |
|---|---|
| Адрес | `wss://<gateway_url>/console/<node_id>?ticket=<билет>`; `gateway_url` плагин берёт из ответа `console-tickets` (без `/` на конце), иначе — из своей настройки |
| Билет | одноразовый, 30 с; проверяется до рукопожатия: недействителен или чужая нода — HTTP 403, `onopen` не наступает |
| Origin | только из `GW_ALLOWED_ORIGINS`; чужой или пустой — HTTP 403, билет не тратится; без настройки шлюз не стартует |
| Ввод | текстовые кадры (`term.onData`); плагин режет их до 4096 символов, лимит шлюза — 64 КБ на сообщение |
| Вывод | бинарные кадры с байтами UTF-8, telnet уже вырезан; текстовые кадры плагин тоже принимает |
| Размер окна | бинарный кадр с JSON `{"cols": N, "rows": M}` после `onopen` и при каждом изменении; шлюз отбрасывает его, пока слот не умеет NAWS. Когда слот научится, клиент менять не нужно |
| Наблюдатель | билет `readonly`: ввод и размер окна шлюз отбрасывает (плагин тоже не шлёт) |
| `4000` | консоль закрылась на стороне слота: плагин перечитывает сессию, нода не `started` — «Нода остановлена», иначе переподключение с паузой |
| `4001` | слот не пустил к консоли (нода не готова, слот недоступен, неверный токен): «Консоль устройства недоступна», дальше как у `4000` |
| ping | раз в 25 с, чтобы прокси не рвали тихую консоль; nginx — `proxy_read_timeout` больше 25 с |

Новые коды закрытия добавляйте с номерами от `4002`. Незнакомый код плагин сейчас считает обрывом сети
и переподключается с паузой.

## 13. Графическая консоль (VNC), плагин 0.7.0

Плагин показывает экран ноды с `console_type: vnc` (noVNC, `amd/src/vnc.js`). Контракт — CONTRACTS §2.4, §2.6, §6, ничего
нового к нему плагин не просит. Вот на что он опирается в шлюзе и менеджере; менять это — только через этот файл
и `PLUGIN_REQUESTS.md`.

| Что | Как сейчас |
|---|---|
| Адрес, билет, origin | те же, что у терминала: `wss://<gateway_url>/console/<node_id>?ticket=<билет>`, новый билет на каждое (пере)подключение |
| Кадры в обе стороны | **двоичные кадры сырого потока RFB**; шлюз пересылает байты как есть и не ищет в них границ сообщений: noVNC читает поток, а не кадры. Плагин сам создаёт `WebSocket` с `binaryType = "arraybuffer"` и отдаёт его noVNC |
| Текстовые кадры, размер окна | плагин не шлёт ни тех, ни других |
| Размер кадров | от шлюза к браузеру — любой: один raw-прямоугольник 1920×1080 это 8 МБ, резать и склеивать нельзя, а очередь не должна расти без предела (контроль скорости — на шлюзе). От браузера к слоту — мелкие: клавиша 8 Б, указатель 6 Б; вставка из буфера — один кадр длиной текста, плагин ограничивает её 8192 символами, лимит шлюза 64 КБ на сообщение достаточен |
| Тип консоли | `console: "vnc"` в `POST /internal/tickets` (CONTRACTS §6), менеджер берёт его из живых статусов нод |
| Наблюдатель | билет `readonly` на `vnc`-ноду плагин **не запрашивает**: отказ даёт сам Moodle (`consolevncobserver`, менеджер не вызывается). Если менеджер всё же ответит `403 console_disabled`, плагин покажет общее «менеджер не смог выполнить запрос». Придёт билет с `readonly: true` — страница не подключается |
| `4000`, `4001` | как у терминала: перечитывается сессия, нода не `started` — «Нода остановлена» и автоподключение при запуске, иначе переподключение с паузой 1 → 2 → 4 … 30 с, `4001` — «Консоль устройства недоступна». Другого кода закрытия при ошибке RFB слот и шлюз давать не должны |
| Пароль | нет, security None: сервер, который просит учётные данные, плагин отключает с сообщением («Сообщите преподавателю») и не повторяет |
| ping | как у терминала: раз в 25 с от шлюза, браузер отвечает сам |

Что проверено без настоящего шлюза: `devtools/mock-manager` отдаёт билет `vnc`-ноды владельцу (с `console: "vnc"`
в теле `/internal/tickets`), `readonly` — `403 console_disabled`; его поддельный слот на `vnc`-ноде говорит по RFB 3.8,
а `devtools/ui-harness/check_vnc.js` ведёт настоящие модули плагина и noVNC в Chromium через поддельный шлюз
(он пересылает двоичные кадры в обе стороны и закрывает `4000`/`4001`), см. `devtools/ui-harness/README.md`. Настоящий
`manager/gateway/console_gateway.py` с `console: "vnc"` и слот с `NodeSpec.console: "vnc"` плагином не проверялись:
в этой ветке шлюз ещё без поддержки `vnc`.

## 14. Одно место на лабу (плагин 0.12.0): сейчас ничего не нужно, предложение на потом

Плагин ограничивает параллельную работу под одной учётной записью (`docs/seat.md`): лабой студента в каждый момент ведёт одно
«место» — одна страница браузера или один вход Moodle (настройка активности `seatmode`: `tab` по умолчанию, `login`, `off`).
Всё решается в Moodle до обращения к менеджеру: второй вход не получает билет к консоли и не может запустить или остановить
лабу. **Контракт (`CONTRACTS.md`, §2, §6) не меняется, от менеджера и шлюза ничего не требуется.**

### П15. Закрывать открытые консоли при смене держателя — *на будущее, не блокирует, решает владелец*

Место проверяется при выдаче билета. Уже открытое соединение остаётся до закрытия самой страницей (`docs/seat.md` §5).
Чтобы потеря места рвала и их, предлагается:

- `DELETE /api/v1/sessions/{session_id}/consoles` — плагин вызывает его, когда место переходит другому входу (и, по желанию,
  при выходе владельца из Moodle). Менеджер находит билеты с `who = <session_id>:owner` и просит шлюз их закрыть;
- шлюзу — `POST /internal/revoke {"who": "<session_id>:owner"}`: закрыть все живые соединения этого `who` кодом `4002`
  и не принимать нерасходованные билеты с тем же `who`, выданные раньше;
- плагин на `4002` не переподключается, а перечитывает место (как на `4000` перечитывает сессию).

Плагин пока этого не использует. Если вы согласны, напишите, какой путь и код вас устраивают, — тогда оформим в `CONTRACTS.md` §6
и плагин начнёт вызывать.

### П16. Командная работа над одним проектом — *на будущее, нужен ваш взгляд на модель*

Режим `off` лишь снимает проверку места. Проект по-прежнему принадлежит одному `user_id`, а менеджер ищет сессию по `(user_id,
instance_id)`. Для лаб, где несколько студентов делают один проект, плагину нужно передавать менеджеру «владельца проекта» —
группу или команду Moodle — вместо отдельного студента (и права на консоли у членов команды). Как это ляжет на `POST /sessions`
и `session_conflict`, решать вам; пока в плагине ничего не заложено, кроме того, что ключ места легко заменить с `(активность,
студент)` на `(активность, владелец проекта)`.
