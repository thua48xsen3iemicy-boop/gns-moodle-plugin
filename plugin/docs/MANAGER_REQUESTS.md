## 0. Что плагин уже делает с API менеджера

Ветка `claude/beautiful-turing-ju7n54`, версия плагина 0.2.0. Всё ровно по SPEC §3, сверх неё плагин **ничего не
отправляет** (CONTRACTS §1.3): ни `options`, ни `client`, пока нет `GET /api/v1/info`.

| Когда | Запрос | Что плагин берёт из ответа |
|---|---|---|
| рендер страницы активности | `GET /api/v1/labs/{lab_ref}/topology` | `.gns3` целиком (превью). Ошибка — демо-лаба и предупреждение |
| кнопка «Запустить лабу» | `POST /api/v1/sessions` `{user_id, instance_id, lab_ref, course_id}` | объект сессии |
| опрос страницы | `GET /api/v1/sessions?user_id=&instance_id=` | раз в 3 с при `queued/starting/stopping`, раз в 15 с при `running`, не опрашивает при `stopped/failed` и без сессии |
| кнопка «Остановить лабу» | сначала `GET /sessions?…`, потом `POST /sessions/{id}/stop` | объект сессии |
| открыть консоль | сначала `GET /sessions?…`, потом `POST /sessions/{id}/console-tickets` `{node_id, readonly, issued_for_user_id}` | `ticket`, `gateway_url`, `expires_in` |
| консоль закрылась с кодом 4000 | `GET /sessions?…` | `nodes[node_id].status`: не `started` — «Нода остановлена», иначе переподключение через 1 → 2 → 4 … 30 с |

Ещё о том, как плагин работает с API:
- **`session_id` плагин не хранит.** Сессию он каждый раз находит по `user_id` + `instance_id` (SPEC §5.1: состояние
  не дублируем). Поэтому перед каждым билетом и перед остановкой идёт `GET /sessions?…`. Браузер `session_id` видит,
  но ничего по нему не запрашивает.
- **Поля сессии, на которые плагин опирается:** `session_id`, `status`, `status_message`, `started_at`, `expires_at`,
  `topology.topology.{nodes,links,drawings}`, у нод — `node_id`, `name`, `x`, `y`, `width`, `height`, `symbol`, `label`,
  `node_type`, `ports`, `console_type`; `nodes{}` — `status`, `console_type`. Неизвестные поля плагин игнорирует.
- **Билет.** Плагин сам проверяет, что нода есть в `topology` сессии, и не просит билет к ноде с `console_type`
  `vnc`/`none`. У чужой лабы `readonly` всегда `true`, это решает сервер Moodle. `gateway_url` берётся из ответа
  менеджера, а если его нет — из настройки плагина `gatewayurl`. К адресу плагин дописывает `/console/<node_id>?ticket=…`.
- **Ошибки.** Плагин показывает свой локализованный текст по коду `error` (`session_conflict`, `lab_not_found`,
  `lab_invalid`, `session_not_running`, `node_not_found`, `gateway_unavailable`, `unauthorized`, остальные — общий
  текст). `message` менеджера уходит только в отладочную информацию Moodle.
- **Сеть.** HTTP-таймаут — настройка плагина, по умолчанию 10 с. Блок-лист curl Moodle (частные сети, нестандартные
  порты) к адресу менеджера не применяется: адрес задаёт только администратор сайта.

## 1. Просьбы

### П1. Список сессий активности для наблюдателя — *блокирует этап 3 плагина*

На странице преподавателя нужен список студентов со статусами их лаб. Сейчас это один `GET /sessions?…` на каждого
студента, то есть десятки запросов при каждом открытии страницы.

Предложение:

```
GET /api/v1/sessions?instance_id=7
→ [{"user_id": 42, "session_id": "s-…", "status": "running", "started_at": "…", "expires_at": "…"}, …]
```

По одной записи на студента: живая сессия или последняя завершённая, как в `GET /sessions?user_id=&instance_id=`.
`topology` и `nodes` не нужны. Пустой список — сессий нет. Фильтр `user_id` при этом не обязателен.

### П2. `stage` и `progress` в сессии — *не блокирует*

`status_message` написан по-русски, а сайт Moodle может быть и на английском. Плагин хотел бы строить текст сам, а
`status_message` показывать как подробность. Для этого не хватает этапа:

```json
{"status": "starting", "stage": "lab_wait", "progress": 40, "status_message": "Проверка устройств… 40%"}
```

`stage` — значения из DESIGN §6.4 (`wait_slot`, `ct_prepare`, `student_dir`, `ct_start`, `slot_ready`, `lab_submit`,
`lab_wait`, `ready`, `lab_stop`, `lab_stop_wait`, `ct_stop`, `ct_park`). `progress` — процент, если известен, иначе
поля нет. Оба поля необязательные: по CONTRACTS §1.2 старый плагин их проигнорирует.

### П3. Подробности конфликта в `409 session_conflict` — *не блокирует*

Сейчас студент видит «У вас уже запущена другая лаба», но не знает, где именно. Предложение — добавить в тело ошибки:

```json
{"error": "session_conflict", "message": "…",
 "conflict": {"instance_id": 5, "course_id": 3, "lab_ref": "ospf-1", "status": "running"}}
```

Плагин покажет ссылку на ту активность (если у студента есть к ней доступ). Это данные того же студента и того же
сайта, так что чужого ничего не утекает.

### П4. `error` у `failed`-сессии — *не блокирует, поддерживаю CONTRACTS §2.3*

Плагин сделает так: при `retryable: true` — кнопка «Запустить снова», при `false` — «Сообщите преподавателю» и код
для обращения. Просьба: перечислите в CONTRACTS все коды, которые могут прийти (`SLOT_START_FAILED`,
`STUDENT_DIR_MISSING`, `AGENT_REJECTED`, `WRONG_STUDENT_MOUNT`, `SLOT_COLD_RESUME_UNSUPPORTED`, `unsupported_lab`, …),
и для каждого — `retryable`. Под коды, которые увидит студент, плагин заведёт тексты.

### П5. Билет к остановленной ноде — *не блокирует*

Сейчас менеджер выдаёт билет к любой ноде из топологии. Если нода остановлена, шлюз закрывает сокет с 4000, и плагин
делает ещё один `GET /sessions`, чтобы понять причину. Предложение: `console-tickets` отвечает
`409 {"error": "node_not_running"}`, если `nodes[node_id].status != "started"` (с учётом вашего кеша в 3 с). Тогда
плагин сразу покажет «Нода остановлена». Код нужно добавить в CONTRACTS §2.4.

### П6. Признак, что статусы нод устарели — *не блокирует*

`live_nodes()` при ошибке слота молча отдаёт снимок из `sessions.topology`. Для плагина это значит: после 4000 он
увидит `started` у упавшей ноды и будет переподключаться с паузой до 30 с, а не скажет «нода остановлена».
Предложение: необязательное поле `nodes_stale: true`, когда отдан снимок. Плагин тогда напишет «Состояние нод
неизвестно» вместо бесконечных попыток.

### П7. Зафиксировать в контракте имена портов в живой топологии — *не блокирует*

`properties` у нод живой топологии пустые, поэтому имена портов из `ports_mapping` плагину недоступны. Плагин теперь
берёт их из `nodes[].ports[].short_name | name`: `ports` у вас в `NODE_KEYS` уже есть. По этим именам консоль
подсвечивает порт на схеме, когда студент нажимает `Gi0/1` в выводе. Просьба:
- записать в CONTRACTS §2.3, что `ports` (с `name`, `short_name`, `adapter_number`, `port_number`) и
  `links[].nodes[].label` в живой топологии сохраняются;
- проверить, что Lab Slot в `GET /v1/labs/{pid}/topology` вообще отдаёт `ports`. Если нет, то откуда их взять (В6).

## 2. Вопросы

### В1. Адрес шлюза — *нужно подтверждение*

Плагин берёт `gateway_url` из ответа на билет, так что менеджер может выдавать разные шлюзы для разных узлов
(SPEC §8, вопрос 4). Подтвердите формат: `ws://` или `wss://`, хост, порт, путь — **без `/` на конце**, к нему плагин
дописывает `/console/<node_id>?ticket=…`. И ещё: менеджер всегда отдаёт `gateway_url`? Если да, настройку
`gatewayurl` в плагине оставлю только как запасную.

### В2. Остановка лабы преподавателем — *решает владелец, нужно мнение менеджера*

SPEC §8, вопрос 2. Технически `POST /stop` по `session_id` уже работает для любой сессии сайта. Если владелец
разрешит, хотите знать, кто остановил? Предложение: необязательное тело `POST /stop {"requested_by_user_id": 17}` —
только для журнала `events`, как `issued_for_user_id` у билета.

### В3. Сохраняется ли работа студента — *нужно для текстов плагина*

При `LAB_PERSISTENCE=fresh` каждая сессия начинается с нуля. Тогда студента надо честно предупредить на кнопке
«Остановить»: «Работа не сохранится». Как плагину узнать режим? Предложение: возможность `resume` в
`GET /api/v1/info → features`, когда менеджер продолжает проект. Нет `resume` — плагин предупреждает.

### В4. Повторный запуск после `failed` и `stopped` — *нужно подтверждение*

По коду `POST /sessions` после `failed` или `stopped` создаёт новую сессию и отвечает `201`. Верно? А в `GET /sessions`
после этого приходит уже новая сессия (последняя по времени)?

### В5. Частота опроса — *нужно подтверждение*

Одна открытая вкладка студента — это `GET /sessions` раз в 3 с при переходных статусах и раз в 15 с при `running`.
Плюс по одному запросу на каждое открытие консоли и каждое переподключение. На 30 студентов в аудитории это до
~10 запросов в секунду в пике. Устраивает? Если нужен другой интервал, скажите — поменяю.

### В6. Откуда имена портов, если слот не отдаёт `ports` — *если ответ на П7 «не отдаёт»*

Варианты: менеджер берёт `ports_mapping` и имена из эталонного `lab.gns3` по имени ноды (как сейчас `drawings`);
или имена задаются в `ticket.json`. Как вам удобнее?

## 6. Раунд 3: очередь без слотов

Найдено на стенде: менеджер запущен, агентов и слотов ещё нет. Студент нажимает «Запустить», сессия
уходит в `queued` / `wait_slot` и остаётся там навсегда: у этапа `wait_slot` нет тайм-аута
(`orchestrator.py`, `"wait_slot": None`). Студент видит «Ожидание свободного слота…» без конца.

Решать это лучше менеджеру: только он знает, есть ли рабочие слоты. Плагин уже показывает `failed`
по `error.code` и `error.retryable` («попробуйте ещё раз» или «сообщите преподавателю код: …»), так что
новых полей не нужно — только новые коды. Отменить ожидание студент может уже сейчас: `POST /stop` в `queued`
работает.

### П8. Сразу `failed`, если запускать не на чем — *не блокирует, но нужно до живых студентов*

Если в реестре нет ни одного слота в состоянии, из которого его можно выдать (`free`, есть в конфиге), или все
их узлы недоступны, — сессия сразу `failed` с кодом, например, `NO_SLOTS`, `retryable: false`. Студент увидит
«Лаба не запустилась. Сообщите преподавателю код: NO_SLOTS», а не бесконечное ожидание. Слоты, которые сейчас
заняты (`busy`, `preparing`, `releasing`), — это не «не на чем», а обычная очередь.

### П9. Тайм-аут очереди — *не блокирует*

Настройка `QUEUE_TIMEOUT` (например, 600 с): если за это время слот не нашёлся, сессия `failed` с кодом,
например, `QUEUE_TIMEOUT`, `retryable: true` («Лаба не запустилась. Попробуйте запустить ещё раз»).
`0` — ждать без ограничения, как сейчас.

Оба кода прошу внести в CONTRACTS §2.5. Если удобнее одним кодом с разным `retryable` — тоже подходит:
плагин смотрит на `retryable`, код показывает как есть.

### Что сделано в плагине в этом раунде (0.3.1)

- В превью лабы от менеджера (до запуска) больше нет выдуманных статусов нод: их рисовал вьюер прототипа
  («каждая пятая нода остановлена»). Статусы нод теперь только у запущенной сессии, из `nodes` менеджера.
  Демо-кнопки «Живые данные», «Демо-факты», «Открыть .gns3» и метка «Только просмотр» видны только в демо.
- Имена узлов на схеме: без выделения — поверх подписей портов, при выделении объекта — под ними.
  Менеджеру ничего не нужно.
