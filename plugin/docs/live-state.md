# Живое состояние лабы: факты и слои L1 / L2 / L3 / маршрутизация

Черновик формата. Здесь описано, что бэкенд (lab-agent или менеджер — здесь неважно, кто)
присылает о запущенной лабе и как плагин строит из этого схемы слоёв.
Эталон поведения — `prototypes/topology-viewer.html`. Пример данных — `fixtures/ospf-multi-area.facts.json`
(конфиг верный) и `fixtures/ospf-multi-area.facts-broken.json` (тот же конфиг с ошибками).
Прототип открывается с `file://` и не может их загрузить, поэтому держит у себя копии
(`<script type="application/json" id="facts-ok">` и `facts-broken`): правите фикстуру — обновите и копию.

## 1. Принципы

1. **Три слоя данных, связь по ID.** `.gns3` — кабели и координаты, его не трогаем.
   Факты — отдельный документ, ноды в нём ключуются тем же `node_id`, что в `.gns3`,
   физический порт — парой `adapter`/`port`, как в `topology.links[].nodes[]`.
   Имя интерфейса в фактах может не совпадать с подписью в GNS3 (`ens18` против `Ethernet0`) — связывает только порт.
2. **Факты, а не готовые картинки.** Бэкенд сообщает, как настроено и в каком состоянии устройство,
   в нормализованном виде, без привязки к вендору. Сырые конфиги и вывод `show` плагин не разбирает.
3. **Схемы строит плагин.** Правила из §4 — чистые функции «факты → граф + список проблем».
   Бэкенд остаётся сборщиком, правила лежат в одном месте и проверяются на фикстурах.
4. **Схема показывает то, что есть, а не то, что задумано.** Ошибся студент — схема строится неправильно.
   Сравнение с эталоном — отдельный режим, на усмотрение автора лабы (не в этом документе).
5. **Полный снимок каждый раз.** Без дельт: при опросе раз в ~30 с и десятках нод это копейки.
   Историю изменений ведёт менеджер (`manager/docs/DESIGN.md` §6.7); плагину дельты не нужны.
6. **Хранятся факты, не выводы.** Проблемы из §4 нигде не сохраняются: те же функции пересчитывают их
   над любым снимком, в том числе над сохранённым из истории.

## 2. Конверт

```json
{
  "schema": "gns3lab.facts/1",
  "rev": 42,
  "generated_at": "2026-10-16T10:00:30Z",
  "ttl": 90,
  "nodes": { "<node_id>": { … } }
}
```

| Поле | Что значит |
|---|---|
| `schema` | версия формата; несовместимое изменение — новая цифра |
| `rev` | необязательное целое: растёт при любом изменении фактов сессии. Плагин передаёт последнее известное значение в `since_rev` и получает `304`, если ничего не менялось (`manager/docs/CONTRACTS.md` §2.7). У фикстур поля нет |
| `generated_at` | когда собран снимок (UTC); у отдельной ноды время сбора может быть раньше — см. `collected_at` |
| `ttl` | через сколько секунд данные считать устаревшими. Данные всё равно показываются — последние пришедшие; UI только отмечает их («обновлено N мин назад»): сбор идёт нештатно |
| `nodes` | факты по нодам; ноды, о которых ничего не известно, можно не перечислять |

## 3. Нода

```json
{
  "status": "started",
  "router_id": "1.1.1.1",
  "vlans": [ { "id": 10, "name": "USERS" } ],
  "interfaces": [ … ],
  "adjacencies": [ … ]
}
```

| Поле | Обяз. | Что значит |
|---|---|---|
| `status` | да | `started` / `stopped` / `suspended` |
| `name` | нет | имя ноды в лабе. По нему менеджер связывает историю проектов, пересозданных с новыми `node_id`; плагин для подписей берёт имя из `.gns3` |
| `interfaces` | нет | список интерфейсов. Нет поля — фактов нет (нода не опрошена: остановлена, на паузе, не отвечает). Пустой список — интерфейсов действительно нет |
| `router_id` | нет | ID маршрутизатора для протоколов маршрутизации; по нему сопоставляются соседи |
| `vlans` | нет | база VLAN коммутатора (для подписей; на построение не влияет) |
| `adjacencies` | нет | соседства протоколов маршрутизации, как их видит эта нода |
| `routes` | нет | таблица маршрутов (§3.3). Нет поля — не собиралась; `[]` — таблица пуста. В слоях §4 пока не участвует, плагин показывает её в сведениях о ноде |
| `mac_table` | нет | таблица MAC коммутатора (§3.4). Нет поля — не собиралась; пустой `entries` — ничего не выучено |
| `collected_at` | нет | когда факты этой ноды собраны (UTC). Нет поля — ни одного успешного сбора не было |
| `error` | нет | последняя попытка сбора не удалась: `{ "code": "unreachable" \| "timeout" \| "stopped" \| "unsupported" \| "failed", "message": "…" }` (`failed` — команда сбора завершилась ошибкой или её вывод не разобрался; плагин показывает неизвестный код как общий текст). Факты рядом, если они есть, — **последние известные, а не текущие**: UI бледнит их и пишет «обновлено N мин назад». Ошибка сбора **не** означает `oper: down`: недоступный агент не должен рисовать ложную аварию |

### 3.1. Интерфейс

| Поле | Что значит |
|---|---|
| `name` | имя на устройстве: `Gi0/1`, `e0/0`, `Vlan99`, `ens18`, `vmbr0.20` |
| `kind` | `physical` — порт с кабелем; `subif` — сабинтерфейс (VLAN-интерфейс поверх физического); `svi` — интерфейс VLAN на коммутаторе; `loopback` |
| `port` | `{ "adapter": 1, "port": 0 }` — только у `physical`: к какому порту `.gns3` относится. Нет поля — сопоставить не удалось или оно неоднозначно: сборщик **не угадывает по порядку интерфейсов**, а плагин не рисует такой интерфейс на кабеле, только в сведениях о ноде |
| `mac` | MAC-адрес в нижнем регистре через двоеточие: `0c:3a:5e:00:01:00`. Помогает сборщику сопоставить интерфейс гостя с портом GNS3 (у QEMU-нод слота адаптер N имеет MAC `mac_address` ноды + N, проверено на стенде); схемы §4 его не читают |
| `parent` | у `subif`: имя физического интерфейса |
| `admin` / `oper` | `up` / `down`. `admin: down` — выключен (shutdown); `oper: down` — нет несущей |
| `switchport` | у портов коммутатора: `{ "mode": "access", "vlan": 10 }`, `{ "mode": "trunk", "allowed": [10, 99] \| "all", "native": 1 }` или `{ "mode": "none" }`. У транка нет `native` — по умолчанию 1 (как у IOS); `"native": null` — у транка нет VLAN без тега (Linux-мост без PVID: кадры без тега не принимаются и не отдаются). `none` — у порта нет членства ни в одной VLAN, кадры не пересылаются (загрузка, новая карта при сохранённой политике): плагин не строит для него L2 и пишет «без VLAN» |
| `mirror` | `true` у порта коммутатора-«аппарата», которым студент не управляет (образ `images/linux-switch/`): состояние порта на схеме повторяет порт на другом конце кабеля (§4, L1). Ставит только сборщик, который знает это про устройство. Нет поля — порт управляется на устройстве (Cisco, Linux-хост) и в L1 читаются его собственные `admin` / `oper`. Наличие `switchport` ничего не говорит о `mirror`: у Cisco-коммутатора `switchport` есть, а `shutdown` студент делает сам |
| `dot1q` | у `subif`: тег VLAN |
| `vlan` | у `svi`: номер VLAN |
| `stp` | `{ "state": "forwarding" \| "blocking" \| …, "role": "root" \| "designated" \| … }` |
| `ipv4` | список адресов с маской: `["10.0.12.1/30"]` |
| `gateway` | шлюз по умолчанию (у хостов) |
| `ospf` | `{ "area": "0", "passive": true }` — интерфейс участвует в OSPF |

Порт без `switchport` — это порт хоста или маршрутизатора: кадры без тега идут на сам интерфейс,
кадры с тегом — на его сабинтерфейс с тем же `dot1q`.

### 3.2. Соседство

```json
{ "proto": "ospf", "peer_router_id": "2.2.2.2", "iface": "Gi0/1", "area": "0", "state": "full" }
```

`state` — как в протоколе (`full`, `2way`, `init`, `exstart`…). Сосед находится по `router_id` другой ноды.

### 3.3. Маршрут

```json
{ "dst": "10.1.10.0/24", "via": "10.0.12.2", "dev": "ens18", "proto": "static", "metric": 100 }
```

`dst` — сеть с маской или `default`; `via` — следующий шаг (нет у подключённых сетей); `dev` — имя интерфейса
на устройстве, как в `interfaces[].name`; `proto` — источник маршрута как его называет устройство
(`kernel`, `static`, `dhcp`, `ospf`…); `metric` — необязательно. Поле `gateway` интерфейса хоста остаётся:
оно соответствует маршруту `default`, но слои §4 читают его, а не `routes`.

### 3.4. Таблица MAC

Поле ноды `mac_table` — таблица коммутации устройства: какой MAC за каким портом и в какой VLAN коммутатор выучил.
Имя не привязано к вендору; сейчас его заполняет коллектор `switch.fdb/1` (Linux-коммутатор, `manager/docs/CONTRACTS.md` §4.6),
у Cisco та же таблица — `show mac address-table dynamic`.

```json
{
  "entries": [ { "mac": "52:54:00:12:34:56", "iface": "eth1", "vlan": 10 } ],
  "truncated": false
}
```

| Поле | Что значит |
|---|---|
| `entries` | **изученные** адреса. `mac` — как в `interfaces[].mac`; `iface` — имя порта коммутатора, как в `interfaces[].name`; `vlan` — VLAN, в которой адрес выучен. Порядок — по `vlan`, `mac`. Пустой список — ничего не выучено (нода только загрузилась, записи состарились). Служебных записей (собственные MAC портов, групповые адреса) в таблице нет |
| `truncated` | `true`: таблица прочитана не целиком, `entries` собраны из прочитанного, состав может меняться от опроса к опросу. Плагин пишет «таблица неполная» |

Нет поля `mac_table` — таблица не собиралась (нода не коммутатор, нет фактов); это не «пустая таблица».
Таблица снимается раз в ~30 с: адрес, выученный и состарившийся между опросами, в снимок не попал, поэтому «адреса нет в таблице»
не доказывает, что кадров с него не было. Записи стареют сами (по умолчанию 300 с), а не по команде студента.

Как читает плагин (только показ, на слои §4 таблица не влияет и «проблем» не порождает — принципы 3 и 6):
в сведениях о ноде-коммутаторе таблица «MAC → порт → VLAN». Порт `iface` связывается с кабелем через `interfaces[].port`, MAC —
с другой нодой по `interfaces[].mac` её фактов: «PC2 (ens3)»; чужой MAC показывается как есть. Нет `port` у `iface` — строка
остаётся без ссылки на схему.

## 4. Как плагин строит слои

### L1 — физика

Линк из `.gns3`. Он **не работает**, если линк приостановлен (`suspend`), нода на одном из концов
остановлена или интерфейс на конце `admin: down` / `oper: down`.
Причины перечисляются: «R1 Gi0/2: shutdown». «Нет несущей» на втором конце упоминается, только если других причин нет.

**Порт с `mirror: true` повторяет состояние порта на другом конце.** Студент не управляет портами такого коммутатора и
не видит их состояния в госте (у Linux-коммутатора несущая QEMU есть всегда), поэтому у интерфейса с `mirror: true`
собственные `admin` / `oper` в L1 не читаются. Порты без `mirror` — в том числе порты Cisco-коммутатора, где студент
сам делает `shutdown`, — работают как раньше. Конец линка с `mirror: true` считается упавшим тогда и только тогда, когда линк не
работает по остальным причинам: он приостановлен, нода на любом из концов остановлена, интерфейс на другом конце
`admin: down` / `oper: down`. Студент поднял порт на узле — порт коммутатора на схеме поднялся, выключил — опустился.
Эти состояния видны везде, где рисуется конец линка: на схеме, в карточке линка, в таблице портов коммутатора.

- Нет фактов о другом конце (нет данных, порт не сопоставлен) — порт коммутатора не считается упавшим: ложной аварии нет.
- Линк между двумя портами с `mirror: true`: собственных причин у концов нет, линк падает только от состояния нод и `suspend`.
- Линк между портом с `mirror: true` и портом Cisco-коммутатора: порт Cisco падает от своего `shutdown`, порт-зеркало повторяет его.
- Это условность отображения, а не измерение. Факты остаются честными: `admin` / `oper` порта коммутатора в
  снимке — то, что видит гость; хранится факт, а повторяет ли его схема, решает только плагин (принципы 3 и 6).
- Линк по-прежнему падает, если упал любой конец. Меняется одно: собственные `admin` / `oper` конца с `mirror: true`
  больше не причина (раньше `oper: down` порта коммутатора уронил бы линк и вписал «нет несущей» в причины).

### L2 — VLAN и широковещательные домены

1. Для каждого конца линка вычисляется, что порт отправляет и принимает на проводе:
   «без тега» и набор тегов dot1q.
   - access-порт: только без тега, внутри — его VLAN;
   - транк: без тега (= native VLAN) и теги из `allowed` (`"all"` — любые);
   - порт хоста или маршрутизатора: без тега — если у самого порта есть адрес или у него нет сабинтерфейсов;
     плюс теги всех его сабинтерфейсов.
2. По линку проходит то, что принимают оба конца. Если один конец шлёт тег, а другой его не принимает, —
   это **проблема линка**: «VLAN 99 не проходит: R2 шлёт его с тегом, а на транке SW1 e0/0 он не разрешён».
3. Вершины графа: «коммутатор + VLAN» и «интерфейс хоста/маршрутизатора». Каждый прошедший по линку тег
   склеивает две вершины. Связные компоненты — **L2-домены** (широковещательные домены).
4. Участники домена — интерфейсы с адресами, SVI, сабинтерфейсы (даже без адреса: например, мост гипервизора
   для гостевых VM в этом VLAN) и сетевые карты хостов.
   Проблемы домена:
   - участник один, а в домене есть коммутатор («PC2 e0 один в своём L2-домене»);
   - в домене смешались разные VLAN (не совпали native или access VLAN на концах линка).
5. На схеме: цвет линка — VLAN, который по нему проходит; транк — несколько параллельных полос;
   линк, по которому не проходит ничего, — пунктир.

### L3 — IP-подсети

1. Каждый адрес (кроме loopback) даёт подсеть «адрес & маска». Одна подсеть — один объект на схеме,
   к нему тянутся интерфейсы с адресами из неё; у интерфейса подписан номер хоста (`.1`).
2. Проблемы:
   - один адрес на двух интерфейсах (дубль);
   - пересекающиеся подсети (почти всегда — разные маски на одном сегменте);
   - **подсеть разорвана на L2**: участники одной подсети попали в разные L2-домены.
     Эта сверка L2 ↔ L3 ловит самые частые ошибки: не тот VLAN на порту, VLAN не пропущен по транку;
   - в одном L2-домене несколько непересекающихся подсетей.
3. Положение подсети: между её участниками; если участник один — между ним и соседом по кабелю.
   Подсеть не ставится поверх устройств и других подсетей.

### Маршрутизация (OSPF)

1. Рёбра — соседства из `adjacencies`; пары, которые видят друг друга, склеиваются в одно ребро.
2. **Ожидаемое соседство**: у двух маршрутизаторов есть не-passive OSPF-интерфейсы в одном L2-домене
   или на двух концах одного кабеля. Если соседство не установлено, рисуется красное ребро
   «нет соседства» с причиной, которую видно по фактам:
   линк не работает → адреса в разных подсетях (маски) → разные area →
   «по фактам не видно, проверьте таймеры, аутентификацию, MTU».
3. Маршрутизатор с OSPF без единого соседа — отдельная проблема: его сети не попадут к остальным.

## 5. Фикстура с ошибками

`ospf-multi-area.facts-broken.json` — тот же конфиг с пятью типичными ошибками:

| № | Ошибка | Где видно |
|---|---|---|
| 1 | SW1 e0/2 в VLAN 20 вместо 10 | L2: PC2 один в домене VLAN 20; L3: подсеть 10.1.10.0/24 разорвана на L2 |
| 2 | На транке SW1 e0/0 не разрешён VLAN 99 | L2: проблема линка R2–SW1, SVI Vlan99 одна в домене; L3: подсеть 10.1.99.0/24 разорвана |
| 3 | R3 Gi0/1 с маской /24 вместо /30 | L3: подсети 10.0.23.0/30 и 10.0.23.0/24 пересекаются; OSPF: нет соседства R2–R3 «адреса в разных подсетях» |
| 4 | R1 Gi0/2 выключен (shutdown) | L1: линк R1–R3 не работает; OSPF: нет соседства R1–R3, R3 без соседей |
| 5 | PVE1 взял адрес шлюза 10.2.20.1 | L3: дубль адреса R3 Gi0/2.20 и PVE1 vmbr0.20 |

## 6. Контракт с менеджером

Маршруты `state` и `state/refresh` описаны в `manager/docs/CONTRACTS.md` §2.7 (менеджер 0.8). Здесь — то, что
относится к самим фактам и к тому, как их читает плагин (0.6.0).

- Moodle забирает снимок сам, сервер-сервер (`manager_client::get_session_facts`), и кэширует его (MUC `facts`,
  `classes/local/session_facts.php`) на 15 с. Старше — запрос с `since_rev`, `304` продлевает запись. `generated_at`
  у менеджера сдвигается при каждом сборе, а `rev` — только при изменении фактов, поэтому снимок старше половины `ttl`
  перечитывается без `since_rev`: иначе после `304` устаревание по `ttl` было бы ложным.
- Браузер спрашивает Moodle через `mod_gns3lab_get_facts` раз в 30 с, пока лаба запущена, в `session.features` есть
  `facts` и страница видна; передаёт `sincerev` и при том же `rev` получает `changed: false` без документа, но со свежими
  `generatedat` и `ttl`. «Обновить сейчас» — `mod_gns3lab_refresh_facts`, через ~5 с — внеочередное чтение. Права и выбор
  сессии — только на сервере (`lab_access::resolve_user`, `find_session`); id сессии браузер не передаёт.
- На схеме: живые факты меняют слои без пересоздания модели и вида; статусы нод — из `session.nodes`, `status` в снимке
  только справочный. Нода с `error` и её подписи бледные, в карточке — причина по коду и «обновлено N мин назад» по
  `collected_at`. `now − generated_at > ttl` — «данные устарели» в карточке и пунктирная рамка у переключателя слоёв.
- `rev`, `collected_at` и `error` — в §2 и §3: нет данных — серое «нет данных», а не ложная ошибка.
- Поля нет — неизвестно; `[]` — точно пусто. Сырой вывод команд в браузер не отдаётся: плагин работает с
  нормализованными фактами (принцип 2). Менеджер его тоже не хранит (DESIGN §6.7).
- `children` (гости Proxmox, хранилища, LXC: `{kind, id, label, status, fields}`) и `metrics` (`{key, label, value, unit}`; скорости считает менеджер).
- Ноды ключуются `node_id` **запущенного** проекта — тем же, что в `session.topology`; `name` — рядом. `node_id`
  постоянен, пока жив проект студента (повторная сессия делает `resume` и сохраняет его); новые UUID появляются,
  только когда проект создан заново. По `name` менеджер связывает историю разных проектов одной лабы.
- Две скорости сбора: статусы и линки из API GNS3 — 5–10 с; интерфейсы, VLAN, адреса, OSPF с устройств — 30–60 с и по `refresh`.
- Факты с Cisco собирать не через консоль студента (aux-консоль или сеть управления), с Debian — через QGA (`ip -j …`).
- В прототипе: имитация обновления раз в 30 с и состояние «нет данных».
