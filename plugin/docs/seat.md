# Одно место на лабу: «злой двойник» и совместная работа

Плагин 0.12.0. Решение внутри плагина; контракт с менеджером, слотом и шлюзом **не меняется**
(`manager/docs/CONTRACTS.md` не тронут). Что можно добавить на стороне шлюза — §7, это предложение, а не код.

## 1. Что защищаем

Лаба принадлежит студенту (в менеджере сессия ищется по `user_id` и активности). Ничто в Moodle не мешает второму человеку,
знающему пароль, войти под той же учётной записью и работать в той же лабе параллельно: он видит те же консоли и
печатает в них. Это и есть «злой двойник». Стандартной настройки «этим модулем — только из одного места» в Moodle нет;
сайтовая настройка «Limit concurrent logins» (`limitconcurrentlogins`) действует на весь сайт, а не на модуль, и выбрасывает
старый вход, а не новый.

Задача: по умолчанию лабой управляет **одно место**, при этом ограничение — настройка активности, а не жёсткий запрет:
для будущих общих лаб его можно снять.

## 2. Как это устроено

**Место (seat)** — «право вести лабу студента в активности прямо сейчас». Держит его одна страница браузера. Только
держатель может: запустить и остановить лабу, получить билет к консоли, записать маску открытого (`mod_gns3lab_reveal`).
Остальные видят на странице стену с объяснением и ничего не могут. Чтение состояния (`get_state`, `get_facts`) место не
охраняет — см. §5.

Кто есть кто:

- **вход** — сеанс Moodle. Определяется по SHA-256 от `session_id()`: идентификатор сеанса сам по себе — учётные данные,
  в таблицу он не попадает. Второй человек с паролем — всегда другой вход;
- **страница** — случайный идентификатор (16 байт), который браузер делает при каждой загрузке `lab.php`
  (`amd/src/seat.js`). Это не секрет и ничего не доказывает: он лишь различает вкладки одного человека.

**Режимы активности** (`gns3lab.seatmode`, поле формы «Параллельная работа под одной учётной записью»):

| Режим | Что значит | Для кого |
|---|---|---|
| `tab` (по умолчанию) | одна страница. Новая страница **того же входа** забирает место сама (старая узнаёт, закрывает консоли, студент может вернуть кнопкой «Работать с лабой здесь»). **Другой вход** место не получает никогда | типовые лабы |
| `login` | один вход, сколько угодно вкладок. Другой вход получает отказ | студент, которому нужны две вкладки |
| `off` | без проверки | лабы, задуманные как общие |

Решение (`classes/local/seat.php`, `seat::verdict`, чистая функция с таблицей тестов):

| Состояние места | `tab`: страница открыта / «здесь» | `tab`: биение | `login` |
|---|---|---|---|
| свободно или не обновлялось > 90 с | получает | получает | получает |
| держит эта же страница | получает | получает | получает |
| держит другая страница **того же входа** | получает (забирает) | `othertab` | получает |
| держит **другой вход** | `otherlogin` | `otherlogin` | `otherlogin` |

Другой вход не забирает место, даже если нажал «здесь»: кто работает, тот и держит. Освобождается оно само через 90 с
после последнего признака жизни держателя — закрытие браузера не требует никаких действий.

## 3. Поток

```
lab.php открыт → seat.js: mod_gns3lab_claim_seat(cmid, tabid, takeover=true)
                    ├─ held        → лаба как обычно
                    ├─ othertab    → стена «открыта в другой вкладке» + кнопка → claim_seat(takeover=true)
                    └─ otherlogin  → стена «открыта под другим входом»; кнопки нет
каждые 20 с     → claim_seat(takeover=false)   // «биение»: продлевает своё место или подхватывает свободное,
                                               //  чужое не забирает — две страницы не воюют
start / stop / get_console_ticket / reveal → у каждой tabid; сервер сам вызывает seat::require_seat:
                    держатель → дальше; нет → moodle_exception seatotherlogin | seatothertab
                    (страница по этому коду сразу поднимает стену, не дожидаясь биения)
```

Числа (`seat::TTL`, `seat::BEAT`): место живёт 90 с, биение раз в 20 с. Запас больше минуты нужен потому, что браузер
замедляет таймеры вкладки в фоне до раза в минуту. Заснувшая надолго вкладка при следующем биении сама подхватывает место,
если никто не занял его. Биение, пришедшее от держателя в течение трети срока, в БД ничего не пишет и блокировку не
берёт; смена владельца идёт под блокировкой (`lock_config`) и уникальным индексом `(gns3labid, userid)`.

Наблюдатель (преподаватель, `userid` ≠ свой) места не имеет и не занимает: он может смотреть лабу студента, даже когда
место держит другой вход студента. Билет наблюдателя по-прежнему только `readonly`.

## 4. Данные, журнал, приватность

- Таблица `gns3lab_seat` — одна строка на студента и активность: `sessionkey` (хеш), `tabid`, `timeclaimed`,
  `timemodified`. Строка живёт полторы минуты после последнего признака жизни; просроченные строки перезаписываются
  при следующем захвате, чистильщика нет (строк не больше, чем пар «студент-активность»). Удаляется вместе с активностью и по
  запросам Privacy API (метаданные, список контекстов, удаление; **экспорта нет** — хеш и случайный id страницы вне
  работающей страницы ничего не значат).
- Событие `\mod_gns3lab\event\seat_denied` пишется, когда **другой вход** получил отказ: страница при открытии или
  при нажатии кнопки, либо вызов, которому нужно место. Адрес запроса журнал Moodle хранит рядом с событием; это
  след второго человека (или второго устройства самого студента). Биения отказавшей страницы и отказ из-за второй
  вкладки того же входа не пишутся.

## 5. Что НЕ защищено (известные границы)

1. **Передача пароля.** Место не мешает отдать пароль: оно не даёт двоим работать одновременно. Двойник, который ждёт, пока
   студент закроет страницу, получит место через 90 с. Это уже не «параллельная помощь».
2. **Чтение.** `get_state` / `get_facts` / `get_reveal` место не охраняют: двойник за стеной всё ещё может (через инструменты
   браузера) читать топологию и факты. Печатать и менять он не может. Закрыть чтение просто (то же `require_seat`), но тогда
   страница отказавшего не нарисует даже схему; решение владельца (§8, вопрос 3).
3. **Уже открытая консоль.** Потерявшая место страница закрывает свои консоли сама (`lab.js`, `seatChanged`), сервер уже
   открытые WebSocket'ы не рвёт: билет проверяется один раз, при открытии. Двойник с модифицированной страницей, который
   не закрыл консоль, сохранит её, даже если место перешло к студенту после истечения 90 с. Закрыть такое соединение без
   шлюза нельзя (§7, а).
4. **Модифицированный клиент в пределах одного входа** (две вкладки одного человека) может не закрыть консоль при потере
   места. Это один человек с правами студента, угрозы нет.
5. **Выход из Moodle** место сразу не освобождает (ждёт срок 90 с). Это можно ускорить (§7).

## 6. Как проверить на стенде (запускает владелец)

Нужна активность в режиме по умолчанию («Одна страница браузера») и студент.

1. Студент открывает лабу в Chrome: стены нет, лаба запускается, консоли открываются.
2. Тот же студент открывает ссылку на лабу **в новой вкладке того же Chrome**: новая вкладка работает; в старой за ≤ 20 с
   (или при следующем клике) появляется «Лаба открыта в другой вкладке», консоли закрыты. Кнопка «Работать с лабой здесь»
   возвращает лабу в старую вкладку, а новая получает стену.
3. Тот же студент входит в Moodle **в другом браузере** (или в окне инкогнито) и открывает лабу: сразу стена «Лаба открыта
   под другим входом», кнопки нет, запуск и консоли недоступны. В журнале курса — событие «Лаба не открыта: учётная запись
   работает в другом сеансе входа» с адресом второго браузера.
4. Закрыть первую вкладку, подождать 1,5 минуты: стена во втором браузере сама исчезает (биение подхватывает место), консоли
   открываются.
5. Поставить в настройках активности «Один вход, сколько угодно страниц»: две вкладки одного браузера работают вместе, другой
   браузер всё равно получает отказ. «Без ограничений» — работают оба.
6. Преподаватель открывает лабу студента (режим просмотра) в тот момент, когда место держит другой вход: видит схему и
   консоли только для чтения.

Без Moodle: `plugin/devtools/ui-harness/check_seat.js` (стена, «использовать здесь», телефон, русский текст, минифицированные
модули `--min`), серверная часть — PHPUnit `tests/local/seat_test.php`, `tests/external/seat_test.php`,
`tests/privacy/provider_test.php` (в сессии разработки PHPUnit не запускался: в контейнере нет Moodle; логика
`seat::verdict` проверена отдельным прогоном той же таблицы).

## 7. Что можно сделать дальше (предложения, не реализовано)

**а) Принудительно закрывать консоли на шлюзе.** Сейчас место проверяется при выдаче билета. Чтобы смена держателя
рвала уже открытые WebSocket'ы, нужно: плагин сообщает менеджеру «закрой консоли сессии X этого владельца», менеджер
передаёт шлюзу, шлюз закрывает соединения кодом `4002`. Менеджер уже передаёт шлюзу в билете `who = <session_id>:owner|observer`
(`CONTRACTS.md` §6), по нему шлюз узнал бы, какие соединения закрывать. Это изменение контракта браузер ↔ шлюз и менеджера ↔ шлюз — только по договорённости
(`docs/MANAGER_REQUESTS.md` §14). Нужно, если захотим защиту и от модифицированного клиента.

**б) Совместная работа нескольких студентов над одним проектом.** Режим `off` снимает только проверку места. Сам проект
по-прежнему принадлежит одному `user_id`. Для настоящей командной работы менеджеру нужна сущность «владелец проекта» (группа или
команда Moodle) вместо одного `user_id`, а плагину — ключ места `(активность, владелец проекта)` вместо `(активность, студент)` и
режим «команда» (несколько входов допускаются, но только членам команды). Таблица и логика места к этому готовы: достаточно
заменить пару ключа; формат менеджера придётся менять (`manager/docs/CONTRACTS.md` §2.2).

**в) Освобождение при выходе.** `\core\event\user_loggedout` + `pagehide` с `fetch(..., {keepalive: true})` освобождали бы
место сразу, а не через 90 с.

**г) Уведомление владельцу** (сообщение Moodle «кто-то пытался открыть вашу лабу») и **кнопка преподавателя «освободить
место»** в списке студентов.
