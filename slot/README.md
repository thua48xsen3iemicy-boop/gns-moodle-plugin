# Lab Slot — 0.9.0

**Новый обязательный протокол:** до изменяющих запросов менеджер вызывает
`POST /v1/fence` с `{epoch,generation}`; команды содержат `X-Lab-Epoch` и
`X-Lab-Generation`. Примеры curl ниже описывают прежний lifecycle и требуют
добавления этого шага/заголовков. После рестарта нужен строго более новый владелец.
Есть HTTPS/WSS: `SLOT_TLS_CERT_FILE` и `SLOT_TLS_KEY_FILE`.
Обновление, новый контракт и приёмка — [pilot-hardening](../docs/pilot-hardening/README.md).

Независимый исполнитель одной активной лаборатории внутри непривилегированного LXC:
Ubuntu 24.04, GNS3 **2.2.61**, Python, FastAPI, Uvicorn. Moodle и Proxmox не входят
в обязанности Slot. `manager/` и `plugin/` этим изменением не обновляются.

## Размещение и установка

Общий код, venv и unit: `/srv/gns3-ro/slot/` на RO CephFS. Рабочие проекты:
`/opt/gns3/projects/` на RW CephFS; образы: `/opt/gns3/images/{QEMU,IOU}`;
QGA: `/opt/gns3/qga/`. Общие образы никогда не изменяются.

На RW-стороне с Ubuntu 24.04/Python 3.12 и той же архитектурой,
где подготовленный код также доступен по `/srv/gns3-ro/slot`:

```sh
cd /srv/gns3-ro/slot
python3 -m venv venv
venv/bin/python -m pip install -r requirements.txt
```

Venv собирается по тому же абсолютному пути, который видят LXC. Обновлять общий
код следует только при согласованно остановленных использующих его сервисах.
Выбор версии и источника монтирования относится к внешнему Lab Manager.
На каждом LXC (администратор; проверить параметры перед выполнением):

```sh
sudo install -d -m 0700 /etc/lab-slot
sudo cp /srv/gns3-ro/slot/slot.env.example /etc/lab-slot/slot.env
sudo sed -i "s/REPLACE_WITH_LONG_RANDOM_SECRET/$(openssl rand -hex 32)/" /etc/lab-slot/slot.env
sudo chmod 600 /etc/lab-slot/slot.env
sudo install -d -o gns3 -g gns3 -m 0700 /opt/gns3/qga /opt/gns3/projects/.slot-locks
sudo cp /srv/gns3-ro/slot/lab-slot.service /etc/systemd/system/lab-slot.service
sudo systemctl daemon-reload
sudo systemctl enable --now lab-slot.service
```

`StateDirectory=lab-slot` создаёт `/var/lib/lab-slot` с владельцем `gns3`.
Там хранится SQLite с операциями и ключами идемпотентности. Не удалять эту директорию
между перезапусками. Не разделять её между LXC.

Запись о лабе (манифест, состояние, признак завершённой подготовки) лежит в каталоге
студента: `/opt/gns3/projects/.lab-slot/labs/<project_id>.json` (`SLOT_LAB_STATE_DIR`,
по умолчанию `/opt/gns3/projects/.lab-slot`). Слот создаёт каталог сам при старте, пишет
атомарно (временный файл, `fsync`, `rename`). Так проект переезжает в любой слот вместе
с каталогом студента — возможность `student-state` (раздел «Версия 0.4.0»).
Переменные и токен находятся в `/etc/lab-slot/slot.env`, не на общей RO CephFS.
GNS3 API фиксирован: `http://127.0.0.1:3080/v2`. Uvicorn: порт 8080, адрес
`SLOT_LISTEN_HOST` (по умолчанию loopback; адрес LXC — только с firewall для Manager и шлюза),
**один worker**. Второй экземпляр с тем же state-dir блокируется файловой блокировкой.
Mount CephFS должен быть доступен до запуска сервиса.

## Жизненный цикл и гарантии

`deploy`: `DEPLOYING → STARTING → PROVISIONING → READY`. Ответ HTTP **202**
означает принятие операции. Успех определяется только её статусом `SUCCEEDED`.
Проверяются версия GNS3, состав нод и связей, фактический `started` всех устройств,
QGA Debian, serial-getty и доступность локальных Telnet-консолей. Ping между
учебными устройствами, VLAN, STP и административное состояние NIC не проверяются.

`auto_start` по умолчанию true; явное false отклоняется (422). При создании проекта
внутренний GNS3 auto_start выключен, чтобы порядок запуска контролировал Slot.

`stop`: `STOPPING → STOPPED` после подтверждения остановки всех нод.
`resume` использует прежний UUID и рабочие файлы, запускает и проверяет устройства.
Отсутствующий сохранённый проект вызывает `FAILED`, без пересоздания дисков.
Повторный deploy с прежним UUID не пересоздаёт ноды, диски или соединения.
Несовпадение сохранённого манифеста или топологии вызывает ошибку.

Команды `provisioning` выполняются только при первом создании проекта. При resume
проверяется serial-getty, но не повторяются первоначальные команды и enable.
Если первоначальная подготовка не завершилась либо была прервана, её результат
считается неопределённым: повторное исполнение и пропуск запрещены. Нужна ручная
диагностика/согласование; автоматического восстановления частично созданных
проектов и публичного маршрута принудительного подтверждения нет. Импорт ранее
неизвестного Slot проекта также не подтверждает выполненную преднастройку.

После рестарта незавершённые операции получают `FAILED / SERVICE_RESTART`.
Ранее READY лаборатории получают FAILED до явного resume: это позволяет заново
захватить блокировку и проверить реальность состояния. Автоматического replay
гостевых команд нет. Журнал операций сохраняется; автоматической очистки пока нет.

Монитор каждые `SLOT_MONITOR_INTERVAL` секунд проверяет ноды и служебную готовность.
Потеря ноды, QGA, getty или консоли переводит READY в FAILED. Проверки ограничены
`SLOT_READY_TIMEOUT`; обнаружение отказа служебного интерфейса может занять этот
таймаут дополнительно к интервалу. Автоперезапуска неисправных устройств нет.

Одновременно выполняется одна изменяющая операция. Конфликт возвращает 409.
Вторая лаборатория запрещена, пока первая не STOPPED; FAILED сохраняет владение
(409 `SLOT_OCCUPIED`) до перезапуска службы. Владение — это блокировка проекта,
которую держит текущий процесс. После рестарта блокировок нет, и FAILED-лаба прошлого
запуска (как правило, другого студента, чей каталог уже не смонтирован) слот не держит.
Запуск новой лабы при этом всё равно откажет, пока в GNS3 есть другой проект с
запущенными нодами.
Для повтора передавайте **Idempotency-Key**: тот же ключ и тело возвращают прежнюю
операцию с `replayed:true`, другое тело — 409. Если постусловие прежнего успеха
уже нарушено, возвращается `409 STALE_IDEMPOTENCY_KEY`. Новый намеренный запуск
требует нового ключа. Актуальное состояние находится в `laboratory.state`, отдельно
от исторического `status` операции.
Без ключа дедуплицируются только одновременно выполняющиеся идентичные запросы;
для deploy без UUID обязательно используйте ключ, иначе после завершения запроса
невозможно отличить новую лабораторию от повтора.

Блокировка UUID в `/opt/gns3/projects/.slot-locks` удерживается до STOPPED либо
завершения процесса. Все Slot должны видеть один RW-каталог блокировок, а CephFS
должна поддерживать согласованный flock. Это защита сотрудничающих Slot;
полноценные распределённые lease/fencing остаются задачей Manager. Также перед
запуском проверяется отсутствие другого запущенного проекта в локальном GNS3.
Не запускайте проекты вручную параллельно Slot.

## Доступ к QGA: брокер каналов

QEMU обслуживает одного клиента на сокет QGA, а qemu-ga выполняет один запрос за раз.
Поэтому обмены с одной нодой не должны пересекаться: монитор, команды менеджера,
автопроверки и сбор метрик делят один канал. Весь доступ идёт через `Lifecycle.qga`
(`api/qga.py`); сокеты `/opt/gns3/qga/*.sock` напрямую не открывать.

- **Очередь на ноду.** Замок держится на один обмен «запрос-ответ», а не на всю команду.
  `guest-exec` асинхронен: статус опрашивается между чужими обменами, поэтому долгая команда
  не блокирует остальных. Ноды между собой независимы.
- **Приоритеты:** `LIFECYCLE` (готовность, provisioning) → `COMMAND` (команды менеджера,
  автопроверка) → `METRICS` (фоновые, необязательные). Идущий обмен не прерывается.
- **Фоновые запросы уступают.** `wait=False` вместо ожидания в очереди даёт `QgaBusy`; пока
  канал в back-off (подряд 3 сбоя обмена, пауза 2 с, потом 4, 8 … до 30 с), `METRICS`
  отклоняются без обращения к сокету. Команды и готовность по-прежнему пытаются дойти:
  они же и выводят канал из back-off.
- **Одно постоянное соединение на ноду.** После (пере)подключения — `guest-sync-delimited`
  (мусор прежнего клиента отбрасывается). Любой сбой или таймаут обмена закрывает соединение.
  После 15 с простоя соединение отпускается: пока слот держит его, QEMU не пустит второго
  клиента (например, `socat` оператора).
- **Состояние:** `Lifecycle.qga.state(node_id)` — `status` (`idle` / `busy` / `unreachable`),
  `queue_depth`, `in_flight`, `consecutive_failures`, `retry_in`, `last_ok_at`, `last_error`,
  `latency_ms`. Пока только внутри процесса; маршрут добавляется вместе с правкой `CONTRACTS.md`.
- **Общий результат:** `exec(..., max_age=N)` для команд только на чтение: свежий результат
  переиспользуется, одинаковые одновременные запросы делят одно выполнение.
- **Ошибки:** `QgaTimeout` (одновременно `TimeoutError`), `QgaUnavailable`, `QgaBusy`,
  `QgaCommandError` — все наследуют `QgaError(RuntimeError)`. Маршруты отвечают прежним
  `502 QGA error: <Тип>: <текст>`.

Проверено на фейковом агенте, который повторяет одноклиентский сокет QEMU (`tests/test_qga.py`).
На стенде проверить: второй клиент на сокете ждёт, а не получает отказ; `guest-sync-delimited`
в qemu-ga образа Debian 12; монитор (10 с) вместе с `/qga/exec` на 20 с не переводит лабу в `FAILED`.

### Долгие команды и владелец слота

Изменяющие запросы принимаются под `command_lock` с проверкой `X-Lab-Epoch` / `X-Lab-Generation`.
`POST …/qga/exec` и `POST …/serial/enable` (команда в госте может идти минуты) не держат замок на
весь запрос: сразу после проверки владельца запрос регистрируется (`Lifecycle.admit()`), и только
потом замок отпускается. Поэтому `stop`, `deploy` и другие команды проходят, пока гость выполняет
команду, а команды на разные ноды идут параллельно.

- `POST /v1/fence` дожидается этих команд так же, как фоновых операций, и не отменяет их:
  `guest-exec` убить нельзя, отмена потеряла бы только ответ.
- Запрос с прежней парой после `fence` получает `409 STALE_OWNER`, до гостя он не доходит.
- Если клиент оборвал HTTP-запрос, команда доработает до конца и всё это время считается
  выполняющейся.
- Остальные маршруты работают как раньше. Новый долгий маршрут нужно внести в `LONG_COMMAND`
  (`main.py`) и запускать работу через `admitted()` (`api/nodes.py`).
- `stop` теперь закрывает QGA-каналы остановленных нод (`QgaBroker.forget`).

## Факты о нодах

Слот сам собирает сетевые факты из гостей и держит последние результаты в памяти; менеджер забирает их
(`GET /v1/labs/{project_id}/facts`) и хранит историю. Контракт — `manager/docs/CONTRACTS.md` §4.6,
хранение — `manager/docs/DESIGN.md` §6.7, формат фактов — `plugin/docs/live-state.md`.

- **Коллектор** — одна гостевая команда и разбор её вывода (`api/facts.py`). Сейчас пять, четыре из них для QEMU-нод
  с QGA, пятый (`ios.config/1`) читает файлы IOU-ноды; список отдаёт `GET /v1/capabilities`. `linux.net/1` выполняет `ip -j -d addr` и `ip -j route`
  одним `exec` и отдаёт `interfaces` и `routes`. Описаны loopback, физические интерфейсы и подинтерфейсы
  802.1Q; мосты, bond и туннели пропускаются. В `data` попадают только значения состояния: сроки аренды
  DHCP/SLAAC, `expires` и счётчики отбрасываются, иначе каждый опрос выглядел бы изменением.
- **Коллектор `switch.net/1`** — Linux-коммутатор (`images/linux-switch/`). Роли ноды в билете нет, поэтому
  слот спрашивает гостя: один `exec` проверяет `/usr/local/sbin/switchctl` (нет — код 127), затем
  вызывает `switchctl ports` и `switchctl vlans`. В `data` только `interfaces` — порты моста `br0`:
  `admin`/`oper` как у гостя, `mac`, `port` по MAC адаптера и `switchport` по **фактическому** членству
  VLAN (`access`, `trunk` с `native`, возможно `null`, или `none`); счётчики, FDB и желаемая политика не
  попадают. Запись `switch.net` слот публикует только у настоящего коммутатора: код 127 — ноды нет в
  выдаче, и слот не спрашивает её снова; `timeout`, `unreachable` и `stopped` до первого успеха тоже без
  записи (недоступность узла сообщает `linux.net`); `failed` публикуется всегда; после первого успеха
  сбои видны, как у `linux.net`. Ответ запоминается до смены владельца или выхода лабы из `READY`.
  `switch.net` стоит после `linux.net`, и менеджер заменяет его `interfaces` целиком (`routes` остаются).
  Коллекторы одной ноды идут по очереди: у них общий QGA-канал, а параллельная попытка получила бы `busy`.
- **Коллектор `switch.fdb/1`** — таблица MAC того же коммутатора, отдельным коллектором: она меняется при каждом
  новом MAC, а менеджер пишет в журнал `data` коллектора целиком. Один `exec`: проверка `switchctl` (нет — код
  127), затем одна страница `switchctl fdb --params '{"limit":1024}'`. В `data` только
  `mac_table: {entries, truncated}`; в `entries` лежат **изученные** строки `bridge -j fdb` (`state` не
  `permanent` и не `static`, флага `self` нет) в виде `{mac, iface, vlan}`, по `vlan`, `mac`, `iface`.
  Служебные строки (MAC портов и моста, групповые адреса) не попадают никак; поля iproute2, кроме трёх,
  отбрасываются. `truncated: true` — в таблице больше 1024 строк (`entries` из прочитанных) или гость ответил
  `RESULT_TOO_LARGE` (`entries: []`; это не сбой, иначе менеджер перенёс бы его в `error` всей ноды). Роль и
  молчание до первого успеха — как у `switch.net`, память у коллектора своя; обычная нода стоит один `exec`
  с кодом 127.
- **Коллектор `windows.net/1`** — гость Windows 10+ (Server 2016+). Какая ОС, слот спрашивает у гостя:
  `guest-get-osinfo` один раз на ноду (`id: mswindows` — Windows; агент без команды — Linux), ответ помнится
  до смены владельца или выхода лабы из `READY`. Пока ОС неизвестна, ни один коллектор для ноды не
  работает и записей нет (чужая запись у менеджера не удаляется). Для Windows вместо `linux.net`,
  `switch.net` и `switch.fdb` идёт один запуск PowerShell (`-EncodedCommand`, `QgaBroker.exec(shell="powershell")`):
  `Get-NetAdapter`, `Get-NetIPAddress`, `Get-NetRoute`. `data` — `interfaces` и `routes` в том же формате,
  что у `linux.net`; `Disconnected` даёт `oper: down` при `admin: up`, `Disabled` — `admin: down`.
  Правила — `manager/docs/CONTRACTS.md` §4.6.
- **Коллектор `ios.config/1`** — Cisco IOL, по сохранённой конфигурации (`api/ios_config.py`). Гостя не спрашивает:
  читает файлы из каталога ноды (`/opt/gns3/projects/<project_id>/project-files/iou/<node_id>/`, его же отдаёт GNS3
  в `node_directory`; `SLOT_PROJECTS_DIR` меняет корень). Нода может быть остановлена, QGA ей не нужен, при
  занятом канале QGA сбор не откладывается. Источник — по порядку:
  1. `startup-config.cfg`, если он **не пуст**: GNS3 2.2.61 кладёт его в NVRAM при каждом старте ноды и обновляет
     после изменения NVRAM (`IOUVM.save_configs`). Но **только** если файл у ноды уже был непустым при создании
     (`startup_config_content`). Слот создаёт IOU-ноды без него, поэтому для них GNS3 файл не напишет никогда;
  2. иначе `nvram_<application_id>`: текст достаёт `nvram_export` из `iou_export.py` установленного gns3server (разбора
     двоичного формата в слоте нет). Файл грузится сам по себе, пакет `gns3server` не импортируется, потому что он
     может стоять под другим интерпретатором. Где искать: `SLOT_IOU_EXPORT` (путь к `iou_export.py`), иначе пакет
     `gns3server`, который видит интерпретатор слота. Не нашёл — `unsupported`. Приватная конфигурация (ключи) не
     читается.
  Разбор — только блоки `interface` и `vlan` (`interfaces`: имя, вид, порт GNS3 по точному имени, `admin`, `ipv4`,
  `switchport` у коммутатора, то есть при `spanning-tree mode …`; `vlans` — только при `vtp mode transparent|off`).
  Нет `oper`, `routes`, `ospf`: конфигурация их не знает. Тексты баннеров и макросов пропускаются. Файл перечитывается,
  только если изменились размер или время (или порты ноды), даже испорченный не разбирается заново. Сырой текст
  (в нём пароли) наружу не уходит, в сообщениях об ошибках только имена интерфейсов. Нет сохранённой конфигурации
  (нет файла, NVRAM пуст) — записи нет; запись была, а источник пропал (`write erase` с перезагрузкой) — `ok: false`
  с прежними `data`. Сбой чтения или разбора — `failed`. Поведение GNS3 выше взято из исходников 2.2.61; на стенде оно
  не проверено (`manager/docs/SLOT_REQUESTS.md` §8).
- **Не мешает остальным.** Сбор идёт фоновой задачей через `Lifecycle.qga` с `Priority.METRICS`,
  `wait=False`: занятый канал — пропущенная попытка (не ошибка, результаты не меняются), канал в back-off —
  `unreachable`. Вывод гостя наружу не отдаётся.
- **Когда.** Только для лабы в `READY` и только пока у слота есть владелец (`fence`). Пока ноды грузятся,
  сбора нет, поэтому недоступный QGA не считается ошибкой. Период — `SLOT_FACTS_INTERVAL` (30 с), таймаут
  команды — `SLOT_FACTS_TIMEOUT` (10 с), не больше `SLOT_FACTS_CONCURRENCY` (8) нод одновременно.
- **Ошибка сбора** (`ok: false`, `error.code`: `timeout`, `unreachable`, `stopped`, `unsupported`,
  `failed`) не стирает прежние `data` и `observed_at`: это последние известные факты, а не текущие.
- **Порт GNS3.** `port` интерфейса задаётся, только если его MAC в точности совпал с MAC адаптера:
  GNS3 нумерует адаптеры от `properties.mac_address` ноды вверх. Нет базового MAC или совпадения —
  поля `port` нет, по порядку интерфейсов слот не угадывает.
- **Сброс.** Результаты стираются, когда меняется владелец (`POST /v1/fence`) и когда лаба выходит из
  `READY`. Запрос о неизвестной лабе — `200` с `nodes: {}`, а не 404: 404 менеджер читает как «слот без фактов».
- `POST /v1/labs/{project_id}/facts/refresh` (с заголовками владельца) просит собрать сейчас; чаще раза
  в `SLOT_FACTS_MIN_REFRESH` (5 с) запросы объединяются, ответ всё равно `202`.

```sh
curl -fsS -H "Authorization: Bearer $TOKEN" "$BASE/v1/labs/$PROJECT_ID/facts"
curl -fsS -X POST -H "Authorization: Bearer $TOKEN" -H "X-Lab-Epoch: $EPOCH" -H "X-Lab-Generation: $GEN" \
  "$BASE/v1/labs/$PROJECT_ID/facts/refresh"
```

## Преднастройка

В доверенном описании ноды можно задать:

```json
"provisioning": [
  {"command": "test -x /usr/bin/ip", "timeout_seconds": 20}
]
```

Для QEMU команды исполняются через QGA и `/bin/sh -c`; ненулевой exit code — FAILED.
Debian должен иметь установленный qemu-guest-agent. QGA и serial обязательны.
Для IOL команды — отдельные строки CLI, включая явные переходы режима (`enable`,
`configure terminal`, `end`), если они нужны. `cli_prompt` — регулярное выражение
ожидаемого prompt, по умолчанию `(?m)^[^\r\n]+[>#]\s*$`. Используйте точный prompt
своего образа. Адаптер обрабатывает Telnet negotiation, ждёт prompt после каждой
команды, распознаёт стандартные Cisco `% Invalid/Error/Incomplete/Ambiguous/Unknown`.
Авторизация, интерактивные подтверждения и нестандартные ошибки требуют отдельного
адаптера: текущий механизм не подтверждает семантическую корректность конфигурации.
Без provisioning проверяется только TCP-доступность CLI, не интерактивный login.
Время ожидания начального CLI prompt — 30 секунд, каждой команды — её timeout.

## API и ручная проверка GNS3 2.2.61

Ниже команды выполняют реальные операции только при запуске оператором.
Пример `examples/cisco-3x2.json`: три Cisco в кольце и шесть Debian.
Сначала проверьте наличие образов и достаточную RAM: теперь запускаются все ноды.

```sh
cd /srv/gns3-ro/slot
TOKEN=$(sudo sed -n 's/^SLOT_API_TOKEN=//p' /etc/lab-slot/slot.env)
BASE=http://127.0.0.1:8080

curl -fsS "$BASE/healthz"
curl -fsS -H "Authorization: Bearer $TOKEN" "$BASE/v1/readyz"

# Сохраните project_id и operation_id из ответа; повтор с этим ключом безопасен.
curl -sS -X POST "$BASE/v1/labs/deploy" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: lab-demo-deploy-001' \
  --data-binary @examples/cisco-3x2.json
PID=PROJECT_UUID_FROM_RESPONSE
OP=OPERATION_UUID_FROM_RESPONSE
curl -sS -H "Authorization: Bearer $TOKEN" "$BASE/v1/operations/$OP"
curl -sS -H "Authorization: Bearer $TOKEN" "$BASE/v1/labs/$PID/status"
curl -sS -H "Authorization: Bearer $TOKEN" "$BASE/v1/labs/$PID/topology"

curl -sS -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Idempotency-Key: lab-demo-stop-001' "$BASE/v1/labs/$PID/stop"
# Дождитесь SUCCEEDED новой operation_id, затем:
curl -sS -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Idempotency-Key: lab-demo-resume-001' "$BASE/v1/labs/$PID/resume"
# Дождитесь SUCCEEDED; UUID нод, связи и рабочие данные должны сохраниться.
NODE=NODE_UUID_FROM_TOPOLOGY
curl -sS -X POST "$BASE/v1/labs/$PID/nodes/$NODE/wipe" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: lab-demo-wipe-001' -d '{"confirm":true}'
# Polling вернёт NOT_SUPPORTED; устройства и файлы остаются нетронутыми.
```

Сохранены `GET /v1/labs`, `GET /v1/labs/{project_id}`, topology, node console,
`POST .../qga/exec`, `POST .../serial/enable` и WS `/v1/console/{project_id}/{node_id}`.
Отдельные публичные node start/stop, lab start/open/close удалены: используйте
deploy/resume/stop для всей лаборатории. WebSocket авторизуется субпротоколами
`['lab-slot', 'bearer.' + token]`; данные двоичные, согласование telnet уже вырезано.
Маршрут один для обоих типов консоли, тип слот берёт у GNS3 (`console_type` ноды), нода должна быть
`started`. `telnet` — как описано выше. `vnc` (QEMU-нода с `console: "vnc"`) — сырой мост
WebSocket ⇄ TCP `127.0.0.1:<порт VNC>`: двоичные кадры в обе стороны без изменений (поток RFB, ни
разбора telnet, ни удвоения `0xFF`); текстовый кадр от клиента закрывает сессию кодом `1003`.
Закрылась одна сторона — слот закрывает другую (WS закрывается кодом `1000`, TCP-соединение с VNC
закрывается). Остальные типы консоли, порт VNC вне диапазона `5900–65535`, нода не `started`,
неверный токен — закрытие `1008`; VNC-порт не отвечает — `1011`.
Токеном может быть `SLOT_API_TOKEN` или `SLOT_CONSOLE_TOKEN`. Консольный токен выдаётся
шлюзу консолей (`plugin/gateway`) и открывает только WS-консоли, не REST API и не QGA.
Размер окна (telnet NAWS) пока не передаётся. WS требует пакет `websockets` из
`requirements.txt`: без него Uvicorn отвечает на WS 404. Существующий venv обновите
`venv/bin/python -m pip install -r requirements.txt`; `release.py check` проверяет его наличие.

Bearer API предназначен доверенному Manager. QGA даёт выполнение команд в госте;
не выдавайте токен студентам. Для удалённого доступа нужен защищённый шлюз/mTLS;
защитите также `/docs` и `/openapi.json`.

## Node Wipe: намеренный отказ от неподтверждённого удаления

Маршрут требует `confirm:true`, проверяет принадлежность ноды проекту и возвращает
асинхронный **NOT_SUPPORTED**. Ни нода, ни её соседи не останавливаются, файлы не
меняются. Лаборатория возвращается в предыдущее состояние. Успешный wipe в этой
версии не реализован, вместо него нет имитации успеха.

Исследованы исходники upstream тега v2.2.61:

- [QemuVM](https://github.com/GNS3/gns3-server/blob/v2.2.61/gns3server/compute/qemu/qemu_vm.py):
  `_disk_options` создаёт `*_disk.qcow2` в working_dir для linked clone; присутствуют
  отдельные ветви создания/rebase и дополнительные накопители.
- [IOUVM](https://github.com/GNS3/gns3-server/blob/v2.2.61/gns3server/compute/iou/iou_vm.py):
  `_nvram_file`, `_push_configs_to_nvram`, `_rename_nvram_file` связывают NVRAM,
  startup/private config и vlan.dat с application_id; работает file watcher.

Знания имён недостаточно: пока не подтверждены полный список изменяемых файлов,
отсутствие открытых дескрипторов, правильный эталон и атомарное восстановление.
Поэтому Slot не удаляет overlays или NVRAM вслепую. Следующий адаптер должен
подтвердить эти условия и сохранить UUID/имя/координаты/соединения и соседние ноды.

## Версия 0.8.0: VNC-консоль

- `NodeSpec.console`: `"telnet"` (по умолчанию) или `"vnc"`; `vnc` допустим только для `kind: "qemu"`
  (иначе 422). Возможность `vnc` объявлена в `features` (`GET /v1/capabilities`).
- `vnc`-нода создаётся в GNS3 с `console_type: "vnc"`; серийной консоли у неё нет вовсе (GNS3 не
  добавляет `-serial`), поэтому ни `serial-getty`, ни telnet-порта нет. Порт задаёт GNS3: свободный
  от 5900, QEMU запускается с `-vnc <console_host>:<порт − 5900>`. `console_host` — это `host` из
  `[Server]` в `gns3_server.conf`; в поставляемых конфигах это `127.0.0.1`, `allow_remote_console`
  не задан, так что экран слушает только loopback слота и пароля у него нет. Менять `host` или
  включать `allow_remote_console` нельзя: экран станет виден всей сети слота.
- Готовность `vnc`-ноды (`provision`): достаточно TCP-подключения к `127.0.0.1:<порт>`, с теми же
  таймаутом и повторами (`SLOT_READY_TIMEOUT`), что у telnet. Проверка `serial-getty` и `guest-ping`
  пропускаются. Исключение: если у ноды есть `provisioning` и это первый запуск, слот ждёт
  `guest-ping`, потому что команды идут через QGA. QGA и факты от типа консоли не зависят.
  Учтите: VNC-порт QEMU открывается при старте процесса, раньше гостя, поэтому «готова» значит
  «экран доступен», а не «система загрузилась».
- `POST …/serial/enable` для `vnc`-ноды — `409` без обращения к гостю.
- «Паспорт» проекта. При повторном deploy слот сравнивает `model_dump` билета с сохранённым, и тот
  же дамп входит в отпечаток `Idempotency-Key`. Чтобы новое поле не ломало продолжение старых
  проектов, `NodeSpec` не выдаёт `console` в дамп, пока оно `"telnet"`: у таких нод представление
  байт в байт прежнее (в том числе когда поля нет во входном JSON), старые записи и ключи
  продолжаются без `409`. Нода с `vnc` даёт другой паспорт: проект, сохранённый как `telnet`,
  нельзя продолжить с `vnc` и наоборот (`409 Existing project manifest differs`).
- `deploy/2` в слоте пока нет (`deploy_schemas` — только `gns3lab.deploy/1`): менеджер выбирает
  лабу с `vnc` по `features`, `requires` слот не разбирает.

## Исправления по итогам интеграционных испытаний, версия 0.3.0

По предоставленным результатам испытаний исходный цикл на GNS3 2.2.61 прошёл:
Deploy → READY (3 Cisco + 6 Debian) → Stop → STOPPED → Resume → READY,
QGA и сохранность `/root/slot-test.txt` (`SLOT_PERSISTENCE_OK`) после Stop/Resume
и перезагрузки LXC. Это результаты испытаний предыдущего жизненного цикла,
предоставленные оператором, а не проверка текущего обновления в этой среде.
Основной порядок запуска, QGA/CLI/WS и сохранение QCOW2 не переписывались.

### Готовность и ошибки

`/healthz` означает только живой процесс; содержит версию. `/v1/readyz` возвращает
200 `ready` или 503 `not_ready`: `version`, `build_id`, `gns3_version`, `checks`.
Проверяются Lifecycle/monitor, транзакционная запись SQLite с rollback, временная
запись/fsync во внутреннее хранилище, временный flock в каталоге блокировок,
локальный GNS3 2.2.61 и manifest текущего релиза. Для сетевых и файловых проверок
readiness установлен таймаут 3 секунды на проверку; SQLite использует busy timeout
1 секунду. Это не жёсткое ограничение зависания ядра/диска: проблемный CephFS mount
требует диагностики ОС. Проверки не запускают и не останавливают VM, не меняют
проектные файлы. Заранее создайте каталог блокировок с владельцем `gns3`.

Startup отказывается запускаться при нарушении manifest. Перед любыми изменяющими
HTTP-запросами повторно проверяются manifest и исходная build identity; неполный
Lifecycle или изменённый релиз дают 503 с диагностическим кодом. Ошибки SQLite и
файловой системы преобразуются в `STATE_STORAGE_ERROR` / `FILESYSTEM_ERROR`,
без содержимого секретов. Конфликт с текущей операцией — `OPERATION_IN_PROGRESS`.
`FAILED` требует проверки status/операции; проект автоматически не пересоздаётся,
QCOW2 не удаляются и первоначальная преднастройка не повторяется.
Исправлено восстановление после сбоя между сохранением STOPPED и завершением
операции: сервис поднимается с диагностикой FAILED вместо ошибки перехода FSM.
Начальное состояние и запись принятой операции сохраняются одной транзакцией;
при её отказе новая файловая блокировка освобождается.

POST deploy/resume/stop/wipe возвращает компактные `operation_id`, `project_id`,
`action`, `status`, `replayed`, `laboratory`. GET operation добавляет `stage`,
`progress`, `error`, `updated_at` и `nodes` только с UUID/именем/типом/статусом.
Полные параметры остаются в GET lab/topology и node console; команды QEMU не
дублируются в ответах операций. Поле `nodes` сохранено, его элементы стали сводкой:
клиентам, читавшим properties из операции, следует использовать topology.

Одинаковый Idempotency-Key и параметры во время RUNNING возвращают ту же операцию.
После завершения ответ содержит `replayed:true` и актуальную лабораторию.
Успешный deploy/resume имеет постусловие READY, stop — STOPPED. Если оно уже
нарушено (в том числе после рестарта с FAILED), ответ — 409 с
`detail.code=STALE_IDEMPOTENCY_KEY`, прежним operation_id и актуальным состоянием.
Новая операция не запускается. Другие параметры с тем же ключом —
`IDEMPOTENCY_KEY_CONFLICT`. Новое намеренное действие требует нового ключа.
Исторический GET operation остаётся доступен даже при изменении состояния.
Эти правила действуют и для ключей, сохранённых предыдущей версией SQLite.

### Подготовка и запуск из фиксированного RO-каталога

Внутри LXC код и venv всегда находятся в `/srv/gns3-ro/slot`, непосредственно
в смонтированном RO CephFS. Других каталогов версий или ссылок Slot не требует.
Он не выбирает версию, не меняет mount point и не управляет другими LXC.
Будущий Lab Manager выбирает источник CephFS, управляет LXC, обновлением, откатом
и координацией нескольких Slot. Конкретный физический источник кода Slot не знает.

На текущем ручном стенде перед заменой общего кода администратор согласованно
останавливает **все использующие этот код lab-slot.service**. После подготовки
и проверки файлов он запускает сервисы снова. Это временный административный
порядок, а не функциональность Slot. Нельзя менять используемый код по одному
файлу во время работы процессов. Рабочие проекты, SQLite, конфигурация и токены
при обновлении кода не заменяются; GNS3 и VM можно оставить работающими.

На каждом использующем обновляемый код LXC:

```sh
sudo systemctl stop lab-slot.service
# Проверить, что на всём согласованном списке LXC сервисы остановлены.
sudo systemctl is-active lab-slot.service  # ожидается inactive, ненулевой exit code
```

Затем на RW-стороне подготовить полный комплект кода. Окружение должно быть
Ubuntu 24.04/Python 3.12 той же архитектуры. Venv создаётся по тому же абсолютному
пути `/srv/gns3-ro/slot/venv`, который виден в LXC; готовый venv не переносить
из другого абсолютного пути. После подготовки исходников:

```sh
cd /srv/gns3-ro/slot
python3.12 -m venv venv
venv/bin/python -m pip install -r requirements.txt
venv/bin/python -m pip check
# SHA коммита пакуемого кода задаётся администратором на RW-стороне.
BUILD=REPLACE_WITH_SOURCE_COMMIT_SHA
venv/bin/python release.py seal --build-id "$BUILD"
venv/bin/python release.py check
```

`seal` — только инструмент подготовки пакета на RW-стороне, не средство обновления
или выбора версии в LXC. Manifest SHA256 включает Python, unit, requirements,
примеры и документацию. `check` проверяет обязательные файлы, контрольные суммы,
Python 3.12, диапазоны зависимостей и импорты. `build_id` — заданный source SHA
или автоматически вычисленная идентичность содержимого. Это контроль целостности,
не подпись поставщика. При ошибке проверка завершается отказом; автоматического
пересоздания manifest нет. Нельзя выполнять seal на работающем Slot для сокрытия
повреждения. После изменения исходников в разработке обновите manifest перед тестами.

На LXC код остаётся RO; выполняются только проверка и запуск. Изменения каталогов
и миграция текущего стенда не требуются:

```sh
sudo -u gns3 /srv/gns3-ro/slot/venv/bin/python /srv/gns3-ro/slot/release.py check
sudo cp /srv/gns3-ro/slot/lab-slot.service /etc/systemd/system/lab-slot.service
sudo systemctl daemon-reload
sudo systemctl start lab-slot.service
sudo systemctl status lab-slot.service
```

Unit использует Python из `/srv/gns3-ro/slot/venv`, этот же WorkingDirectory,
`/etc/lab-slot/slot.env`, SQLite в `/var/lib/lab-slot` и локальный GNS3 API.
`run.py` проверяет путь кода и соответствие venv, выполняет preflight и запускает
Uvicorn с одним worker. Ни startup, ни readiness, ни check не требуют записи
в каталог исходников; unit отключает запись bytecode. Не отключайте проверку
manifest ради запуска неполного пакета.

После перезапуска ранее READY получает FAILED до явного Resume с новым ключом.
Состояние SQLite и проекты остаются на прежних путях. Диагностика перед Resume:
`venv/bin/python tools/check_slot.py` с токеном из защищённой конфигурации.

### Короткая повторная интеграционная проверка

Диагностический режим не создаёт проекты, проверяет существующий JSON до HTTP,
версию API и readiness. Он не зависит от файлов `/tmp`. Передайте токен через
переменную окружения (не аргумент CLI и не Git):

```sh
cd /srv/gns3-ro/slot
export SLOT_API_TOKEN  # установите из защищённой конфигурации LXC
venv/bin/python tools/check_slot.py
# Только по явному решению оператора: создание/запуск эталонной лаборатории.
venv/bin/python tools/check_slot.py --deploy --key integration-deploy-NEW001
```

1. Сохранить PID/OP из ответа, polling GET operations до SUCCEEDED, status READY,
   topology — девять started; до этого не считать deploy успешным.
2. QGA создать/прочитать контрольный файл на одной Debian, как в прежних испытаниях.
3. POST stop с новым ключом, дождаться STOPPED/девяти stopped.
4. POST resume с ключом `integration-resume-NEW001`, дождаться READY; прочитать файл.
5. Повторить тот же Resume — тот же OP, `replayed:true`, `laboratory.state=READY`.
6. Stop с новым ключом; старый Resume-ключ должен дать 409 STALE_IDEMPOTENCY_KEY,
   лаборатория остаётся STOPPED. Новый Resume-ключ снова запускает её.
7. В согласованное окно перезапустить LXC; проверить SQLite/readiness, Resume с новым
   ключом и содержимое контрольного файла. Старые записи операций остаются доступны.

Ни проверочный CLI, ни процедура обновления не удаляют проекты. Автоматические
тесты покрывают mock GNS3, повреждение релиза, replay/stale, SQLite и блокировки.
Ручной проверки требуют CephFS/флот LXC/права/venv/systemd и повтор основного цикла
с реальными девятью устройствами и QCOW2. Безопасный Node Wipe по-прежнему отдельно.
